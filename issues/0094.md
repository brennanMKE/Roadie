# 0094 — Thumbnail cache tests can exhaust the thread pool and hang the test run

| | |
|---|---|
| **Status** | open |
| **Module** | SkinKit |
| **Platform** | macOS |
| **First seen** | 2026-10-19 |

## Description

Found in the #0093 implementation and review (commit d890d3d). `CountingRenderer` in the SkinLibrary test support calls a blocking `Latch.wait()` inside the thumbnail cache's `Task.detached` render jobs, so each blocked render holds a cooperative-pool thread until its test opens the latch. Five `SkinThumbnailCacheTests` together can hold up to 6 blocked threads (`rendersAreBoundedAndOffMain` 2; `newestRequestRendersFirst`, `cancelledBeforeStartIsDropped`, `cancelledAfterStartStillCaches`, `secondCallerKeepsAQueuedJobAlive` 1 each), which is exactly the guest's pool width. If they all block before any test body resumes, the test process hangs at 0% CPU with no time limit; on a machine with fewer cores the risk is higher. During #0093 a similar pile-up (with the old `StubIngester` gate) did hang a fast-tier run.

Expected: no test blocks a cooperative-pool thread while waiting for another test step (use async gates, continuations or a dedicated thread for the renderer stub), or the suite is `.serialized` with a `.timeLimit` so a hang fails fast instead of stalling the VM run. Coverage of ordering, cancellation and bounded concurrency stays the same.
