## Description

`BackendNowPlayingTests.identicalPollsDoNotYield` (from #0064, commit 11f05b5) failed once in the VM during #0075's implementation (run `20261018-224811-99209`), on code it does not touch, and passed on the next runs. The implementer's reading: a wait on the fake clock and ping timing ran out, the same shape as #0083.

Expected: the test waits on a state that only exists once the second poll has run (not on elapsed time or sleeper counts), and passes every time under `scripts/run-tests-vm.sh --stress`.

## Plan

**Hypothesis.** The test's `settled(rig)` waits for `rig.clock.sleeperCount == 2` and assumes those two are the ping loop and the poll loop. They need not be. Every `MusicAssistantClient.call` starts a `timeoutTask` that sleeps on the **same** `ManualClock` for `callTimeout` (15 s) until the reply arrives (`MusicAssistantClient.swift`, `call(_:timeout:)`). The wait `waitFor { gets(rig) == before + 1 }` returns as soon as `players/get` is **sent**, while the poll's `refetch()` is still running: the `players/get` reply, then `player_queues/get_active_queue` (and maybe `player_queues/get`) follow, each with its own 15 s timeout sleeper. At the next `settled(rig)`, "ping sleeper + one in-flight call-timeout sleeper" is also 2. The test then calls `advance(by: .seconds(1))` while the poll loop is still in `refetch()`. That wakes nobody, because the timeout is 15 s and the ping 25 s. When the poll loop then reaches `clock.sleep(for: eagerPoll)`, its deadline is `now + 1 s` on the clock that has already moved, so nothing advances it again. `players/get` is never sent, and `waitFor` gives up after its 5 s default.

**Evidence.**
- `build/vm-tests/20261018-224811-99209/playerkit-tests.log` line 1525: the failure is at `BackendNowPlayingTests.swift:162`, the `gets(rig) == before + 1` wait. The `settled(rig)` before it passed, so the count of 2 was reached and the advance was spent on the wrong state.
- The test failed after 6.298 s: the 5 s `waitFor` timeout plus about 1.3 s of a parallel, loaded run (the neighbouring suites finish at about 1.3 s). That matches a missed advance, not a slow poll.
- Only rounds 2 and 3 are exposed: before round 1 the initial refetch finishes before `items.count == 1`. The window is a few actor hops wide, so it shows up only under load in the VM. That fits a single failure followed by passing runs.

**Shared cause with #0083.** The cause is the same. A bare `sleeperCount == N` cannot tell apart the loops sharing one `ManualClock`: ping interval, pong timeout, call timeouts, poll, and debounce. In #0083 the pong-timeout sleeper (10 s) passes for the next ping-interval sleeper (25 s). So the two issues need the same test-support fix: wait for a sleeper with a **specific deadline**. To avoid conflicting edits, both use one helper with this exact name and shape, added to `ManualClock` in `Packages/PlayerKit/Tests/MusicAssistantKitTests/TestSupport.swift`:

```swift
/// true when some sleeper's deadline is exactly `duration` from now: a loop that just called `sleep(for: duration)`.
func hasSleeper(dueIn duration: Duration) -> Bool
```

The body is `state.withLock { s in s.sleepers.values.contains { $0.deadline == s.now.advanced(by: duration) } }`. `Clock.sleep(for:)` defaults to `sleep(until: now.advanced(by:))`, and `now` moves only in `advance(by:)`, so the match is exact. **Whichever of #0083 and #0088 lands first adds the helper. The other reuses it and must not add a second variant.** Leave `sleeperCount` in place, because other suites still use it.

**Files.**
- `Packages/PlayerKit/Tests/MusicAssistantKitTests/TestSupport.swift`: add `hasSleeper(dueIn:)` (unless #0083 already has).
- `Packages/PlayerKit/Tests/MusicAssistantKitTests/BackendNowPlayingTests.swift`: the waits.
- `scripts/stress-realtime-gapless.sh`, `scripts/run-tests-vm.sh`, `docs/testing-in-vm.md`: a stress filter (see Verification). This is also shared with #0083, under the same first-lands rule.
- No production code changes. `MANowPlayingWatch` behaves correctly; only the test's notion of "idle" is wrong.

**Fix.**
1. Redefine the helper in `BackendNowPlayingTests` as `settled(_ rig:, poll: Duration = .seconds(1)) async -> Bool { await waitFor { rig.clock.hasSleeper(dueIn: poll) } }`. Its doc comment says: "the poll loop is asleep, so the last refetch, including its queue calls, has finished". The poll loop sleeps only after `await refetch()` returns, so this state exists only once the previous poll is complete. It is the state the issue's Expected line asks for. Ping and call-timeout deadlines (25 s minus elapsed time, and 15 s) never equal 1 s or 10 s in these tests.
2. In `identicalPollsDoNotYield` and `pollsEverySecondUntilAnEventApplies`, keep the `settled(rig)` → `advance(1 s)` → `gets == before + 1` loop. It is now race-free.
3. `pollRelaxesToTenSecondsOnceEventsWork`: the `settled(rig)` after the eager poll becomes `settled(rig, poll: .seconds(10))`, because the next sleep is relaxed. Keep the first one at the default.
4. `garbledEventTriggersOneDebouncedRefetch`: replace `settled(rig, sleepers: 3)` with `waitFor { rig.clock.hasSleeper(dueIn: .milliseconds(150)) }` (the debounce sleeper). Keep the preceding `settled(rig)`.
5. `cancellingTheStreamStopsPollingAndEvents`: the `settled(rig, sleepers: 1)` after `stop()` becomes `waitFor { rig.clock.sleeperCount == 1 }` inline. That is safe there, since the earlier `settled(rig)` ensured no refetch was in flight. Drop the `sleepers:` parameter.
6. The pushed-event tests (`pushedPlayerUpdatedChangesState`, `pushedQueueTimeUpdatedMovesElapsed`, `pollPicksUpAnExternalPauseWithoutEvents`, `reconnect…`) keep `settled(rig)`, which is now stronger. It also stops an event from landing mid-refetch and being overwritten by the fetched snapshot.

## Root cause

`BackendNowPlayingTests.settled(rig)` waited for `sleeperCount == 2`, assuming those were the ping and poll loops. Each `MusicAssistantClient.call` also sleeps on the same `ManualClock` for its 15 s call timeout, so "ping + one in-flight call-timeout sleeper" satisfied it while the poll's `refetch()` was still running. The test's `advance(by: 1 s)` then woke nobody, the poll loop's next 1 s sleep started after the advance, and `players/get` never came within `waitFor`'s 5 s.

## Fix

As planned. `settled(_:poll:)` now waits for `rig.clock.hasSleeper(dueIn: poll)` (default 1 s), which exists only once the poll loop is asleep after a finished refetch. `pollRelaxesToTenSecondsOnceEventsWork` uses `poll: .seconds(10)` after the eager poll; `garbledEventTriggersOneDebouncedRefetch` waits for the 150 ms debounce sleeper; `cancellingTheStreamStopsPollingAndEvents` waits inline for `sleeperCount == 1`. The `sleepers:` parameter is gone. Reused `hasSleeper(dueIn:)` and `--stress-filter` from #0083; no test-support, script or production change.
