# 0244 — The Music Assistant drop tests sometimes time out waiting for play_media

| | |
|---|---|
| **Status** | open |
| **Module** | Tests |
| **Platform** | macOS |
| **First seen** | 2026-10-29 |

## Description

Three of #0228's `PlayerModelDropTests` fail now and then in VM runs for issues that don't touch the app. Each time, the 10 s `waitUntil` for a `player_queues/play_media` command runs out, and the scripted server's command list stops at `get_active_queue`:

- `testDropOnAMusicAssistantQueueAppends`: #0233 run 20261029-015601-98926 (`["auth", "auth", "all", "time", "all", "all", "get", "all", "get", "get_active_queue"]`), passed on rerun 20261029-020638-3932.
- `testOptionDropOnAMusicAssistantQueueReplaces`: #0234 review run 20261029-024649-26536, passed on rerun 20261029-025155-29255. Failed again in run 20261029-035501-59590 (list ends `"get_active_queue", "get"`).
- `testOptionDropOnAMusicAssistantWindowFallbackReplaces` (`PlayerModelDropTests.swift:224`): run 20261029-035749-61184, command list ends `... "get_active_queue", "get_a…` with no `play_media`.

Every failing run had two VM guests busy, and each test passed on rerun. The test connects, sets `model.selectedOutput` to the scripted speaker, then drops; the failures look like the drop arriving before the speaker's queue is active (a connect-then-select race, like the one fixed in #0221's UI test), so the drop goes to the local queue or is dropped. (That was the first guess; the code says otherwise, see `## Plan`.)

## Expected behavior

The tests wait for the selected speaker's queue to be ready before dropping, or the model queues the drop until it is, and they pass on every run.

## Plan

### What actually races

The output switch is not the problem. `dropLibraryItems(_:at:replacing:)` (`App/Playlist/PlaylistWindowView.swift:466`) calls `playFromLibrary` (`App/PlayerModel.swift:1161`), which reads `selectedOutput` synchronously (`:1173`) and sends `backend.play(items, on: output, mode:)` to that speaker. Setting `selectedOutput` only restarts the now-playing and queue watchers (`didSet`, `:136`). No speaker queue has to be "ready", and nothing routes the drop to the local queue. The `get_active_queue` lines in the failure lists come from those watchers, not from the drop.

What breaks is the **connection**. Two `connect()` calls run at once and each opens its own socket. The `"auth", "auth"` at the start of the #0233 list shows it.

1. `PlayerModel.init` connects by itself when a verified server exists (`App/PlayerModel.swift:592–597`: `selection.resolveNow()`, then `ma.connect()`), and the scripted configuration has one verified server. The test's `connectMusicAssistant` (`PlayerModelDropTests.swift:63`) then calls `connect()` too. In the app, `LibraryBrowserModel.startConnect()` (`Packages/PlayerKit/Sources/LibraryBrowser/LibraryBrowserModel.swift:333`, called from `appeared()`) and the fallback's source probe (`LibrarySource.swift:24`) are more callers that can overlap the launch connect.
2. `MusicAssistantBackend.connect()` (`Packages/PlayerKit/Sources/MusicAssistantKit/MusicAssistantBackend.swift:155`) returns early only when a client is **already installed** and connected (`:160–165`). Two callers that arrive while `client == nil` each build a `MusicAssistantClient` and run the handshake. Since #0061 the later one to finish wins: it installs its client and resets `players` (`:199–208`), then calls `raced.disconnect()` on the earlier client (`:218`).
3. The test's `connect()` can finish **first** when the guest is loaded. The test then sees `isConnected`, sets the speaker and drops. `play` takes the first client (`requireClient`) and sends `players/get` because the cache is empty (`requireOutput`, `:797–800`). That is the trailing `"get"` in the lists. The launch connect then finishes, installs the second client and disconnects the first. `MusicAssistantClient.disconnect()` fails every pending call with `.disconnected` (`MusicAssistantClient.swift:197–210`, `failAllPending` `:448`). A call sent after that gets `.notConnected` (`:396`). `MusicAssistantBackend.map` turns `.disconnected` into `MusicBackendError.unreachable` (`MusicAssistantBackend.swift:860`), so `playFromLibrary`'s catch posts "Can't reach the Music Assistant server" and hands the failure to `fallback.report` (`PlayerModel.swift:1189–1194`). `play_media` is never sent.

#0228's Gotcha (run 20261027-173236-61397: "a play sent while it authenticates fails with Can't reach…") was this same race. `sources.select` never connects (its doc comment says so, `LibrarySourceController.swift:76–78`). The second connection was always the launch connect, and moving `select` before `connect` only changed the timing.

### App bug, not a test bug

A user hits the same race. At launch with a verified server and the Library window open, the launch connect and the browser's `appeared()` connect overlap. Whatever goes out on the losing socket fails with "Can't reach the Music Assistant server": a play, a drop, the Output list refresh or a browse. The `.unreachable` failure also reaches `sources.onBackendFailure` → `selection.activeServerDropped()` (`PlayerModel.swift:603–608`), which re-picks a server that is fine. The tests have no readiness condition to wait for that a user could also wait for: `isConnected` is already true when the drop goes out. The fix goes in `MusicAssistantBackend.connect()`: **concurrent connects to the same server share one attempt**.

### Steps

1. **Test hook first** (`Packages/PlayerKit/Sources/MusicAssistantKitStub/`). Add `ScriptedMusicAssistant.holdReplies(for:)` and `release(command:)`. A hold applies to every transport the server has made and to each one `makeTransport()` makes later, so the second connection's `auth` can be held before its socket exists. `release` releases on every transport. Releasing one connection only goes through `server.transports[i].release(command:)` (it exists already). Add `heldRepliesApplyToLaterTransports`.
2. **Write the regression test and prove it fails** (see `## Tests`) on the current `connect()`: `verify.sh --expect-fail` (first `## Which tier` command). Commit nothing yet.
3. **Coalesce `connect()`** in `MusicAssistantBackend`. After `requireConfiguration()` (that is the first `await`; everything from here to the handshake runs on the actor without suspending):
   - If a client is installed, connected (or reconnecting) and the same identity, return, as now.
   - If an attempt for the same identity (`sameIdentity(as:)`) is in flight, **join it**: wait for it to end, then go back to the top of `connect()` and check again. If it succeeded, the check returns. If it failed with an error other than cancellation, rethrow that error rather than opening a second socket to a server that just refused. If it was cancelled while this caller was not, take over as the new leader. A cancelled joiner throws `CancellationError` and does not cancel the leader.
   - Otherwise become the leader. Register the attempt (an id plus its configuration) **before** the first suspension, run the handshake inline as now so the caller's cancellation behaves the same, and clear the registration on every exit path, but only if it is still this attempt.
   - A connect to a **different** identity does not join. It runs as now and the later one wins (the `raced` close at `:218` stays for that case and for anything that slips past). `disconnect()` during an attempt is unchanged (not in scope).
   - How joiners wait is the implementer's choice: a stored `Task` with a result, or a list of continuations resumed on exit. Keep it inside the actor and add no public API.
4. Update the `connectMusicAssistant` doc comment in `PlayerModelDropTests.swift`: the launch connect and this one now share one connection (#0244). The old "selecting after connect starts a second connection" wording is wrong. Keep select-then-connect.
5. Fast run with `--expect` (second command). The three flaky drop tests are in the list. They should now pass every time because only one socket ever exists.

### Not in this fix (note for the orchestrator)

There is a second hazard nearby. The first server resolution calls `onChange(nil, server)`. With Music Assistant as the selected source, that runs `activeMusicAssistantServerChanged()` (`PlayerModel.swift:714–727`, `:781–797`), whose `Task { await ma.disconnect() … }` can land **after** a connection was installed and drop it with nothing reconnecting. No failure so far shows that pattern: it would leave one `auth`, then the drop failing with "Not connected". It is a candidate follow-up issue (skip the disconnect when `old == nil`). Don't change it here unless a run shows it.

## Tests

Fast, swift-testing, `Packages/PlayerKit/Tests/MusicAssistantKitTests/ScriptedMusicAssistantTests.swift`. Use the file's `scripted(_:connect: false)` rig. The `ManualClock` means no call times out.

- **`aPlayDuringAConcurrentConnectReachesTheSpeaker`**: the **regression test**, which must fail on the current code. It is deterministic because it holds the server's replies and does not depend on load:
  1. `server.holdReplies(for: "auth")` and `server.holdReplies(for: "player_queues/play_media")`.
  2. `first = Task { try await backend.connect() }`. Wait (`waitFor`) until the server has received one `auth`.
  3. `second = Task { try await backend.connect() }`. Wait up to 1 s for a second `auth`. The current code always sends one, because the first attempt is held and `client` is still nil. The fixed code never does, so ignore the result of this wait.
  4. `server.transports[0].release(command: "auth")`, then `try await first.value`.
  5. `play = Task { try await backend.play([MediaID(.album, "library://album/27")], on: speaker, mode: .append) }`. Wait until `play_media` is in `receivedCommands`.
  6. `server.release(command: "auth")` (the current code's second socket finishes and closes the first), `try await second.value`, then `server.release(command: "player_queues/play_media")`.
  7. Expect `try await play.value` not to throw (current code: `.unreachable`), `server.transports.count == 1` (current code: 2), `server.transports[0].closeCodes.isEmpty`, and `await backend.isConnected`.
- `aCancelledFirstConnectLetsTheJoinedOneConnect`: hold `auth`. Start the first connect, wait for its `auth`, start the second, then cancel the first. Release `auth`. The second returns with `isConnected` true.
- `aFailedConnectFailsItsJoinerWithoutASecondSocket`: same server, scenario `.badToken`. Hold `auth`, start two connects and release. Both throw `MusicBackendError.unauthorized`, and `server.transports.count == 1`.
- `aConnectToAnotherServerStillReplacesAnInFlightOne`: with the address closure switched to a second configuration between the two calls (copy the setup of `BackendServerProviderTests.changingConfigurationAtTheSameBaseURLReconnects`), the second connect opens its own socket and the first socket ends up closed. This guards the later-wins rule for an identity change.
- `heldRepliesApplyToLaterTransports` (stub hook): a hold set before any transport exists holds `auth` on the first and second transports. `release` frees both.
- Unchanged, but in `--expect` to show the flake is gone (`Tests/RoadieTests/PlayerModelDropTests.swift`): `testDropOnAMusicAssistantQueueAppends`, `testOptionDropOnAMusicAssistantQueueReplaces`, `testOptionDropOnAMusicAssistantWindowFallbackReplaces`, `testOptionDropOfFilesOnASpeakerKeepsTheQueue`.
