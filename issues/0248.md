## Description

Three loose ends from #0239's review (f5a559a):

1. **Help survives a close.** Closing the visualization window with the help card open leaves `isHelpOpen` set, so the card (and its overlay hold and auto-advance suspension) is still up when the window reopens. #0240's review noted the same for the preset list (`presetList` and its `.list` suspension survive a close).
2. **Track observation piles up.** Each `open()` starts a new `withObservationTracking` chain in `VisualizationModel+Title.swift` without ending the previous one when no change came in between. `noteTrack`'s identity check keeps the shows correct, but the chains accumulate over repeated opens.
3. **A late Music Assistant artist shows the title twice.** The track identity includes the artist, so a Music Assistant snapshot whose artist arrives after its title changes the identity and starts a second title show. Unit tests call `noteTrack` directly, so `currentTrackIdentity` is covered only by the local-queue UI test.

## Expected behavior

1. Closing the window closes help and the preset list and clears their holds and suspensions.
2. Opening the window replaces any previous track observation, so at most one chain is live.
3. The title shows once per real track change; a metadata refresh of the same track (same queue item / Music Assistant item id) doesn't start another show. A unit test covers `currentTrackIdentity` for both a local and a Music Assistant track.

## Relation

- Parent: [#0231](0231.md)

## Plan

1. `close()` (the real close, after any full-screen exit) sets `isHelpOpen = false` and calls `closeList()`; their existing paths clear the `.help`/`.browser` overlay holds and the `.help`/`.list` suspensions. The #0242 flash notice is left alone.
2. `TitleState.trackGeneration` is bumped by each `open()`; the `withObservationTracking` onChange captures the generation it was armed under and re-arms only while it's current, so a stale chain fires once and ends. `trackObservationRearms` counts live re-arms for the test.
3. `currentTrackIdentity` moves into `static trackIdentity(nowPlaying:current:)`: the local queue entry's id when the local queue plays, else the snapshot's `item` (Music Assistant id), else the title alone. The artist is no longer part of it.

## Root cause

1. `close()` cleared only `isOpen`, the visibility and the window setting. `isHelpOpen` and `presetList` survived, so did their `.help`/`.browser` overlay holds and `.help`/`.list` suspensions.
2. `withObservationTracking` can't be cancelled. Each `open()` armed a new chain, and a chain from an earlier open that had seen no change re-armed itself forever.
3. `currentTrackIdentity` joined title, artist and the queue entry. A Music Assistant snapshot whose artist arrived late changed the identity and started a second show.

## Fix

As planned. `close()` sets `isHelpOpen = false` and calls `closeList()`, and their existing paths clear the holds and suspensions. The #0242 notice is untouched. `TitleState.trackGeneration` is bumped in `startTrackingTitle()`. Each chain captures it, and when it fires it re-arms only while that generation is current. `TitleState.armedTrackObservations` counts observations armed and not yet fired, for the test. The identity moves to `static trackIdentity(nowPlaying:current:)`, which returns `queue:<entry id>`, else `item:<MediaID>`, else `title:<title>`, else nil. `suspensions` is now `private(set)` so tests can read it.

## Gotchas

- `Player.restoreQueue` returns false on a non-empty queue. Call `clearQueue()` first.
- A stale `withObservationTracking` chain still fires once on the next change. The generation check only stops it from re-arming, so a count of onChange calls can't tell stale chains from live ones. Count armed observations instead.
