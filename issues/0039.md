## Description

Optional: start playback while the download continues, so long tracks (podcasts) don't wait.

## Resolution notes

> 🟢 Resolved 2026-10-14 — an uncached Plex track with a known size now starts after a short preroll while it downloads, through a CoreAudio callback reader and feeder thread that feed the same player node, with a whole-file fallback for containers that cannot stream.

> Review (Opus): read `git show 262286f` in full. Thread model is sound: every blocking call (`waitForBytes`, `fetchRange`'s semaphore, `ExtAudioFile*`) runs on plain `Thread`s under the reader's `io` lock; the render thread is never touched (completion handlers only take a short `NSCondition`), and the main actor only hops in through `Task { @MainActor }` events filtered by feeder generation. Teardown never blocks: `cancel` sets a flag the 50 ms polls see, `close` disposes on its own thread after the feeder lets go of the lock, and the refcon stays valid because that thread retains the reader. Range requests carry the token in the header only, ask for `bytes=lo-(hi-1)`, check the 206 length, and are cancelled through the poll. Cache integrity holds: the index learns a key only in `insert` after the size check, `DownloadProgress.finish` runs after `insert`, abandon needs no waiters, no holders and no pin, and the reader's own descriptor survives the move. The changed `PlexBackendPlaybackTests` expectation is right: junk bytes now fail at open (still before the graph, still a per-track #0068 skip) and are no longer cached; #0071 restores without a position, so the seek clamp does not affect it. One bug fixed in `02a4fe9`: a device change during the preroll (state `.loading`, feeder already queued) was skipped by `handleConfigurationChange`, so the first buffer would call `playerNode.play()` on a stopped engine (an Objective-C exception); the change now restarts the engine and the feeder for a loading progressive track, and `beginProgressive` restarts the engine after its client-format await. New test `deviceChangeDuringThePrerollRestartsTheEngineAndTheFeeder`. Verification re-run: `20261014-075012-26524` (`--launch`, code commit only), then with the fix `20261014-075308-27704` (`--launch`) and `20261014-075608-28774` (`--stress 10`, `stress: 0/10 failed`); every step PASS, AudioCore "191 tests in 35 suites passed", TrackCache "84 tests in 11 suites", PlexBackendKit "37 tests in 5 suites", every new progressive test passed by name including `progressiveTrackAdvancesToTheNextFileRealtime`, `AUDIO silent` each time. Residual risks for the host check: only `.notStreamable`/`.formatUnsupported` fall back, so a real file the callback open rejects with an `.open` status (an unknown extension such as Ogg gets no type hint) fails the track instead of waiting for the whole file; a server that ignores `Range` makes each side fetch download the whole part into memory.

## Root cause

`Player.startCurrentTrack` awaited `resolver.localURL(for:)`, which for a Plex track resolved only after `PlexPartDownloader` had streamed the whole part and `TrackCache.insert` had verified and moved it. `AVAudioFile` can only open a finished path, so nothing played until the last byte.

## Fix

Option C of the plan, implemented in full.

- **AudioCore** (`Sources/AudioCore/Progressive/`): `ProgressiveByteSource` (public protocol; `waitForBytes` takes a timeout and returns `.timedOut` so the reader polls and notices an interrupt), `ProgressiveReadPolicy` (pure), `ProgressiveAudioReader` (`AudioFileOpenWithCallbacks` + `ExtAudioFileWrapAudioFileID`; read callback serves, waits, or side-fetches a range; blocking only on plain `Thread`s), `ProgressiveFeeder` (own thread, holds the reader for its session, 8-buffer window, `.dataConsumed` throttle, stall/resume/started/reachedEnd/scheduledLast events). `TrackResolver.resolve(_:)` with a default of `.file(localURL)`. `GaplessScheduler.adjustLength`. `Player+Progressive.swift`: open-before-graph (random bytes never open the device), fallback to the whole file on `.notStreamable`/`.formatUnsupported` (joins the in-flight download before closing the source), node run rule (`isBuffering`), seek clamp to `bufferedTime`, restart on seek/device change/queue reconcile.
- **TrackCache**: `CacheDownloader` gains `progress:` and `fetch(partKey:range:)`; `TrackCache.open` returns `.ready(url)` or `.downloading(ProgressiveDownload)` registered as a holder (abandon rule is now "no waiters, no holders, not pinned"); `DownloadProgress` is resolved after `insert`. `PlexPartDownloader` reports progress per 256 KB flush and serves ranges (token in the header, 206 or the slice of a 200). `PlexTrackResolver.resolve` overrides the default.
- **Adaptations to landed work**: a decode failure surfaces as a per-track error through `trackFailed` (#0068 skip, `PlayerEvent.failed`); a download failure while streaming rethrows the `TrackCacheError` the cache produced, so `SourceScopedError` still decides skip vs stop. The queue-restore, EQ (`player.eq` reaches the node as before) and analyzer paths needed no change; gapless diagnostics (#0055) record the progressive schedule item (no node sample time, so no lead).
- **Deviations from the plan**: (1) the feeder uses its own thread and holds the reader's lock for its session instead of running on the reader's thread; (2) `.dataConsumed` throttles the window (settled by the offline render tests; it fires under manual rendering); `.dataPlayedBack` still marks the last buffer for the queue advance; (3) the end of stream is detected by a short read; if the track ends exactly on a buffer boundary a one-frame silent buffer carries the end marker; (4) `ProgressiveAudioReader.open` takes no bitrate (the player computes the preroll); (5) the client-rate versus file-rate unit of `ExtAudioFileSeek` is calibrated at runtime when the rates differ (not testable in the VM, see checklist); (6) a Plex track whose bytes are not audio now fails at open and is not cached (the download is abandoned), where it was cached and then failed to play. `PlexBackendPlaybackTests.playAlbumQueues...` no longer expects a cache entry for its junk part. (7) the length of an MP3 is an estimate until the decoder ends; `adjustLength` fixes the schedule at the end only, so `currentTime` can clamp at the estimate in the last stretch of a VBR MP3 without a Xing header. (8) `Content-Length` is not used; a Plex track without `Part.size` plays as before.
- **Findings**: CoreAudio's WAV open reads the first 8192 bytes and then 8-byte chunk headers; the first decode reads 8 KB (float WAV) or 64 KB (16-bit WAV) chunks, so small files need more than a header before the first buffer. The generated AAC `.m4a` has `moov` at the front (59,568 bytes, `dataOffset` 57,344): the open went sequential, 0 bytes side-fetched, and decoded frames equal `AVAudioFile`'s exactly.

## Plan

### Where the delay comes from

`Player.startCurrentTrack` awaits `resolver.localURL(for:)`; for a Plex track that is `PlexTrackResolver` → `TrackCache.file(forKey:partKey:expectedSize:)`, which resumes its waiters only in `finish` → `insert`, after `PlexPartDownloader.write` has streamed the whole part into `tmp/<key>-<uuid>.part`, the size has been checked against `Part.size` and the file has been moved into `Tracks/`. Only then does `AVAudioFile(forReading:)` open it and `begin` schedule it with `scheduleSegment`. The marquee sits in `.loading` for the whole download; on a 53-minute podcast that is tens of megabytes before the first sample.

Everything downstream of the player node (EQ, mixer tap, `GaplessScheduler`, `NowPlayingBridge`) is agnostic to where the node's samples come from. The change is confined to how the *current* track's samples reach the node while its bytes are still arriving.

### Design note: the options

| | A. `AVAudioFile` on the growing `.part` file | B. Streaming decoder (`AudioFileStream` + `AudioConverter` → PCM buffers) | C. Byte-range-aware reader (`AudioFileOpenWithCallbacks` + `ExtAudioFile` → PCM buffers) **recommended** | D. `AVPlayer` on the part URL |
|---|---|---|---|---|
| Starts early | Only if the header is at the front; `length` is fixed at open, so the player node hits EOF at the open-time size, or reads zeros / garbage past the frontier if the file is preallocated | Yes | Yes: the reader reports the *final* size and blocks until the bytes it is asked for exist | Yes |
| M4A with `moov` at the end, ID3v1 / APE tags at the end of an MP3 | Cannot open until complete | `kAudioFileStreamError_NotOptimized` for `moov`-at-end; no way to satisfy a tail read | A far read becomes one HTTP `Range` request (the server honours byte ranges, `docs/plex-music-library.md`) | Fine |
| Gapless trim (AAC priming / remainder frames), VBR seek tables | Handled by AVAudioFile | By hand: packet descriptions, `kAudioFileStreamProperty_PacketTableInfo`, discontinuity flags | Handled by ExtAudioFile, the same component `AVAudioFile` wraps, so decoded frames are identical to the file path | n/a |
| Seek | `scheduleSegment` as today, but only inside the open-time length | `AudioFileStreamSeek` → byte offset → re-parse with discontinuity | `ExtAudioFileSeek(frame)`; the read callback then waits for, or range-fetches, the bytes | Yes |
| EQ + analyzer | Unchanged | Unchanged (buffers go through the same node) | Unchanged (same) | Needs an `MTAudioProcessingTap`; rejected on 2026-10-12 |
| New code | Small but unsafe | Large (parser, converter, trim, seek) | Medium (one C-callback file reader, one feeder thread, Player plumbing) | Large and parallel graph |

**Decision: C.** AVAudioFile can only open a path, but the thing it wraps, ExtAudioFile, can wrap an `AudioFileID` opened with `AudioFileOpenWithCallbacks`. Our callbacks hand CoreAudio a file whose `getSize` is `Part.size` and whose `read` serves bytes from the cache's temp file, blocks (on a non-cooperative thread) while the sequential download catches up, and turns a far jump into a byte-range request. CoreAudio's own container parsers and decoders do the rest, including the gapless trim, and because they are the same code that `AVAudioFile` runs, the frames scheduled on the node are bit-identical to what the file path would schedule. The player node takes PCM buffers (`scheduleBuffer`) in the same queue as file segments, so the next track is still pre-scheduled behind the current one and the EQ / tap never know the difference.

Not in scope, recorded as follow-ups: a second HTTP stream to play *from* a seek point beyond the frontier (seek is clamped instead, see below); gapless pre-scheduling of a *next* track whose download has not finished when the current one ends (it starts after a short preroll instead of after the whole file, which is already the win this issue is after); a marquee "Buffering…" string and a downloaded-extent mark on the position slider (the player publishes `isBuffering` and `bufferedTime`; the M4 window issues own the drawing); `Content-Length` as a substitute when `Part.size` is missing (such a track plays as today).

### 1. AudioCore: `ProgressiveByteSource` (`Sources/AudioCore/Progressive/ProgressiveByteSource.swift`)

AudioCore stays Plex-free. It defines what it needs from a file that is still arriving:

```swift
public enum ProgressiveWaitOutcome: Sendable { case available, failed(any Error), cancelled }

/// One file whose bytes arrive in order. Implemented by TrackCache over its temp file.
/// `waitForBytes` and `fetchRange` block the calling thread and are only ever called from the
/// reader's own `Thread`, never from a Swift concurrency task.
public protocol ProgressiveByteSource: AnyObject, Sendable {
    var finalSize: Int64 { get }
    /// Contiguous bytes from offset 0 that are on disk now.
    var availableBytes: Int64 { get }
    /// "m4a", "mp3", … (the cache's sanitized extension); AudioCore maps it to an `AudioFileTypeID` hint.
    var pathExtension: String { get }
    /// Returns when `availableBytes >= end`, the download fails, or `cancel()` is called.
    func waitForBytes(through end: Int64) -> ProgressiveWaitOutcome
    /// `pread` on the temp file. Short only at `finalSize`.
    func read(into buffer: UnsafeMutableRawPointer, offset: Int64, count: Int) throws -> Int
    /// Out-of-order bytes by range request; never written to the file.
    func fetchRange(_ range: Range<Int64>) throws -> Data
    /// Wakes a blocked `waitForBytes` / `fetchRange` with `.cancelled`.
    func cancel()
    /// The reader is done; the source may cancel the download if nobody else needs it.
    func close()
}

/// What a resolver hands the player: a complete file or a source still arriving.
public enum ResolvedAudio: Sendable { case file(URL), progressive(any ProgressiveByteSource) }

public protocol TrackResolver: Sendable {
    func localURL(for track: Track) async throws -> URL
    /// Default: `.file(try await localURL(for:))`. TrackCache overrides it.
    func resolve(_ track: Track) async throws -> ResolvedAudio
}
```

`GateResolver`, `FileTrackResolver` and #0062's stubs keep conforming through the default.

### 2. AudioCore: `ProgressiveReadPolicy` (pure, `ProgressiveReadPolicy.swift`)

```swift
struct ProgressiveReadPolicy: Sendable {
    /// Reads that start within this many bytes past the frontier wait for the sequential download.
    var waitWindowBytes: Int64 = 4 << 20
    /// Total bytes a reader may fetch by range before giving up on streaming this file.
    var maxSideFetchBytes: Int64 = 8 << 20
    /// Range fetches are rounded out to this granularity and cached in the reader.
    var sideFetchGranularity: Int64 = 64 << 10
    var prerollSeconds: TimeInterval = 2
    var minimumPrerollBytes: Int64 = 256 << 10

    enum Decision: Equatable { case serve, wait(through: Int64), sideFetch(Range<Int64>), endOfFile, giveUp }
    func decide(offset: Int64, count: Int, available: Int64, finalSize: Int64, sideFetched: Int64) -> Decision
    /// `max(minimumPrerollBytes, bitrateKbps * 125 * prerollSeconds)`, capped at `finalSize`; nil bitrate → 192 kbps.
    func prerollBytes(bitrateKbps: Int?, finalSize: Int64) -> Int64
}
```

Rules: `offset >= finalSize` → `.endOfFile`; `end = min(offset + count, finalSize)`; `end <= available` → `.serve`; `offset < available + waitWindowBytes` → `.wait(through: end)`; else `.sideFetch(offset..<end)` unless `sideFetched + (end - offset) > maxSideFetchBytes` → `.giveUp`. A read callback must never return a short read before the true end (AudioFile treats a short read as EOF), so there is no "serve what you have" case.

### 3. AudioCore: `ProgressiveAudioReader` (`ProgressiveAudioReader.swift`)

Owns one `Thread` ("SkinAmp.progressive-reader", QoS user-initiated), the `AudioFileID`, the `ExtAudioFileRef`, a `[Range<Int64>: Data]` side-fetch cache and the policy. Nothing in it is touched from any other thread; the public API hops onto the thread and resumes a continuation.

- `static func open(_ source: any ProgressiveByteSource, bitrateKbps: Int?, policy: ProgressiveReadPolicy = .init()) async throws -> ProgressiveAudioReader`: `AudioFileOpenWithCallbacks(clientData, readProc, nil, getSizeProc, nil, hint(source.pathExtension), &fileID)`, `ExtAudioFileWrapAudioFileID(fileID, false, &ext)`, reads `kExtAudioFileProperty_FileDataFormat` and `kExtAudioFileProperty_FileLengthFrames`, `kAudioFilePropertyDataOffset`. **No client format and no graph yet**: a corrupt or non-audio file fails here, before `Player` ever calls `ensureGraph()`, exactly like `AVAudioFile(forReading:)` fails before `begin` today (this keeps #0062's "random bytes never open the device" rule intact).
- `readProc`: loop on `policy.decide`: `.serve` → `source.read`; `.wait` → `source.waitForBytes` (`.failed(e)` stashes `e` in `lastError` and returns `kAudioFileUnspecifiedError`; `.cancelled` likewise with `CancellationError`); `.sideFetch(r)` → round `r` out to the granularity, `source.fetchRange`, cache it, serve from the cache; `.giveUp` → `ProgressiveError.notStreamable`; `.endOfFile` → `actualCount = 0`, `noErr`. `getSizeProc` → `source.finalSize`.
- `func setClientFormat(_ format: AVAudioFormat) throws` (standard float, the node's rate, 2 channels; `kExtAudioFileProperty_ClientDataFormat`). If ExtAudioFile refuses (channel layout it cannot map) → `.notStreamable`.
- `func seek(toFrame:) throws` → `ExtAudioFileSeek`. `func read(into: AVAudioPCMBuffer) throws -> Bool` (true at EOF) → `ExtAudioFileRead`; an error with `lastError` set rethrows the stashed Swift error, so a failed download surfaces as the `TrackCacheError` the cache produced.
- `var lengthFrames: Int64`, `var fileSampleRate: Double`, `var dataOffset: Int64`, `var sideFetchedBytes: Int64` (diagnostics), `func bufferedFrames() -> Int64`: `lengthFrames` once `availableBytes == finalSize`, else `lengthFrames * (available - dataOffset) / (finalSize - dataOffset)` minus the preroll's worth of frames, clamped to `0...lengthFrames`. Byte-proportional, exact for CBR and close enough for VBR because the reader still waits for the real bytes.
- `func cancel()` → `source.cancel()` + a flag the thread checks; `func close()` → `ExtAudioFileDispose`, `AudioFileClose`, `source.close()`, thread exits. `open` on a never-arriving header returns promptly after `cancel()`.
- `enum ProgressiveError: Error { case notStreamable(String), open(OSStatus), read(OSStatus), formatUnsupported }`. Only `.notStreamable` and `.formatUnsupported` are fallback triggers; the rest are real failures.

### 4. AudioCore: `ProgressiveFeeder` (`ProgressiveFeeder.swift`)

Runs on the reader's thread and keeps the player node fed with PCM:

- `init(reader:, node: AVAudioPlayerNode, format: AVAudioFormat, startFrame: Int64, prerollBytes: Int64, delegate: ProgressiveFeederDelegate)`; `func start()`, `func cancel()` (sets a generation so late completions are ignored, wakes the reader, joins).
- Waits until `source.availableBytes >= min(finalSize, dataOffset + prerollBytes)` (or the download is complete), then `reader.seek(toFrame: startFrame)` and loops: decode one buffer of `format.sampleRate` frames (1 s; ~353 KB at 44.1 kHz stereo), `node.scheduleBuffer(buffer, completionCallbackType: .dataRendered) { … }` and count it as outstanding; keep at most `windowBuffers = 8` outstanding (≈2.8 MB, 8 s of lead), sleeping on a condition that each `.dataRendered` completion signals. If `.dataRendered` turns out not to fire under offline manual rendering, use `.dataConsumed` (the render test in section 9 settles it; `.dataPlayedBack` is known not to fire offline, `AudioCoreTests/TestSupport.swift`).
- The **last** buffer (EOF from the reader) is scheduled with `.dataPlayedBack` and the delegate's completion token, so `Player.segmentFinished` runs exactly as it does for a file segment. Before scheduling it the feeder reports the frames it actually produced (`delegate.feederDidReachEnd(framesProduced:)`) so the scheduler's item length can be corrected (section 5) before anything is appended behind it; then `delegate.feederDidScheduleLastBuffer()` → the player pre-schedules the next file.
- **Stall**: when the reader is about to block (`waitForBytes`) and `outstanding == 0`, `delegate.feederDidStall()`; when the next buffer is scheduled again after a stall, `delegate.feederDidResume()`. Both hop to the main actor with the feeder's generation.
- First buffer scheduled → `delegate.feederDidStart()` (the player moves `.loading` → `.playing`/`.paused`).
- Every buffer is checked with `buffer.format.isEqual(node.outputFormat(forBus: 0))` before `scheduleBuffer`; a mismatch is reported as a failure, never scheduled (the node raises an Objective-C exception for a wrong format).

### 5. AudioCore: `Player` and `GaplessScheduler`

`GaplessScheduler`: `mutating func adjustLength(of token: ScheduleToken, to frames: Int64)`: no-op unless the token is the current generation and the item is `items.last`; otherwise sets `frameLength` so the next `append` starts at the right frame. Unit-tested.

`Player` (`Player.swift`, plus `Player+Progressive.swift` for the delegate conformance; the members it needs become internal, not `private`):

- `@ObservationIgnored private var file: AVAudioFile?` becomes `private var source: CurrentSource?` with `enum CurrentSource { case file(AVAudioFile), progressive(reader: ProgressiveAudioReader, feeder: ProgressiveFeeder) }` and helpers `lengthFrames`, `fileSampleRate`. `updateCurrentTime`, `seek`, `reconcileSchedule`, `handleConfigurationChange` switch on it. `nextFile` stays an `AVAudioFile?`: pre-scheduling is file-only (follow-up above).
- New observable state: `public private(set) var isBuffering = false` (true between `feederDidStall` and `feederDidResume`), `public private(set) var bufferedTime: TimeInterval?` (nil for file sources; refreshed on the 100 ms tick and on seek), both `nil`/`false` on `stop()`. `PlaybackState` is unchanged, so `LocalPlayerOutput.snapshot` (#0062) and `NowPlayingBridge` need nothing.
- `startCurrentTrack`'s load task: `let resolved = try await resolver.resolve(track)`; `.file(url)` → as today. `.progressive(source)`:
  1. `let reader = try await ProgressiveAudioReader.open(source, bitrateKbps: track.bitrate)` (no graph yet).
  2. `catch ProgressiveError.notStreamable / .formatUnsupported` → **fallback**: `let url = try await resolver.localURL(for: track)` (for Plex this joins the download already in flight as a waiter), *then* `reader?.close()` / `source.close()`, then `begin(AVAudioFile(forReading: url))`. Log once at `info` with the cache key and the reason. Any other error → `fail(error)` as today, after closing the source.
  3. Otherwise `beginProgressive(reader)`: `ensureGraph()`, `discardSchedule()`, `playerNode.stop()`, `try graph.start()`, `try reader.setClientFormat(graph.processingFormat!)`, append one scheduler item for the whole track (`frameLength: nodeFrames(lengthFrames, fileRate, nodeRate)`, `seekOffset: 0`) and hand its token to a new feeder, `source = .progressive(...)`, `feeder.start()`; state stays `.loading` until `feederDidStart`, which does what `begin` does after scheduling (`playerNode.play()` + `.playing` + `startTimeUpdates()` when `autoplayAfterLoad`, else parked `.paused`). `scheduleNextIfNeeded()` is *not* called here; it runs from `feederDidScheduleLastBuffer`.
- `scheduleNextIfNeeded`: unchanged except the guard also requires "no feeder still scheduling" (`feeder == nil || feeder.hasScheduledLastBuffer`). It still resolves the next track with `localURL(for:)` (full download, then `scheduleSegment`), which is the existing prefetch; the lead behind a progressive track is the 8-buffer window, far more than the ~0.49 s #0055 measured for file-to-file.
- `discardSchedule()` also cancels and drops the feeder (it already precedes every `playerNode.stop()`), so `stop`, `startCurrentTrack`, `seek`, `reconcileSchedule(.restartCurrent)` and `handleConfigurationChange` tear it down. Restarting from a frame (`seek`, `.restartCurrent`, device change) means: `discardSchedule()`, `playerNode.stop()`, `reader.setClientFormat` again if the processing format changed, append a fresh scheduler item (`frameLength: nodeFrames(lengthFrames - frame, …)`, `seekOffset: frame / fileRate`), new feeder from `frame`, same reader. The reader survives feeders; only `stop()`/`startCurrentTrack`/`fail` close it.
- **Node run rule**: the node runs iff `state == .playing && !isBuffering`. `feederDidStall` → `playerNode.pause()` (the node's sample timeline stops, so `scheduler.position` stays right), `isBuffering = true`; `feederDidResume` → `isBuffering = false`, `playerNode.play()` only if `state == .playing`. `play()` from `.paused` while buffering sets `.playing` without starting the node; `pause()` while buffering just sets `.paused`. Stale (older generation) feeder callbacks are ignored.
- **Seek beyond the downloaded bytes is clamped**: for a progressive source `target = min(target, Double(reader.bufferedFrames()) / fileRate)`, then the restart above; `emit(.seeked(actual))` carries the clamped value and `bufferedTime` is refreshed. Once the download is complete `bufferedFrames() == lengthFrames` and seek behaves as for a file. `seek` to a frame `>= lengthFrames` still calls `trackEnded()`.
- `fail(_:)` closes the reader before `stop()` so the cache can drop an unpinned download.
- `feederDidReachEnd(framesProduced:)` → `scheduler.adjustLength(of: token, to: framesProduced)`; MP3 lengths are estimates and resampling rounds, and the next item's `startFrame` must match what the node will actually play.

### 6. TrackCache: progressive downloads

`CacheDownloader` gains progress and ranges (two conformers: `PlexPartDownloader` and the test stub):

```swift
public protocol CacheDownloader: Sendable {
    /// `progress` is called with the bytes on disk so far after every flush and once at the end.
    func download(partKey: String, to fileURL: URL, progress: @escaping @Sendable (Int64) -> Void) async throws -> Int64
    /// `Range: bytes=lo-hi`. 206 → the body; 200 → the slice (the server ignored the range; log once at info);

```

`PlexPartDownloader.write` calls `progress(total)` after each 256 KB flush and after the final one; `fetch(partKey:range:)` builds the request with `client.request(path:)` (token in the header, never in the URL), sets `Accept: */*` and `Range`, uses the same ephemeral session, and checks the body length against the range.

`TrackCache`:

- `public enum CachedFile { case ready(URL), downloading(ProgressiveDownload) }` and `public func open(forKey:partKey:expectedSize:) async throws -> CachedFile`: hit → `.ready(url)` (touches `lastAccess` as `hit` does); miss with `expectedSize == nil` → `.ready(try await file(forKey:…))` (no size, no streaming); miss with a size → join or start the `Inflight` and return `.downloading(ProgressiveDownload)` registered as a **holder** on it. `file(forKey:)` is untouched.
- `Inflight` gains `holders: Set<UUID>` and a `Progress` object (`NSCondition`-guarded `frontier: Int64`, `outcome: Result<Void, any Error>?`, `cancelled: Bool`) that the download task's `progress` closure advances and `finish` completes. The abandon rule becomes "no waiters, no holders, not pinned" in `leave`, `setPinned` and the new `release(key:holder:)`. `finish` resolves the `Progress` *after* `insert` so a reader that sees `.completed` can rely on the file having been verified and indexed.
- `public final class ProgressiveDownload: ProgressiveByteSource, @unchecked Sendable`: `finalSize = expectedSize`, `pathExtension` from `TrackCache.fileName`, its own read descriptor on the temp file opened at creation (the inode survives the move into `Tracks/` and even an unlink on failure, so reads never race the cache), `availableBytes`/`waitForBytes` over the `Progress` condition, `read` = `pread`, `fetchRange` bridges to `downloader.fetch` with a semaphore (the caller is the reader thread, never a task), `cancel()` wakes waits, `close()` → `Task { await cache.release(key:holder:) }` (idempotent). `public var state: .downloading / .completed / .failed(Error)` for tests and logs. No token, no URL, no request is stored; `description` is `"ProgressiveDownload(<key>)"`.
- Integrity is unchanged by construction: the index only ever learns a key in `insert`, after the size check; a progressive reader reads `tmp/` through its own descriptor and never a path the index knows; `prepare()` still wipes `tmp/` at launch; `clear()` and eviction ignore in-flight keys as today.
- `PlexTrackResolver.resolve(_:)`: `.file` → `.file(url)`; `.plex` → the same server-mismatch check, then `cache.open(…)` → `.ready(url)` → `.file(url)`, `.downloading(d)` → `.progressive(d)`. `localURL(for:)` is unchanged (the fallback and the prefetch use it).
- `CachePinner` is unchanged: it pins current + next from the queue, and a progressive current track is therefore pinned, so skipping *to* a prefetching track joins its download instead of restarting it.

### 12. Risks and gotchas

- **AudioFile's read pattern per container is a black box.** Expected: WAV/AIFF/faststart M4A sequential; MP3 may read the last 128 bytes for an ID3v1 tag; `moov`-at-end M4A reads the tail; FLAC and VBR MP3 without a Xing header may walk the file to build a packet table. The side-fetch budget turns the first two into one or two range requests and the last into a fallback to today's behaviour, never a hang. Log `sideFetchedBytes` at `debug` so the user's real-file check can read it off the Console.
- **Blocking belongs on the reader's `Thread` only.** `waitForBytes`, `fetchRange` and every ExtAudioFile call block; calling them from a Swift concurrency task would stall a cooperative thread. `open` and `fetchRange`'s bridge use a continuation / semaphore in the right direction. ExtAudioFile is not thread-safe: a restart joins the old feeder before the new one touches the reader.
- **Never open the device before the header parses.** `ProgressiveAudioReader.open` runs before `ensureGraph()`; #0062's playback tests feed random bytes and rely on `.loading → .stopped` without a device. Keep that order.
- **`scheduleBuffer` format.** A buffer whose format differs from the node's connection format raises an Objective-C exception; the feeder checks `isEqual` and fails instead. Mono files must be converted to the 2-channel client format by ExtAudioFile; if it refuses, that is `.formatUnsupported` → fallback.
- **Completion types offline.** `.dataPlayedBack` never fires in manual rendering; the throttle must use `.dataRendered` (or `.dataConsumed` if that also stays silent) or the render tests will stop after eight buffers. Stopping the node fires every outstanding completion; the feeder generation must make them stale.
- **The stall pause.** `playerNode.pause()` freezes `playerTime`, which is what keeps `scheduler.position` honest; the stall test guards it. If a pause/play pair clicks on a real device, the alternative is to let the node run dry and shift the scheduler's `startFrame` by the dry frames, which is more bookkeeping, not less.
- **`length` estimates.** MP3 `FileLengthFrames` is an estimate; `adjustLength` before pre-scheduling the next track is what keeps the next track's `currentTime` right. Do not append behind a progressive item before the feeder reports its true length.
- **Fallback ordering.** Join the full download (`localURL(for:)`) *before* closing the reader, or an unpinned download can be abandoned and restarted between the two.
- **Side fetches are not integrity-checked and not cached on disk** on purpose: the final file is still one sequential download verified against `Part.size` and indexed by `insert`. The reader's in-memory range cache is capped by `maxSideFetchBytes`.
- **Seek clamp is byte-proportional.** Exact for CBR; for VBR the reader still waits for the real bytes, so a slightly optimistic clamp shows "buffering" briefly rather than playing the wrong frame.
- **`Content-Length` is not used.** A Plex track without `Part.size` plays as today (`open` → `.ready` after the full download). Every recorded fixture has a size.
- **Memory.** Eight 1 s buffers at the output rate; a 96 kHz device doubles it. Fine. Do not schedule the whole track.
- **#0062 ordering.** If #0062 lands first, `PlexPlaybackStack.standard()` needs no change (`PlexTrackResolver.init` is unchanged) and `LocalPlayerOutput` needs no change (`PlaybackState` is unchanged). If this lands first, #0062's "random bytes never reach the engine" rule holds because of the open-before-graph order above; say so in `## Fix`.
