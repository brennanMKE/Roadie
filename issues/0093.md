## Description

Found while implementing #0085 (commit 86a433f). With the two 100k scale tests moved to the full tier, `SkinLibraryTests` still took 10.3 s in the fast-tier run `20261019-000504-24208` (18.3 s with them). Every other test target in both packages finishes in under 2 s, and most in under 0.3 s.

The user expects unit tests that mock their dependencies to run well under 10 s in total. The SkinLibrary tests use real temp directories, real SQLite stores, thumbnail rendering and indexer passes; some may also wait on real time.

Expected: find what the 84 tests spend their time on (per-test times in `skinkit-tests.log`, noting that Swift Testing runs tests in parallel, so a test's reported time includes waiting), then cut the target to a couple of seconds without losing coverage: in-memory SQLite where the file format isn't under test, smaller fixtures, injected clocks instead of sleeps, fewer files per test. Anything that genuinely needs scale or real time moves to the full tier (#0085).

## Plan

### Findings

Times are from the fast-tier run `20261019-000504-24208` (`skinkit-tests.log`). The full-tier run `20261019-000756-26260` agrees. Swift Testing starts all 84 tests at once on the cooperative pool (6 threads, one per VM CPU). A reported time is therefore "finished at", not "cost".

1. **Most of the time goes to a 100k test that #0085 didn't gate: `SkinSearchBudgetTests.searchOnHundredThousandRowsStaysUnder200ms`.** #0085 gated only the two `SkinIndexScaleTests` (`.enabled(if: SlowTests.isEnabled)`). The budget test has no gate, so it runs in the fast tier, and the fast log shows its output:
   - `SEARCH seed 100000 rows: 4.902247041 seconds`.
   - After that, 7 query cases × (1 warm-up + 5 timed) × (page + count). Medians reach 57 ms ("common") and 103 ms ("sk"), which adds about 1.5 s.
   - It finishes at 6.564 s.
   - About 40 unrelated tests finish in a band between 6.30 and 6.81 s, right as it ends: every thumbnail test, all real-ingester indexer tests, and `skinIDsForHashesHandlesMoreThan500`. Tests that ended before the seed got going (SQLite, readme and store tests) took about 0.2 s each. Those other tests do milliseconds of work. They waited for pool threads and CPU while the budget test held one thread for about 6.5 s, and the two sleeping indexer tests below held the others.
   - The test belongs to #0035 (Skins window, 200 ms search budget on 100k rows). It is a scale test, so it moves to the full tier.
2. **`SkinIndexerTests.cancelMidPassKeepsCommittedBatchesAndTheNextPassFinishes` takes 9.112 s (11.9 s in full).**
   - It uses `StubIngester(delayPerFile: 0.005)` on 200 stub files. `StubIngester.note` calls `Thread.sleep` in both `hash` and `inspect`.
   - Those calls run inside `SkinIndexer.boundedMap`'s task-group children, so each sleep blocks a cooperative-pool thread. At `concurrency: 4`, the test holds 4 of the 6 threads asleep for the whole second pass (180 files × 10 ms).
   - The delay isn't needed. The cancel comes from the progress callback (`processed >= 20`), and with `progressInterval: .zero` `emit` fires after every batch. The `cancelFlag` check at the top of the next loop iteration then stops the pass. So with no delay, the cancel still lands after batch 2: exactly 20 files committed, every time.
3. **`SkinIndexerTests.concurrentRunThrowsPassAlreadyRunning` is the slowest test: 10.258 s (13.2 s in full), and it ends the run.**
   - It uses `StubIngester(delayPerFile: 0.02)` on 60 files at `concurrency: 2`. That is 60 × 2 calls × 20 ms / 2 threads, at least 1.2 s of blocked pool threads.
   - The sleep exists only to keep pass 1 running while the test polls `isRunning` and calls `run()` again.
   - It finishes about 1.15 s after `cancelMid…`, which matches its own sleep budget running once the pool frees up.
   - A gate that holds pass 1 until the test opens it does the same job without timing.
4. **The rest is not slow, and stays as it is.**
   - **Real SQLite files:** each open costs milliseconds. The store and SQLite tests that finished before the contention took 0.17–0.26 s, including the WAL checkpoint test with 200 × 2 KB rows. `checkpointTruncatesTheWAL`, `migrateCreatesSchema…` and `newerSchemaThrowsIncompatible` need real files. Switching the rest to `:memory:` would add a test-only code path in `SQLiteDatabase` / `SkinIndexStore.open` for no measurable gain.
   - **Thumbnail tests:** they render one 275×116 image or use `CountingRenderer`. Their `Latch` waits end as soon as the test opens the latch. They only looked slow because they finished in the 6.3–6.8 s band.
   - **`makeCorpus`:** writes five tiny ZIPs. Cheap.

   No test sleeps on a fixed duration apart from the two in items 2 and 3. `waitUntil` polls at 1 ms and has no timing assertion.

## Resolution notes

> 🟢 Resolved 2026-10-19 — Fast-tier `SkinLibraryTests` dropped from 10.3 s to about 0.5 s by gating the 100k search-budget test to the full tier and removing `StubIngester`'s `Thread.sleep`, with no coverage lost.

Review (claude-opus-5-5, medium) of d890d3d:

- **Coverage.** The budget test's body is unchanged and runs in the full tier. `cancelMidPass…` is tighter than before: `committed == 20` replaces `committed % 10 == 0 && 10 <= committed < 200`, and the next pass asserts exact `added`/`unchanged`/`files`. `concurrentRunThrows…` still asserts `isRunning` during pass 1, a `SkinLibraryError` on the second `run()`, `added`, and `isRunning == false` afterwards. No assertion was weakened.
- **Cancel count is exact.** With `progressInterval: .zero`, `emit` never throttles (`duration < .zero` is always false), so progress fires after every batch. The callback cancels at `processed == 20`, and the `cancelFlag` check at the top of the next loop iteration breaks before batch 3. The result is always 20.
- **Concurrent-run probe.** The `.scanning` emit runs on the actor with `running == true`, and `run()` then suspends on the detached folder scan. The probe `Task` is queued before that scan, at a higher priority than its `.utility`, and reaches the actor while pass 1 is suspended. This is ordered by the executor rather than by a guarantee in the language. If it ever lost the race, `wasRunning` would be false and the test would fail loudly; it can't pass falsely. Nothing blocks a thread.
- **Nit, not bounced:** the `/// An ingester that costs nothing…` doc line now sits above `LockedBox` (which has two doc lines), and `StubIngester` has none. Swap them on the next edit to `TestSupport.swift`.
- **Follow-up (recorded, not bounced): the thumbnail tests can still exhaust the pool.** `CountingRenderer.render` calls `Latch.wait()` inside `SkinThumbnailCache`'s `Task.detached` render jobs, so each latched render blocks a cooperative-pool thread until its test body runs `latch.open()`. Five `SkinThumbnailCacheTests` hold latched renders: `rendersAreBoundedAndOffMain` 2, and `newestRequestRendersFirst`, `cancelledBeforeStartIsDropped`, `cancelledAfterStartStillCaches` and `secondCallerKeepsAQueuedJobAlive` 1 each. That is 6 threads, exactly the VM's pool width. If all five reach their latched state before any of their bodies resumes from `waitUntil`, the process hangs at 0% CPU with no time limit. On a machine with fewer than 6 cores it gets more likely. This commit didn't introduce it, and removing the sleeps lowered the pressure; both runs below passed. Suggested fix for a new issue: mark `SkinThumbnailCacheTests` `.serialized` (at most 2 blocked threads), or give the latched suites a `.timeLimit` so a hang fails instead of stalling. The `Thread.sleep` in `CorpusRunTests` is bounded (≤ 1 s) and in another test target and process, so it isn't a deadlock risk.

## Root cause

Two things slowed the target, and neither was SQLite or fixtures:

- `SkinSearchBudgetTests.searchOnHundredThousandRowsStaysUnder200ms` seeds 100k rows (about 5 s, plus about 1.5 s of timed queries) and #0085 never gated it, so it ran in the fast tier.
- `StubIngester(delayPerFile:)` called `Thread.sleep` inside `SkinIndexer.boundedMap`'s task-group children. `cancelMidPass…` and `concurrentRunThrows…` kept up to 4 + 2 of the VM's 6 cooperative-pool threads asleep for seconds. About 40 millisecond-cost tests queued behind them and reported 6–10 s.

## Fix

Followed the plan, with one deviation:

- `SkinSearchBudgetTests` is gated with `.enabled(if: SlowTests.isEnabled)`. Its body is unchanged, so the full tier checks the same budget.
- `StubIngester.delayPerFile` and its sleep are removed.
- `cancelMidPass…` runs 60 stub files with no delay. It asserts exactly 20 committed, then `added == 40`, `unchanged == 20` and `files == 60`.
- **Deviation, `concurrentRunThrowsPassAlreadyRunning`:** the plan's `Latch` gate in `StubIngester.hash` deadlocked the first fast-tier run. A `sample` of the hung `SkinLibraryTests` process in the guest showed all 6 cooperative threads in `Latch.wait()`: the gated `hash` call plus the `SkinThumbnailCacheTests` `CountingRenderer` latches. That left no thread to run the test bodies that open them. That run was killed and isn't quoted. Instead the test now starts its second `run()` in a `Task` from the `.scanning` progress callback. That callback fires synchronously on the actor inside pass 1 with `running == true`, and pass 1 suspends right after it (the detached folder scan). So the probe reaches the actor while pass 1 is still running, with no thread blocked and no timing involved. It asserts `isRunning` was true, that a `SkinLibraryError` was thrown, `added == 10`, and that `isRunning` is false afterwards. A small `LockedBox` in `TestSupport.swift` carries the task out of the `@Sendable` callback. The `Latch` gate wasn't added. `SkinLibraryError` isn't `Equatable`, so the optional exact-case check was skipped.
- Docs: `Issues.md` and `docs/testing-in-vm.md` now say "the three 100k SkinLibrary tests (`SkinIndexScaleTests`, `SkinSearchBudgetTests`)". `SkinQueryTests` and `SlowTests` comments name the full tier and both suites.

Five slowest SkinLibrary tests in the fast tier: `cancelMidPass…` 0.503 s, `concurrentRunThrows…` 0.483 s, and the rest at or below the target's 0.504 s end. The whole target is under the 2 s goal, so no further changes were needed.

## Gotchas

- **Never block a cooperative-pool thread on something only another test body can release.** Swift Testing runs every test in parallel on a pool with one thread per CPU (6 in the VM). The thumbnail tests' `CountingRenderer(latch:)` waits already hold several threads, and one more indefinite wait deadlocks the whole process at 0% CPU with no timeout. `sample <pid>` inside the guest (`tart exec`) showed it at once.
- **The full tier ran 18.152 s, not the plan's estimated 15–16 s.** The target ends with `hundredThousandStubFilesIndexAndReindexIncrementally` (18.145 s: create 7.9 s plus three passes), not with the budget test.
- **Killing `run-tests-vm.sh` from outside left the clone running.** It was stopped and deleted with `tart stop`/`tart delete`.
