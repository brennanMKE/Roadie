## Description

Reported by the user on 0.1.0-2671617 (MacBook). Turning on the equalizer or the playlist editor (the EQ and PL buttons on the main window, or presumably Window › Equalizer / Playlist Editor) shows that window but the main player window disappears. The main window should stay visible, with the new window docked below it as in Winamp.

## Expected behavior

- Showing EQ or PL leaves the main window on screen and where it was; the new window docks under it (or where it was last placed).
- Hiding EQ or PL leaves the main window alone.
- Works on a fresh install (no saved layout) and with a saved layout, and on a smaller laptop screen.

## Plan

### Root cause (medium confidence; not reproduced)

Nothing in the code orders the main window out. Read paths: `observeEQWindow` / `observePlaylistWindow` (`App/AppDelegate.swift`) only call `show(below:)` / `hide()` on the EQ or PL controller; `SkinWindowController.show(below:)` only positions *its own* window and calls `makeKeyAndOrderFront`; `windowDidBecomeKey` → `WindowDockingCoordinator.raiseGroup` only issues `order(.below, relativeTo:)` within the skinned group (`WindowStacking.raise`); `PlayerModel.setEQWindowOpen` / `setPlaylistWindowOpen` only flip a persisted flag; no `orderOut`, `close`, `hide`, `alphaValue` or `collectionBehavior` touches the main window anywhere in `App/`. No commit since #0072 (`d1501a6`) changed `App/Window/` or `AppDelegate`'s window code, so this is a latent bug the user first hit on a laptop, not a regression. Two mechanisms can make main "disappear" while EQ/PL appear; the fix covers both:

1. **The shown window lands on top of main (most likely with a saved layout).** EQ is exactly main's size (275x116 skin px) and PL is as wide and taller, so a window placed at main's frame hides it completely. Hidden windows don't take part in docking: `dockedWindows()` (used by `DragSession`, `resize`, `ensureOnScreen`) lists only visible windows, but `layoutDidChange` saves *every* `isPositioned` window and `show(below:)` reuses a saved position as-is (`isPositioned` short-circuits the "dock under reference" branch). So: EQ docked under main, EQ closed, main dragged (alone) down or over to where EQ was, or `ensureOnScreen` shifting/resetting the visible group on the smaller laptop screen, or Double Size resizing main while EQ is hidden: on the next EQ/PL show the stale saved spot overlaps or exactly covers main. Evidence: code paths above; nothing re-validates a saved position against the windows on screen.
2. **Stage Manager on the MacBook (possible; matches "shows that window but main disappears" exactly).** The three skinned windows are separate top-level `NSWindow`s with default `collectionBehavior`. With Stage Manager on and "Show windows from an application: One at a time", making the new EQ/PL window key moves the app's other window (main) to the strip. #0072's review flagged Stage Manager interplay as an unverified residual risk. Not checkable here: this host (Mac mini) has Stage Manager off (`com.apple.WindowManager` has no `GloballyEnabled`), and the user's MacBook settings are unknown.

Ruled out: launch-time ordering (bug is on toggle), `raiseGroup` hiding anything (it only orders within the group, `order(.below, relativeTo:)` with a live window number), the SwiftUI Library/Skins close loop at launch (matches only `library*`/`skins*` identifiers).

### Fix A: never show EQ/PL over another skinned window (pure, tested)

- `Packages/SkinKit/Sources/WindowDocking/LayoutRules.swift`: add
  `public static func showPosition(size: CGSize, saved: Offset?, below reference: Box, visible: [DockedWindow], screens: [Box], primary: Box) -> Offset`.
  Returns `saved` when it is set, its box intersects no box in `visible` (strict overlap, touching edges are fine: docked windows share an edge) and its title strip is on a screen (`isGrabbable`); otherwise the top-left directly under `reference` (`x: reference.x, y: reference.bottom`). If that box would hang below the bottom of the screen `reference` is on, keep it there anyway (Winamp lets windows hang off the bottom; the title strip is what must stay on screen) and never move `reference` (expected behaviour: main stays where it was).
- `App/Window/SkinWindowController.swift` `show(below:)`: on **every** show while not visible (not just the first), ask the coordinator for the position instead of the `isPositioned`/`hasBeenShown` branch. Keep `window.center()` for the no-reference case. Keep `applyLayout()` on first show.
- `App/Window/WindowDockingCoordinator.swift`: add `func showPosition(for controller: SkinWindowController, below reference: NSWindow) -> NSPoint` (converts with `desktop`, passes `dockedWindows()` excluding `controller`, `saved` = current frame's box when `controller.isPositioned`); `show` moves there, sets `isPositioned`, calls `layoutDidChange()`.
- `AppDelegate`: no change to the observers; `playlistReference` already picks EQ when visible.
- Hiding stays `orderOut` only; main is never moved by show/hide.

### Fix B: Stage Manager (only if Step 0 (c) reproduces)

In `SkinWindowController.init`, give `.main` `collectionBehavior.insert(.primary)` and EQ/PL `.insert(.auxiliary)` (macOS 13+, target is 14) so Stage Manager keeps them with the main window instead of swapping it out. Read the SDK's `NSWindow.h` doc comments for `.primary`/`.auxiliary` first and confirm in the VM that Mission Control, ⌘` cycling and Spaces still behave; if `.auxiliary` misbehaves, fall back to recording the finding in `## Notes` and filing a follow-up rather than switching to child windows (child windows move with the parent and would fight the docking engine).

## Root cause

Not reproduced (the implementer cannot drive the app in the VM). When the EQ or playlist window was shown it went back to its saved position without checking it. That position was saved while the window was hidden, and hidden windows don't take part in docking. So after main was moved alone, or shifted by on-screen recovery or a Double Size change, the saved spot could overlap or exactly cover main, and the newly shown window hid it.

### Second pass (3ee0b4d)

Reproduced in a Tart VM (see the second-pass entry in `## Notes`): Stage Manager with "Show windows from an application: One at a time" (`AppWindowGroupingBehavior` 0). The three skinned windows are separate top-level `NSWindow`s with the default collection behaviour, so Stage Manager treats each as its own set. Making EQ or PL key put the main window (and any other skinned window) into the strip. Stage Manager off, or "All at once", did not show the bug. The overlap that Fix A covers is a real defect, but it was not what the user saw.

## Fix

Fix A from the plan. `LayoutRules.showPosition` (pure) keeps the saved top-left only when that box overlaps no visible skinned window (shared edges are allowed) and its title strip can be grabbed on a screen. Otherwise it returns the spot directly under the reference window. It never moves the reference, and the window may hang off the bottom of the screen. `WindowDockingCoordinator.place(_:below:)` applies it on every show from hidden, not only the first, then marks the window positioned and saves the layout. `SkinWindowController.show(below:)` routes through it. With no reference, an unpositioned window still centres.

Deviations from the plan:
- `showPosition` takes an extra `titleBarHeight` argument, which `isGrabbable` needs.
- Step 0 (reproducing in the VM) was skipped, so Fix B (Stage Manager `.primary`/`.auxiliary` collection behaviour) was not done. If the user still sees the bug on the MacBook with Stage Manager on, Fix B is the follow-up.

### Second pass (3ee0b4d)

Fix B from the plan. `WindowKind.windowGroupRole` (pure, in `WindowDocking`) returns `.primary` for main and `.auxiliary` for the equalizer and playlist. `SkinWindowController.init` inserts the matching `NSWindow.CollectionBehavior` (`.primary` / `.auxiliary`, macOS 13+) through a small `WindowGroupRole.collectionBehavior` mapping. The SDK's `NSWindow.h` says to specify at most one of `.primary`, `.auxiliary` or `.canJoinAllApplications`, with `.auxiliary` meant for utility panes; nothing else in the app sets `collectionBehavior`. Fix A stays in place.
