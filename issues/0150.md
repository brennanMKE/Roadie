## Description

Reported on build 0.1.0 (20261022.0456): while listening to a playlist, pressing the main window's forward (next track) button does nothing. Playback continues on the current track.

The playlist was started from the Library (Music Assistant), so the queue is Music Assistant's (#0144). Not yet known whether the output was This Mac (Sendspin) or a speaker, or whether ⌘→ / the media keys / Now Playing next behave the same.

## Root cause

Not proven against a live server; read this as the most likely cause, with medium-low certainty.

Before the fix, next and previous on any output that Music Assistant feeds (This Mac through its universal-player wrapper over Sendspin, or a speaker) went to the player as `players/cmd/next` / `players/cmd/previous`. The app side delivers those correctly. The main window and shade buttons, the Playback menu, ⌘→/⌘← and the media keys all reach `PlayerModel.send`, which yields `(command, selectedOutput)`. `PlaybackRouter.backend(for:command:)` sends This Mac to Music Assistant while `ThisMacFeed` is `.musicAssistant`, which is set synchronously by a Library play on This Mac, so the command does not land on the local AudioCore queue. `MusicAssistantBackend.transport` then redirects a synced member to its leader. No control is disabled or guarded. `get_active_queue` decodes with `MAPlayerQueue` (already used by `queueID(for:)` and the recorded fixture). The reviewer found no more likely app-side cause.

On the server side, the repo has the queue controller source but not the players controller, so how MA 2.10.6 handles `players/cmd/next` is not in hand. The recorded players (`players-all-sendspin.json`, `docs/ma-protocol/sendspin-probe.json`) give a hint. None of them lists the `next_previous` feature. The universal players (This Mac's wrapper among them) have only the `Music Assistant Queue` source with `can_next_previous: false`, so a player-level next has nothing to act on unless the server forwards it to the queue. The reviewer's memory of upstream MA is that it does forward to the active queue. If so, the command would have worked, or failed with an error notice, and this would not be the cause. The user saw no notice. That fits "accepted, nothing done" better than an error, but it is not proof. A live check is still owed: press forward with an MA playlist on This Mac and on a speaker, on the old and new builds.

## Fix

`MusicAssistantBackend.transport` maps `.next` / `.previous` to `player_queues/next` / `player_queues/previous`. The `queue_id` comes from `player_queues/get_active_queue` on the (leader-redirected) player id and falls back to the player's own id. This is the queue controller's own command. In the MA source (`player_queues` controller), it moves `current_index` at once, signals the queue update, and starts `play_index` after a one-second debounce. So it works whatever `players/cmd/next` does, as long as the queue is active, which is true when the player's `active_source` is the queue, as recorded. The other transport commands still go to `players/cmd/*`. The local AudioCore path is unchanged.

## Notes

- Root cause: every output that Music Assistant feeds (This Mac via Sendspin, and any speaker) got next and previous as `players/cmd/next` / `players/cmd/previous` on the player. MA accepts those but does not move the queue for these players, so nothing happened. The main window buttons, ⌘→/⌘←, the media keys and Now Playing all use this path (`PlayerModel.send` → `PlaybackRouter` → `MusicAssistantBackend.transport`).
