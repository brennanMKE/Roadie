## Description

Part of M13: Playlists ([#0132](0132.md)). Work item W1 of the playlists design, [docs/design/playlists.md](../docs/design/playlists.md) §4; the UX is in §2, the architecture in §3 and the Music Assistant command facts in §1.

## Root cause

`LibraryPlaylist` carried only id, name, count and artwork. `MAMapping` dropped Music Assistant's `is_editable`, `is_dynamic`, `owner` and provider mapping, and `MATrack` didn't decode `position`. So the Library had no way to tell a user playlist from a built-in or a provider's one, and showed them all as one flat list.

## Fix

Followed W1 of docs/design/playlists.md.
- `MediaKind`/`MAMediaKind` gain `.radio`, and the one exhaustive switch in FolderBackend now handles it. `PlaylistEditing` (addRemove, reorder, rename, delete) and `PlaylistSource` (user, builtIn, provider(name:)) are new. `LibraryPlaylist` gains `isEditable`, `isDynamic`, `owner`, `source`, `editing`, `isFavorite` and `libraryID`. `LibraryTrack` gains `isFavorite` and `playlistPosition`, and `LibraryAlbum`/`LibraryArtist` gain `isFavorite`.
- `MAPlaylist` decodes `supported_mediatypes` and `MATrack` decodes `position`.
- `LibraryPlaylist(ma:canReorder:)`:
  - Source comes from the first mapping's `provider_domain`. A `builtin` playlist is `.builtIn` when its owner is "Music Assistant" or it is not editable, and `.user` when it is editable.
  - `library` (or no domain) maps to `.user`, and any other domain to `.provider(display name)`.
  - Editing is `addRemove` when the playlist is editable and not dynamic, plus `reorder` only when `canReorder` is true. It defaults to false until W4a adds feature detection. `rename`/`delete` are included unless the playlist is built-in.
  - `libraryID` is the `item_id` when `provider == "library"`.
- New pure `LibraryBrowser/PlaylistGrouping` has:
  - groups: My Playlists, Built-in, then each provider in first-seen order, with "· read-only" when none of a provider's playlists is editable;
  - the flattened header and playlist rows;
  - `countText` ("∞" for dynamic playlists);
  - `detailLine` (source · owner · Read-only · Dynamic).
- `PlaylistListView` draws section headers (selection disabled, lock icon on read-only providers) and the "∞" count. The track detail header adds the source/owner/Read-only/Dynamic line for a selected playlist.

Deviations:
- **Built-in detection.** The recorded 2.10.6 built-in playlists have `owner: "user"`, not "Music Assistant", so the read-only test does the work there.
- **Provider names.** They come from a small domain table plus title-casing in `MAMapping.providerDisplayName`, not from `providers.json`.
- **Owner shown as "you".** This needs `auth/me` and is left for a later item.
- **Function reference changed.** `MusicAssistantBackend.playlists(page:)` now maps with a closure, because the new defaulted argument broke the `init(ma:)` function reference.
- **Test placement.** The `ModelDecodingTests` tests live in an `extension ModelDecodingTests` in a new file, so they stay apart from #0133's edits to that file.
