Umbrella for milestone **M15.1: 0.0.4 fixes**. These are the bugs and gaps the user hit in Roadie 0.0.4, the release that shipped M15 ([#0173](0173.md)). The milestone ships no code itself and stays open until every child is resolved, closed or won't-fix.

## Findings (checked against the code, 2026-10-24)

- **Double-click → first track, both from the playlist and from ⌘J.** Both go through `PlaylistModel.playRow(_:)` (`App/Playlist/PlaylistModel.swift:233`; ⌘J calls it from `JumpToFilePanel.playSelected`, `App/JumpToFile/JumpToFilePanel.swift:272`).
  - On a Music Assistant queue it sends `remote.items[index].index` to `player_queues/play_index`.
  - That `index` comes from `MAQueueWatch.item` (`Packages/PlayerKit/Sources/MusicAssistantKit/MAQueueWatch.swift:170`) as `item.index ?? fallbackIndex`. Music Assistant's `QueueItem.index` has a **default of 0** (`docs/ma-protocol/openapi.json`, `QueueItem.index`, `"default": 0`). A server that leaves it at the default sends `"index": 0` for every item, so the `??` never falls back, every row's index is 0, and every double-click plays item 0.
  - The test fixtures never caught this: they are synthetic and set `"index": n` (`BackendQueueTests.itemJSON`, whose doc comment says the recorded `player-queue-items.json` is empty).
  - The local path (`onPlayLocal` → `Player.play(at:)` → `PlayQueue.select`) checks out, and `PlayerTests` covers `play(at:)`. #0187 adds logging at every hop so a local repro, if there is one, can be pinned.
- **Drag from the Library (⌘L).** Artist rows (`ArtistListView`, the section the Library opens on) and playlist rows (`PlaylistListView`) have no `.draggable` at all. So in the default view nothing drags. Album and track rows do drag (#0136), but #0184's drop into the skinned editor was never tested by hand (#0184 resolution notes, check 1), and its AppKit target has never been seen to receive a SwiftUI drag. The planned SwiftUI fallback was not built. #0188 hardens the target, adds the fallback and logging, and makes artists draggable.
- **Playlists.** Named playlists come only from Music Assistant. `FolderBackend.playlists` throws `.unsupported(.playlists)` (`Packages/PlayerKit/Sources/FolderBackendKit/FolderBackend.swift:325`), and its `play` refuses `.playlist` ids (line 373). Music Assistant's `play` sends the ids' URIs to `play_media`, which expands a playlist URI. `PlayerModel.loadPlaylist` already plays a playlist that way. The Library's playlist rows just never offer it (#0189).
- **The skinned editor and playlists.** The skinned playlist editor *is* the play queue (Winamp's model). LIST › Save and LIST › Load exist (#0140, #0146) and follow the queue the editor shows (`QueueSaveTarget`):
  - The local queue saves and loads M3U/PLS files.
  - A Music Assistant queue saves as a server playlist and loads one with `PlaylistPickerSheet`.
  - The gap: while the editor shows the **local** queue and the Library's source is Music Assistant, LIST › Load only opens a file panel. There's no way from the skin to reach "Party" (#0190).
  - Nothing explains any of this (#0191).
