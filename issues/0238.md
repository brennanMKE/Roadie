## Description

The user: "What I want for full screen mode [is] to show the song and artist and playback details but when the mouse cursor has been idle it should disappear and just show the visualization." After #0237 the visualization goes full screen but shows only the picture (and a small preset name); there's no way to see what's playing without leaving it, and the cursor sits on top of the picture.

Design: [docs/design/visualization.md](../docs/design/visualization.md) §2.4, §4.4, §3.1 (`OverlayVisibility`).

## Plan

### The overlay view

`App/Visualization/VisualizationOverlayView.swift` (SwiftUI, in an `NSHostingView` added by `VisualizationHostView` above the renderer view, filling it; the hosting view returns nil from `hitTest` except over the card, so double-click and right-click on the picture still reach the host view):

- **Top strip:** the preset name (replaces #0235's `vis.preset` label; same id and value), an order badge ("Random" / "In order") and a lock symbol when locked.
- **Card** (bottom-centre, `.ultraThinMaterial` over black at 0.55, corner radius 12, 24 pt margin, max width 720, white text with a shadow; group `vis.overlay`, accessibility label "Now playing"):
  - title, large (`vis.overlay.title`; "Nothing is playing" when idle);
  - "Artist — Album" (`vis.overlay.artist`; album omitted when unknown);
  - a state symbol ▶ / ❚❚ / ■ / "Loading…" (`vis.overlay.state`, label "Playing" / "Paused" / "Stopped" / "Loading"), elapsed, a thin progress bar (display only), total (`vis.overlay.time`, label "Elapsed 1:12 of 5:20"; remaining when the main window shows remaining time); elapsed updates once a second from `PlayerModel.mainWindowStatus`, not at frame rate;
  - "Next: <title>" when the local queue knows the next track (`player.queue` up-next and order, the same source the playlist uses), omitted otherwise (`vis.overlay.next`); the output's name; "Volume 72%" (`vis.overlay.output`);
  - the key hint "← → presets · Space next · L list · F1 help" for the first three times the overlay shows in a launch.
  - **Audio note** (`vis.overlay.note`) when `audioSource == .remote(name)`: "Playing on <name>. The visualization needs the music playing on this Mac."
- **Badge** (`vis.badge.noAudio`): "No audio on this Mac", small, dim, bottom-left, shown whenever `audioSource` is remote, whether or not the card is up.
- Fade 0.25 s in and out.
- All data from `PlayerModel` (`nowPlaying`, `mainWindowStatus`, `selectedOutput`, `volume`) through `VisualizationModel`, observed (no polling at frame rate).

### Idle hiding

- `VisualizationModel` owns `overlay: OverlayVisibility` (#0234) with `settings.overlayIdleSeconds` (Debug `-RoadieVisOverlayIdle <s>` overrides) and `now` from `CACurrentMediaTime()`.
- `VisualizationHostView`: a tracking area (`.mouseMoved, .mouseEnteredAndExited, .activeInKeyWindow, .inVisibleRect`) → `pointerMoved(inside: true)` / `pointerExited`; the card's `.onHover` → hold `.pointerOnOverlay`.
- Holds: `.notPlaying` while `playbackState` isn't playing/loading, `.menu` while the right-click menu is open (#0236's delegate); later issues add `.browser`, `.help`, `.voiceOver`, `.notice`.
- `show(at:)` when the window opens and on `windowDidEnterFullScreen`.
- A one-shot `Timer` scheduled for `overlay.nextDeadline` (rescheduled after every input) calls `overlay.tick`; the view binds `isOverlayVisible`.
- **Cursor:** when the state machine hides the cursor and the pointer is inside the view, `NSCursor.setHiddenUntilMouseMoves(true)`; AppKit shows it again on the next movement, which also reaches `pointerMoved`. Never hide it while the window isn't key or the app isn't active. On close, resign key and exit from full screen, `NSCursor.setHiddenUntilMouseMoves(false)`.
- Probe: `overlay` (`shown|hidden`), `cursorHidden` (the state machine's value).
- Key presses don't show it (arrowing through presets keeps the picture clean; #0236's toast names the preset).

## Root cause

An addition: the window showed only the picture and the preset name. The first implementer's overlay drew correctly but its four UI tests failed for two reasons, neither in the hide/show logic:

1. The card's texts were plain `Text(…).accessibilityIdentifier(…).accessibilityLabel(…)`. On macOS XCUITest finds those by identifier but reads `label` as `""` (#0200), so `vis.overlay.state` read "" in the paused test, and VoiceOver got no usable value.
2. The tests launched with `-RoadieVisOverlayIdle 1`. XCUITest's first query after `hover()` lands about 1.1 s later, by which time the card had hidden again (the attachments show the hover at 724.0, the hide at about 725.0, the first query at 725.1, and the probe then `overlay: hidden, cursorHidden: true`). The movement path worked.

A third failure showed up once those were fixed: `isFullScreen` read the main window's probe first, and that element can leave the tree between `exists` and `value` while the vis window enters its own Space ("No matches found … state.probe").

After review (bounced): the cursor could hide while the pointer was outside the picture. `OverlayVisibility` starts with `pointerInside = true` and `show(at:)` never corrected it. So opening the window by ⇧⌘K or a menu with the pointer over the main window or menu bar hid the cursor there after the idle time: the tracking area never saw an enter or exit, and `hideCursor` checked only that the window was key and the app active. The same happened when the pointer left while the window wasn't key (the tracking area is `.activeInKeyWindow`) and the window then became key by keyboard.

## Fix

Follows the plan, with these points:

- `VisualizationOverlayView.swift`: an `NSHostingView` subclass whose `hitTest` is nil, filling the picture, so double-click and right-click reach the host view. Every text (title, artist, state, time, next, output, note, badge) is a `.skinDisplay(id, label:, value:)`; the card is a `.contain` group `vis.overlay` labelled "Now playing".
- `VisualizationModel+Overlay.swift`: the content (`VisualizationOverlayContent.make`) and the idle hiding on `OverlayVisibility`, with a one-shot timer rescheduled after every input. The holds are `.notPlaying` (synced from the window controller's observation), `.menu` (the right-click menu's delegate), `.pointerOnOverlay` (the card's `onHover`) and `.browser` (`openList` / `closeList`, from the #0240 merge).
- Pointer movement: the host view's tracking area, plus a local `mouseMoved` monitor for the window, because the hosting views sit above the host view. The cursor hides via `NSCursor.setHiddenUntilMouseMoves(true)` only while the window is key in the active app, and is reset on close.
- Deviation: the top strip's preset name stays #0235's `vis.preset` `NSTextField`; the card's first line repeats the preset name, its order ("Random" / "In order") and the lock.
- Tests: the overlay UI tests use a 3 s idle hook (60 s for `testOverlayShowsTheSong`, which only reads the card), find the card first and then wait up to 10 s for it to go. `VisualizationUITests.isFullScreen` reads the canvas frame first and the probe only when the canvas can't be read. A first try that read the probe through `snapshot()` in the shared helper broke every probe read (run 2) and was reverted.

After the bounce (1f78dbb, on the merge of main at 8b68952, which brings #0241's Settings › Visualization):

- The window controller's `isPointerInside` converts `window.mouseLocationOutsideOfEventStream` into the host view and checks its bounds; the model reads it through `VisualizationModel.isPointerInside`. `syncPointerInside()` marks the pointer as outside when it is. It runs in `showOverlay()` (so `show()` and `setFullScreen(true)`), on `windowDidBecomeKey`, when the idle setting changes, and before every idle tick, so the probe's `cursorHidden` is the real state.
- `hideCursor` refuses unless that same check finds the pointer inside (the safety net).
- A comment on the window's never-removed mouse-moved monitor: the controller lives as long as the app, the closure is weak, and it filters to this window.
- The live setting: `updateSettings` calls `applyOverlayIdleTimeout()` when `overlayIdleSeconds` changes. The running overlay takes `overlayIdleTimeout` (nil = Never), shows, and counts again from now; Never keeps it up.

## Review notes

> 🔴 Bounced 2026-10-29: the cursor can hide while the pointer is outside the visualization, which the design forbids.

My re-run of the implementer's command at 6100971 passed with no retries: `VERIFY PASS (exit 0) 20261029-063651-41768: 17 steps passed, 1928 tests in 17 test runs`; `UI 23 tests passed (VisualizationUITests) on base`; `AUDIO silent`; `EXPECT all 11 expected test(s) passed`. Everything else in the change is sound: the content, the holds, the timer, the hit-test-nil hosting views, `.skinDisplay` on every text, the Debug-only hook, the canvas-first `isFullScreen`, the docs and the CHANGELOG line.

**What fails.** `OverlayVisibility` starts with `pointerInside = true`, and `show(at:)` doesn't change that. Say the window opens (⇧⌘K, the menu, `vis.open()`) or enters full screen while the pointer is somewhere else: over the main skinned window, the menu bar, or the windowed vis window's surroundings. The window's tracking area never sees an enter or exit, so the state machine still thinks the pointer is inside. After the idle timeout `tickOverlay` sets `isCursorHidden`. `hideCursor` checks only that the window is key and the app active, both true right after opening, and then calls `NSCursor.setHiddenUntilMouseMoves(true)`. So the pointer vanishes over the main window or the menu bar 3 s after the user opens the visualization from there. That is the most common way to open it. It comes back on the next movement, but design §2.4 says the cursor hides "only while the pointer is inside the view". The plan says the same in By hand 5. The same gap applies whenever the pointer leaves while the window isn't key (the tracking area is `.activeInKeyWindow`), then the window becomes key again by keyboard.

**What the next pass must fix:**
1. Seed the pointer position from the real mouse location whenever the overlay is shown by the window rather than by movement: `showOverlay()` from `show()` and `setFullScreen(true)`, and on `windowDidBecomeKey`. For example, the controller computes `hostView.bounds.contains(hostView.convert(window.mouseLocationOutsideOfEventStream, from: nil))` and calls `overlayPointerExited()` (or passes `inside:`) when it is false. The probe's `cursorHidden` then reflects it.
2. As a safety net, have `hideCursor` itself refuse unless that same check finds the pointer inside the host view.
3. Add a regression test that fails on 6100971 (`--expect-fail`). Preferred is a UI test in `VisualizationUITests`: open the vis window with the pointer hovering the main window (`roadie.main` element `.hover()` first, then open by key/menu without touching the canvas), wait past the 3 s idle, and expect the probe to say `overlay: hidden` and `cursorHidden: false`. Also add a unit test in `VisualizationOverlayTests` if the seeding goes through the model.

**Minor, no change required:** the window's local `mouseMoved` monitor is never removed. That's acceptable, because the controller is cached for the app's life (`AppDelegate.visualizationWindow`) and the closure is weak and filters by window, but a comment saying so would help. `testOverlayStaysUpWhilePaused` sleeping 5 s against a 3 s timeout is fine: it's a negative check and can't fail falsely from the sleep. The plan's deviation (the top strip is still #0235's `vis.preset` field, with the preset, order and lock repeated in the card) is acceptable; #0239's readouts can revisit it. VoiceOver and Reduce Motion are #0242's. The card's `onHover` hold under a hit-test-nil hosting view has no automated test; check it by hand (By hand 3).
