## Resolution notes

> 🟢 Resolved 2026-10-21 — The Library now follows Music Assistant's `media_item_*` and `favorite_updated` events: playlists created, renamed or deleted elsewhere reload the list (and the open playlist), favorites toggled elsewhere update the hearts, and plays nudge Discover.

Review (Opus, phase 3): read `git show 644b77f e4d541e` against design §1.4, §3.3–3.5 and W5. `MALibraryChanges.classify` is pure and lenient: it takes the URI from `object_id`, else `data.uri`, returns `[]` for unknown events or unparseable URIs, maps `media_item_updated` with `favorite` to `.favoriteChanged` (the 2.10.6 form) and `media_item_played` to `.played`. The backend follows `client.events()` only while `libraryChangeContinuations` is non-empty (`restartLibraryChanges()` returns early otherwise, and the last `onTermination` stops the task); it is stopped before an old client is replaced and in `disconnect()`, and restarted after `connect()` installs a client. The client's `events()` broadcasts every frame to each continuation (`MusicAssistantClient.swift`, the `yield` loop) and survives its own reconnect loop, so the Notes' claim holds: this subscription can't take frames from the now-playing, queue or activity watchers, and `reconnectRefetchesAndKeepsTheStream` never subscribes to it. No task leaks: `LibraryBrowserModel.disappeared()` cancels `changesTask`, which ends its `for await` and terminates the stream, and `streamRestartsAfterReconnect` and `playlistAddedElsewhereReloadsTheList` check the subscriber count drops to 0. Hooks: `.favoriteChanged` goes to `favorites.apply(favorite:for:)`, `.played` to `discover?.scheduleRefresh()`, added/deleted/updated reload `playlists` when it has loaded, and a deleted selected playlist clears the selection. Minor, not blocking:
- The classifier checks only `mediaType == .playlist`, not the `library` provider, so a `spotify://playlist/…` event would also reload the list. The Fix text claims `library://` only. It's a harmless extra refetch, and §1.4 says these events carry library URIs anyway.
- A playlist rename reloads the selected playlist's tracks through `retryTracks()` as a stand-in for `PlaylistEditor.reloadIfOpen` (noted in Fix).
- If the client gives up reconnecting (`stopReconnecting` finishes its event streams), `libraryChangeTask` stays set until the next `connect()` replaces the client. That's the same as the other watchers.

## Root cause

The backend API had no way to report library changes. Music Assistant pushes `media_item_*` and `favorite_updated` events, but nothing turned them into anything the Library could use. Lists only reloaded on an explicit refresh, so a playlist created, renamed or deleted elsewhere, or a favorite toggled elsewhere, stayed stale.

## Fix

- `MusicBackendKit`: `LibraryChange` (`playlistAdded/Updated/Deleted`, `favoriteChanged(id, Bool?)`, `played`) and `MusicBackend.libraryChanges() async -> AsyncStream<LibraryChange>`, whose default is a stream that finishes at once. The requirement is `async` (design §3.1 had it sync) to match `nowPlaying(on:)` and so the actor stub can conform. The MA implementation must be `async` too: a sync overload loses to the protocol's async default in async contexts, which made the first verify run fail.
- `MusicAssistantKit/MALibraryChanges.swift`: `MALibraryChanges.classify(_:)` is a lenient, pure classifier. It takes the URI from `object_id`, falling back to `data.uri`; playlist events only for `library://…/playlist/…` URIs; `favorite_updated` or a `media_item_updated`/`added` carrying `favorite` gives `.favoriteChanged`; `media_item_played` gives `.played`. Anything it can't parse yields nothing. The backend plumbing works like `playbackActivity()`: it follows the installed client's `events()` only while subscribed, restarts on connect, stops on disconnect, and the client's stream survives its own reconnects.
- `LibraryBrowserModel`: a changes task starts when connected and appeared and stops in `disappeared()`. `apply(_:)` reloads the playlists list on added, deleted and updated, and clears the selection when the selected playlist is deleted. On updated it reloads the selected playlist's tracks; this stands in for `PlaylistEditor.reloadIfOpen` until that lands. `.played` calls `discover?.scheduleRefresh()` and `.favoriteChanged` calls `favorites.apply(favorite:for:)`. Every change is then forwarded to `onLibraryChange`, a seam for models not yet owned here.
- `StubMusicBackend`: `pushChange(_:)`, `libraryChanges()` and `changeSubscriberCount`.
