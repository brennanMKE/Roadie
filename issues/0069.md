## Description

`PlayerModel.mainWindowStatus` (`App/PlayerModel.swift`) uses `nowPlaying.elapsed(at: Date())` for the time digits when `selectedOutput` is not This Mac. Nothing re-evaluates the main window on a clock for that path: on This Mac the body is driven by `player.currentTime`, which the player updates every 100 ms, but for other outputs the view only re-renders when a new `NowPlaying` snapshot arrives. The digits would freeze between snapshots and jump when the next one lands.

Latent today (no UI sets `selectedOutput` to anything but This Mac), but it will show as soon as remote outputs (#0064) can be selected.

Expected: while a non-local output is playing, the elapsed/remaining digits advance once a second (for example a `TimelineView(.periodic(from:by: 1))` around the time digits that exists only while the remote state is `.playing`, so the app has no idle wakeups).

## Plan

### Where the freeze is

Every reader of `PlayerModel.mainWindowStatus` has the same problem, not just the big digits:

- `App/MainWindowView.swift`: `MainWindowStatusLayer` (time digits) and `positionSlider` (it reads `model.positionFraction`, which reads `mainWindowStatus`).
- `App/MainShadeView.swift`: `MiniTimeView` and the shade `positionSlider`.
- `App/Playlist/PlaylistWindowView.swift`: `PlaylistMiniTimeView` (around line 255).

On This Mac they re-render because `player.currentTime` is observed and changes every 100 ms. For any other output, `Date()` inside a computed property is not observable, so nothing re-renders until the next `NowPlaying` snapshot arrives. All five views need the clock, but only while a non-local output is `.playing`.

### Approach

1. **The pure part goes in MusicBackendKit, so it can be tested without the app or #0064** (`Packages/PlayerKit/Sources/MusicBackendKit/Playback.swift`, next to `elapsed(at:)`). Add to `NowPlaying`:

   ```swift
   /// When a 1 s clock for `selected` should start so that each tick lands just after the elapsed time
   /// crosses a whole second. nil on This Mac (the local player drives the view) and unless playing, so
   /// nothing ticks while idle, paused, loading or stopped.
   public func remoteClockAnchor(selected: OutputDevice.ID) -> Date?
   ```

   Return nil when `selected == OutputDevice.thisMacID` or `state != .playing`. Otherwise return `updatedAt - elapsed.truncatingRemainder(dividingBy: 1) + clockLead`, where `clockLead` is a small fixed offset (for example 0.05 s, as a `static let`). The offset keeps a tick from evaluating to 14.9999 and flooring to the old second. `TimelineView(.periodic(from:by:))` aligns its entries to `from`, so the digits change on the remote's real second boundaries and do not drift between snapshots.

2. **PlayerModel takes a date** (`App/PlayerModel.swift`):
   - Change `mainWindowStatus` into `func mainWindowStatus(at now: Date = Date()) -> MainWindowStatus`, or keep the property as a wrapper around `mainWindowStatus(at: Date())` to keep the diff small. The remote branch uses `nowPlaying.elapsed(at: now)`; the local branch is unchanged.
   - Do the same for `positionFraction` (`positionFraction(at:)`). `scrub` and `seek` only need `duration`, so they can keep calling the no-argument form.
   - Add `var remoteClockAnchor: Date? { nowPlaying.remoteClockAnchor(selected: selectedOutput) }`. It is computed from the observed `nowPlaying` and `selectedOutput`, so a view that reads it re-renders when either one changes. That includes a new snapshot re-anchoring the clock, and leaving `.playing`, which removes the TimelineView.

3. **One small clock view in the App** (new file `App/RemoteClock.swift`; `project.yml` uses `sources: [App]`, so it is picked up automatically after XcodeGen):

   ```swift
   /// Re-evaluates `content` once a second while `anchor` is set (a non-local output playing), else once.
   struct RemoteClock<Content: View>: View {
       let anchor: Date?
       @ViewBuilder let content: (Date) -> Content
       var body: some View {
           if let anchor {
               TimelineView(.periodic(from: anchor, by: 1)) { content($0.date) }
           } else {
               content(Date())
           }
       }
   }
   ```

   Pass `timeline.date` and not `Date()`, so the digits are worked out for the aligned tick. When `anchor` is nil there is no TimelineView, so This Mac playback, pause, stop and idle add no wakeups. `BlinkingView` stays as it is. It runs only while paused, and pause never has an anchor.

4. **Wrap only the views that need it.** Do not wrap the whole `normalBody`, because the marquee, visualizer and buttons should not rebuild every second.
   - `MainWindowView.normalBody`: `RemoteClock(anchor: model.remoteClockAnchor) { MainWindowStatusLayer(skin:, status: model.mainWindowStatus(at: $0), …) }`, and the same for `positionSlider` (pass the date into `positionFraction(at:)`). One `RemoteClock` around a small `ZStack` that holds both is fine too.
   - `MainShadeView`: `MiniTimeView` and `positionSlider`, the same way.
   - `PlaylistMiniTimeView`: wrap its body content and read `model.mainWindowStatus(at:)`.
   - Keep each view's `.offset` outside or inside the wrapper as it is now, so the layout does not move. `MainWindowStatusLayer` and `MiniTimeView` take `status` already, so their own code does not change.

5. **Leave alone**: `NowPlayingBridge` (Control Center works out elapsed time from a rate itself), the `BlinkingView` timing, and anything in #0064's output picker. The fix only depends on `selectedOutput` and `nowPlaying`, which already exist. It is inert until something sets `selectedOutput` to a non-local id, and it starts working as soon as #0064 does that.

### Tests to add

Add these to `Packages/PlayerKit/Tests/MusicBackendKitTests/ModelTests.swift`, in `NowPlayingTests`. Each one builds a fake remote snapshot (`NowPlaying(output: OutputDevice.ID(rawValue: "homepod"), state: .playing, duration:, elapsed:, updatedAt:)`), so none of them needs #0064:

- `remoteClockAnchorIsNilOnThisMac`: a playing snapshot with `selected: OutputDevice.thisMacID` gives nil.
- `remoteClockAnchorIsNilUnlessPlaying`: a remote id with `.paused`, `.stopped` and `.loading` gives nil every time. This is the no-idle-wakeups guarantee.
- `remoteClockAnchorAlignsToWholeSeconds`: elapsed 10.7 at time `t` gives an anchor of `t - 0.7 + clockLead`, and `elapsed(at: anchor)` is just past a whole second (fractional part equal to `clockLead`, within a small tolerance).
- `remoteClockTicksAdvanceOneSecondEach`: for n in 0..<5, `Int(elapsed(at: anchor + n))` goes up by exactly 1 each step. Use several starting elapsed values (0, 10.0, 10.999, 59.5) so the floor edge is covered.
- `remoteClockTicksClampAtDuration`: ticks past `duration` stay at `duration` and do not wrap. This documents that the clock may keep ticking until the remote reports `.stopped`.

No app-level unit test target exists, so `PlayerModel` and the SwiftUI wrapper are covered by the app build and the launch smoke in the VM. Keep the decision logic in `remoteClockAnchor` so that the views stay a thin mapping.

## Root cause

For any output other than This Mac, `PlayerModel.mainWindowStatus` and `positionFraction` read `nowPlaying.elapsed(at: Date())`. `Date()` is not observable, so the main-window time, the shade mini time, the playlist mini time and both position sliders re-rendered only when a new `NowPlaying` snapshot arrived.

## Fix

Per the plan:

- `NowPlaying.remoteClockAnchor(selected:)` and `NowPlaying.clockLead` (0.05 s) in MusicBackendKit. The anchor is nil on This Mac and unless `.playing`; otherwise it is `updatedAt - frac(elapsed) + clockLead`, so 1 s ticks land just past the remote's whole seconds.
- `PlayerModel`: `mainWindowStatus(at:)` and `positionFraction(at:)`, with the old properties kept as wrappers for `Date()`; `remoteClockAnchor` computed from the observed `nowPlaying` and `selectedOutput`.
- New `App/RemoteClock.swift`: a `TimelineView(.periodic(from: anchor, by: 1))` only while an anchor exists, else plain content. So This Mac, pause and idle add no wakeups.
- It wraps only the five readers: `MainWindowStatusLayer` and `positionSlider` in `MainWindowView`, `MiniTimeView` and `positionSlider` in `MainShadeView`, and `PlaylistMiniTimeView`'s body. Offsets stay where they were. I re-checked these against the code after #0064 and #0078–#0082; the plan still matched it.

Deviation: in `remoteClockAnchorAlignsToWholeSeconds`, the alignment check uses `elapsed(at: anchor + 1)` instead of `elapsed(at: anchor)`. The anchor is earlier than `updatedAt`, and `elapsed(at:)` does not extrapolate backwards, so at the anchor itself it returns the snapshot's raw `elapsed`. The first run failed on this. The first tick after the snapshot is the one that matters, and it lands exactly `clockLead` past a second. The tolerance is 1e-4 because of `Date` precision at 1.8e9 s.
