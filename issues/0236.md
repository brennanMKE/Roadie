## Description

The user: "The arrow keys should move between visualizations. Make sure to replicate the classic Winamp behavior beyond that." In MilkDrop, Space went to the next preset with a blend, H cut to it, Backspace went back, R switched random and sequential order, Scroll Lock locked the preset, Z X C V B drove Winamp, and presets changed on their own every 16 s or so with a 2.7 s blend. After #0235 the visualization window shows one preset and ignores the keyboard.

Design: [docs/design/visualization.md](../docs/design/visualization.md) §1.3, §1.4, §2.5, §2.6, §5.3.

## Plan

### Keys

- `VisualizationHostView` becomes first responder when the window is key (`acceptsFirstResponder` true, `window.makeFirstResponder` in `windowDidBecomeKey`) and overrides `keyDown(with:)`: map the `NSEvent` to #0234's `VisKey` (`specialKey` for arrows, delete (`.delete`/`.backspace`), F1–F5 (`.f1`…), Return, Escape; else `charactersIgnoringModifiers`; space as `.space`), call `VisKeyMap.command(…)` with the device-independent modifier flags and `isARepeat`; non-nil → `model.visualization.perform(_:)`, nil → `super.keyDown` (so ⌘ shortcuts reach the menu bar via `performKeyEquivalent`, which runs first anyway).
- `VisualizationModel.perform(_ command: VisCommand)`:
  - `nextPreset` → `navigator.next()`, load with `VisualizationSettings.keyBlend` (1.7 s); `previousPreset` → `previous()`, 1.7 s; `hardCut` → `next()`, transition 0.
  - `toggleOrder` → `navigator.order` flips, persisted (`visualization.order`); `toggleLock` → `isLocked` flips, persisted.
  - `transport(.previous/.play/.pause/.stop/.next)` → `PlayerModel.perform(WinampHotkey …)` (the same path `SkinWindow.onHotkey` uses); `.volumeUp/.volumeDown` → `WinampHotkey.volumeUp/.volumeDown`.
  - `presetList`, `showSongTitle`, `help`, `toggleReadout`: no-ops here (wired by #0239, #0240); `toggleFullScreen`, `escape`: no-ops (wired by #0237).
  - Every preset change (key, list, auto) increments the probe's `presetChanges` and records `lastTransition` (`"blend 1.7"`, `"blend 2.7"`, `"cut"`).
- A key change shows a toast with the preset name for 2 s (`vis.toast`, a small rounded label top-centre, fades; `.accessibilityLabel` the name). Automatic changes don't toast.

### Auto-advance

- `VisualizationModel` owns `clock: AutoAdvanceClock` (#0234) with `settings.autoAdvancePolicy`, seeded from `-RoadieVisSeed` in Debug. `restart(at:)` after every successful load. Each `tick(now:)`: `if clock.isDue(at: now) { if let p = navigator.advanceAutomatically() { load(p, transition: settings.blendSeconds) }; clock.restart(at: now) }`.
- Suspended (`suspend`/`resume`) while not rendering (#0235's `setVisible`), while the right-click menu is open (`menuWillOpen`/`menuDidClose` below); later issues add the list, help, notice and Reduce Motion.
- Debug hook `-RoadieVisAutoAdvance <seconds>` overrides the interval (and turns `varies` off) so a UI test sees a change quickly. Release ignores it.

### Right-click menu (design §2.6)

`VisualizationContextMenu.make(model:)` built from `VisKeyMap.rows`: Next Preset, Previous Preset, Next Preset Without Blending, separator, Random Order (✓ when random), Lock Preset (✓), Presets…, separator, Show Song Title, Song Title / Song Time / Preset Name / Frame Rate (✓ per readout), separator, Enter Full Screen / Exit Full Screen, Keyboard Shortcuts. Each item's title carries its key at the end after a tab-like spacing (`"Next Preset    Space"`) because a bare key can't be an `NSMenuItem` key equivalent without stealing it from the view; items whose command is a no-op until a later issue are present but disabled (and enabled by that issue). Popped in the host view by `rightMouseDown` / control-click (`NSMenu.popUpContextMenu(_:with:for: hostView)`), so it's under the window for XCUITest and VoiceOver. Its delegate suspends auto-advance while open.

## By hand

1. Open the visualization with music playing. → and ←: the preset changes with a short crossfade and its name shows briefly at the top; Space and Delete do the same. H changes instantly.
2. Hold →: one change, not a race. Hold ↑: volume climbs (watch the main window's slider).
3. R, then → a few times: random order (no immediate repeats). R again: in order.
4. Wait 16–26 s: the preset changes on its own with a slower blend. \` locks it: no more automatic changes; → still works.
5. Z X C V B control playback from the vis window; ⌃⌘← / ⌃⌘→ still seek.
6. Right-click the picture: every command is listed with its key; the open menu pauses automatic changes.

## Root cause

An addition, not a bug: after #0235 the window ignored the keyboard and had no auto-advance.

## Fix

As planned:
- **Model:** `VisualizationModel.perform(_:)` is the general dispatch. `.toggleFullScreen` and `.escape` are no-ops here, left for #0237. The list, song title, help and readouts are no-ops for #0239 and #0240.
- **Auto-advance:** the model owns an `AutoAdvanceClock`. It is suspended while the window isn't rendering or the right-click menu is open.
- **Probe:** gains `lastTransition`.
- **Debug hook:** `-RoadieVisAutoAdvance`.
- **Host view:** it becomes first responder and maps keys through `VisKeyMap`. It shows the `vis.toast` and supplies the menu through `menu(for:)`.
- **Menu:** `VisualizationContextMenu`.

Changes from the plan:
- **Menu keys:** each item shows its key as a bare key equivalent instead of in its title, so titles stay exact for XCUITest.
- **Disabled items:** the commands that later issues wire are listed but disabled.
- **Transport test:** `testTransportCommandsReachThePlayer` observes the commands through the `performHotkey` test seam. The real path to `PlayerModel.perform` is covered by `testVolumeKeysNudgeTheVolume`.
- **Failed preset:** following #0233's reviewer note, a key change selects the last usable preset when the current one failed.
