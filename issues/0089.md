# 0089 — Music Assistant tracks cannot play through this Mac over HTTP

| | |
|---|---|
| **Status** | open |
| **Module** | MusicAssistantKit / AudioCore / App |
| **Platform** | macOS |
| **First seen** | 2026-10-19 |

## Description

Browsing works and #0064 plays Music Assistant music on its speakers, but nothing plays it through the Mac, so the EQ, balance and visualizer never apply to it. #0066 plans that through Sendspin (no Swift SDK, technical preview, 16-bit). A smaller path may exist: fetch a track's audio from the Music Assistant server over HTTP and feed it to the existing progressive player (`ProgressiveByteSource` / `TrackResolver`, which streams Plex tracks today and which #0074 keeps generic).

This first needs a check that Music Assistant offers a per-track audio URL a client can fetch (its stream server listens on 8097; the web UI has a preview feature), what it requires (auth, player registration), and what format it returns. Read-only probes of the user's server are allowed with `scripts/record-ma-fixtures.py`-style tooling; never print the host, server id or token.

Expected: with This Mac selected and Music Assistant as the source, playing a library track plays it through the Mac's output path with the EQ and analyzer working, gapless where the format allows. If no such endpoint exists, record that in this issue and close the path in favour of #0066.

Unblocks #0074 (removing direct Plex support), which is on hold until Music Assistant can play through the Mac.

## Plan

### 0. What the recorded protocol and upstream source already say

The planner did not contact the server. Sources: `docs/ma-protocol/commands.json` (310 commands, server 2.10.6, schema 65), `docs/ma-protocol/openapi.json`, `docs/ma-protocol-notes.md`, the fixtures, and `music-assistant/server` on GitHub (`dev`, read 2026-10-19: `controllers/webserver/controller.py`, `controllers/streams/controller.py`, `controllers/music/media/tracks.py`).

- **The only per-track audio command is `music/tracks/preview`** (`provider_instance_id_or_domain`, `item_id` → `string`, scope `library.read`, so any signed-in user can call it). Upstream `get_preview_url` returns the provider's own preview URL when the track has `metadata.preview` (streaming providers), otherwise `mass.webserver.create_preview_url(...)`: a URL on the **API webserver (8095), path `/preview`**, not on the stream server.
- **`GET /preview` is a 30-second AAC sample, not the track.** `serve_preview_stream` sets `Content-Type: audio/aac` and streams `streams.get_preview_stream`, which runs ffmpeg with `-t 30` and `AudioFormat(content_type=AAC)` (raw ADTS, chunked, no `Content-Length`). On current `dev` the handler takes no Authorization header; the URL carries a `token` query parameter minted by the command, valid for `PREVIEW_TOKEN_TTL = 60` s and reusable inside that window (`_resolve_preview_token`). Older servers used `?provider=…&item_id=…` with no token; which form 2.10.6 uses is one thing the probe settles.
- **The stream server (8097) serves full tracks only to a registered player with a live queue session.** Its routes are `/flow/{session_id}/{queue_id}/{queue_item_id}/{player_id}.{fmt}`, `/single/…` (same shape), `/source/…`, `/command/…`, `/announcement/{player_id}.{fmt}` and `/info`. `serve_queue_item_stream` 404s unless the queue exists, `session_id` matches the queue's current session, the player is registered and the queue item exists, and it rechecks the session during the stream. The server is unauthenticated ("basic, unprotected HTTP-only") but unusable without being the player a queue is playing to. No HTTP route serves an arbitrary library track in full.
- **No client-registration command exists on 2.10.6.** `commands.json` has no `builtin_player/*` (the old web-UI "this device" player is gone) and nothing named `stream`/`get_stream_url`. The web UI's own playback is now `sendspin/pair_web_player` plus the authenticated `/sendspin` WebSocket proxy on 8095, which is #0066's path.
- **Hijacking a queue is out.** Calling `player_queues/play_media` on a real player and then fetching its `/single/…` URL would start that speaker, and the session check ties the URL to the player that is fetching. The recorder never sends a playing command.

**Verdict before the probe: high confidence (about 85%) that no full-track HTTP endpoint exists for a client that is not a player; very high confidence (about 95%) that `music/tracks/preview` returns a 30 s AAC sample only.** The likely outcome of this issue is "path closed in favour of #0066", and step 2 below is built only if the probe proves otherwise.

### 1. Step 1: read-only probe (the implementer runs it on the host)

**Where.** A new `--probe-audio` mode in `scripts/record-ma-fixtures.py`, reusing `read_env`, `Session`, `http_get`, the scrubber and `run()`'s error reduction. A separate script would duplicate the secret handling, which is the part that must not regress. Add `music/tracks/preview` to `ALLOWED` (it is a read: `library.read`) and keep the module docstring's promise ("nothing that plays…"). Update the docstring's `Run:` lines. Python 3.9 compatible, `/usr/bin/python3 -I`.

**Reachability.** The probe runs on the host (never in the guest, which has no secrets), and needs the `.env` server reachable from the host, on the API port (8095, from `MUSIC_ASSISTANT_URL`) and, for check 7, the stream port 8097 of the same host. If `GET /info` fails (`network error: <class>`), the implementer stops, writes `## Notes` saying the server was unreachable and when, leaves status `open`, and bails per `issues/Issues.md`. No guessing from the source alone.

**Never printed or written:** the host or any IP or `.local` name, `server_id`, the token, the preview token, the full preview URL, file paths from `provider_mappings[].item_id`, user names. Print only booleans, status codes, content types, counts, durations and parameter *names*. The token goes only into the `auth` frame and into an `Authorization` header (check 5b), never into a URL.

**Checks**, one `probe: <name> ok|FAIL|info <detail>` line each, plus a summary line:

1. `info`: `GET /info` → `server_version`, `schema_version` (safe to print; already in the notes).
2. `commands`: `GET /api-docs/commands.json` → presence of `music/tracks/preview`; names of any commands matching `stream|preview|builtin_player|web_player|register` (command names are not secrets). Confirms nothing new appeared since the recording.
3. `track`: `music/tracks/library_items` with `limit` 20, `summary: false`; pick the first track with `duration >= 90` (so a 30 s preview cannot be mistaken for the track). Print its duration and its mapping's `provider_domain` and `audio_format.content_type` only.
4. `preview-cmd`: `music/tracks/preview` twice: (a) `provider_instance_id_or_domain: "library"`, `item_id` = library id; (b) the mapping's `provider_instance` and `item_id`. For each: success or `error_code`; result is a string; scheme; whether the host equals the configured host (bool); whether the port is 8095, 8097 or other; the path (expected `/preview`); the sorted query parameter **names** (expect `token`, or `provider,item_id` on an older server).
5. `preview-get`: GET the returned path+query **with the host rewritten to the configured base** (as `MAImageProxy` does for artwork; the server's own base URL can be a LAN address the user did not type). (a) no `Authorization`; (b) with `Authorization: Bearer`. Read up to 16 MB with a 45 s timeout. Record status, `Content-Type`, whether `Content-Length` and `Accept-Ranges` are present, bytes, time to first byte, and, by parsing ADTS headers in Python (sync `0xFFF`, sampling-frequency index, frame length; 1024 samples per frame), frame count, sample rate, channel config and the decoded duration. Verdict `full` if the duration is within 2 s of the track's, `preview` if it is about 30 s.
6. `preview-ttl`: only when a `token` parameter was present: wait 65 s and GET the same URL again; expect 404 (confirms the 60 s TTL, which decides whether a resolver may cache the URL). `--no-wait` skips it.
7. `stream-server`: `GET http://<configured host>:8097/info` with no auth: status and key names only. Proves the stream port is reachable from a client and unauthenticated; no `/flow` or `/single` request is made (they need a live session and would only 404).

**Output.** With `--probe-audio --write`, a scrubbed `docs/ma-protocol/track-audio-probe.json` (the fields above, URL as `http://ma.example:8095/preview?<param names>`), never the audio bytes. Extend `gate()`/`--check` to scan that file too and confirm `--check` passes. Add section 13, "Per-track audio over HTTP", to `docs/ma-protocol-notes.md` with the verdict, and update `docs/music-assistant-integration.md`'s local-playback section with one paragraph pointing at it.

**Verification for step 1.** `/usr/bin/python3 -I scripts/record-ma-fixtures.py --probe-audio --write` and `--check` on the host (network only, no audio: the probe reads bytes and never decodes to a device; it must not shell out to `afplay` or `ffplay`). Then `scripts/run-tests-vm.sh` (fast tier) to show nothing else moved, as every phase does. Paste the `probe:` lines (already secret-free) into `## Verification`.

**Decision.**

- **`preview` (expected):** no Swift code. Code commit `#0089 Add a read-only per-track audio probe to the MA recorder` (script, probe JSON, the two docs). In the issue: `## Notes` with the verdict ("Music Assistant 2.10.6 offers no full-track HTTP endpoint to a non-player client; `/preview` is 30 s AAC; full audio needs a player: Sendspin, #0066"), status stays `open`, and the orchestrator asks the user to confirm `wontfix` for this path. Never set `wontfix` by inference. Also note in #0066's `## Notes` that `/sendspin` on 8095 is an authenticated proxy, so #0066 may not need port 8927 open.
- **`full` (unexpected: a newer server or a provider whose `metadata.preview` is a full-length URL):** continue with step 2 in the same issue, as a second code commit.

### 2. Step 2 (only if the probe returned `full`): `MusicAssistantTrackResolver`

AudioCore stays Music-Assistant-free. The progressive player path (`ResolvedAudio`, `ProgressiveByteSource`, `ProgressiveAudioReader`, `ProgressiveFeeder`, `Player+Progressive.swift`) is used as is.

1. **`Track.Source.musicAssistant(uri: String, serverID: String, size: Int64?)`** in `AudioCore/Track.swift` (an opaque key, like `.plex`); `FileTrackResolver` throws `unresolvableSource` for it. `QueueSnapshot` (#0071) gets a `kind` for it. On restore, an entry whose `serverID` is not the active server is dropped per item, like #0074's Plex rule.
2. **MusicAssistantKit:** `MARequest.trackAudioURL(provider:itemID:)` (whatever command the probe confirmed), a URL builder that rewrites the host to the configured base (share `MAImageProxy`'s helper), and an `MAHTTPTransport.download(_:headers:to:progress:)` that streams to a file (`URLSession.bytes`/download delegate), reporting bytes as they land and the `Content-Length` if any. Auth exactly as the probe found it: no header if the URL token suffices, never the long-lived token in a URL.
3. **New target `MusicAssistantPlayback`** (`MusicAssistantKit`, `AudioCore`, `LocalPlayback`), mirroring how `PlexBackendKit`/`TrackCache` join Plex to AudioCore. `MusicAssistantTrackResolver: TrackResolver` asks the backend for a fresh URL per resolve (tokens expire in 60 s; never cache the URL), starts the download into a temp file under `~/Library/Caches/<bundle id>/MusicAssistant/` and returns:
   - `.progressive(MAProgressiveDownload)` when the response has a `Content-Length` (`finalSize` is required by `ProgressiveByteSource`); `fetchRange` uses `Range` only if the probe saw `Accept-Ranges`, else throws `ProgressiveError.notStreamable` so a far seek falls back to the whole-file wait.
   - otherwise (chunked ffmpeg output) `.file(url)` once the download finishes, since the reader needs a known length. No LRU cache, no pinning: the temp file is deleted when the player is done with it.
   - `localURL(for:)` downloads fully. Cancellation follows the player's look-ahead cancel, as `PlexTrackResolver` does.
4. **One `Player`, one resolver:** a `CompositeTrackResolver` (in `LocalPlayback`) dispatches by `Track.Source`: `.file` → passthrough, `.plex` → `PlexTrackResolver` (until #0074), `.musicAssistant` → the new resolver. `PlexPlaybackStack` (or #0074's `LocalPlaybackStack`) takes it.
5. **Routing:** `MusicAssistantBackend.play(_:on:mode:)` keeps throwing for `thisMacID` today; it gains `.localOutput` in `capabilities`. For `thisMacID` it resolves the `MediaID`s (tracks, or an album's/playlist's tracks via the existing children calls) into `Track`s (`title`, `artist`, `album`, `duration`, `bitrate`/`sampleRate`/`channels` from `provider_mappings[].audio_format`) and hands them to `LocalPlayerOutput.play(_:mode:)`, the same output the folder backend uses. `PlaybackRouter` is unchanged (This Mac → local), but `PlayerModel.playFromLibrary` must send Music Assistant + This Mac to the MA backend's local path instead of the refusal; `LocalPlaybackGate.refusal(source:output:)` already allows it once the capability is there.
6. **EQ, balance, visualizer:** unchanged and automatic, because the audio goes through `Player`'s graph (EQ node, mixer, analyzer tap) like any local file.
7. **Gapless:** works for formats the progressive reader trims (MP3 with LAME/Xing info, M4A with `iTunSMPB`, FLAC, WAV). ADTS AAC from ffmpeg carries no priming/padding metadata, so AAC transitions have about 2112 samples of priming silence; acceptable, and noted in `## Gotchas`. The look-ahead resolve of the next track is the prefetch, so a 60 s token is minted in time.
8. **Tests (fakes, silent, in the guest):** an `MAHTTPTransport` fake that serves a bundled short generated file in chunks (with and without `Content-Length`, with a 404 for an expired token), and a fake `MusicAssistantClient` call returning the fixture URL. Cases: resolve with length → `.progressive` and the reader reads the whole file; without length → `.file` after completion; expired token → one retry with a fresh URL, then a `MusicBackendError`; cancel mid-download deletes the temp file; composite routing per source; `play` on `thisMacID` builds `Track`s from `tracks-page-full.json`; queue restore drops a foreign-server entry. Rendering is offline (manual mode), like `ProgressivePlaybackIntegrationTests`. Add `MusicAssistantPlaybackTests` to the scheme and `project.yml`. Verification: `scripts/run-tests-vm.sh --launch`, plus `--full` because `Player+Progressive` is guarded by real-time tests.

### 3. How this unblocks #0074

#0074 is on hold until Music Assistant can play through the Mac. If step 2 lands, Plex reached through Music Assistant plays on This Mac via `MusicAssistantTrackResolver`, so #0074 can proceed. Its plan then changes in two places: `CompositeTrackResolver` loses its `.plex` arm (not the whole resolver seam), and the AudioCore progressive path it already keeps gains a real user. If the probe returns `preview` (expected), #0074 stays on hold behind #0066 and its "On hold" line should say "(#0066; the HTTP path was ruled out in #0089)".

### 4. Rules

- No playing, pausing, queueing or volume command is ever sent. The probe is read-only and silent.
- Nothing secret appears in output, files, argv or the environment; `--check` must pass.
- Swift builds and tests run only in the VM; the probe runs only on the host.
