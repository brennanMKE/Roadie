## Description

The new rule (design §7, #0213) is that every bug fix adds a regression test that fails before the fix. Today the only way to show that is to read the test. `scripts/verify.sh` gets `--expect-fail NAMES`: the run passes (exit 0) only if each named test ran and **failed**, and everything else passed. The implementer writes the test first, asks for one `--expect-fail` run, then fixes the code and asks for the usual `--expect` run; both reports go in `## Verification`. One extra Haiku run per bug fix.

- Re-verify after the review fix (4724500) and the merge with main (4dc6fbc, `release-tools` now chains `test_release_tools.py`, `test_fetch_test_skins.py` and `test_verify_report.py`), `scripts/verify.sh --head`:
  `==> VERIFY  PASS (exit 0) 20261024-202507-14559: 12 steps passed, 1670 tests in 14 test runs`
  `==> TIER  fast: 100k scale and real-time audio tests skipped (scripts/run-tests-vm.sh --full runs them)`
  `==> AUDIO  silent: no host 'Starting IO' events during the run`

## Plan

### 1. `scripts/verify.sh`

- Parse `--expect-fail NAMES` (comma-separated, repeatable, `--expect-fail=…`) into `expect_fail`.
- After the run, for each name: it must appear as failed in a step log (`^✘ Test name(.*)` for swift-testing, or `Test Case '.*[ .]name]' failed` for XCTest). Compute `wrong=()`: names that passed or never ran.
- Exit code: the run's own exit is 1 because a test failed; with `--expect-fail`, if the only failing tests are exactly the expected ones (every `✘`/`failed` test name in the logs is in `expect_fail`, and `wrong` is empty), set `RC=0` and print `==> EXPECT-FAIL  all N expected test(s) failed as required`. Otherwise `RC=1` and `==> EXPECT-FAIL  M of N expected test(s) passed or never ran: …` and/or `==> EXPECT-FAIL  other tests failed too: …`.
- The pass report prints the `EXPECT-FAIL` line next to `EXPECT`. Build failures and INFRA are unchanged (a test that doesn't compile is not "failing").
- `--expect` and `--expect-fail` may be combined (a fix that also adds a passing test), but a name can't be in both (exit 2).
- `--report DIR` honours it, so the Python test below needs no VM.

### 2. `scripts/tests/test_verify_report.py`

If #0200 created it, extend; else create it. Cases with a fabricated results dir (`summary.txt` with `FAIL playerkit-tests`, a `playerkit-tests.log` with one `✘ Test rowIndexIsThePosition()` and otherwise `✔` lines): `test_expect_fail_passes_when_only_the_named_test_fails` (exit 0, the `EXPECT-FAIL` line), `test_expect_fail_fails_when_the_test_passed` (log shows `✔ Test rowIndexIsThePosition()`; exit 1), `test_expect_fail_fails_when_another_test_fails_too`, `test_name_in_both_lists_is_a_usage_error` (exit 2). Run `scripts/verify.sh --report <dir> --expect-fail rowIndexIsThePosition` with `subprocess`.

### 3. Docs

`scripts/verify.sh` header and `docs/testing-in-vm.md` "Quick start": the new option with the two-run recipe. `docs/verify-runner-plan.md`: one line. `issues/Issues.md` phase 2 step 4: the `VERIFY:` line may carry `--expect-fail` (one sentence; #0213 writes the rule).

## Resolution notes

> 🟢 Resolved 2026-10-24 — `scripts/verify.sh --expect-fail NAMES` passes only when each named test ran and failed and nothing else failed (no other test, step, crash, build, SKIP, INFRA or host audio), so a bug fix's regression test can be shown to fail before the fix.

## Fix

- `scripts/verify.sh`: `--expect-fail` as planned. A failed step with none of the expected failures in it, or a `BUILD`/`SKIP`/`INFRA`/audio line in the summary, also counts as "other tests failed too".
- Review (4724500): a crash in the same step as the expected failure (a `Fatal error`/`unexpected signal`/precondition/assertion line after the expected test had already failed) was a false pass; it now counts as `crash in step <name>`. Three more cases in `test_verify_report.py`: that crash, exact XCTest matching (`testBar` vs `testBarBaz`), and a build failure. Known limit: names are matched without the suite, so two suites with the same function name can't be told apart.
- Deviation: the `release-tools` step runs `test_verify_report.py` as a second `unittest discover` instead of widening its pattern to `test_*.py`, because `test_render_changelog.py` already has its own `changelog` step and would run twice.
