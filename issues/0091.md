# 0091 — Two menu commands claim Command-K

## Description

Found in the #0082 review: `App/SkinAmpApp.swift:28` gives a window scene `.keyboardShortcut("k")` and `App/SkinBrowser/SkinsCommands.swift:21` gives "Skin Library…" the same ⌘K. One of them never fires, or the menu shows the shortcut twice.

Expected: each shortcut is claimed once; the Skin Library and the Library window each have a distinct, documented shortcut that matches the options menu (#0078) labels.

## Plan

### What the two ⌘K claimants are

- **`App/SkinAmpApp.swift:28`.** `Window("Skins", id: "skins") { … }.keyboardShortcut("k")` is a **scene** modifier. SwiftUI adds the scene's own "open this window" item, titled "Skins", to the **Window** menu with ⌘K.
- **`App/SkinBrowser/SkinsCommands.swift:21`.** `Button("Skin Library…") { openWindow(id: "skins") }.keyboardShortcut("k")` is an ordinary command **Button** in the Skins `CommandMenu`.
- **How the clash resolves.** SwiftUI does not merge or warn. Both become `NSMenuItem`s with key equivalent ⌘K, so the menu bar shows ⌘K twice (Skins › Skin Library… and Window › Skins). AppKit's `NSMenu.performKeyEquivalent` walks the main menu in order and fires the first enabled match. The Skins menu comes before Window, so the Button wins and the scene's item never fires from the keyboard. Both open the same window (`id: "skins"`), so nothing visibly breaks. It is still a duplicate, and whichever item wins depends on menu order.
- **⌘L** is claimed once, by the `Window("Library", id: "library")` scene, so the Library window and the Skin Library already have different shortcuts. The fix is to remove the duplicate ⌘K, not to pick new letters.

### Decision

Keep ⌘K on **Skins › Skin Library…** (the Button) and **remove `.keyboardShortcut("k")` from the `Window("Skins")` scene**. Reasons:
- The Skins menu groups everything about skins (Skin Library… ⌘K, Next ⌘], Previous ⌘[, Random ⇧⌘R) and matches the options menu's **Skins ▸** submenu. #0080's plan and its host checklist already document ⌘K as "Skin Library".
- With the shortcut on the Button, the binding sits next to the other skin commands, and `SkinsCommands.swift` is the one place to read.
- Window › Skins stays, without a shortcut, and still opens or focuses the window. Do **not** rename the scene or its `id`: `AppDelegate.swift:39` matches window identifiers by the `"skins"` prefix.
- Leave ⌘L on the Library scene. It has one claimant, and nothing in the Library menu duplicates it.

Not chosen: keeping the scene's ⌘K and dropping the Button's. That leaves the Skins menu without a visible shortcut for its first item. No new letter is needed. ⌘K and ⌘L stay as they are, and every alternative letter would only add churn.

### Keep the options menu (#0078) in sync

The options menu has no Library or Skin Library entry, so ⌘K/⌘L need no label there. Do not add one; that would be a feature change, and `perform(_:)` has no `openWindow`. One sync gap does exist, and fixing it is in scope because the issue asks that the shortcuts match the options menu. #0078 left Playback's items "no shortcuts until #0080", and #0080 added the menu-bar chords but never updated the model. Repeat and Shuffle in **Options ▸** also lack their ⌃⌘R / ⌃⌘S. Add these display-only shortcuts to `MainMenu` (SkinKit):
- `playbackEntries`: Previous ⌃⌘Z, Play ⌃⌘X, Pause ⌃⌘C, Stop ⌃⌘V, Next ⌃⌘B, all as `MainMenuShortcut("z", [.command, .control])` and so on.
- `optionsEntries`: Repeat ⌃⌘R, Shuffle ⌃⌘S.

Seek and Volume are not in the options model, so leave them alone. `MainMenuBuilder` already turns `shortcut` into `keyEquivalent` plus a modifier mask. That is display only in a popped-up menu, so nothing double-fires.

Compare pairwise, or map each one to a `"\(key)|\(modifiers.rawValue)"` string and compare `Set` count to array count. Either way, do not change the public type just for the test.
- **`shortcutsMatchMenuBar`** (extend): add the ⌃⌘Z/X/C/V/B expectations for `.previous … .next`, ⌃⌘R for `.toggleRepeat`, ⌃⌘S for `.toggleShuffle`, and ⌘]/⌘[/⇧⌘R for skin navigation, which is not asserted today.

- The menu bar itself has no test bundle (the app target has none), so this mechanical check covers it. Phases 2 and 3 run it on the host and quote the output in `## Verification`. It prints nothing when every chord literal is claimed once:

### Host checklist (for the user; not automatable)

1. The Skins menu shows **Skin Library… ⌘K**. The Window menu shows **Skins** with **no** shortcut and **Library ⌘L**. ⌘K appears nowhere else in the menu bar.
2. ⌘K opens or focuses the Skin Library window, with the window closed and with it open behind other windows. ⌘L opens the Library window.
3. Window › Skins (clicked) still opens the Skin Library window.
4. Right-click the main window, or use its options button. **Playback ▸** shows ⌃⌘Z/X/C/V/B beside Previous/Play/Pause/Stop/Next, and **Options ▸** shows Repeat ⌃⌘R and Shuffle ⌃⌘S. Choosing them still works and fires once.
5. Spot-check that the other chords in the table still fire: ⌘1/2/3, ⌃⌘W/E/P, ⌘]/⌘[, ⇧⌘R, ⌘S, and the ⌃⌘ transport chords.
