## Resolution notes

> 🟢 Resolved 2026-10-21 — On a speaker or the Sendspin-fed Mac, the playlist editor now removes, crops, clears and drags (one row at a time) Music Assistant queue rows. Edits show at once, are sent in order, and roll back with a marquee notice when the server refuses.

Review (Opus, phase 3): read `git show 3535ff5 de9e27e` against design §1.3, §2.6, §3 and W10.
- **Removes:** `QueueEditPlan.removal` sorts the picked rows descending, and the backend sorts again by `index` before sending one `delete_item` per `queue_item_id`. Deleting by id makes the order a safety margin rather than a requirement.
- **Crop:** deletes the complement from `QueueRows.indicesToRemove(cropping:)`. Nothing selected does nothing.
- **Current row:** removes always leave it out. Remove says "Can't remove the playing track" (30 characters) when the current row was selected. Since de9e27e, crop keeps an unselected current row without the notice.
- **Moves:** a single-row drag is clamped to the queue and sends `move_item` with `pos_shift = to − from`. I checked this against `controllers/player_queues/controller.py` `move_item` on the server's `dev` branch, whose docstring says a positive value moves the item down and a negative one moves it up. `pos_shift` 0 means "move to next" there, and `edit` never sends 0. A drag of more than one row is refused with "Drag one track at a time".
- **Clear:** REM › Remove all and LIST › New send `player_queues/clear`.
- **Optimistic edits:** `sendRemote` applies `QueueEditPlan.apply` at once, so row ids, and with them the selection, follow the moved item. It chains each edit's Task after the previous one, so drag steps arrive at the server in order. On an error it restores the snapshot from before that edit, but only if the output hasn't changed, and the queue watcher's refetch reconciles afterwards.
- **Buffered refusals:** detecting them is still a guess, but a sound one. The server raises `IndexError(f"{item_index} is already played/buffered")`, and the check matches "indexerror" or "buffer" in the error details, so the "buffer" substring catches it even if the class name is left out. A buffered delete is a silent server no-op that the refetch restores, as §2.6 says.
- **Notices:** "Track already buffered" (22) and the fallback "Music Assistant refused" (23) fit the 31-character marquee. The shortening from the design's longer sentence is a recorded deviation.
- **Sort:** MISC › Sort opens with every entry disabled and posts the existing notice. Sort, reverse and randomize keep `refusesRemoteEdit()`.
- **Additive changes:** the `PlayerModel` change only adds the two hooks and `editRemoteQueue`. Every local branch in `PlaylistModel` is unchanged after the `if let remote` early returns. `map` now passes `QueueEditError` through.

Minor, not blocking:
- `editRemoteQueue` resolves `selectedOutput` when the edit is sent, not the snapshot's output. If the user switches outputs while edits are still queued, a late edit could go to the new output's queue, where the item id would not match and the server would refuse it.
- `apply(.clear)` keeps `total` at `total − items.count`, which isn't 0 when the queue was larger than the paging cap. This lasts only until the refetch.
- If one edit in a chain fails, the edits after it are still sent, against the server's real state.

## Root cause

The playlist editor showed a Music Assistant queue read-only (#0144). `QueueEdit` had only `.play`, so the remove, crop, clear, drag and Delete actions on a remote queue only showed the "Not for Music Assistant queues" notice.

## Fix

- **API:** `QueueEdit` gains `.remove(items:)`, `.move(itemID:shift:)` and `.clear`. A new `QueueEditError.buffered` error has the marquee text "Track already buffered".
- **Music Assistant:**
  - Remove sends one `player_queues/delete_item` per item, by `queue_item_id`, highest index first.
  - Move sends `player_queues/move_item` with `pos_shift`. Clear sends `player_queues/clear`.
  - A server error whose details name `IndexError` or buffering becomes `.buffered`, and `map` passes that error through.
- **Plan:** `QueueEditPlan` in `LibraryBrowser/QueueRows.swift` turns a selection into edits:
  - Remove and crop list the rows to delete, highest index first, and never include the current row. Remove reports when it left the playing row out.
  - A drag of more than one row is refused. A single-row drag is clamped to the ends of the queue.
  - `apply` builds the optimistic snapshot.
- **App:**
  - `PlaylistModel` routes REM (remove selected, crop, remove all), LIST › New, the Delete key and single-row drags to the remote queue.
  - It shows each edit at once and sends edits one after another. If the server refuses an edit, the rows go back to how they were and the marquee shows the error.
  - The marquee also says "Can't remove the playing track" and "Drag one track at a time".
  - The MISC Sort menu entries are disabled on a remote queue, with the existing notice.
  - `PlayerModel` wires `onEditRemote` and `onRemoteNotice` (additive).

Deviations from the plan:
- The request builders live in `MusicAssistantBackend+Queue.swift`, not `MARequest.swift`, to keep clear of parallel edits.
- `StubMusicBackend` and `PlaylistWindowView` are unchanged: the protocol default covers the stub, and `run` already goes through `PlaylistModel`.
- The buffered refusal text is shortened to fit the marquee's 31-character limit.
