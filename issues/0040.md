# 0040 — Removing the current track while paused starts playback

## Description

`Player.removeTrack(at:)` on the current track while the player is `.paused` starts the next track playing, because `startCurrentTrack()` always plays. Found in the #0002 review.

## Steps to reproduce

1. Queue two or more tracks and play the first.
2. Pause.
3. Remove the current track (`removeTrack(at:)` with the current index).

## Expected behavior

The next track becomes current and the player stays `.paused` at its start (or `.stopped` if the queue is now empty).

## Actual behavior

The next track starts playing.

## Plan

Written while #0003 (gapless scheduling) is landing in `Player.swift`, so this describes intent and the state machine, not line numbers. #0003 keeps the same transport shape (`removeTrack(at:)` → `startCurrentTrack()` → async resolve → `begin(file)`), so the change below applies on top of it.

### Change (`Packages/PlayerKit/Sources/AudioCore/Player.swift`)

1. Give the start path an intent. `startCurrentTrack()` becomes `startCurrentTrack(autoplay: Bool = true)` and remembers the intent in an `@ObservationIgnored private var autoplayAfterLoad = true` (#0041 reuses this flag as the pending intent of its `.loading` state). The load task is unchanged: cancel the previous load, invalidate the schedule, stop the node, resolve, open the file.
2. `begin(file)` honours the intent. After `connect` / `start` / `schedule(file, from: 0)` / `currentTime = 0`:
   - `autoplayAfterLoad == true` → `playerNode.play()`, `state = .playing`, start the time loop, pre-schedule the next track (#0003) as today.
   - `autoplayAfterLoad == false` → do **not** call `playerNode.play()`; set `state = .paused`, leave the time loop stopped. The segment stays scheduled on the stopped node, so the existing `play()` `.paused` branch (`playerNode.play()`) resumes it from frame 0 with nothing else to do. #0003's `scheduleNextIfNeeded()` may still run here (it is keyed on `state != .stopped`), which is fine.
3. `removeTrack(at:)` decides by state when the removed index was current (`PlayQueue.remove(at:)` has already moved `currentIndex` to the following track, or to `nil` when the queue emptied):
   - `.stopped` → nothing; the queue repositions and the engine is untouched (current behaviour; #0003's `reconcileSchedule()` still runs for the non-current case).
   - `.playing` → `queue.current == nil ? stop() : startCurrentTrack(autoplay: true)` (current behaviour).
   - `.paused` → `queue.current == nil ? stop() : startCurrentTrack(autoplay: false)`, so the new current track is loaded and parked at 0:00 in `.paused`.
   - (`.loading`, once #0041 lands → reload with the intent already stored in `autoplayAfterLoad`.)
   Removing a non-current track never changes `state` or `currentTime` in any state.
4. `pause()` keeps its `guard state == .playing`; `togglePause()` is unchanged. No `didSet` on anything (see #0002 Gotchas: `@Observable` + self-assigning `didSet` recurses).

## Resolution notes

> 🟢 Resolved 2026-10-12 — removing the current track while paused now parks the new current track paused at 0:00 (or stops on an empty queue), playing keeps playing, stopped is untouched (code commit 9b14cc6).

Diff checked: `begin` parks without `playerNode.play()` and skips a duplicate `.stateChanged(.paused)`; `removeTrack` resets `currentTime` before the queue change, so the Now Playing bridge publishes the new track paused at elapsed 0; the parked track's successor is still pre-scheduled (`scheduleNextIfNeeded` runs while `.paused`), so resume is gapless; superseding selections cancel the load task and reset `autoplayAfterLoad`; `stop()`/`fail` clear `loadPending`.

Left for #0041 (which replaces `loadPending` with `.loading`; no conflict, it folds in cleanly):
- While a parked load is pending, `play()` flips the intent to play but `pause()`/`togglePause()` cannot flip it back (state is already `.paused`, so `pause()` is a no-op and `togglePause()` calls `play()` again). #0041's `.loading` row for `pause()`/`togglePause()` fixes this.
- `startCurrentTrack` does not clear `file`, so `seek(to:)` / `reconcileSchedule` / `handleConfigurationChange` during any pending load act on the previous track's file until `begin` overwrites it (pre-existing for the playing path, harmless while parked because nothing plays). #0041's step 1 sets `file = nil`.
- `removeTrack` passes `autoplay: state == .playing`; once `.loading` exists it must pass `autoplayAfterLoad` for that state (#0041 step 5), and the `play()` `.paused` + `loadPending` branch and the `loadPending` resets in `stop()`/`begin` should be removed.
- The load task's `queue.current?.id == track.id` early return leaves `loadPending` set; unreachable today (every path that changes the current track restarts or stops the load), and #0041's generation check replaces it.

## Root cause

`removeTrack(at:)` handled a removed current track in any non-stopped state by calling `startCurrentTrack()`, and `begin(file)` always ended with `playerNode.play()` / `state = .playing`. The transport state (paused) was never carried into the reload.

## Fix

Followed the plan, adapted to the post-#0007/#0046 code (`Packages/PlayerKit/Sources/AudioCore/Player.swift`):

- `startCurrentTrack(autoplay: Bool = true)` stores the intent in `@ObservationIgnored autoplayAfterLoad` (reusable as #0041's pending intent).
- `begin(file)` plays only when `autoplayAfterLoad`; otherwise it leaves the segment scheduled on the stopped node, keeps the time loop stopped and sets `.paused` (only if not already `.paused`, so observers get no duplicate `.stateChanged(.paused)`). The existing `play()` `.paused` branch resumes it from frame 0.
- `removeTrack(at:)`: `startCurrentTrack(autoplay: state == .playing)`; empty queue still `stop()`s; `.stopped` untouched. The existing `currentTime = 0` before the queue change is kept, so observers see the new track at 0:00 while `state` stays `.paused`.

Deviations from the plan:
- Added `loadPending` (set in `startCurrentTrack`, cleared in `begin` and `stop`, which `fail` calls). Without it, `play()` pressed while the parked load is still in flight would run `playerNode.play()` on an empty node, set `.playing`, and then `begin` would flip back to `.paused`. With it, `play()` in that window sets `autoplayAfterLoad = true` and returns; the load then plays. #0041's `.loading` state should replace this flag.
- Tests use `renderSilently(player)` and `GaplessRenderTests.writeSine` instead of the plan's manual engine setup and new helper; they poll with the existing `waitUntil`.
