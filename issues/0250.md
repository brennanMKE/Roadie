# 0250 — The first drag on the equalizer after its PRESETS menu closes may be lost

| | |
|---|---|
| **Status** | open |
| **Module** | App |
| **Platform** | macOS |
| **First seen** | 2026-10-29 |

## Description

Found by #0207's UI tests (run 20261029-203010-55326, `testPresetsMenu`). After choosing PRESETS › Load › Rock, the next pointer drag on the equalizer's preamp had no effect: it was pressed at (56, 144) and dragged to (56, 163.5) in window points, the same geometry that lands in the other EQ tests, and the probe still read `"preamp":0` afterwards. Every other drag in that run, including the band and preamp drags in `testBandsAndToggles`, `testGraphValue` and `testEqPersistsAcrossRelaunch`, landed. XCUITest's "Found 1 interrupting element" line (the docked playlist window at {{0,494},{550,406}}) appears on all ten drags, so it doesn't explain the lost one.

So the first mouse-down after the skinned pop-up menu closes may be swallowed, or the equalizer may not be key yet. If that happens to a user, a preset followed by an immediate slider drag silently does nothing. Unconfirmed: it hasn't been reproduced by hand.

#0207 works around it (a title-strip click, then one retry of the drag), so its test doesn't catch this.

## Check by hand

Choose a preset from PRESETS › Load with the mouse, then at once drag a band or the preamp. Does that first drag move the slider?

## Plan

To be planned once confirmed. Start from how the skinned pop-up is shown (`popUp(positioning:at:in:)`) and how the EQ window's slider view handles the first mouse-down after it closes (`acceptsFirstMouse`, key-window state). A fix lands with a UI test that drags right after the menu closes, without #0207's workaround, proven to fail first.
