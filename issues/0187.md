## Description

Double-clicking a track in the skinned playlist editor restarts the first song on the list. Choosing a track in Jump to File (⌘J) and pressing Return or double-clicking does the same. The user's report is in [#0186](0186.md).

Both go through one function, `PlaylistModel.playRow(_:)`:

- the editor's double-click (`PlaylistListInputView.mouseDown`, `clickCount >= 2`, `App/Playlist/PlaylistWindowOverlays.swift:106`);
- Return (`playFirstSelected`);
- the row menu's Play;
- Jump to File's Play (`JumpToFilePanel.playSelected`, `App/JumpToFile/JumpToFilePanel.swift:265–275`).

When the editor shows a Music Assistant queue (a speaker, or This Mac fed by Music Assistant), every row's queue index is 0, so every play request asks the server for item 0.

## Steps to reproduce

1. Connect to a Music Assistant server. In the Library (⌘L), play an album on This Mac or on a speaker. The playlist editor now shows that Music Assistant queue.
2. Double-click the third row of the playlist editor.
3. Or press ⌘J, type part of the third track's title, and press Return.

## Expected behavior

The double-clicked (or chosen) track plays.

## Actual behavior

The first track in the queue starts again.

## Root cause

`App/Playlist/PlaylistModel.swift:233–241`:

```swift
func playRow(_ index: Int) {
    if let remote {
        if remote.items.indices.contains(index) { onPlayRemote(remote.items[index].index) }
        return
    }
    ...
```

The `.index` it sends comes from `MAQueueWatch.item` (`Packages/PlayerKit/Sources/MusicAssistantKit/MAQueueWatch.swift:166–176`):

```swift
id: item.queueItemID, index: item.index ?? fallbackIndex,
```

Music Assistant's `QueueItem` schema gives `index` a **default of 0** (`docs/ma-protocol/openapi.json`, `components.schemas.QueueItem.properties.index`: `{"type": "integer", "default": 0}`). The server serialises dataclass defaults, so a queue whose items don't have `index` filled in sends `"index": 0` on every item of `player_queues/items`. `MAQueueItem.index` (`Models/MAPlayers.swift:144`) then decodes to `0`, not `nil`, and the positional `fallbackIndex` is never used. Every `RemoteQueueItem.index` is 0, so:

- `PlayerModel.playRemoteQueueRow` sends `QueueEdit.play(index: 0)`;
- `MusicAssistantBackend.edit` sends `player_queues/play_index` with `index: 0` (`MusicAssistantBackend+Queue.swift:33`);
- the server plays the first item.

Why the tests missed it: `BackendQueueTests.itemJSON` (`Packages/PlayerKit/Tests/MusicAssistantKitTests/BackendQueueTests.swift:25–31`) is synthetic and sets `"index": n`. Its doc comment says the recorded `player-queue-items.json` was empty, so the real shape was never seen.

The positional index is always right. `MAQueueWatch.refetch` pages `player_queues/items` by `offset` in queue order, so item `k` of the page at offset `o` is at queue position `o + k`. That is exactly the `fallbackIndex` it already computes. `QueueEditPlan.apply` already renumbers by position after an optimistic edit (`QueueRows.swift:109`).

The same wrong index also reaches `MusicAssistantBackend.edit`'s `.remove` ordering (`items.sorted(by: { $0.index > $1.index })`, line 35). With every index at 0 the deletes go out in arbitrary order. That's harmless today because they're keyed by item id, but it's wrong.

**The local queue.** No defect was found by reading the code. `onPlayLocal` (`App/PlayerModel.swift:423–426`) switches the feed and calls `stopOthers(startingOn: thisMac)`. `PlaybackOwnership.stops` (`Packages/PlayerKit/Sources/LibraryBrowser/PlaybackOwnership.swift:35–52`) never stops This Mac's local player when the target is This Mac. Then `Player.play(at:)` (`Packages/PlayerKit/Sources/AudioCore/Player.swift:308–313`) calls `queue.select(index)` and `startCurrentTrack()`. `PlayQueue.select` (`PlayQueue.swift:226–239`) sets `currentIndex = index`, and nothing after it selects row 0 again. `PlayerTests` covers `play(at: 1)` and `play(at: 2)`. The first click of the double-click only selects the row (`click`), and nothing else in the playlist window handles clicks on rows. Since the user also plays from Music Assistant, the remote cause above is the likely one. The logging in step 3 is there in case a local repro turns up.

## Plan

### 1. Use the position, not the server's `index` (`MAQueueWatch.swift`)

- In `MAQueueWatch.item(_:fallbackIndex:)`, set `index: fallbackIndex` and ignore `item.index`. Rename the parameter to `position:` and update the two call sites (`refetch` and the test).
- Update its doc comment: "`index` is the item's position in the queue (paging offset + place in the page). Music Assistant's own `QueueItem.index` defaults to 0 and isn't reliable."
- Keep `MAQueueItem.index` in the model (decoding stays lenient), and add a doc comment saying it's not used for positions.

### 2. Play by row position (`PlaylistModel.playRow`)

Keep `QueueEdit.play(index:)`, and pass it the row:

```swift
if let remote {
    if remote.items.indices.contains(index) { onPlayRemote(index) }
    return
}
```

After step 1, `remote.items[index].index == index` anyway, but this removes the dependency. `remote.items` is the full fetched list from position 0 (the cap only cuts the tail, #0132), so the row is the queue position.

- **Not doing:** sending the `queue_item_id` string to `play_index`. It's accepted (`docs/ma-protocol/commands.json`: `index` is `integer | string`), and it would survive the queue changing between fetch and click. But older servers may only take integers, and the bug is fixed without it. Note it in `## Gotchas` as a possible follow-up.

### 3. Logging (permanent, `.debug`, no PII)

Add `private static let log = Logger(subsystem: "co.sstools.roadie", category: "PlaylistPlay")` to `PlaylistModel`, and log at each hop:

- `PlaylistModel.playRow`: `"play row \(index) remote=\(remote != nil) count=\(count)"`.
- `PlayerModel.playRemoteQueueRow`: `"play_index \(index) on remote queue"`, using the existing `Self.log`.
- After `player.play(at: index)` in the local branch: `"local current=\(player.queue.currentIndex ?? -1)"`.

No titles or paths in the log, only numbers. If the user still sees row 1 play on the local queue, `log stream --level debug --predicate 'subsystem == "co.sstools.roadie" AND category == "PlaylistPlay"'` shows which hop picked it. Don't add logging to `AudioCore` (that would need the full tier).

## Resolution notes

> 🟢 Resolved 2026-10-24 — Music Assistant queue rows take their paging position as their index, and playing a row sends the row number, so double-click, Return, the row menu and Jump to File play the chosen track instead of item 0.

## Fix

Followed the plan with no changes. `MAQueueWatch.item(_:position:)` sets each row's `index` to its position (paging offset plus its place in the page) and ignores the server's `index`. `PlaylistModel.playRow` sends the row number to `onPlayRemote`. Debug logging under the `PlaylistPlay` category (numbers only) covers `playRow` and the local play, and `PlayerModel.playRemoteQueueRow` logs the `play_index` it sends. `MAQueueItem.index` is still decoded; its doc comment says it isn't used for positions. The root cause above was confirmed: a read-only probe of the user's live Music Assistant server (2026-10-24) showed every `player_queues/items` row with `"index": 0`, including a 14-item queue whose `current_index` was 2.
