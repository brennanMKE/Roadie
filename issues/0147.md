## Resolution notes

> 🟢 Resolved 2026-10-21 — Music Assistant radio stations now appear in a Radio section of the Library and in Favorites. "Add Radio URL…" (or PL ADD › URL with Music Assistant) adds an http or https stream as a station.

Review (Opus, phase 3): I read `git show 11e5247 f855601` against design §1.3, §2.1 and W12.
- **Lenient decoding:** `MARadio` requires only `item_id` (a string or an int), `name` and `uri`. `provider`, `metadata` and `favorite` use `try?`. `lenientList` decodes each row separately and drops the ones that fail, so one bad row doesn't fail the page. The fixtures are synthetic and say so (no capture until #0133). The tests are offline: they use the scripted control transport and the stub backend.
- **`builtin/add_radio`:** the request sends `url` and `name`. That matches the server's `dev` branch: `music_assistant/providers/builtin/__init__.py` has `BuiltinProvider.add_radio(self, url: str, name: str, image_url: str | None = None) -> Radio`, registered in `loaded_in_mass` with `Scope.LIBRARY_WRITE`. It also matches `docs/ma-protocol/commands.json`, where `image_url` is optional and omitted here. The server checks the URL scheme itself (`_ensure_stream_url`: http, https, rtsp, rtmp).
- **URL validation:** `RadioURLInput.parse` trims the text and accepts only `http` or `https` (case-insensitive) with a non-empty host. `file:`, `ftp:` and text with no scheme are rejected, both in the sheet's Add button and again in `LibraryBrowserModel.addRadio`. The name defaults to the host.
- **Capability gating:** `.radio` is `1 << 8`. Only `MusicAssistantBackend` declares it. `sections` adds `.radio` only with the capability, and `addRadio` refuses without it. The default `MusicBackend` methods throw `.unsupported`.
- **PL ADD › URL:** it acts only when `model.library.sections.contains(.radio)`, which means the source is Music Assistant. It then selects the Radio section, raises the sheet and opens the Library window. Other sources still do nothing.
- **Favorites:** `FavoriteKind.radios` maps to and from `.radio`. Counts, lists, cancel and reset cover it. A favorite toggle patches the Library and Favorites radio lists.

Minor, not blocking:
- The Radio section shows with the capability even when there are no stations, where the design's sidebar sketch says "count > 0". This is reasonable, since that's where Add lives.
- The "Add Radio URL…" toolbar button shows in every section, not only Radio.
- If `add_radio` answers with something that isn't a `Radio`, the returned `LibraryRadio` uses the stream URL as its id. The caller discards it and refetches the list, so nothing visible changes.

## Root cause

Radio stations never reached the Library. The backend had no radio listing or add command, the Library had no Radio section, and Favorites left radio out.

## Fix

- The backend reports a radio capability. Music Assistant lists stations (`music/radios/library_items` with its count), lists favorite stations, and adds a stream URL as a station (`builtin/add_radio`). Station decoding is lenient: a row without an id, name or URI is skipped instead of failing the page.
- The Library has a Radio section, shown only when the backend has radio. Double-click plays a station; the context menu has Play and the favorite toggle. An "Add Radio URL…" button in the toolbar opens a sheet that accepts an http or https URL; the name defaults to the host.
- Favorites lists radio stations as a fifth kind.
- PL ADD › URL: with Music Assistant, it opens the Library on the Radio section with the add sheet showing. Other sources still do nothing.
