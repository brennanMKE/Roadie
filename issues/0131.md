## Description

Requested by the user: "Add the option to delete a skin. This could be done with a context menu from the library view." The Library tab of the Skins window (⌘K) lists every indexed skin, and with the Museum (#0126) it's now easy to collect skins you don't want, but the only way to remove one is to find the file in Finder and wait for the next index pass.

## Plan

- `SkinIndexStore.removeFile(atPath:)`: delete that one `files` row; when it was the skin's last file, delete the skin (FTS trigger follows) and return its hash. Exposed through `SkinIndexReading`.
- `SkinThumbnailCache.remove(hash:)` (memory + disk PNG/marker); `SkinThumbnailProviding.remove(hash:)` (default no-op) wired through `SkinThumbnailAdapter`.
- `SkinBrowserModel.moveToTrash(path:name:)` with an injected `FileRemover` (default `FileManager.trashItem`): refuse paths outside the folder, treat "no such file" as already gone, otherwise show `trashError`; then drop the row/thumbnail, refresh the listing (no rescan) and call `onTrashed` so the Museum re-badges. Applied skin is left alone.
- Museum `badge()` clears `downloaded` for shown skins the index no longer has.
- UI: "Move to Trash" in the Library cell context menu and the Museum cell context menu (downloaded only); one alert for errors in the Skins window. The Library grid has no selection, so no Delete-key binding.
- Tests: store removal (linked duplicate vs last file), cache removal, model trash paths via a stub remover, Museum badge clearing.

## Expected behavior

- Right-click a skin in the Library tab › **Move to Trash**. Also on the Delete key / ⌘⌫ for the selected skin(s) and from the Museum grid's context menu for a downloaded skin. Multiple selection works if the grid supports it.
- The file goes to the Trash (recoverable; `FileManager.trashItem`), not a permanent delete, so no extra confirmation is needed. If two index rows point at the same file content (linked duplicates), only the chosen file is trashed.
- The skin's row and its thumbnail are removed from the index right away (no full rescan); the grid updates; a Museum skin loses its "Downloaded" badge.
- If the trashed skin is the one currently applied, it stays applied for this session (it's already loaded), and the next launch falls back the way a missing skin does today.
- Errors (file locked, outside the skins folder, already gone) show a short message; an already-missing file is just removed from the index.
- Tests: index removal by id (row + thumbnail), trashing through an injectable file-remover so no test touches the real Trash, the Museum badge clearing.

## Root cause

There was no way to remove a skin from inside the app: the index only dropped a file on the next folder pass, and neither the Library nor the Museum cell offered a delete action.

## Fix

- `SkinIndexStore.removeFile(atPath:)` drops one `files` row; when that was the skin's last file it also drops the skin row (the FTS trigger follows) and returns the hash. It is exposed on `SkinIndexReading`.
- `SkinThumbnailCache.remove(hash:)` clears memory and the disk PNG/marker; it is reached through `SkinThumbnailProviding.remove(hash:)` (default no-op) and `SkinThumbnailAdapter`.
- `SkinBrowserModel.moveToTrash(path:name:)` uses an injected `FileRemover` (default `FileManager.trashItem`). It refuses paths outside the skins folder, treats "no such file" as already gone, and shows other failures in `trashError`. After that it drops the row and thumbnail, refreshes the listing and counts without a rescan, and fires `onTrashed`. The applied skin is not touched.
- The Museum's `badge()` now clears `downloaded` for shown skins the index no longer has; `PlayerModel` re-badges the Museum on `onTrashed`.
- UI: "Move to Trash" in the Library cell's context menu and in the Museum cell's context menu for downloaded skins (`PlayerModel.trashDownloadedMuseumSkin(at:)`). The Skins window has one error alert. The Library grid has no selection, so there is no Delete-key binding.
