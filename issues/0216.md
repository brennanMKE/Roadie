## Description

In #0212's run `20261029-191545-21712`, `SkinsSettingsView` is at 97.9 % and `LibrarySettingsView` at 82.8 % (251 of 303 lines). These remain:

- `MusicAssistantSettingsView` (622 lines, the largest gap in the app) is at 0.3 %: the identity line (`identityText`), the token prompt, the status line and its server-mismatch Replace, and `ServerRow`'s status dot for each status and ranking outcome.
- `MusicAssistantDiscoveryViews` is at 30.4 % (56 of 184): `DiscoveredServersSection` and `DiscoveredServerRow` never show, and the Library banner's searching, found and nothing-found states only partly run.
- `WelcomeView` (222 lines) is at 0 % and `WelcomeWindowController` at 10.5 % (4 of 38): the first-launch window is never shown in a test.
- `LibrarySettingsView`'s folder choice: `chooseMusicFolder(startingAt:)` (shared with the Welcome window) and `chooseFolder()` never run.
- `UpdatesSettingsView` (100 lines) is at 0 %.
- The system network wrappers are at 0 %: `SystemServiceBrowser` (131 lines; Bonjour), `SystemWiFiNetwork` (48; the Location-gated SSID) and `SystemNetworkEvents` (30; the `NWPathMonitor` change stream).

[#0209](0209.md) (in flight) adds `FirstLaunchUITests` and `SettingsUITests` over the Settings tabs, the Welcome window and the Debug update UI, so the view numbers above will move once it merges. Recheck them against that run before starting, and drop what it covered. This issue tests the logic those UI tests can't reach.

## Plan

1. `MusicAssistantSettingsView`: move `identityText`, `tokenPrompt`, `failed`/the status line's mismatch rule and `ServerRow.statusDot`'s choice into `static` functions (or an enum the view switches on) with no behaviour change, and test them for every `MusicAssistantSettingsModel.Status` and `MusicAssistantServerRanking.Outcome`. The add, remove and validate rules are `MusicAssistantSettingsModel`'s and already tested in `MusicAssistantKitTests/SettingsModelTests`. Test file: `Tests/RoadieTests/MusicAssistantSettingsLogicTests.swift`.
2. `MusicAssistantDiscoveryViews`: the banner's state (not started, searching, offers, nothing found) and which offers `DiscoveredServersSection` lists (configured ones hidden) as `static` functions over `MusicAssistantDiscoveryModel`, fed by a fake `MusicAssistantServiceBrowser`.
3. `SystemServiceBrowser.host(of:type:)`: make it `internal static` and test it with `NWEndpoint.hostPort` values (IPv4, a name, IPv6 skipped) and `.service`/`nil` for both service types. No browsing; the guest has no Bonjour peers.
4. `SystemNetworkEvents`: move the "skip the first path" rule out of `MonitorBox` into a value the test can feed path updates to, and check that the first update yields nothing and each later one yields once. `SystemWiFiNetwork`: map `CLAuthorizationStatus` to `WiFiAuthorization` in a `static` function and test every case; check that two `requestAuthorization()` calls share one pending request by injecting the request call. No real Location prompt.
5. The folder picker: inject `chooseMusicFolder` (a `(URL?) -> URL?` seam on the model, defaulting to the panel) and check that the chosen URL reaches the folder backend from Settings › Library and from `WelcomeView.chooseMusic`, and that the folder becomes the selected source when no server is verified.
6. `WelcomeWindowController`: `show(openMuseum:)` twice builds one window (the second reuses it), `close()` calls `onDismiss` once, and `openMuseum` sets `pendingSkinsSource` to `.museum`. Headless, with an off-screen window.
7. `UpdatesSettingsView`: whatever logic remains after #0209's run, which should be little. Note the rest under `## Notes` as #0209's.
