# 0128 — Museum screenshot downloads keep running after their cells scroll away

| | |
|---|---|
| **Status** | open |
| **Module** | SkinMuseum / SkinBrowser |
| **Platform** | macOS |
| **First seen** | 2026-10-20 |

## Description

Found in the #0126 review. `MuseumScreenshotCache` runs each fetch in an unstructured `Task`, and its waiter queue can't be cancelled, so a fast scroll through the Museum grid still downloads every screenshot it passed (at most 4 at a time). The plan's etiquette section asked for fetches to be cancelled when a cell leaves the screen, to keep load on the Museum's CDN down.

Smaller items from the same review, worth folding in:
- The 16 MB download cap is checked only after the whole body is in memory; stream and stop at the cap instead.
- Redirects are followed without checking they stay on https.
- While a stale cached page is refreshing, scrolling can start the next page, so two queries briefly overlap.
- A full index pass started during `indexer.add` fails with `passAlreadyRunning` instead of being queued.

## Expected behavior

- A screenshot fetch whose cell scrolls away before it finishes is cancelled, unless another cell still waits for the same md5.
- Downloads stop at 16 MB without buffering more, and a redirect to a non-https URL fails.
- At most one Museum query in flight; a pass requested during `add` runs after it.
