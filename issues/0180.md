## Description

Phase B of M15. Winamp's Jump to File (with the bundled JTFE plugin) had a **Queue** button: it adds the selected entry to the play-next queue without interrupting the current song. In Roadie the panel (#0176) has the button hidden, and ⇧Return does nothing.

With the play-next list (#0177) and the playlist editor's `toggleQueue` (#0179) in place, this issue:

- Shows the Queue button and wires it and ⇧Return.
- Shows `[n]` on queued results.

On a Music Assistant queue, Queue reaches `toggleQueue`'s remote branch, which #0182 fills in. Until then the button is disabled there.

Default until #0174 row 8: Queue leaves the panel open, and it toggles like `Q`. Several selected results queue in result order.

## Resolution notes

> 🟢 Resolved 2026-10-23 — Jump to File's Queue button and ⇧Return toggle the selected results (or the first) in the play-next list without closing the panel, and queued results show [n].

Review (Opus, medium): b895408 matches the plan. `queueSelected()` maps the selected table rows through `results` to full-queue indices (the same indices `playSelected` passes to `playRow`) and calls `PlaylistModel.toggleQueue`, the same path as the playlist's Q. There's no parallel path, and `toggleQueue` re-checks the remote/local guard itself. The panel stays open, and focus goes back to the search field only if the click moved it. Plain Return still calls `playSelected()`, and only shift-Return queues. The button is enabled only when there are results, `remote == nil` and `queueRowsSource == .local`, so it's off for Music Assistant queues and for `.none`. Its title is "Dequeue" only when every selected result is queued (the `selectionIsQueued` rule). Enabling and title are re-checked after each `apply`, on selection change, after Queue, and on up-next changes. The `[n]` column reads `PlaylistText.queueMarker(upNextPosition(of:))` and is blank on a remote queue.

`observeUpNext` re-arms in its handler and checks `isObserving` and `observationID`, so after a close or a re-show, a stale registration fires once and does nothing. Updates hop to the main actor with `Task { @MainActor }`. This is AppKit, so no SwiftUI state is mutated during a view update. No new tests: the plan named none, and the logic is in `PlayQueue.toggleUpNext` and `PlaylistText.queueMarker`, both already tested. What's left is AppKit wiring, which the by-hand checks cover.

By hand (not run, for the user): (1) `J`, type a query, ⇧Return: `[1]` shows in the panel and the playlist editor, the song keeps playing and the panel stays open. (2) ⌘-click three results and click Queue: they get `[1] [2] [3]` in playlist order, the button turns to Dequeue, and clicking it removes all three. (3) As queued tracks play, the panel's markers count down while it's open. (4) On a Music Assistant queue, Queue is disabled. (5) Plain Return still plays and closes the panel.

Nit, not blocking: `observeRows` reads `model.playlist.tracks`, and on the local queue that reads `player.queue`, the whole struct. So an up-next change also triggers `queueChanged` and an index rebuild, and the separate marker-only loop doesn't actually save the rebuild. The result is still correct. Tightening it would mean `observeRows` tracking `player.queue.tracks` alone, which Observation can't do through a stored struct property.

## Root cause

#0176 shipped the panel with the Queue button hidden and ⇧Return swallowed, because the play-next list (#0177) and `toggleQueue` (#0179) didn't exist yet.

## Fix

Implemented as planned, in `JumpToFilePanel`:
- `queueSelected()` takes the selected results' indices in result order, or the first result, and calls `model.playlist.toggleQueue`. The panel stays open and focus returns to the search field. ⇧Return calls it.
- The button is enabled only when there are results, `playlist.remote == nil` and `queueRowsSource == .local`. Its state is re-checked after each filter (a source change triggers a rebuild, then a filter), on selection change, and on up-next changes. The title is "Dequeue" when every selected result is queued, else "Queue".
- A 40 pt `marker` column sits between name and time. It shows `PlaylistText.queueMarker(player.queue.upNextPosition(of:))`, or "" on a remote queue.
- Small divergence: `player.queue.upNext` is watched in its own `withObservationTracking` loop (`observeUpNext`), not in the rows block. That way an up-next change reloads only the visible marker cells and doesn't rebuild the index. The name column went from 260 to 220 pt to make room.

## Plan

### 1. Panel (`App/JumpToFile/JumpToFilePanel.swift`)

- **Queue button:**
  - Remove `isHidden = true`.
  - `queueSelected()`: the selected results' queue indices, in result order (that's playlist order), else the first result. Call `model.playlist.toggleQueue(indices)`.
  - Leave the panel open, and keep the field focused (`makeFirstResponder(searchField)` if the click moved it).
- **⇧Return:** in `control(_:textView:doCommandBy:)`, the `insertNewline(_:)` + shift branch calls `queueSelected()`.
- **Enabling:**
  - Enabled when there are results and `model.playlist.remote == nil && model.queueRowsSource == .local`.
  - Disabled for a remote queue until #0182, which changes this line to "enabled unless the source is `.none`".
  - Re-check after each filter and on a source change.
- **Marker column:** add a `marker` column (about 40 pt, right-aligned) between name and time, showing `PlaylistText.queueMarker(model.player.queue.upNextPosition(of: track.id))` for local rows and "" for remote ones.
- **Refresh:** the panel already watches `model.playlist.tracks`. Also watch `model.player.queue.upNext` in the same `withObservationTracking` block. On a change, reload only the visible rows (`reloadData(forRowIndexes: rows(in: visibleRect), columnIndexes: [marker column])`), not the index, so markers update after Queue and as tracks play.
- **Button title:** "Queue" while any selected result is unqueued, else "Dequeue". This mirrors the playlist menu's `selectionIsQueued` rule, computed over the selected results' tracks.
