## Description

`PlexPinSignInTests.cancellationStopsPollingWithoutAToken` failed once in a Tart VM run during #0056 (run `20261013-133121-50083`) and passed on the re-run with no change. After the cancelled sign-in task had returned `.cancelled`, the stub recorded one more poll: `pollCount(handle)` went from 1 to 2 during the 0.3 s check at `PlexPinSignInTests.swift:64`. See [the log excerpt](0058/playerkit-tests-excerpt.log).

A second test in the same suite, `pollingSurvivesTransientFailures`, failed once in the 30x loop (see Root cause) and is fixed here too.

## Expected behavior

Once the sign-in returns `.cancelled`, no further poll reaches the server, and the test passes every run.

## Actual behavior

Intermittently, one more poll is recorded after the task has returned.

## Notes

Seen again in #0056's review, run `20261013-133544-55358`; the re-run passed. Two failures in about four VM runs since #0014 landed.

Two explanations to tell apart:

- **Test race.** A poll that `URLSession` had already started when the task was cancelled reaches `StubURLProtocol.startLoading` (where it is recorded) after `task.value` returns, because session callbacks run on their own queue. Then the request was never really "after" the cancel, and the test should take its baseline only once in-flight requests have settled, or count requests that complete rather than start.
- **Real bug.** The polling loop in `PlexPinSignIn` issues another request after it observed cancellation (for example, a retry path that doesn't check `Task.isCancelled` before the next `fetch`). That would also mean Forget or closing Settings can trigger one more plex.tv request.

Check the loop first; then fix whichever it is. Run the suite in a loop in one VM clone to get a failure rate before and after.

## Plan

### Diagnosis: a test race, not a loop bug

**The loop cannot issue a request after it has seen cancellation.** In `Packages/PlayerKit/Sources/PlexKit/PlexPinSignIn.swift` the only request inside the loop is `account.pin(pin)` at line 112, and every iteration reaches it only through `Task.sleep` (line 105, which throws on a cancelled task and is mapped to `.cancelled` at 107) and `if Task.isCancelled { throw .cancelled }` (109). Every `throw` leaves the function. The retry path (lines 120–122, a transport or 5xx failure under `maxConsecutiveFailures`) does not re-fetch; it goes back to line 105, where the sleep throws at once if the task was cancelled meanwhile. A cancel that lands *during* the fetch comes back as `URLError.cancelled` → `PlexError.transport(.cancelled)` (`PlexClient.swift:80–82`) → `.cancelled` (`failure(_:)`, lines 129–134) → `default: throw failure` (123). `run` (76–83) only logs and rethrows; nothing is detached. So Forget, Cancel and closing Settings never cause an extra plex.tv request; at most a poll already handed to `URLSession` is cancelled by it.

**What the stub counted is a request that was in flight when the cancel arrived.** `StubURLProtocol` records a request in `startLoading` (`Sources/PlexKitStub/StubURLProtocol.swift:133–136`), that is, when `URLSession` starts the load on its custom-protocol queue, not when `PlexClient` calls `session.data(for:)` (`PlexClient.swift:79`) and not when the load completes. When `task.cancel()` lands while the loop is inside `data(for:)`, `URLSession` cancels its task and resumes the continuation with `.cancelled` from its delegate queue, while `startLoading` for that same request can still be queued behind it. Order seen in the failing runs: continuation resumes → `task.value` returns `.failure(.cancelled)` (the first `#expect` at `PlexPinSignInTests.swift:61` passed) → the test takes `count = 1` (line 62) → the stub records the already-cancelled poll → line 64 sees 2. The `stopped` flag the stub sets in `stopLoading` (172–174) only gates *delayed* routes (158–164); with `delay == 0` the record and the immediate `deliver` both happen, harmlessly, for a dead task.

**Why it is intermittent.** The test cancels as soon as `PlexTv.wait` (10 ms polling) sees the first poll, and the poll route answers at once, so the loop is normally already in its 50 ms sleep: the sleep throws, no request is in flight, nothing can be recorded late. It fails only when the test task is stalled for ≥ 50 ms between seeing poll 1 and calling `task.cancel()` (line 59), so the cancel lands inside poll 2's `data(for:)`. That matches the logs: the test took 0.513 s and 0.479 s in the two failing runs (`20261013-133121-50083`, `20261013-133544-55358`) against 0.445 s and 0.463 s when it passed and a floor of about 0.36 s, with all 16 PlexKit suites running in parallel in the 6-vCPU guest.

The neighbours are safe as written: `timeoutFails` (lines 78–87) has the same count-then-sleep shape, but `.timedOut` is thrown by the loop itself at line 110 *before* a poll is issued, and the previous poll was recorded before it completed, so no late record is possible. `PlexSettingsModelTests.cancelSignInLeavesIdle` asserts `signInStatus` and `store.saves`, not request counts. Nothing in the app changes.

2. **`PlexPinSignInTests.swift`** — delete `cancellationStopsPollingWithoutAToken` (lines 53–65) and add:

   - **`cancellationWhileAPollIsInFlightStopsWithoutAToken`** (cancel lands in the fetch, the path that failed). Routes: `createRoute()` + `pollRoute(delay: 60)`; default `options`. Start `Task { await Self.run(signIn, recorder) }`; `#expect(await PlexTv.wait { pollCount(handle) >= 1 })` — the poll has reached `startLoading` and the stub holds it, so the loop is inside `data(for:)` and cannot leave on its own for 60 s. Then `let start = ContinuousClock.now; task.cancel(); let outcome = await task.value`. Assert `outcome == .failure(.cancelled)`, `ContinuousClock.now - start < .seconds(5)` (the cancel, not the gate, ended the held request: if cancellation did not reach the in-flight task, `task.value` would only return once the stub answered at 60 s), `handle.recorded.map(\.method) == ["POST", "GET"]`, `pollCount(handle) == 1`, and `recorder.opened.count == 1`. No sleep: the only poll ever handed to `URLSession` was recorded before the cancel, and `run` has returned with no detached work, so the count cannot change. Put that sentence in a comment above the assertions; it is the lesson of this issue.
   - **`cancellationBetweenPollsSendsNoPoll`** (cancel lands in the sleep, the path the old test usually exercised). `Options(pollInterval: .seconds(60), timeout: .seconds(120), maxConsecutiveFailures: 3)`; routes `createRoute()` + `pollRoute()`. Start the task; `#expect(await PlexTv.wait { recorder.opened.count == 1 })` — the opener runs at `PlexPinSignIn.swift:99`, immediately before the first `Task.sleep`, and from there no poll can be issued for 60 s. `task.cancel()`; `await task.value == .failure(.cancelled)` (the sleep throws; if the cancel lands between lines 99 and 105, the sleep throws on entry). Assert `pollCount(handle) == 0` and `handle.recorded.map(\.method) == ["POST"]`. Both tests return in milliseconds.

3. **`Sources/PlexKitStub/StubURLProtocol.swift`** — one doc-comment sentence on `Handle.recorded` (and the static `recorded`): a request is recorded when `URLSession` starts loading it, which can be after a cancelled `data(for:)` has already thrown; tests that count requests after a cancel must hold the request in flight (`delay`) or make the next one impossible (a long interval) instead of sleeping. No behaviour change.

### Risks

- The in-flight test depends on `URLSession` cancelling a task whose custom protocol is mid-load and completing it with `.cancelled`; two existing tests already rely on exactly that. The 5 s bound against a 60 s gate leaves a wide margin for a stalled guest. If the bound ever trips, the gate (not the cancel) ended the request, which would be a real finding.
- A gated route keeps its `StubURLProtocol` instance in a GCD block for 60 s after the test; the `stopped` check means it delivers nothing, and the test process exits long before. Harmless.
- `PlexTv.wait` is still a 10 ms bounded poll with a 5 s cap, as everywhere in these suites; it waits for a positive condition, not for a count to settle.

## Root cause

A test race. The polling loop in `PlexPinSignIn` was correct (no request can be issued after it observes cancellation), and the app is unaffected. `StubURLProtocol` records a request when `URLSession` starts loading it, which can be after a cancelled `data(for:)` has already thrown. When the test's cancel landed inside a poll's fetch, `task.value` returned, the test took its baseline count, and the already-cancelled poll was recorded afterwards, so the count went from 1 to 2.

Second race, `pollingSurvivesTransientFailures`: the options are a 50 ms interval and `maxConsecutiveFailures: 3`. The test waited for `pollCount >= 2` and then swapped in the claimed route. If the test task stalled about 50 ms, a third failing poll landed before the swap and sign-in correctly failed with `.unreachable`, so the `.success` expectation failed (seen once in 31 runs, `PlexPinSignInTests.swift:114`).

## Fix

No production code. In `Packages/PlayerKit/Tests/PlexKitTests/`, `cancellationStopsPollingWithoutAToken` is replaced by `cancellationWhileAPollIsInFlightStopsWithoutAToken` (poll held with `delay: 60`, cancel ends it, asserts it returned in under 5 s and recorded exactly POST, GET) and `cancellationBetweenPollsSendsNoPoll` (60 s interval, cancel during the sleep, no poll). Neither sleeps before counting. `pollRoute` gained a defaulted `delay`; `StubURLProtocol.recorded` documents when recording happens. As planned, no deviation.

Second commit: `StubURLProtocol.Route` gains an optional `times` (the route stops matching after that many requests; `pollRoute(times:)` passes it through). `pollingSurvivesTransientFailures` now registers create, a failing poll route with `times: 2`, and the claimed poll route up front, so the stub itself fails two polls and then answers with the claimed PIN; no mid-flight swap and no timing dependence. It also asserts `pollCount == 3`. The second half (three failures give `.unreachable`, `pollCount == 3`) is unchanged.
