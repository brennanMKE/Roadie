## Resolution notes

> 🟢 Resolved 2026-10-23 — `queue.json` saves the play-next list as an optional `upNext` key of indices (still version 1), and restore rebuilds it without opening the engine.

Review: the synthesized `Decodable` on `Stored` with a plain `JSONDecoder` ignores unknown keys, so an older build loads a new file and drops only the markers; `decodeIfPresent` makes a missing key an empty list. Indices go through the stored→kept map, so entries for dropped items go, duplicates keep the first, and out-of-range or negative indices are dropped. Saving by index is also safe against the loader minting fresh ids for missing or duplicate ones. `restoreQueue` runs `appendUpNext` after `select`, so a saved list holding the current entry (to replay after itself) survives. The decision not to save `shufflePosition = -1` / `isPlayingFromUpNext` holds. Unshuffled, the flag doesn't change `nextTarget` or `previousTarget` (both use `currentIndex ± 1`). Shuffled, the order itself isn't saved, and restore's `setShuffle(true)` puts the current track at position 0 of a fresh pass. So if you quit while a queued entry Q plays, Q is the restored anchor: it was already taken off `upNext` when it started, so it doesn't replay, and once the queue empties the pass goes on from position 1. The only loss is the old pass history, which was already lost before #0178. Independent run, `scripts/verify.sh --head --full --expect <the 9 tests>`:

## Description

Phase B of M15. After #0177, "This Mac" has a play-next list (`PlayQueue.upNext`). `QueueSnapshot` / `QueueStore` save only the items, the current index, repeat and shuffle, so a quit and relaunch loses the queue and its `[n]` markers.

This issue saves `upNext` as indices into `items` and restores it.

**Correction to the spec, umbrella decision 1:** the spec says to bump `QueueSnapshot.currentVersion` and load older versions with an empty `upNext`. But `QueueStore.loadQueue()` accepts only `stored.version == QueueSnapshot.currentVersion`. A bump would reject every existing `queue.json` unless the loader changed too, and an older Roadie would then throw away new files. Instead, add an **optional `upNext` key and keep version 1**:

- An old file has no key, so it loads with an empty list.
- An older build ignores the key (`Codable` skips unknown keys), so a downgrade keeps the queue and loses only the markers.

## Root cause

`QueueSnapshot` and `QueueStore` saved only the items, the current index, repeat and shuffle. `PlayQueue.upNext` (#0177) was never written, so quitting and relaunching lost the play-next list.

## Fix

Followed the plan. `QueueSnapshot.upNext: [Int]` holds indices into `items`. It's saved as an optional `upNext` key, always written, and `currentVersion` stays 1. On load the indices are remapped through a stored-index→new-index map, so entries for dropped items go away, as do duplicates (the first is kept) and out-of-range indices. `LocalPlayerOutput.queueSnapshot()` maps `queue.upNext` ids to positions. `restore` passes the list to `Player.restoreQueue(..., upNext:)`, which calls `queue.appendUpNext` after the select and shuffle steps. It still never opens the engine. Autosave needed no change.

Deviation from the #0177 review note ("save and restore the -1 `shufflePosition` with `isPlayingFromUpNext`"): neither value is saved. The shuffle order isn't saved either; restore rebuilds it with the current track at the head. A restored current track is therefore a pass entry with `isPlayingFromUpNext == false`, and a saved -1 position would point into an order that no longer exists. The play-next list itself does survive.

## Plan

### 1. Snapshot (`Packages/PlayerKit/Sources/LocalPlayback/QueueSnapshot.swift`)

- `QueueSnapshot`: add `public var upNext: [Int]`, documented as "indices into `items`, in play-next order (#0178)". Add the init parameter `upNext: [Int] = []` last, so existing call sites compile.
- `currentVersion` stays 1. Add a comment: "the optional `upNext` key (#0178) didn't need a bump."
- Private `Stored`: add `var upNext: [Int]?` and the `upNext` CodingKey.
- **Save:** always write `upNext: snapshot.upNext`, even when empty, so the key set stays fixed for the pinning test.
- **Load:**
  - `decodeIfPresent`; nil means `[]`.
  - While walking `stored.items`, build `newIndex: [Int: Int]` (stored index → index in `items`) for each item kept. `currentIndex` already does this inline.
  - Then `upNext = (stored.upNext ?? []).compactMap { newIndex[$0] }`, dropping duplicates (keep the first) and anything out of range.
  - A dropped item (unknown source kind) drops out of `upNext` too.

### 2. Output (`Packages/PlayerKit/Sources/LocalPlayback/LocalPlayerOutput.swift`)

- `queueSnapshot()`: build `let position = Dictionary(uniqueKeysWithValues: tracks.enumerated().map { ($1.id, $0) })` once, then `upNext: player.queue.upNext.compactMap { position[$0] }`.
- `restore(_:)`: pass `upNext: snapshot.upNext` to `player.restoreQueue`.

### 3. Player (`Packages/PlayerKit/Sources/AudioCore/Player.swift`)

- `restoreQueue(_:currentIndex:repeatMode:isShuffled:upNext: [Int] = [])`. After the existing select and shuffle steps: `queue.appendUpNext(upNext.compactMap { tracks.indices.contains($0) ? tracks[$0].id : nil })`.
- It still never opens the engine or starts a load. Update the doc comment.

### 4. Autosave

`QueueAutosaver.observe()` tracks `output.player.queue`. `upNext` is part of `PlayQueue`, so queueing or dequeueing a row already triggers a save. Just confirm it with the test below; no code change.
