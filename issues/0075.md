# 0075 — Only one Music Assistant server can be configured

| | |
|---|---|
| **Status** | open |
| **Module** | MusicAssistantKit / App |
| **Platform** | macOS |
| **First seen** | 2026-10-14 |

## Description

The user runs a different Music Assistant server at each location (home, another site), and sometimes reaches one remotely over Tailscale. SkinAmp should hold several Music Assistant configurations and connect to whichever one is reachable, switching automatically when the Mac moves between networks.

## Acceptance criteria

- Settings › Music Assistant lists multiple servers. Each has a name, an address (LAN host, `.local`, IP, or a Tailscale MagicDNS name or 100.x address), its own token in the Keychain (one item per server), and the server id learned on first successful connection.
- Each server can optionally be tied to one or more Wi-Fi network names (SSIDs). "Use current network" fills it in from the network the Mac is on.
- Choosing the active server:
  1. Servers tied to the current SSID are tried first.
  2. Then every other server, in the user's list order. This covers Tailscale, where the SSID tells nothing.
  3. A server counts as reachable only if its `/info` answers in time **and** its `server_id` matches the one stored for that configuration. A different server answering at the same address never receives the token (the MA API docs recommend this check).
- The choice is re-evaluated when the network changes (`NWPathMonitor`, Wi-Fi changes, Tailscale coming up or going down) and when the active server drops. The switch goes through #0070's source controller without interrupting what is playing on This Mac.
- Settings and the Library window say which server is in use and why ("Home — on network X", "Studio — via Tailscale", "none reachable").
- If none is reachable, #0067's fallback goes to the local folder as today.
- Tokens, addresses and SSIDs never appear in logs; addresses and SSIDs live in UserDefaults, tokens only in the Keychain.

## Plan

### Scope and decisions

This issue is **not folded into #0063**. #0063 already builds what this issue needs from it: the server list (name, address, one Keychain item per server, the learned `server_id`, a `networks` field with no UI yet), Test Connection, the `MusicAssistantActiveServer` box, the backend's `ServerProvider` seam, `LibrarySourceController.reload(_:)`, and `NSAllowsArbitraryLoads`, which already lets `http`/`ws` reach `*.ts.net`, `100.x` and public DNS names. This issue replaces #0063's "first verified server" rule with automatic selection. Status stays `open`; this plan writes no code. It lands after #0063, and before or after #0074 (it does not touch Plex).

- **Pure decision, separate driver, system adapters at the edge**, as in #0067:
  - `MusicAssistantServerRanking` (pure) orders candidates and picks a winner from probe outcomes.
  - `MusicAssistantServerSelector` (actor) runs the `/info` probes with an injected fetcher and clock.
  - `MusicAssistantSelectionController` (`@MainActor @Observable`) owns the current choice, the "why" text, the triggers, the debounce and cancellation.

  All three go in `MusicAssistantKit`, still free of Network, CoreWLAN and CoreLocation. The real `NWPathMonitor`, `CWWiFiClient` and `CLLocationManager` adapters are thin types in `App/Network/` behind two protocols, and the tests use stubs.
- **The SSID is only a hint.** With no Location permission, no Wi-Fi (Ethernet) or a nil SSID, ranking is plain list order, and the probe alone decides. Permission is requested **only** when the user presses "Use Current Network". It is never requested at launch, on a network change, or in the guest. When access is denied or restricted, Settings says the shortcut needs Location access and offers to open the Location Services pane.
- **Probes run in parallel and the decision follows rank order.** Every verified candidate gets an unauthenticated `GET /info` at once, with a 3 s timeout each. The winner is the highest-ranked candidate that answered with **its own stored `server_id`**. A higher-ranked probe still in flight is waited for, up to its timeout, before a lower-ranked success can win. The selector never sees a token (it has no token provider), so a different server at the same address can't receive one. The backend's socket re-checks the id before `auth` anyway (#0061).
- **No network at launch.** The selector runs when:
  1. the MA backend connects (the Library window) or #0067 probes MA. Both go through the backend's `ServerProvider`, which resolves lazily.
  2. a debounced network change arrives **after** a first resolution, or after a Settings edit. `NWPathMonitor` starts at launch but its first update is ignored.
  3. the active server drops: a client state of `.reconnecting` lasting more than 10 s, or `.failed`, or a #0067 browse failure.

  In the guest no server is configured, so nothing probes or prompts.
- **Switching goes through #0070's controller without interrupting playback.** When the winner's identity changes:
  - If MA is the selected source: `await backend.disconnect()`, then `sources.reload("musicAssistant")`.
  - If the fallback has the folder active: `fallback.retryNow()`, so #0067 probes MA (now resolving to the new winner) and restores it.
  - If the winner is nil: no reload. The backend's connect throws `.unreachable`, and #0067's failure path falls back to the folder.

  `LocalPlayerOutput` and its queue are never touched. Controlling a remote MA player (#0064) across a server change is out of scope; that player belonged to the old server.
- **Stickiness.** If the current server still answers and no higher-ranked candidate does, the choice stays and nothing reloads. A path change that leaves the same winner causes no reload.
- **Location entitlement.** The app runs with the hardened runtime (`ENABLE_HARDENED_RUNTIME: YES`), which needs `com.apple.security.personal-information.location` for Location Services. The app gets an entitlements file in `project.yml`.

### 3. Protocols (in `MusicAssistantKit`)

```swift
public enum WiFiAuthorization: Hashable, Sendable { case notDetermined, denied, restricted, authorized }

/// The current Wi-Fi network name. Reading never prompts; only `requestAuthorization()` may.
@MainActor public protocol WiFiNetworkProvider: AnyObject {
    var authorization: WiFiAuthorization { get }
    /// nil without permission, without Wi-Fi, or when CoreWLAN returns nil. Never logged.
    func currentSSID() -> String?
    /// Called only from a user action. Returns the resulting authorization.
    func requestAuthorization() async -> WiFiAuthorization
}

/// Network path changes. The first value after `start()` describes the current path and is not a change.
public protocol NetworkChangeSource: Sendable {
    func changes() -> AsyncStream<Void>
}
```

`App/Network/SystemWiFiNetwork.swift`: `final class SystemWiFiNetwork: NSObject, WiFiNetworkProvider, CLLocationManagerDelegate`.
- The `CLLocationManager` is created **lazily** on first use of `authorization` or `requestAuthorization`, never in `init`.
- `authorization` maps `.authorizedAlways`/`.authorized`/`.authorizedWhenInUse` → `.authorized`.
- `currentSSID()` returns `CWWiFiClient.shared().interface()?.ssid()` only when authorized, else nil, without calling CoreWLAN.
- `requestAuthorization()` calls `requestWhenInUseAuthorization()` and awaits `locationManagerDidChangeAuthorization` through a checked continuation (one at a time; a second call awaits the same one).

`App/Network/SystemNetworkEvents.swift`: an `NWPathMonitor` on a private queue that yields `Void` on each `pathUpdateHandler` call. It drops the first, initial path. It also yields on `CWEventType.ssidDidChange` when monitoring is permitted; skip that if CoreWLAN event monitoring needs more than the location permission, because path updates already fire on a network change. It never reads or logs interface names or addresses.

### 4. `MusicAssistantServerRanking` (pure)

```swift
public struct MusicAssistantServerRanking: Hashable, Sendable {
    public enum Basis: Hashable, Sendable { case network(String), listOrder }
    public struct Candidate: Hashable, Sendable { public var server: MusicAssistantServerConfiguration; public var basis: Basis }
    public enum Outcome: Hashable, Sendable { case reachable, unreachable, timedOut, mismatch, schemaUnsupported }

    /// Verified servers only. Those whose `networks` contain `ssid` (exact match after trimming; SSIDs are
    /// case-sensitive) first, in list order with basis `.network(ssid)`; then every other one in list order (`.listOrder`).
    public static func candidates(_ servers: [MusicAssistantServerConfiguration], ssid: String?) -> [Candidate]

    /// The first candidate in order whose outcome is `.reachable`, but only once every candidate ranked above it
    /// has an outcome (nil outcome = still probing → `.undecided`).
    public enum Decision: Hashable, Sendable { case undecided, chosen(Candidate), none }
    public static func decide(_ candidates: [Candidate], outcomes: [UUID: Outcome]) -> Decision
}
```

"Why" text, a pure `static func reason(for: Candidate) -> String` plus constants:
- `.network(ssid)` → "\(name) — on network \(ssid)".
- `.listOrder` with `MusicAssistantAddressSecurity.classify(baseURL) == .tailscale` → "\(name) — via Tailscale".
- Other `.listOrder` → "\(name) — first reachable".
- `.none` → "No Music Assistant server reachable".
- No verified server → "No Music Assistant server tested yet".

These strings are for the UI only: never logged, never in a `StatusNotice` detail that is logged.

### 5. `MusicAssistantServerSelector` (actor)

```swift
public actor MusicAssistantServerSelector {
    public typealias InfoFetcher = @Sendable (URL) async throws -> MAServerInfo   // no headers, no token
    public init(fetch: @escaping InfoFetcher, clock: any Clock<Duration> = ContinuousClock(), probeTimeout: Duration = .seconds(3))
    public struct Result: Hashable, Sendable { public var decision: MusicAssistantServerRanking.Decision; public var outcomes: [UUID: MusicAssistantServerRanking.Outcome] }
    /// Probes every candidate concurrently; returns as soon as `decide` is not `.undecided` (cancelling the rest) or all are done.
    public func resolve(_ candidates: [MusicAssistantServerRanking.Candidate]) async -> Result
}
```

- Outcome mapping:
  - The fetch returns and `info.serverID == server.address.serverID` → `.reachable`. A different id → `.mismatch`. A schema below the minimum → `.schemaUnsupported`.
  - A thrown error → `.unreachable`.
  - The timeout races through the injected clock → `.timedOut`.
  - A cancellation of `resolve` itself propagates (the caller discards the result).
- Concurrent `resolve` calls are **coalesced**: a call made while one is running with the same candidate list awaits that one. Otherwise the running one is cancelled and the newest wins.
- The production fetcher is `{ try await MusicAssistantClient.serverInfo(at: $0, http: URLSessionHTTPTransport(), timeout: .seconds(3)) }`. Tests use closures over a table keyed by URL with `ManualClock` delays.

### 6. `MusicAssistantSelectionController` (`@MainActor @Observable`)

```swift
public final class MusicAssistantSelectionController {
    public private(set) var current: MusicAssistantServerRanking.Candidate?
    public private(set) var reasonText: String          // "Home — on network X" etc.
    public private(set) var lastOutcomes: [UUID: MusicAssistantServerRanking.Outcome]   // for Settings status dots
    public private(set) var isResolving: Bool
    @ObservationIgnored public var onChange: (@MainActor (_ old: MusicAssistantServerConfiguration?, _ new: MusicAssistantServerConfiguration?) -> Void)?

    public init<C: Clock>(store: MusicAssistantServerStore, active: MusicAssistantActiveServer, selector: MusicAssistantServerSelector,
                          wifi: any WiFiNetworkProvider, network: any NetworkChangeSource, clock: C, debounce: Duration = .seconds(2))
        where C.Duration == Duration
    public func start()                 // subscribes to `network.changes()`; no probe, no SSID read
    public func resolveNow() async -> MusicAssistantServerConfiguration?   // the backend's ServerProvider and #0067's probe call this
    public func currentOrResolve() async -> MusicAssistantServerConfiguration?   // cached `current` while valid, else resolveNow()
    public func serversChanged()        // Settings edits: invalidate; re-resolve only if resolved before
    public func activeServerDropped()   // client failure / browse failure on MA
    public func stop()
}
```

- `resolveNow()`:
  1. Read the servers from the store.
  2. `ssid = wifi.authorization == .authorized ? wifi.currentSSID() : nil`. Never prompts.
  3. Build the candidates and call `selector.resolve`.
  4. Map the decision to `current`, `reasonText` and `lastOutcomes`, then `active.set(current?.server)`.
  5. If the identity changed, call `onChange(old, new)` exactly once.

  Logging is limited to the decision kind, the count of candidates and the counts per outcome: no names, addresses or SSIDs.
- `currentOrResolve()` returns `current` without probing when `current` is set and no invalidation happened since. Invalidations are a network change, `serversChanged`, and `activeServerDropped`. Otherwise it runs `resolveNow()`.
- Network changes are debounced through the injected clock (2 s; a burst becomes one resolution) and act only when `hasResolvedOnce`. A network change before any use does nothing, so launch is silent.
- `activeServerDropped()` invalidates and resolves immediately (no debounce).

### 12. Risks and gotchas

- **Location needs the entitlement under the hardened runtime.** Without `com.apple.security.personal-information.location`, authorization can be denied silently and the SSID is always nil; the probe still works, so the failure is invisible. The entitlement check and checklist step 2 cover it. TCC keys permission to the code signature, so ad-hoc rebuilds may ask again.
- **`CWWiFiClient.interface()?.ssid()` is nil without authorization on macOS 14+**, and may be nil briefly right after a network change. The debounce absorbs most of it, and the probe decides anyway.
- **`NWPathMonitor` floods** (several updates per change, Tailscale's utun toggling). The 2 s debounce and the stickiness rule keep it to at most one reload per real change. `onChange` fires only on an identity change.
- **Parallel probes reach every configured server**, including a public DNS name while at another site. They are unauthenticated `/info` GETs, the same as MA's web UI, but they do reveal to each server that the client exists. Acceptable; noted in the docs.
- **Two servers at the same URL** (both `homeassistant.local:8095` at two sites): only the matching `server_id` is `.reachable`, so the other is a `.mismatch`. Both probes hit the same URL; deduplicate fetches by URL within one round and evaluate each candidate against the shared `MAServerInfo`, and test it (`sameURLForTwoServersFetchesOnceAndPicksTheMatchingID`, add it to `ServerSelectorTests`).
- **Races with #0067.** A fallback probe and a network-change resolution can run together; the selector coalesces them. A `reload` after the fallback has already moved to the folder returns false, harmlessly. `select` and `reload` never connect, so ordering can't double-connect.
- **The backend's provider is async now** (#0063 §5 made `ServerProvider` async for this). `connect()` awaits the selection before touching the Keychain, so an unreachable or mismatched server never causes a Keychain read.
- **Logging.** The "why" text contains SSIDs and names, which are user data. It may appear in the UI and a marquee notice (name only), never in `Logger` calls or `StatusNotice.detail`.

## Notes

Reading the Wi-Fi SSID on macOS 14 and later (`CWWiFiClient.shared().interface()?.ssid()`) returns nil unless the app has Location Services permission. That means adding `NSLocationUsageDescription` and requesting `CLLocationManager` authorization. The plan must decide how to handle a denied permission. Recommended: the SSID is only a hint, so with no permission or no Wi-Fi (Ethernet, Tailscale) the reachability probe alone picks the server, and Settings explains that the SSID shortcut needs Location access.

Builds on #0061 (client) and #0063 (settings). It may simply be folded into #0063 if that issue isn't implemented yet; the planner decides.
