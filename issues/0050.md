## Description

Before choosing an architecture, build the Phase 0 spike from [docs/airplay-macos-handoff.md](../docs/airplay-macos-handoff.md): a minimal macOS app (no skins) with an `AVRoutePickerView` and four toggleable engines — `AVQueuePlayer` with the picker's `player` set (A), the same with `player` nil (A′), A with an `MTAudioProcessingTap` doing gain + RMS (A+tap), and `AVSampleBufferAudioRenderer` + synchronizer playing decoded PCM with `player` nil (B).

## Plan

### Scope and decisions

This is a spike, not a feature. It produces three things: a throwaway harness app in `Spikes/AirPlaySpike/` that an implementer can build, unit-test and smoke-launch silently in the VM; a hand-test protocol the user runs on the host against their HomePods; and `docs/airplay-spike-results.md`, which ends with the A / B / C recommendation that unblocks #0051 and #0052. Nothing under `App/`, `Packages/` or `project.yml` changes (an implementer is on #0030 in those files at the same time). The harness has no skin, no Plex, no EQ: only what the acceptance criteria need to be answered.

- **The spike cannot be resolved by a subagent alone.** Every per-engine cell in the acceptance criteria needs a HomePod, and the VM has no AirPlay path and no audio path. "Done" for the implementer is: harness committed, VM run green with the spike steps, results doc skeleton committed with the SDK findings filled in and every hand-test cell marked `untested`. The issue then stays `in-progress` until the user has run section 6 and pasted the results; a short follow-up pass (any model) turns them into the recommendation in the doc, and only then does the reviewer resolve. The reviewer of the implementation pass checks the harness and the doc skeleton and leaves the status alone.
- **Five engines, not four.** The four from the handoff plus one cheap extra, **B-dev**: engine B with `AVSampleBufferAudioRenderer.audioOutputDeviceUniqueID` set to the HomePod's CoreAudio device UID (macOS 10.13+; the HomePod shows up as a CoreAudio output with transport `AirPlay` once macOS knows it) and the picker not involved. It is one property and one device list, and it is the fallback #0051 needs if the picker turns out to do nothing for a renderer on macOS: per-app routing without enhanced buffering. `AVPlayer` has the same property (macOS 10.9+), so A-dev is a one-line variant if B-dev proves interesting; not in the matrix by default.
- **SDK facts, read from the installed SDK on the host (read-only; `MacOSX27.0.sdk`, Xcode 27.0, host macOS 27.0).** These settle the long-form check's first half now; the implementer re-runs the grep with `check-sdk.sh` (section 3) and records it in the doc:
  - `AVFAudio/AVAudioSession.h`: **every** member, including `-setCategory:mode:routeSharingPolicy:options:error:` and `routeSharingPolicy`, is `API_UNAVAILABLE(macos)`. There is no ObjC-only macOS path; the WWDC17 "minimal AVAudioSession on macOS" does not exist in this SDK. No shim is possible. Long-form identification on macOS is therefore the Info.plist key or nothing.
  - `AVFAudio/AVAudioSessionTypes.h`: `AVInitialRouteSharingPolicy` is documented only next to `LongFormVideo`. The `LongFormAudio` policy's doc says it plays "to the same output as the built-in Music (iOS), Podcasts, or iTunes (macOS) applications", so the shared long-form route exists system-side on macOS; whether the plist key opts an app into it is the hand test.
  - `AVKit/AVRoutePickerView.h`: macOS 10.15+; `player` is macOS-only. The class discussion reads: *"Media from an AVPlayer, or from an AVSampleBufferAudioRenderer **on iOS and tvOS**, can be routed to compatible AirPlay destinations."* That sentence is the written case against option B on macOS; engines A′ and B exist to test it, B-dev is the fallback if it holds.
  - `AVRouteDetector` lives in **AVFoundation** on macOS (`AVFoundation/AVRouteDetector.h`, macOS 10.13+), not AVKit; `detectsCustomRoutes` is unavailable on macOS.
  - `AVSampleBufferAudioRenderer.h` / `AVSampleBufferRenderSynchronizer.h`: the classic API (`requestMediaDataWhenReady(on:using:)`, `enqueue`, `flush`, `flush(fromSourceTime:)`, `addRenderer`) is **deprecated in macOS 27** in favour of `sampleBufferReceiver()` / `addReceiver(_:)` with async `enqueue`. The deployment target is 14, so the spike (and later #0052) uses the classic API and accepts the deprecation warnings; no `#available(macOS 27)` branches. `synchronizer.currentTime()` is macOS 10.14+, `delaysRateChangeUntilHasSufficientMediaData` 11.3+; `audioOutputDeviceUniqueID` warns that changing it may change the synchronizer's clock.
  - `MediaToolbox/MTAudioProcessingTap.h` and `AVAudioMixInputParameters.audioTapProcessor`: macOS 10.9+. `MPNowPlayingInfoCenter.playbackState`: macOS 10.12.2+ (already used by `NowPlayingBridge`).
- **Production code stays out.** `AudioCore` is not linked. The only pieces worth copying later are the PCM-to-`CMSampleBuffer` packager and the lead meter, and they are written so #0052 can lift them (`SpikeKit`, no app dependencies). Nothing is shared the other way.
- **Verification is `scripts/run-tests-vm.sh` only, never a host build.** The script gets an additive `--spike` flag (section 4) so the VM builds, tests and smoke-launches the harness in the same muted, no-audio guest. The default run (no flag) is unchanged and must stay green. The harness must never play audio in the guest: its `--smoke` mode constructs every engine and never calls `play()`/`setRate`, the unit tests never touch an output device, and the script's host `coreaudiod` check remains the arbiter.
- **The user builds the harness on the host themselves** for the hand test (`xcodegen generate --spec Spikes/AirPlaySpike/project.yml`, then Xcode or `xcodebuild` on the host, by the user, not a subagent). Ad-hoc signing (`CODE_SIGN_IDENTITY: "-"`), unsandboxed, like SkinAmp.

### 2. `SpikeKit`

Swift 6 language mode, `@MainActor` engines; AVFoundation objects are not `Sendable`, so each engine owns its objects and exposes value snapshots.

- `EngineKind: String, CaseIterable`: `.a` ("A: AVQueuePlayer, picker.player set"), `.aPrime` ("A′: picker.player nil"), `.aTap` ("A+tap"), `.b` ("B: renderer+synchronizer, picker nil"), `.bDevice` ("B-dev: renderer → CoreAudio AirPlay device").
- `protocol SpikeEngine: AnyObject` (`@MainActor`): `kind`, `load(_ urls: [URL]) throws`, `play()`, `pause()`, `seek(by seconds: TimeInterval)`, `next()`, `var volume: Float`, `var currentTime: TimeInterval`, `var rate: Float`, `var leadSeconds: TimeInterval?` (see below), `func attach(to picker: AVRoutePickerView)` (A sets `picker.player`; all others set it to nil), `func detach()`, `func probe() -> [(String, String)]` (a diagnostic snapshot: item status, `timeControlStatus`/`reasonForWaitingToPlay`, `isReadyForMoreMediaData`, renderer `status`/`error`, `audioOutputDeviceUniqueID`, synchronizer rate), `func teardown()` (rate 0, stop requesting data, flush, drop items). Constructing an engine never starts I/O; only `play()` does.
- `QueuePlayerEngine(kind: .a | .aPrime | .aTap)`: `AVQueuePlayer` with one `AVPlayerItem` per URL, `actionAtItemEnd = .advance`. `.aTap` builds an `AVMutableAudioMix` with one `AVMutableAudioMixInputParameters` per item's first audio track and `audioTapProcessor = GainRMSTap` (create with `MTAudioProcessingTapCreate`, `kMTAudioProcessingTapCreationFlag_PreEffects`). `leadSeconds` for `.aTap` is `tap.lastProcessedEnd − player.currentTime().seconds` (the only A-side lead measurement there is; `loadedTimeRanges` is meaningless for local files); nil for `.a`/`.aPrime`. Observe `AVPlayer.rateDidChangeNotification` with its reason key and `AVPlayerItemDidPlayToEndTime`, log both.
- `GainRMSTap`: a `final class` box passed through the tap's `clientInfo` as `Unmanaged`; C callbacks are `nonisolated` static functions that only touch the box. `process`: `MTAudioProcessingTapGetSourceAudio`, multiply by `gain` (an atomic `Float`, 0…1, set from the UI), compute RMS with `vDSP_rmsqv`, and store `(hostTime: mach_absolute_time, pts: timeRange.start + duration, rms)` in a few lock-free fields the main thread reads. `prepare`/`unprepare` log the processing format and flags. Note in the doc that under enhanced buffering `pts` may run minutes ahead of `currentTime`; that number *is* the measurement.
- `SampleBufferEngine(kind: .b | .bDevice)`: one `AVSampleBufferAudioRenderer`, one `AVSampleBufferRenderSynchronizer`, `addRenderer` once (one renderer per synchronizer, per the long-form rule). `.bDevice` takes a `deviceUID` and sets `renderer.audioOutputDeviceUniqueID` before the first `play()`. `load` opens the files with `AVAudioFile` and builds a `PCMSource`. `play`: install `requestMediaDataWhenReady(on: feedQueue)` (a private serial queue; the closure loops `while renderer.isReadyForMoreMediaData, let buffer = source.next() { renderer.enqueue(buffer) }` and calls `stopRequestingMediaData()` at the end of data), then `synchronizer.setRate(1, time: resumeTime)`. `pause`: `setRate(0, time: synchronizer.currentTime())`, no flush. `seek(by:)`: rate 0 → `stopRequestingMediaData` → `flush` → `source.seek(to:)` → reinstall → rate 1 at the new time; log whether `renderer.status` or `error` changed. `leadSeconds = source.lastEnqueuedEnd − synchronizer.currentTime().seconds`, sampled on the main thread; `LeadMeter` keeps the running max and the last 60 s of samples. Also log every transition of `isReadyForMoreMediaData` (KVO) with the lead at that moment: on a local route the renderer stops asking after a few seconds, on AirPlay 2 after minutes, and that is the "enhanced buffering is active" signal.
- `PCMSource` (`final class`, `@unchecked Sendable` with a lock, owned by `feedQueue`): decodes with `AVAudioFile` into interleaved Float32 (`AVAudioFormat(commonFormat: .pcmFormatFloat32, sampleRate: file rate, channels: file channels, interleaved: true)`, mixed rates back to back are allowed), 1.5 s per buffer, one continuous timeline across files (each file's local time offset by the sum of previous durations, in `CMTime` at the file's rate), `next()` returns the packaged `CMSampleBuffer` or nil at end; `seek(to:)` repositions by scanning the file table. `SampleBufferPackager.make(from: AVAudioPCMBuffer, presentationTime: CMTime) throws -> CMSampleBuffer` is a pure function: `CMAudioFormatDescriptionCreate` from the buffer's ASBD, `CMBlockBuffer` wrapping a copy of the interleaved bytes (no pointer into the PCM buffer), `CMSampleBufferCreateReady` with `numSamples = frameLength`.
- `LeadMeter`: pure struct, `record(lastEnqueued: TimeInterval, now: TimeInterval, at: ContinuousClock.Instant)`, `current`, `max`, `maxInLast(seconds:)`, and `classification` (`.seconds` ≤ 10 s, `.minutes` ≥ 30 s, `.between`), used in the status pane and the log.
- `TestTone.write(to url: URL, seconds: Int = 120, rate: 48_000)`: a 120 s stereo WAV: a quiet 220 Hz tone on both channels with a 20 ms 2 kHz tick at every integer second on the left channel. The ticks make multi-room sync (echo/flam between two HomePods), clock-vs-ear comparison (section 6, step 9) and tap latency audible. Written once per launch into `~/Library/Application Support/AirPlaySpike/tick-120s.wav` on the host, or into `--log-dir` in smoke mode.
- `CoreAudioOutputs.list() -> [OutputDevice]` (`id`, `uid`, `name`, `transport` text: AirPlay / Built-in / USB / Bluetooth / Aggregate / Virtual / four-char code) via `kAudioHardwarePropertyDevices`, `kAudioDevicePropertyDeviceUID`, `kAudioObjectPropertyName`, `kAudioDevicePropertyTransportType`, filtered to devices with output streams. Reads only; nothing here changes the default device. (#0048 plans its own `OutputDeviceProvider`; this is a 60-line read-only copy so the spike does not depend on an unmerged issue.)
- `RemoteCommandProbe`: registers play / pause / togglePlayPause / stop / next / previous / changePlaybackPosition on `MPRemoteCommandCenter.shared()`, disables skip/seek-interval commands, forwards to the active engine, logs `remote: <command> @ <engine time>` and keeps `lastCommand` for the status pane. Publishes `nowPlayingInfo` (title "AirPlaySpike <engine>", duration, elapsed, rate) and `playbackState` on play/pause/seek/track change only. The handler closures are `@Sendable`; they hop to the main actor with a `Task`, as `NowPlayingBridge` does.
- `ResultsSheet`: the acceptance matrix as data (`Check` enum with the ten checks from the acceptance criteria plus `pickerMultiSelect`, `longFormPlistHonored`; `[EngineKind: [Check: Cell]]`, `Cell` = `.untested | .yes | .no | .value(String) | .na`), `markdown()` renders the table the doc carries. Tested so the doc's table and the issue's table never drift.
- `SpikeLog`: `Logger(subsystem: "com.brennanmke.AirPlaySpike", category: "Spike")` plus an appending text file `<logDir>/spike-<yyyyMMdd-HHmmss>.log`, each line `HH:mm:ss.SSS <engine> <message>`. `mark(_ n: Int)` writes `MARK n` lines for the user's ear-timed events. Default `logDir` is `~/Library/Logs/AirPlaySpike/`; `--log-dir` overrides.

### 3. The app (`Sources/AirPlaySpikeApp.swift`)

AppKit `NSApplicationDelegate` + one SwiftUI `NSHostingView` (or plain AppKit; implementer's choice, keep it one file, roughly 250 lines). One window, "AirPlaySpike":

- Top row: engine segmented control (five kinds; switching tears the current engine down first, so at most one plays), "Open Files…" (`NSOpenPanel`, multiple, audio types), "Use tick file" (loads `tick-120s.wav`), the **`AVRoutePickerView`** itself (`isRoutePickerButtonBordered = true`, delegate logs `routePickerViewWillBeginPresentingRoutes` / `DidEndPresentingRoutes`), and a "Present picker" button that walks `picker.subviews` for an `NSButton` and calls `performClick(nil)`, logging `picker button: found|missing`. That is #0051's fragile workaround, tested here once so #0051 knows whether it exists on this macOS.
- Transport row: Play, Pause, Seek +30 s, Next, Volume slider (0…1, sets `engine.volume`), Tap gain slider (0…1, enabled for A+tap only; its changes are logged with the engine time), Mark button (increments and logs `MARK n`), Snapshot button (writes the status pane and `probe()` to the log and the pasteboard).
- Status pane, refreshed at 4 Hz by a main-actor timer: engine, `currentTime`, `rate`, `leadSeconds` with its classification and max, `AVRouteDetector.multipleRoutesDetected` (detector enabled while the window is visible, disabled on close), CoreAudio default output name/transport, `lastCommand`, tap: last processed PTS and RMS, renderer `isReadyForMoreMediaData`, `playbackState`. A **tick flash**: the pane's background flashes for 100 ms whenever `currentTime` crosses an integer second, so the user can judge by eye and ear whether the engine's clock leads the HomePod (section 6, step 9).
- B-dev device menu: a popup of `CoreAudioOutputs.list()` showing `name (transport)`, refreshed on open; selecting one sets the UID for the next `play()`.
- Launch arguments: `--log-dir <path>`; `--smoke`: no window interaction needed. Smoke mode: create the window, the picker and the detector (detection enabled, then disabled), write the tick file, then for each `EngineKind` construct the engine, `load([tick])`, `attach(to:)`, `probe()`, `detach()`, `teardown()`, logging one line per step, then write `smoke: ok (5 engines)` to `<logDir>/smoke.log` and `exit(0)` after 2 s. A hard watchdog `exit(2)` at 8 s guards a hang. Smoke mode never calls `play()` or `setRate`, never sets `audioOutputDeviceUniqueID`, and never enqueues a buffer. The VM proves that: the guest is muted and the host check must stay silent.

### 5. Tests (`SpikeKitTests`, Swift Testing, all silent, no engine instances)

1. `SampleBufferPackagerTests.packagesInterleavedFloat32`: a 0.1 s 48 kHz stereo `AVAudioPCMBuffer` with a known ramp → `CMSampleBuffer` with `numSamples == 4800`, `presentationTimeStamp` equal to the given PTS, `duration == 0.1 s`, format description ASBD rate 48 000 / 2 ch / interleaved Float32, and the block buffer's first and last frames equal to the ramp's (proves the copy, not a dangling pointer).
2. `SampleBufferPackagerTests.consecutiveBuffersAreContiguous`: two buffers from `PCMSource` over a 0.5 s generated file: second PTS == first PTS + first duration; across two files with different rates (44.1 k then 48 k) the timeline stays monotonic and the second file's first PTS equals the first file's duration.
3. `LeadMeterTests.classifiesSecondsAndMinutes`: 3 s → `.seconds`, 95 s → `.minutes`, max tracked, `maxInLast(seconds:)` drops old samples.
4. `TestToneTests.writesTicksOnIntegerSeconds`: write a 3 s file to a temp dir, read it back with `AVAudioFile`, assert the left channel's peak in the 20 ms after t = 1.0 s and 2.0 s is above 0.5 and the right channel's is below 0.2, duration 3 s, 48 kHz stereo.
5. `ResultsSheetTests.markdownHasOneRowPerCheckAndOneColumnPerEngine`: header lists the five engines in `EngineKind.allCases` order, one row per `Check`, an untested sheet renders `untested` in every cell; setting one cell changes exactly one cell.
6. `CoreAudioOutputsTests.listsAtLeastTheDefaultDevice` — **only if** it is read-only and passes headless in the guest (the guest has an Apple Virtual Sound Device); print the list, assert non-empty, and assert no transport string is empty. If the guest reports no device, skip with a message rather than fail.

No test constructs `QueuePlayerEngine`, `SampleBufferEngine`, the tap or the picker; those are covered by `--smoke` in the guest.

### 6. Hand test on the host (user only, HomePods)

The user runs this on the host with their own build; subagents never build, launch or play on the host. Before starting: two HomePods on the network (a stereo pair counts as one route; a second, separate HomePod or Apple TV is needed for the two-speaker checks), the Mac's system output set to the built-in speaker, Music.app quit, and a terminal with

```bash
/usr/bin/log stream --predicate 'subsystem == "com.brennanmke.AirPlaySpike"' --style compact
```

Build and run: `xcodegen generate --spec Spikes/AirPlaySpike/project.yml`, open `Spikes/AirPlaySpike/AirPlaySpike.xcodeproj`, run the `AirPlaySpike` scheme. Load the tick file (or a few MP3/AAC/FLAC files of your own; note which). Run the picker checks once, then the per-engine table for each of the five engines, in order A, A′, A+tap, B, B-dev; stop an engine's run early if it fails check 2, mark the rest `n/a`. ### 9. Risks

- **`open -W` in a headless guest.** The existing `app-launch` step proves `open` reaches the guest's WindowServer; `-W` plus a self-quitting app is the same path. If `-W` never returns because LaunchServices treats the second launch as a reopen, drop `-n`, or run the binary directly (`…/Contents/MacOS/AirPlaySpike --smoke …`) and keep the grep as the pass condition.
- **Engine construction opening an output device in smoke mode.** `AVQueuePlayer` with items at rate 0 and a renderer added to a synchronizer at rate 0 do not start I/O; attaching the tap to an item may run the tap's `prepare` callback (format only). If the host check ever reports `Starting IO` on a spike run, move the engine construction behind a `--smoke-engines` flag off by default and note it; never silence the check.
- **Swift 6 and the C tap.** The tap callbacks must be `@convention(c)` static functions with no actor isolation and no captured context other than `clientInfo`; the box's fields are plain atomics (`import Synchronization` `Atomic<…>` on macOS 15+, or `os_unfair_lock` since the target is 14). The `requestMediaDataWhenReady` closure runs on `feedQueue`; `PCMSource` is the only object it touches.
- **Deprecation warnings** from the classic renderer API under the macOS 27 SDK: expected, not errors; do not enable warnings-as-errors for the spike.
- **The picker is useless without routes.** In the guest there are no AirPlay routes, so smoke mode can only prove construction and `multipleRoutesDetected == false`; everything about routing is the hand test by design.
- **Reading CoreAudio from a test.** `CoreAudioOutputsTests` reads only; the guest's virtual device has no host path. If it proves flaky headless, delete the test rather than add retries.
- **The user's time.** Five engines × twelve steps is an hour. The order (A, A′, A+tap, B, B-dev) front-loads the documented path; if A and B both pass step 2, A′ and B-dev can be shortened to steps 2 and 4.
