# 0050 — Per-app AirPlay 2 routing on macOS is unproven for each playback stack

## Description

Before choosing an architecture, build the Phase 0 spike from [docs/airplay-macos-handoff.md](../docs/airplay-macos-handoff.md): a minimal macOS app (no skins) with an `AVRoutePickerView` and four toggleable engines — `AVQueuePlayer` with the picker's `player` set (A), the same with `player` nil (A′), A with an `MTAudioProcessingTap` doing gain + RMS (A+tap), and `AVSampleBufferAudioRenderer` + synchronizer playing decoded PCM with `player` nil (B).

## Acceptance criteria

- For each engine, on the current macOS, recorded in `docs/airplay-spike-results.md`: whether the picker lists HomePods and allows multiple selection; whether audio moves off the Mac with one HomePod while other system audio stays local; whether two HomePods play in sync; requested-ahead duration local vs AirPlay (last enqueued PTS minus `currentTime()`; minutes means enhanced buffering is active); whether playback survives 10 s with Wi-Fi off; whether HomePod touch and "Hey Siri, pause" reach `MPRemoteCommandCenter`; when the tap runs relative to audible output; whether the synchronizer time includes AirPlay latency; how `volume` maps to HomePod volume.
- The long-form check: grep the installed SDK's `AVAudioSession.h` for macOS availability of `routeSharingPolicy` / `setRouteSharingPolicy:error:`, and test the Info.plist key `AVInitialRouteSharingPolicy` = `LongFormAudio`. Record the result.
- The doc ends with a recommendation: A, B, or C, with the reasons.

## Notes

The spike lives outside the shipping targets (for example `Spikes/AirPlaySpike/`, its own XcodeGen spec) and is not built by `scripts/run-tests-vm.sh`. It plays audio to real speakers, so it is run by hand by the user on the host; the VM has no AirPlay path. Known forum issue: on macOS 12.4, with `player` set, choosing a HomePod was ignored.
