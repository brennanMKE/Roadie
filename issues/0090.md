# 0090 — Some playlist entries do not survive Save then Load

| | |
|---|---|
| **Status** | open |
| **Module** | AudioCore |
| **Platform** | macOS |
| **First seen** | 2026-10-19 |

## Description

Found in the #0082 review (commit d93f918), not blocking there:

- A relative entry whose name has a colon after a letters-only prefix is read as a URL scheme and skipped as a stream. Finder shows `AC/DC - x.mp3`, which is `AC:DC - x.mp3` on disk, so it is written and then dropped on load.
- A relative file name that starts with `#` is written as-is and read back as an M3U comment.
- UTF-16 playlists (with a BOM) are not detected.

Expected: Save then Load round-trips every local file the queue held, and UTF-16 M3U/PLS files load.

## Plan

All three are in `PlaylistFile` (AudioCore). The app's save path (`App/PlayerModel+PlaylistFiles.swift`) and `LocalTrackLoader` call `serialize` / `format` / `parse` / `resolve` and need no changes.

**Files**

- `Packages/PlayerKit/Sources/AudioCore/PlaylistFile.swift`
- `Packages/PlayerKit/Tests/AudioCoreTests/PlaylistFileTests.swift`

**1. Colon names read as URL schemes (reader, plus a writer guard)**

- Reader, in `resolve`: treat a location as a URL only if it starts with `scheme://` (RFC 3986 scheme: a letter, then letters, digits, `+`, `-` or `.`, case-insensitive) or with `file:` (so `file:/abs/x.mp3` still works). Everything else is a path, so `AC:DC - x.mp3` and `AC:DC/Album/01.mp3` resolve relative to the playlist's folder. A small private helper (`urlScheme(of:) -> String?`) keeps `resolve` readable. Streams always carry `://` (`http`, `https`, `mms`, `rtsp`, `icy`, `uvox`…), so they are still skipped with "streams are not supported", and `file://` still resolves as before. Leave the single-letter case (`C:\…`) as it is today; Windows drive paths are out of scope.
- Writer, in `serialize`: when a path is written relative (it had the playlist folder as prefix) and its first path component contains `:`, write it as `./<path>`. That keeps the file readable by players (and older SkinAmp builds) that use the "anything before a colon is a scheme" rule. Absolute paths start with `/` and need nothing. `./` relative entries are read by Winamp, VLC, foobar2000 and mpv, and our reader already drops `./` through `standardizedFileURL`.

**2. Names starting with `#` (writer)**

- A `#` line is a comment in every M3U reader, so this can only be fixed on write: in `serialize`, if the written relative path starts with `#`, write `./<path>`. The same helper does both checks: prefix `./` when the relative path starts with `#` or its first component has a `:`. Leading whitespace is cheap to add to the same rule (the parser trims lines); trailing whitespace stays out of scope.
- Apply the escape in both formats. PLS has no comment problem (`File1=#x.mp3` parses fine), but the colon problem applies, and one rule keeps the code simple.
- The reader does not change for `#`. Playlists already saved by d93f918 with a bare `#name` line will still lose that entry; note this under Gotchas, don't try to guess.

**3. UTF-16 with a BOM (reader)**

- In `decode`: after the UTF-8 BOM check, if the data starts with `FF FE`, drop the BOM and decode `.utf16LittleEndian`; if `FE FF`, `.utf16BigEndian`. If that decode returns nil (odd byte count, bad surrogates), fall through to the existing UTF-8 / Windows-1252 / lossy path. Update the doc comment. `format(for:data:)` goes through `decode`, so `[playlist]` sniffing works for UTF-16 PLS too. BOM-less UTF-16 and UTF-32 stay out of scope (note it). The writer keeps writing UTF-8 without a BOM.

**Tests** (Swift Testing, in `PlaylistFileTests`; existing tests should pass unchanged, since `sub/a.mp3` and `a.mp3` get no prefix)

- `resolvesColonNamesAsRelativePaths`: `AC:DC - x.mp3`, `AC:DC/Back in Black/01.mp3`, `./AC:DC - y.mp3`, `a:b.mp3` resolve under `/tmp/x/`.
- `skipsOnlySchemeURLsAsStreams`: `http://…`, `HTTPS://…`, `mms://…`, `rtsp://…`, `icy://…` are skipped as streams; `file:///abs/d.mp3` and `file:/abs/e.mp3` resolve to files.
- `serializeEscapesHashAndColonNames`: in M3U and PLS, `/tmp/x/#1 Hit.mp3` → `./#1 Hit.mp3`, `/tmp/x/AC:DC - x.mp3` → `./AC:DC - x.mp3`, `/tmp/x/AC:DC/01.mp3` → `./AC:DC/01.mp3`; `/tmp/x/sub/#b.mp3` stays `sub/#b.mp3`; `/elsewhere/AC:DC.mp3` and `/elsewhere/#c.mp3` stay absolute and unprefixed.
- `roundTripsHashAndColonNames`: the paths above through `serialize` → `format` → `parse` → `resolve`, for `list.m3u`, `list.m3u8` and `list.pls`, come back identical and in order.
- `decodesUTF16WithBOM`: an M3U with `#EXTINF` and `Björk/01 Hunter.mp3`, encoded as UTF-16LE with `FF FE` and as UTF-16BE with `FE FF`, parses to the same entries as the UTF-8 version.
- `plsInUTF16IsDetected`: a UTF-16LE `[playlist]` file named `list.m3u` gets `.pls` from `format(for:data:)` and parses its `File1`.
