# 0117 — Changing the Output doesn't move what's playing

| | |
|---|---|

## Description

Reported by the user on 0.1.0-2671617. While a Music Assistant track plays on This Mac, choosing Kitchen (a HomePod) in the Library toolbar's Output menu doesn't move playback. It keeps playing where it was; only after stopping, and possibly starting another song, does the new output take effect.

## Expected behavior

- Choosing another output while something plays moves the current queue there right away, at the same position (Music Assistant's queue transfer), and the old output stops.
- The same applies in both directions: This Mac ↔ a speaker, and speaker ↔ speaker.
- If nothing is playing, the choice only sets where the next play goes, as today.

## Root cause

Choosing an output only assigned `PlayerModel.selectedOutput`, whose `didSet` re-subscribed now-playing. Nothing was sent to Music Assistant, so the queue stayed on the old player; no code sent `player_queues/transfer`.

## Fix

As planned. `MusicBackend.transfer(from:to:autoPlay:)` (default throws `.unsupported(.remoteOutputs)`); `MARequest.transferQueue`; `MusicAssistantBackend.transfer` resolves the source's active queue (else its player id) and the target player, and sends no extra `stop`. `OutputMove.decide` (LibraryBrowser) picks select / transfer(autoPlay) / keepLocal. `PlayerModel.selectOutput(_:)` applies it, chaining transfers through `outputMoveTask`; the Output menu calls it. Fallback reassignments still set `selectedOutput` directly.

Divergence: `transport` needs the full `MAPlayer` (volume checks), so a private `player(for:)` returns the player and the internal `playerID(for:)` wraps it; `play` and `transport` both use them with no behavior change.

## Plan

### Root cause

Choosing an output only assigns `PlayerModel.selectedOutput` (`App/Browser/OutputPickerView.swift`, `entry(_:)`). Its `didSet` just calls `observeNowPlaying()`, so the windows start following the new player's now-playing while nothing is sent to Music Assistant. The queue stays on the old player (the Sendspin player behind This Mac, or the old speaker) and keeps playing there. Only the next `playFromLibrary` or transport command goes to the new id. No code anywhere sends `player_queues/transfer`, the server command that moves a queue (`docs/ma-protocol/commands.json`: `source_queue_id`, `target_queue_id`, optional `auto_play`, scope `queues.control`). `MusicBackend` has no "move playback" operation either.

### Files

- `Packages/PlayerKit/Sources/MusicBackendKit/MusicBackend.swift`: new protocol requirement `transfer(from:to:autoPlay:)`, with a default that throws `.unsupported(.remoteOutputs)` so `FolderBackend` needs no change.
- `Packages/PlayerKit/Sources/MusicAssistantKit/MARequest.swift`: `MARequest.transferQueue(sourceQueueID:targetQueueID:autoPlay:)`.
- `Packages/PlayerKit/Sources/MusicAssistantKit/MusicAssistantBackend.swift`: implement `transfer`, plus a private `queueID(for:)` helper.
- `Packages/PlayerKit/Sources/MusicBackendStub/StubMusicBackend.swift`: record `.transfer`, and allow it to fail and be gated like the other methods.
- `Packages/PlayerKit/Sources/LibraryBrowser/OutputMove.swift` (new): the pure decision of what a user's output change does. 0118 extends it.
- `App/PlayerModel.swift`: new `selectOutput(_:)`, the only entry point for a user's choice.
- `App/Browser/OutputPickerView.swift`: the menu calls `player.selectOutput(device.id)` instead of assigning.
- Tests: `MARequestEncodingTests.swift`, `BackendTransportTests.swift`, `MusicAssistantThisMacTests.swift`, a new `LibraryBrowserTests/OutputMoveTests.swift`, `StubMusicBackendTests.swift`.

### Approach

1. **Request.**
   ```swift
   public static func transferQueue(sourceQueueID: String, targetQueueID: String, autoPlay: Bool) -> MARequest {
       MARequest(command: "player_queues/transfer", args: [
           "source_queue_id": .string(sourceQueueID), "target_queue_id": .string(targetQueueID),
           "auto_play": .bool(autoPlay)])
   }
   ```

2. **Protocol.** Add `func transfer(from source: OutputDevice.ID, to target: OutputDevice.ID, autoPlay: Bool) async throws` to `MusicBackend`. Document it as "moves the source output's queue, position included, to the target and stops the source." Add a default in an extension that throws `MusicBackendError.unsupported(.remoteOutputs)`.

3. **Music Assistant backend.**
   ```swift
   public func transfer(from source: OutputDevice.ID, to target: OutputDevice.ID, autoPlay: Bool) async throws {
       guard source != target else { return }
       try await guarded {
           let client = try requireClient()
           let sourceQueue = try await queueID(for: source, client: client)
           let targetQueue = try await playerID(for: target)   // thisMac → resolveLocalPlayer(), else requireOutput
           guard sourceQueue != targetQueue else { return }
           _ = try await client.call(.transferQueue(sourceQueueID: sourceQueue, targetQueueID: targetQueue, autoPlay: autoPlay))
       }
   }
   /// The queue that plays on `output` now: its active queue (a speaker synced into a group plays the group's), else its own.
   private func queueID(for output: OutputDevice.ID, client: MusicAssistantClient) async throws -> String {
       let playerID = try await playerID(for: output)
       let json = try await client.call(.activeQueue(playerID: playerID))
       if !json.isNull, let queue = try? json.decode(as: MAPlayerQueue.self) { return queue.queueID }
       return playerID
   }
   ```
   `playerID(for:)` is the mapping `play()` and `transport()` already do inline: This Mac → `resolveLocalPlayer().playerID` (which throws `thisMacNotRegisteredText` or the pending/unavailable texts), any other id → `requireOutput(output).playerID` (which throws `unknownOutput`). Factor it out and reuse it in `play` and `transport`, with no behavior change. MA's transfer stops the source itself. Send no extra `stop`: it could hit the target when both sit in one group.

4. **Decision (`OutputMove`, LibraryBrowser).** It is pure so it can be tested without the app.
   ```swift
   public enum OutputMove: Equatable, Sendable {
       case select                       // nothing to move: only where the next play goes
       case transfer(autoPlay: Bool)     // Music Assistant moves the queue
       case keepLocal                    // AudioCore's own queue plays on This Mac; it can't move to a speaker
       public static let localStaysText = "Local files keep playing on This Mac."
       public static func decide(from source: OutputDevice.ID, to target: OutputDevice.ID,
                                 sourceState: NowPlaying.State, thisMacFeed: ThisMacFeed) -> OutputMove {
           guard source != target else { return .select }
           switch sourceState {
           case .stopped: return .select
           case .playing, .loading, .paused:
               if source == OutputDevice.thisMacID, thisMacFeed == .local { return .keepLocal }
               return .transfer(autoPlay: sourceState != .paused)
           }
       }
   }
   ```
   A paused queue moves too, with `auto_play: false`, so Play on the new output resumes it. That reading of "what's playing" is a deliberate choice.

5. **App (`PlayerModel.selectOutput`).**
   ```swift
   /// The Output menu's choice (#0117): moves what plays to `target` (Music Assistant's queue transfer), else only selects it.
   func selectOutput(_ target: OutputDevice.ID) {
       let source = selectedOutput
       guard target != source else { return }
       let state = nowPlaying.output == source ? nowPlaying.state : .stopped
       let move = OutputMove.decide(from: source, to: target, sourceState: state, thisMacFeed: thisMacFeed)
       // Moving onto This Mac: Music Assistant feeds it from now on, so the windows follow its stream (#0109/#0114).
       if case .transfer = move, target == OutputDevice.thisMacID { applyFeed(.musicAssistantPlayRequested) }
       selectedOutput = target
       switch move {
       case .select: break
       case .keepLocal: post(StatusNotice(text: OutputMove.localStaysText))
       case .transfer(let autoPlay):
           let remote = router.remote, previous = outputMoveTask
           outputMoveTask = Task { [weak self] in
               await previous?.value                       // quick re-picks transfer in order
               do { try await remote.transfer(from: source, to: target, autoPlay: autoPlay) } catch {
                   guard let self else { return }
                   if target == OutputDevice.thisMacID {
                       self.applyFeed(.musicAssistantPlayFailed(isStreaming: self.sendspinController.sendspin.isStreaming))
                   }
                   self.showBackendFailure(error)
               }
           }
       }
   }
   ```
   `@ObservationIgnored private var outputMoveTask: Task<Void, Never>?`. Moving from This Mac to a speaker needs no feed change: the Sendspin stream ends and `onStreamStopped` hands This Mac back to `.local`, as it does today. The fallback assignments (`activeMusicAssistantServerChanged`, `refreshOutputs` reconcile) keep assigning `selectedOutput` directly and never transfer, because the old server or player is gone. In `OutputPickerView.entry`, replace `player.selectedOutput = device.id` with `player.selectOutput(device.id)`.

6. **For 0118.** `selectedOutput` stays the single routing id: the leader, where transport, now-playing and `transfer` go. 0118 adds the members on top of it. It should then:
   - give `OutputMove` a group case (`players/cmd/set_members` with `player_ids_to_add` / `player_ids_to_remove` on the leader);
   - call `selectOutput` only when the leader changes, so a leader change transfers first and then regroups;
   - leave the leader alone when a non-leader is checked or unchecked, so the track never restarts.

   Keep `transfer` on `MusicBackend` (not app-only) so 0118's `setMembers` can sit beside it with the same default-throws pattern.
