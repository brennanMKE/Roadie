## Description

Found in review of #0100. `LocalTrackLoader.expandPlaylists` now expands nested playlists in place, stopping cycles (ancestor chain only) and nesting deeper than 8 levels. A playlist that is not a cycle but repeats nested playlists is still unbounded in total work: if `p1.m3u` lists `p2.m3u` ten times, `p2.m3u` lists `p3.m3u` ten times, and so on for 8 levels, the loader reads about 10^7 playlist files and appends up to 10^8 URLs before any track loads, so import hangs and memory grows. Diamonds are meant to expand more than once (Winamp does), so the cycle check can't catch this.

Expected:

- A cap on total work during one expansion, for example at most a fixed number of nested playlist reads (say 256) and/or a fixed number of expanded entries (say 100,000). Past the cap, remaining nested playlists or entries are reported as skipped with a clear reason (for example "too many playlist entries") instead of being expanded.
- Ordinary nesting (#0100's tests, including a small diamond) is unaffected.
- Tests: a fan-out playlist tree written to a temp folder stops at the cap, returns quickly, and reports the skip; a small diamond still expands twice.

## Resolution notes

> 🟢 Resolved 2026-10-19 — Nested playlist expansion now stops at 256 playlist reads and 100,000 entries per call, reporting the rest as skipped, so a fan-out tree returns quickly while diamonds and ordinary nesting expand as before.

## Root cause

`LocalTrackLoader.expandPlaylists` bounded only cycles (ancestor chain) and depth (8). A non-cyclic fan-out tree (each level listing the next many times) has exponential total work, so import read millions of playlist files and appended up to 10^8 URLs.

## Fix

Per the plan: added `maxPlaylistReads = 256` and `maxPlaylistEntries = 100_000`, made `expandPlaylists` internal with defaulted `maxReads`/`maxEntries`. The read check sits after the cycle/depth checks and counts top-level reads; refused playlists are skipped as "too many nested playlists". The entry check runs before each entry (nested references count); on exhaustion the current playlist is skipped as "too many playlist entries", ancestors unwind silently, and later top-level playlists are skipped with the same reason while plain URLs pass through. One `logger.warning` per budget when first exhausted. Doc comment extended. No deviation.

Approach (one budget per `expandPlaylists` call, so per `load`):

1. **Constants.** Next to `maxPlaylistDepth`, add `static let maxPlaylistReads = 256` and `static let maxPlaylistEntries = 100_000` (internal, not private, so tests can name them).
2. **Testable signature.** Make `expandPlaylists` internal (drop `private`) and give it defaulted limits: `static func expandPlaylists(_ urls: [URL], maxReads: Int = maxPlaylistReads, maxEntries: Int = maxPlaylistEntries) -> (items: ..., skipped: ...)` (same return type #0101 left). `load` keeps calling `expandPlaylists(urls)`.
3. **Read budget.** Add `var reads = 0`. In `expand`, after the cycle and depth checks and before `Data(contentsOf:)`: `if reads >= maxReads { skip(playlist, "too many nested playlists"); return }`, then `reads += 1`. Every playlist read counts, top-level ones included. Plain entries keep being appended after the read budget runs out; only further playlist reads are refused, each reported once where it's referenced. That's bounded: once reads stop, the only entries left are those of at most `maxReads` already-parsed playlists, and the entry budget caps them too.
4. **Entry budget.** Add `var entries = 0` and `var entriesExhausted = false`. In the `for entry in entries` loop (rename the local `entries` array to e.g. `parsed` to avoid the clash), at the top of each iteration: `if entries >= maxEntries { entriesExhausted = true; skip(playlist, "too many playlist entries"); return }`, then `entries += 1`. Every entry processed counts: tracks, nested-playlist references and stream skips alike. At the top of `expand`, `if entriesExhausted { return }` with no record (the parents unwind silently; one record names the playlist where the cap hit). In the top-level `for url in urls` loop, a playlist URL met after `entriesExhausted` gets `skip(url, "too many playlist entries")` and is not expanded; non-playlist URLs still pass through as `(url, nil)`.
5. **Doc comment.** Extend the `expandPlaylists` comment: at most `maxPlaylistReads` playlist reads and `maxPlaylistEntries` entries per call; past them, further playlists are reported as "too many nested playlists" / "too many playlist entries". A diamond (two playlists listing the same one) still expands every time; only ancestors count as cycles.
6. Log once (`logger.warning`) when either budget first runs out, with the count, besides the per-skip lines `skip` already writes.

Semantics the tests below rely on (follow them exactly so the counts match): the read check comes after the cycle/depth checks; top-level reads count; the entry check comes before handling each entry; nested-playlist references consume an entry.

Tests (Swift Testing `@Test` in `LocalTrackLoaderTests`; reuse `makeTempDir`/`writeWAV`; call `LocalTrackLoader.expandPlaylists` directly via `@testable` where noted, so no tracks are decoded; `PlaylistFile.resolve` doesn't check existence, so leaf entries needn't exist for those):

- `fanOutPlaylistTreeStopsAtReadCap` — the issue's tree with default limits: `p1.m3u` … `p7.m3u`, each listing `p(n+1).m3u` ten times, and `p8.m3u` listing `t.wav` once (only 8 files on disk). Time `LocalTrackLoader.expandPlaylists([p1])` with `ContinuousClock`. Expect `items.count == 225`, `skipped.count == 55`, every reason `"too many nested playlists"`, and elapsed `< .seconds(10)` (generous for the VM; without the cap it never finishes). Derivation (depth-first, reads counted at open): p1–p5 = 5 reads; each p7 subtree = 11, each p6 subtree = 111; p6#1 and p6#2 → 227; p6#3 = 228; p7#1, p7#2 → 250; p7#3 = 251; five p8 → 256. p8 reads (= items) = 100 + 100 + 10 + 10 + 5 = 225. Refusals: 5 (p7#3) + 7 (p6#3) + 7 (p5) + 9 × 4 (p4, p3, p2, p1) = 55.
- `playlistReadCapSkipsFurtherPlaylists` — small cap: `top.m3u` lists `a.m3u` four times, `a.m3u` lists `t.wav`. `expandPlaylists([top], maxReads: 3)`: items are `t.wav` twice (top, a, a = 3 reads), `skipped.map(\.reason) == ["too many nested playlists", "too many nested playlists"]`, both URLs `a.m3u`.
- `playlistEntryCapStopsExpansion` — `top.m3u` lists `inner.m3u`, `x1.wav`, `x2.wav`; `inner.m3u` lists `i1.wav` … `i5.wav`; `other.m3u` lists `o.wav`. `expandPlaylists([top, other, z.wav], maxEntries: 5)`: item URLs' last path components `["i1.wav", "i2.wav", "i3.wav", "i4.wav", "z.wav"]` (top's `inner` reference is entry 1, i1–i4 are 2–5, i5 hits the cap); `skipped` is `[inner.m3u: "too many playlist entries", other.m3u: "too many playlist entries"]` in that order.
- `diamondPlaylistExpandsEachTime` — end to end through `load`: `top.m3u` lists `a.m3u`, `b.m3u`; both list `shared.m3u`; `shared.m3u` lists `s.wav` (a real 0.2 s WAV). Expect titles `["s", "s"]` and `skipped.isEmpty`.
