## Root cause

Four separate causes, one per test. Three were test bugs; one was a real race in the app.

- **`primaryActionDownloadsIndexesAndApplies` (a real race in `MuseumBrowserModel`).** `show(_:for:)` starts a badge task (`badge(shown)`) for the loaded page. The test's `load` returns once `phase == .loaded`, while that lookup can still be suspended in `lookup()` / `skins(md5s:)`. If the download finished first (setting `downloaded[md5]`) and the lookup returned afterwards, its answer had been taken before the skin was indexed. It had no record for that md5, so the "left the index" branch (#0131) cleared `downloaded[md5]`. **What users saw:** a skin downloaded from the Skin Museum while the page's badge lookup was still running could lose its Downloaded badge right after it was applied, and the next click would download it again.
- **`reconnectRefetchesAndKeepsTheStream` (test ordering).** `MANowPlayingWatch.refetch()` suspends between sending `players/get` and applying the answer. The test pushed its `paused` event once the new socket had *sent* `players/get`, not once the request had been answered. Under load, the refetch's answer (the stub always says `playing`) was applied after the event. The same 2 s clock advance also wakes the eager poll, which can start a second refetch that races the event the same way. The model is right to apply a refetch that is newer than an event, so the bug was in the test.
- **`playNextExpandsAnAlbumIntoUpNext` (test ordering).** `BackendFixture` uses `MissingFileResolver`, so the track queued by `.replace` fails asynchronously. If that failure landed after `.next` had queued the album, `Player.trackFailed` saw a next track and skipped to it, so `currentIndex` became 1. `playTrackByIdAndAppend` had the same race with `.append`.
- **`decidedEarlyCancelsTheRest` (test support).** `FakeInfo.waitUntil` took the URL it records as cancelled from `calls.last`. When a's and b's fetches interleaved (b appends its URL, then a appends its URL, then b's wait reads `calls.last`), b's hang recorded **a** as cancelled. `fake.cancelled.contains(b)` then never became true.

## Fix

- `MuseumBrowserModel`: each finished download increments a `downloadClock` and stamps its md5 (`downloadStamps`). `badge` reads the clock before it suspends and leaves alone every md5 stamped after that, so a newer download keeps its badge. A Debug-only `badgesInFlight` counter lets tests wait for lookups to finish. `StubSkinIndex.gateMD5Lookups()` / `releaseMD5Lookups()` hold `skins(md5s:)`. New regression test `downloadFinishingDuringABadgeLookupKeepsItsBadge` forces the bad ordering every time.
- `reconnectRefetchesAndKeepsTheStream`: `makeBackend` / `connectedBackend` take `extraTransports` for reconnects. The reconnect socket answers with the title "Reconnected Song". The test waits for that title (so the reconnect refetch has finished) and for `settled(rig)` (the poll is asleep) before it pushes the event.
- `playNextExpandsAnAlbumIntoUpNext`, `playTrackByIdAndAppend`: after the `.replace` play, wait until `player.state == .stopped && player.errorMessage != nil` before queueing more.
- `FakeInfo.waitUntil(_ url:_:)` takes the fetch's own URL instead of reading `calls.last`.

The Museum and reconnect changes are the uncommitted fix from worktree agent-a881c24d5a79cb288 (base facdd32), ported unchanged: none of those five files had changed on main since. Every fix waits on a real condition; no timeout was made longer. The other rows still have no fix and remain open: `installedBridgePublishesAndClearsInfoCenter`, the VM guest-agent/golden-image transients, app-quicklook and `ProgressivePlayerRenderTests`, tracked in #0247.
