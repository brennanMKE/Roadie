## Root cause

Nothing drove Jump to File. Writing the tests turned up a second gap: the panel's `NSTableView` rows aren't in the accessibility tree. Run 20261029-200200-41710's dump shows `jump.table` with no children, while the screenshot shows the rows drawn. So `jump.row.N` can't be found by XCUITest, and VoiceOver can't read the rows either. That is filed as #0249 and not fixed here.

## Fix

Commits `ee46e49` (the tests), `b72845f` (the review fixes) and `ec1b106` (merge of main, aa716a0, keeping the probe's `jump` and #0207's `eq`, plus the re-review nit: wait for table row 0 to be selected before the click).

- `Tests/RoadieUITests/JumpToFileUITests.swift`: the six planned tests.
- **Probe workaround:** with the rows unreachable, `JumpToFilePanel.probe` reports the panel's state while it is on screen (nil when closed): its results as playlist rows, the selected rows, the empty-state text, the Queue button's title and the row height (spacing included). `TestProbe` gains `jump`, set only in UI-test mode (`configuration.isUITest`), and `ProbeState.JumpProbe` decodes it. The tests read results, selection and open/closed from it. The double-click aims at table row 1 of "tone c"'s [0, 3, 5]: the table's top plus 1.5 row heights (the probe's `rowHeight`). A first click there must select playlist row 3 (`jump.selected == [3]`), then the double-click must play row 3: `doubleAction` plays the selection and ignores the clicked row, so a miss plays row 0 and a wrong row plays row 5. `jump.search`, `jump.empty` and `jump.queue` (its Queue/Dequeue title, read from the accessibility element) are used through accessibility. A play is checked as the row current *and* `state == "playing"`. When #0249 is fixed, the tests can assert `jump.row.N` too.
- §5.6 rows in `docs/design/test-automation.md` updated to what the tests cover, with a note that the rows and selection come from the probe (`jump`, #0249) and the search field, empty text and Queue button through accessibility.

Departures from the plan:

- **7 fixture rows, not 9:** Other Artist's `Single.m4a` (tagged Tone C), Tone A–D, `05 Tone E`, `06 Tone F` (`scripts/make-test-library.sh`).
- **Substring-matching queries:** `JumpToFileIndex` needs each word as a substring of "artist - title", the album or the file name. So "tone b" lists rows 0–4 ("b" in "Tone Album"), "tone e" lists every row, and "tone c" lists rows 0, 3 and 5 (".flac"). The tests use queries chosen so the expected row is unambiguous: "02" → row 2 (Return), "tone c" → [0, 3, 5] with table row 1 double-clicked → row 3, "05" → row 5 (Queue). `typingFilters` checks "tone c" → [0,3,5], "single" → [0] and "zzz" → none with "No matches". There is no "other" title, so "single" replaces the plan's "other". "Tone A" is also in "Tone Artist", so rows are looked up by "- Tone A" and the like.
- The plays use rows 2 and 3 (2.0–2.5 s), since Tone D–F are 0.5–0.75 s and auto-advance before a check.
- Queue keeps the panel open (`JumpToFilePanel.queueSelected`), and the test asserts that.
- No `--expect-fail` run: this issue adds tests only and fixes no bug.

## Review notes

**Bounced 2026-10-29 (Opus, medium)** on commit `ee46e49`:

1. **Must fix.** The double-click check passed for the wrong reason. `table.doubleAction = #selector(playSelected)` plays the selection (or the first result) and ignores `clickedRow`, and "01" has one result, already selected, so a double-click anywhere passed.
2. **Must fix.** §5.6 of `docs/design/test-automation.md` didn't say the rows are read through the probe.
3. The Queue/Dequeue title was read from the probe, not from the button on screen.
4. `expectPlayed` didn't check that playback started (a short track can auto-advance).

**Fixes (second implementation pass):**

1. `returnPlaysTheChosenRow` types "tone c" (results [0, 3, 5], table row 0 selected), clicks table row 1 by coordinate (table top + 1.5 × the probe's new `jump.rowHeight`), asserts `jump.selected == [3]`, then double-clicks there and expects row 3 to play. A miss plays row 0 and a wrong row plays row 5, so both fail.
2. §5.6 gains a note: the rows and selection come from the UI-test probe (`jump`) because they aren't in the accessibility tree (#0249); `jump.search`, `jump.empty` and the Queue button are driven and read through accessibility.
3. `queueButtonAndEscape` reads the button's title from the `jump.queue` accessibility element (its title, else its label).
4. `expectPlayed` waits for `currentIndex == i` and `state == "playing"` together.

Run 20261029-203630-58033 after these fixes: 5 of 6 passed. `returnPlaysTheChosenRow` stopped at its fixture lookup before the click: rows 0 and 3 are both titled "Tone Artist - Tone C", so `queueIndex("- Tone C")` returned 0. The test now uses row 3 and checks that the "- Tone C" rows are [0, 3].
