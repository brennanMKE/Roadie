# 0086 — A compile error still costs a full VM run

| | |
|---|---|
| **Status** | open |
| **Module** | Tooling |
| **Platform** | macOS |
| **First seen** | 2026-10-19 |

## Description

The user asked for a build-only fast-fail stage in `scripts/run-tests-vm.sh`. Today every step runs regardless of earlier failures (`run_step` records the exit code and continues), and each `swift test` step builds and tests in one go. So code that does not compile still pays for the whole run: clone and boot, both package steps, the app build and the app checks, about 3 minutes, before the agent sees the error.

In the 2026-10-18 experiment, implementers sent code that did not compile into 7 VM runs (#0079 once, #0080 once, #0081 three times, plus test-code compile errors), roughly 15 minutes of the 57 minutes of implementation VM time. Across 2026-10-12 to 10-18 the logs show at least 19 runs that failed on a compile or build error.

Expected:

- A **build stage first**, in the guest: `swift build --build-tests` for SkinKit and for PlayerKit, then the app build (the app target has no unit tests, so `xcodebuild` is the only check that app code compiles). If any of them fails, the script prints the compiler errors (the `file:line:col: error:` lines) in its summary, skips the test and app-check steps, and exits non-zero, marking skipped steps as `SKIP` rather than `FAIL`.
- The test steps then reuse that build (`swift test --skip-build`, or equivalent), so a passing run is not slower than today.
- A **`--build-only`** flag that stops after the build stage, for an implementer to check that everything compiles before a full run. `issues/Issues.md` phase 2 says to use it after code changes and before the verification run; the verification that counts is still a full (fast-tier, see #0085) run.
- Never build on the host: the stage runs in the guest like every other step.

Coordinate with #0085 (fast/full tiers), which edits the same script and the same `Issues.md` sections.
