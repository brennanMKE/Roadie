## Description

The user asked for a build-only fast-fail stage in `scripts/run-tests-vm.sh`. Today every step runs regardless of earlier failures (`run_step` records the exit code and continues), and each `swift test` step builds and tests in one go. So code that does not compile still pays for the whole run: clone and boot, both package steps, the app build and the app checks, about 3 minutes, before the agent sees the error.

In the 2026-10-18 experiment, implementers sent code that did not compile into 7 VM runs (#0079 once, #0080 once, #0081 three times, plus test-code compile errors), roughly 15 minutes of the 57 minutes of implementation VM time. Across 2026-10-12 to 10-18 the logs show at least 19 runs that failed on a compile or build error.

Expected:

- A **build stage first**, in the guest: `swift build --build-tests` for SkinKit and for PlayerKit, then the app build (the app target has no unit tests, so `xcodebuild` is the only check that app code compiles). If any of them fails, the script prints the compiler errors (the `file:line:col: error:` lines) in its summary, skips the test and app-check steps, and exits non-zero, marking skipped steps as `SKIP` rather than `FAIL`.
- The test steps then reuse that build (`swift test --skip-build`, or equivalent), so a passing run is not slower than today.
- A **`--build-only`** flag that stops after the build stage, for an implementer to check that everything compiles before a full run. `issues/Issues.md` phase 2 says to use it after code changes and before the verification run; the verification that counts is still a full (fast-tier, see #0085) run.
- Never build on the host: the stage runs in the guest like every other step.

Coordinate with #0085 (fast/full tiers), which edits the same script and the same `Issues.md` sections.

## Root cause

`run_step` recorded each step's exit code and carried on, and each `swift test` step built and tested in one go. Nothing stopped the run at a compile error, so broken code still paid for every package step, the app build and the app checks before the error showed up, buried in a long log.

## Fix

As planned. `scripts/run-tests-vm.sh` has a build stage (`skinkit-build`, `playerkit-build`, then `app-build`, and with `--spike` `spike-pkg-build` and `spike-build`), run with `run_step … build`. A failed build sets `build_failed`; later test-stage steps record `skip` without running, `app-build` is skipped if a package failed, and the corpus block is wrapped so its copy never runs. Test steps use `swift test --skip-build` / `swift run --skip-build` (no fallback was needed). Steps are kept in `step_order` and the summary prints `PASS`/`FAIL`/`SKIP` in run order, then `BUILD  failed: …` and an `ERRORS` block (ANSI stripped, `file:line:col: error:` lines from the failed build logs, guest prefix removed, de-duplicated, first 30; tail of the log if none match). `Build complete!` was added to the summary grep. `--build-only` stops after the build stage, prints `BUILD-ONLY …` on success, sets the tier to `build-only` (`Tier:` log line, `tier.txt`) and rejects `--stress`, `--load`, `--launch`, `--corpus`, `--corpus-sample`, `--skins`, `--references` and `--full` with exit 2. `--help` now prints the whole leading comment block with `awk`.

Small deviation: when nothing was skipped (an `app-build` failure under `--build-only`), the line reads `BUILD  failed: fix the errors below and rerun` instead of "0 step(s) skipped". Run 3 below showed the "0 step(s)" form, which is now fixed.

### Approach

The script gets two stages. Stage 1 builds everything once. Stage 2 runs the tests and checks against those builds. If any build fails, stage 2 does not run. Every stage-2 step is reported as `SKIP`, the compiler errors are printed in the summary, and the script exits 1. Everything stays in the guest; the host still only exports the source and runs XcodeGen.

**Stage 1, the build stage**, in this order, each a `run_step` with its own log:

| Step | Command (in `~/src`) | Runs when |
|---|---|---|
| `skinkit-build` | `swift build --build-tests --package-path Packages/SkinKit` | always |
| `playerkit-build` | `swift build --build-tests --package-path Packages/PlayerKit` | always, even if `skinkit-build` failed (the packages are independent, so one run reports the errors in both) |
| `app-build` | the existing `xcodebuild … -derivedDataPath build/DerivedData build`, unchanged and moved up | only if both package builds passed; otherwise `SKIP` (it compiles the same package sources again in DerivedData and would only repeat their errors) |
| `spike-pkg-build` | `swift build --build-tests --package-path Spikes/AirPlaySpike/SpikeKit` | only with `--spike` |
| `spike-build` | the existing spike `xcodebuild … -derivedDataPath build/DerivedData-spike build`, moved up | only with `--spike` |

`swift build --build-tests` builds every target in the package, the `skintool` executable included, plus the test bundle (`<Pkg>PackageTests.xctest`, which also holds the Swift Testing tests). It builds into the package's default scratch path, `Packages/<Pkg>/.build/debug`, which is exactly where `swift test` looks. Both default to the debug configuration, and debug builds always enable testability (`@testable import`), so nothing else needs to match. The app build keeps `build/DerivedData`, and the checks keep reading `build/DerivedData/Build/Products/Debug/SkinAmp.app`. Nothing about those paths changes. The `$slow_env` / `$rt_env` variables **[#0085]** are read at runtime through `ProcessInfo`, so they belong on the test steps only, not on the builds.

**Stage 2, the tests and checks**, reusing stage 1:

- `skinkit-tests`: `${slow_env}swift test --skip-build --package-path Packages/SkinKit` (with `--skins`: `SKIN_SAMPLES_DIR=… ${slow_env}swift test --skip-build …`) **[#0085 for the prefix]**.
- `skintool` / `skintool-png` (with `--skins`): `swift run --skip-build --package-path Packages/SkinKit skintool …`. The binary is already built, and `--skip-build` stops a silent rebuild.
- `playerkit-tests`: `${rt_env}swift test --skip-build --package-path Packages/PlayerKit` **[#0085]**.
- `playerkit-stress` (`--stress`): unchanged. `stress-realtime-gapless.sh` already uses `swift test --skip-build` and sets `AUDIOCORE_REALTIME=1` itself, so it reuses the stage-1 build too.
- `app-plist`, `app-entitlements`, `app-quicklook`, `app-launch` (`--launch`): unchanged, after the package tests as today.
- `spike-tests` (`--spike`): `Spikes/AirPlaySpike/check-sdk.sh && swift test --skip-build --package-path Spikes/AirPlaySpike/SpikeKit`. `spike-smoke` is unchanged.
- `corpus-run` / `corpus-report` (`--corpus`): unchanged. They do their own **release** build of `skintool` (`run-skin-corpus.sh`), a different configuration, so it stays out of stage 1. Building it there would add a second full compile to every `--corpus` run, and a release-only compile error is rare. The guest-side corpus copy (`gx "cp -R …"`) sits outside `run_step`, so wrap the whole corpus block in `if (( ! build_failed ))`. When the build failed, record both corpus steps as skipped.

If `swift test --skip-build` turns out to reject the stage-1 build for a reason not foreseen here (for example, `error: no tests found` or a missing `.xctest`), fall back to plain `swift test`. After `swift build --build-tests` it is a null incremental build of a few seconds. Note the fallback in `## Fix`. The verification step below checks for this.

**Step bookkeeping.** Today `step_rc` is an associative array, and the summary loop `for name in ${(k)step_rc}` prints steps in hash order. Change it to:

```zsh
typeset -A step_rc; typeset -a step_order; build_failed=0
run_step() {   # name cmd [stage]
  local name=$1 cmd=$2 stage=${3:-test}
  step_order+=($name)
  if (( build_failed )) && [[ $stage == test ]]; then step_rc[$name]=skip; log "Skip: $name (build failed)"; return; fi
  log "Guest: $name"
  set +e; gx "set -o pipefail; cd $GUEST_SRC && { $cmd; } 2>&1 | tee $GUEST_RESULTS/$name.log"; step_rc[$name]=$?; set -e
  [[ $stage == build ]] && (( step_rc[$name] != 0 )) && build_failed=1
}
```

The build steps pass `build` as the third argument. `app-build` itself is gated explicitly: if either package build failed, record `skip` for it without running it. The `build_failed` check happens only after both package steps have run, so `playerkit-build` still runs when `skinkit-build` fails. `spike-pkg-build` and `spike-build` likewise run only if the main builds passed. Use a small `skip_step name` helper for these explicit skips and for the corpus pair. It appends to `step_order` and sets `step_rc[$name]=skip`. The summary loop then walks `step_order`:

- `0`: `==> PASS  name`
- `skip`: `==> SKIP  name (build failed)` (or `(--build-only)`, see below). It does **not** set `overall=1` by itself. The run fails because the build step failed.
- anything else: `==> FAIL  name (exit N)`, which sets `overall=1`.

After the PASS/FAIL/SKIP lines, if `build_failed`, print `==> BUILD  failed: N step(s) skipped; fix the errors below and rerun`.

**Compiler errors in the summary.** After the results come back, and only if `build_failed`, the host extracts the errors from the logs of the build steps that failed (`$RESULTS_DIR/{skinkit-build,playerkit-build,app-build,spike-pkg-build,spike-build}.log`, whichever exist with a non-zero rc):

1. Strip ANSI colour codes. SwiftPM writes `\e[1;31merror: \e[1;39m…` even when piped through `tee`, as seen in `build/vm-tests/*/playerkit-tests.log` from earlier compile failures. Use `sed $'s/\e\\[[0-9;]*m//g'`.
2. Keep lines matching `^/.*:[0-9]+:[0-9]+: error: `. Test logs also contain the word `error:` in test names, which is one more reason to read only the build logs.
3. Rewrite the guest prefix `/Users/admin/src/` to repo-relative paths, so `Packages/PlayerKit/Sources/PlexKit/PlexSettingsModel.swift:186:35: error: …` can be opened on the host as is.
4. De-duplicate while keeping order (`awk '!seen[$0]++'`), because xcodebuild and SwiftPM can repeat a diagnostic. Print the first 30 lines, indented, under `==> ERRORS  <total> compiler error(s) (first 30; full logs: <name>-build.log …)`.
5. If no `file:line:col: error:` line matched (a linker, manifest or package-resolution failure), print the last 15 non-blank lines of the failed build log instead, under `==> ERRORS  no file:line:col errors; tail of <name>.log`. The `error: SwiftCompile normal arm64 … failed with a nonzero exit code` lines from SwiftPM's build system are noise and are left out of the main list.

Also add `Build complete!` to the summary's `grep -hE` pattern, so a passing run shows the two package build times next to `** BUILD SUCCEEDED **`.

The run still pulls results, runs the host audio check and cleans up when the build fails. "Early exit" means stage 2 never starts: no tests, no Quick Look, no launch, no corpus copy. The results tar, the audio log check and `cleanup` cost a few seconds.

**`--build-only`.** New flag: `BUILD_ONLY=0`, `--build-only) BUILD_ONLY=1 ;;`.

- Runs stage 1 (including the spike builds with `--spike`), then goes straight to results and summary. Stage-2 steps are **not** listed as SKIP in this mode. A clean build-only run prints only PASS lines and then `==> BUILD-ONLY  everything compiles; no tests ran. This is not verification: run scripts/run-tests-vm.sh for that.` It exits 0 if every build passed and 1 otherwise, with the same `ERRORS` block.
- Rejected combinations, exiting 2 with `--build-only runs no tests; drop <flag>`: `--stress`, `--load`, `--launch`, `--corpus`, `--corpus-sample`, `--skins`, `--references`, and `--full` **[#0085]**. Allowed: `--head` and `--spike`.
- **[#0085]** `tier.txt` gets `build-only`, the start-of-run log says `Tier: build-only`, and the `TIER` summary line is replaced by the `BUILD-ONLY` line above.
- The host audio check still runs. It is cheap and keeps "exit 0" meaning the same thing in every mode.

**Header and help.** Add `[--build-only]` to the usage line and a description line: `--build-only  stop after the build stage (both packages with their tests, the app; with --spike the spike too): a quick compile check before a full run, never verification`. Rewrite the in-guest step list as "Build stage" (1. `swift build --build-tests` for SkinKit, then PlayerKit; 2. `xcodebuild` the app; a failure here skips everything below and prints the compiler errors) followed by "Tests and checks" (the existing items, with `swift test --skip-build`). It prints the leading comment block whatever its length, which supersedes #0085's widened `sed` range.
