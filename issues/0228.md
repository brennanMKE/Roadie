## Description

The user, 2026-10-27: "How can I clear the current playlist to change to another one? I just dragged a playlist on top of the playlist window and I think it added the songs, not replacing them." A drop (a Library playlist, Library rows, or files from Finder) inserts at the drop point, as Winamp does. Replacing the list takes LIST › New List or REM › Remove All first, which on an unlabelled skin is hard to find ([#0226](0226.md)).

## Expected

Holding ⌥ while dropping replaces the list with what is dropped and starts playing it (as Open does); a plain drop still inserts. The drag cursor shows which will happen (copy badge vs a replace cue), updating as ⌥ is pressed or released mid-drag. Works for the local queue and a Music Assistant queue, for Library drags and Finder drops alike. The Help page's playlists section ([#0191](0191.md)) mentions it.

## Root cause

Every drop path on the playlist editor was hard-wired to insert: `PlaylistListInputView.performDragOperation` sent `PlayRequest(mode: .insert(at: row))` for Library items and `open(urls, replace: false, at: row)` for files, and the SwiftUI fallbacks (`appendDroppedLibraryItems`, `PlaylistView`'s URL `.dropDestination`) appended. Nothing read a modifier, so there was no way to replace the list by dropping.

## Fix

As planned:
- `LibraryDropDecoder.plan(pasteboard:mask:replacing:) -> DropPlan?` (operation + `PlaylistDropCue?`; nil for a refused drag).
- `PlaylistListInputView.isOptionDown` (`NSEvent.modifierFlags.contains(.option)`); `draggingEntered/Updated` set `PlaylistModel.dropCue`, cleared in exited/perform/conclude/ended. On drop, Library ids → `model.dropLibraryItems(ids, at: row, replacing:)`; files → `model.open(urls, replace: replacing, at: replacing ? nil : row)`. `LibraryDrop` log lines say replace/insert.
- `PlayerModel.dropLibraryItems(_:at:replacing:)` → `.replace()` or `.insert(at:)`; `appendDroppedLibraryItems` became `dropLibraryItems(_ transfers:replacing:) -> Bool`; the fallbacks pass ⌥ read at drop time.
- `PlaylistDropCueView` in `normalBody`: track area shaded with `selectedBackground` at 60 % and `REPLACE PLAYLIST` in the skin's text font, no hit testing, accessibility hidden.
- help.html Playlists item updated.

Divergence: **no UI test.** `PlaylistUITests.testOptionDropReplacesTheQueue` / `testPlainDropStillInserts` were written, but a Library → playlist drag never landed in the guest (two attempts: element drag 0.3 s press, coordinate drag 1 s press; the queue unchanged and the album not even selected), so they were removed and the §5 row's UI half is *by hand*. The regression proof is the unit tests instead: `dropLibraryItems(_:at:replacing:)` was first added ignoring `replacing` (today's insert behaviour) so the tests compiled and failed, then fixed. `MusicAssistantUITests.testOptionDropReplacesTheSpeakerQueue` not added (unit `testOptionDropOnAMusicAssistantQueueReplaces` covers it).

## Plan

### What a ⌥-drop does

| Dropped | Shown queue | Plain drop (today, unchanged) | ⌥-drop |
|---|---|---|---|
| Library items | local (This Mac) | `PlayRequest(mode: .insert(at: row))` | `PlayRequest(items, mode: .replace())`: the backend clears the queue and plays the first item, as double-click in the Library does |
| Library items | Music Assistant (speaker, or This Mac on the MA feed) | `.insert` → `play_media option=add` (appends, #0173) | `.replace()` → `play_media option=replace`: Music Assistant replaces that queue and plays it |
| Finder files / folders | local | `open(urls, replace: false, at: row)` | `open(urls, replace: true)`: File › Open's path (`importLocalFiles(replace: true)` clears and plays the first) |
| Finder files / folders | Music Assistant on This Mac | appended to the local queue (This Mac taken back) | same as File › Open: replaces the local queue and plays; This Mac leaves Music Assistant (`applyFeed(.localPlayRequested)`) |
| Finder files / folders | a speaker | refused with the local-files notice (#0084) | refused the same way; nothing is cleared |
| A `.wsz` (with or without audio) | any | the skin loads | the skin loads; the queue is replaced only if audio came too (`importLocalFiles` ignores an empty list) |

Replacing never happens before the new items are known: the backend (`.replace`) and `importLocalFiles` clear only once the play/load goes ahead, so a refused or failed drop leaves the list alone.

### Reading ⌥ mid-drag

- `NSDraggingInfo` has no modifier flags, and `draggingSourceOperationMask` is ambiguous (with ⌥ held AppKit narrows it to `.copy`, which a plain Finder drag also offers). Read the key itself: `NSEvent.modifierFlags.contains(.option)` in `draggingEntered`, `draggingUpdated` and `performDragOperation`. `wantsPeriodicDraggingUpdates` is true by default, so `draggingUpdated` keeps arriving while the pointer is still, and the cue follows ⌥ pressed or released mid-drag.
- `PlaylistListInputView` gets `var isOptionDown: () -> Bool = { NSEvent.modifierFlags.contains(.option) }` (internal, so a test can set it).

### The cue

- The badge can't carry it: with ⌥ held the source mask is copy-only, so a different `NSDragOperation` (`.generic`, `.move`) would be refused, and the green + appears either way. So the operation stays `LibraryDropDecoder.operation(for:)` (copy) and the **replace cue is drawn in the editor**: while a ⌥-drag is over the track list, the rows are covered with the skin's `playlistStyle.selectedBackground` at about 60 % and `REPLACE PLAYLIST` in the skin's text font (`skin.textImage`) centred in the track area. A plain drag shows nothing new (rows as today, the copy badge).
- `PlaylistModel.dropCue: PlaylistDropCue?` (`enum PlaylistDropCue { case replace }`, observed): set by the track list's `draggingEntered`/`draggingUpdated` when ⌥ is down and the drag is acceptable, nil otherwise; cleared in `draggingExited`, `performDragOperation`, `concludeDragOperation` and `draggingEnded`.
- `PlaylistDropCueView(skin:)` in `PlaylistWindowView.normalBody` after `PlaylistTrackListView`: draws the cue at `layout.trackArea`, `.allowsHitTesting(false)`, accessibility hidden.
- The rest of the window (title bar, scroll bar, bottom bar, shade) uses the SwiftUI fallbacks (`.dropDestination`), which have no per-update hook: there ⌥ is read at drop time (`NSEvent.modifierFlags`) and a ⌥-drop replaces too, without the cue. The track list is most of the window; the Help line says "drop on the list".

### Code

- `LibraryDropDecoder`: `static func plan(pasteboard: NSPasteboard, mask: NSDragOperation, replacing: Bool) -> DropPlan?` with `struct DropPlan { var operation: NSDragOperation; var cue: PlaylistDropCue? }` (cue `.replace` iff `replacing` and the drag is acceptable). `PlaylistListInputView.dragOperation` uses it and sets `model.playlist.dropCue`.
- `PlaylistListInputView.performDragOperation`: `let replacing = isOptionDown()`. Library ids → `model.dropLibraryItems(ids, at: row, replacing:)`; file URLs → `model.open(urls, replace: replacing, at: replacing ? nil : row)`. Log `replace`/`insert` in the existing `LibraryDrop` lines.
- `PlayerModel`: `func dropLibraryItems(_ ids: [MediaID], at row: Int, replacing: Bool)` → `playFromLibrary(PlayRequest(items: ids, mode: replacing ? .replace() : .insert(at: row)))`. `appendDroppedLibraryItems(_:)` becomes `dropLibraryItems(_ transfers: [MediaIDTransfer], replacing: Bool) -> Bool` (appends at the end when not replacing, as now); both SwiftUI fallbacks pass `NSEvent.modifierFlags.contains(.option)`, and `PlaylistView`'s URL `.dropDestination` calls `model.open(urls, replace: ⌥)`.
- Nothing in MusicBackendKit changes: `.replace()` already maps to `play_media option=replace` and to the local output's replace.
