# 0116 — Library sidebar sections can't be selected

| | |
|---|---|
| **Status** | open |
| **Module** | App / LibraryBrowser |
| **Platform** | macOS |
| **First seen** | 2026-10-20 |

## Description

Reported by the user on 0.1.0-2671617 with Music Assistant as the source. In the Library window the sidebar shows Artists, Albums and Playlists, but clicking Albums or Playlists does nothing: the list stays on Artists and no section is highlighted. Only the artist list can be browsed.

[![Library window](0116/library-window.png)](0116/library-window.png)

(The subtitle's server name is blanked out of the screenshot.)

## Expected behavior

- Clicking a sidebar section selects and highlights it and shows its list (all albums, all playlists).
- The selected section survives closing and reopening the window.

## Plan

### Root cause

`App/Browser/LibrarySidebarView.swift` builds the sidebar as `List(library.sections, selection: selection)`, where `selection` is a `Binding<LibrarySection?>`. A data-driven `List` with no explicit `id:` tags each row with the element's `Identifiable.id`. `LibrarySection` (in `Packages/PlayerKit/Sources/LibraryBrowser/LibraryBrowserModel.swift`) declares `public var id: String { rawValue }`, so every row's implicit tag is a `String` ("artists", "albums", "playlists"). But the List's `SelectionValue` comes from the binding, and that type is `LibrarySection`. The tag types don't match, so SwiftUI never matches a row to the selection. Clicking a row doesn't call the setter, and no row is drawn as selected, not even Artists (the screenshot shows no sidebar highlight). `library.section` stays at its default `.artists`, so the content column keeps showing `ArtistListView`. The model side is fine: `section`'s `didSet` already clears the selection and loads the list, and `switchingSectionsLoadsEachListOnce` / `playlistsLoadWhenTheBackendHasThem` cover it. Only the view's binding is broken.

Persistence is already handled by where the model lives. `LibraryBrowserModel` is owned by `LibrarySourceController` and outlives the window. `disappeared()` doesn't touch `section`, and `appeared()` → `resumeSelection()` → `loadSectionIfNeeded()` reloads the current section. So once selection works, the section survives closing and reopening the window. Across app launches and source/server switches it is not kept; that isn't asked for here.

### Files to change

1. `Packages/PlayerKit/Sources/LibraryBrowser/LibraryBrowserModel.swift`: make the section its own identity, so an implicit tag can never be a `String` again:
   ```swift
   public enum LibrarySection: String, Hashable, Sendable, CaseIterable, Identifiable {
       case artists, albums, playlists
       public var id: Self { self }
   }
   ```
   (Nothing else reads `LibrarySection.id`; grep confirmed.)
2. `App/Browser/LibrarySidebarView.swift`: make the identity explicit at the call site too, and tag each row:
   ```swift
   List(library.sections, id: \.self, selection: selection) { section in
       row(for: section).tag(section)
   }
   ```
   (Either change alone fixes it. Do both: the model change is what the unit test pins, and the view change guards against someone changing `id` back.) Keep the existing setter that ignores `nil`, so a click on empty sidebar space doesn't clear the section.

No change to `LibraryWindowView`: its `switch library.section` already picks the right content and detail columns.

### Tests to add (`Packages/PlayerKit/Tests/LibraryBrowserTests/LibraryBrowserModelTests.swift`, `// MARK: Sections`)

- `sectionIdentityIsTheSectionItself`: `#expect(LibrarySection.allCases.map(\.id) == LibrarySection.allCases)`. It only compiles and passes when `id` is `LibrarySection`, which is the type the sidebar's selection binding needs.
- `sectionSurvivesDisappearAndAppear`: on a `connected(capabilities: [.search, .playlists])` model, set `section = .playlists` and wait for `playlists.phase == .loaded`. Then `disappeared()` and `appeared()`. Expect `section == .playlists` and that `playlists` is still loaded (no second `.playlists` backend call), and that `artists` wasn't loaded again. This is the reopen-the-window path.

No app-target UI test exists for the sidebar. The reviewer should confirm by hand (or in the VM) that clicking Albums and Playlists highlights the row and swaps the list.

### Verification tier

**Fast.** The change is in `LibraryBrowser` and `App/Browser`. Nothing under `SkinLibrary/` or the real-time `AudioCore` paths is touched. Run with `--expect sectionIdentityIsTheSectionItself --expect sectionSurvivesDisappearAndAppear`.
