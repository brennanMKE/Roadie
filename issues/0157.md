## Description

M14 work item W6 from [docs/design/release.md](../docs/design/release.md). Depends on: W3.

## Expected behavior

One `MARKETING_VERSION` = 0.0.1 in `project.yml`; explicit plist version keys; `run-tests-vm.sh --build-number`; dSYM and Sparkle tools kept from the Release build. Release bundles report `0.0.1 (<N>)`.

## Resolution notes

> 🟢 Resolved 2026-10-23 — one `MARKETING_VERSION` (0.0.1) drives every bundle and `--build-number` sets the Release build number.

## Root cause

`MARKETING_VERSION` (0.1.0) and `CURRENT_PROJECT_VERSION` were repeated in each of the three targets, and the committed
Info.plists held literal `1.0`/`1`, so the shipped version depended on Xcode overriding them. The Release build number
was always computed in the guest, so a release couldn't name it ahead of time, and the dSYM was left behind.

## Fix

- `project.yml`: `MARKETING_VERSION: "0.0.1"` and `CURRENT_PROJECT_VERSION: "1"` once in `settings.base`; the
  per-target copies removed; `CFBundleShortVersionString: $(MARKETING_VERSION)` and
  `CFBundleVersion: $(CURRENT_PROJECT_VERSION)` set explicitly in all three targets' `info.properties`.
- `run-tests-vm.sh --build-number YYYYMMDD.HHMM` (needs `--dmg`; anything else exits 2), passed through by `verify.sh`;
  default stays "now, in UTC".
- The `app-release` step also returns `release/Roadie.app.dSYM.zip` and `release/dsym-uuids.txt`. `sparkle-bin` is
  left to W7 (#0158), as the plan allows.
