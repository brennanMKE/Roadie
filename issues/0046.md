## Description

Running `swift test --package-path Packages/PlayerKit` played audible tones through cameron's speaker. Reported by the Homelab session: Core Audio logged "Speaker Starting IO" during repeated runs. The `RealtimeAudio` probe and the two `MixedFormatRealtimeTests` started a real-time `AVAudioEngine` on the default output with an unmuted mixer. Five `NowPlayingTests` also started real-time engines; they were muted, but still opened the output device.

## Expected behavior

The default test run is silent and never opens the output device.

## Actual behavior

Sine tones at amplitude 0.05 played on every run that included the real-time tests, and so did the reviewers' scratch harnesses.

## Notes

The Homelab session's requirements: stop any running test loops; render offline or mute every test that needs a running engine; keep genuinely real-time tests out of the default run behind an env var; verify that `log show --last 2m --predicate 'process == "coreaudiod" AND eventMessage CONTAINS "Speaker Starting IO"'` prints nothing.

## Root cause

The default `swift test` run started real-time `AVAudioEngine`s on the default output: the `RealtimeAudio` probe (skipped only by `AUDIOCORE_SKIP_REALTIME`), the two `MixedFormatRealtimeTests` with an unmuted mixer (amplitude 0.05 sine tones), and five `NowPlayingTests` that muted the mixer but still opened the device. Nothing in the tests or the workflow rules forbade it.

## Fix

- `RealtimeAudio.isAvailable` now requires `AUDIOCORE_REALTIME=1` before it creates or starts any engine, so the probe itself is silent by default. Its gated tests (both `MixedFormatRealtimeTests`, `autoAdvanceUpdatesInfoCenterAndAttachesArtwork`) set `player.volume = 0`.
- `mixedFormatsAdvanceWithoutGapRealtime` records with `PeakRecorder` on the EQ node's output instead of the main mixer. The EQ sits upstream of the muted mixer and is connected at the processing format (output rate, stereo), so the gap and audible-length measurements see the real signal; the mixer's analyzer tap no longer has to be disabled.
- The four remaining `NowPlayingTests` that called `play()` use a new `renderSilently(_:)` helper (`TestSupport.swift`) that puts the engine in offline manual rendering mode before `play()`.
- Product fix: `Player.updateCurrentTime` skips a `lastRenderTime` with neither a valid sample time nor a valid host time instead of passing it to `playerTime(forNodeTime:)`, which raises an Objective-C exception. Offline mode exposed it, and the same invalid render time can occur in the app just after an engine (re)start, before the first render cycle, when the 100 ms timer fires.
- `issues/Issues.md` gains the "Tests must be silent" rule, covering review harnesses too.

Coverage moved out of the default run: real-time gapless advance across mixed formats, seek within a resampled file, and the Now Playing auto-advance/stale-elapsed check of #0007. None has an offline substitute here: `.dataPlayedBack` completions are not delivered in offline manual rendering mode (see the note in `GaplessRenderTests`), so tracks never advance. Offline gapless rendering and the pure scheduler/promotion tests stay in the default run, so the loss is limited to end-to-end real-time behavior, which reviewers can run with `AUDIOCORE_REALTIME=1`.

## Resolution notes

> Approved on review. Nit for later, not blocking: the `updateCurrentTime` guard accepts a render time with only a valid host time; `playerTime(forNodeTime:)` needs the sample time, so `renderTime.isSampleTimeValid` alone would be the tighter check. In practice real-time render times carry both and offline ones carry the sample time, so the current guard covers the observed crash.
