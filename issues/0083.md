## Description

`ClientConnectionTests.pingIsSentEveryIntervalWhileConnected` (MusicAssistantKitTests) failed once in the VM with `pingCount` 1 where 2 was expected (review run `20261018-211623-56833` of #0079, which does not touch this code). It passed on the re-run.

The #0079 reviewer's reading: the test's `sleeperCount == 1` wait can match the pong-timeout sleeper before the next interval sleeper is registered, so the clock advances too early. The test comes from #0061.

Expected: the test waits for the interval sleeper specifically (or for a state that only exists once it is registered), and passes every time.

## Plan

**Not as rare as "failed once".** In `build/vm-tests/`, 6 of the 37 runs that include this test failed it: `20261018-211623-56833`, `-222224-80869`, `-223234-84437`, `-225141-649`, `-231028-7607` and `-231356-8839`. Every failure looks the same. Line 122 passes, then line 124 (`pingCount == 2 && sleeperCount == 1`) times out after 5 s, and line 128 reports `pingCount → 1`. So the second ping never goes out.

**Root cause (test-only; the reviewer's reading is right).** In `MusicAssistantClient` (around lines 306–320), each heartbeat sleeps `pingInterval` on the clock and then calls `Self.ping` (around line 548). `Self.ping` is a task group with two children: `transport.ping()`, and a pong-timeout `clock.sleep(for: pongTimeout)`. Here is what happens after the test's first `advance(by: 25)` (clock `now` = 25):

1. The interval sleeper fires (sleepers: 0).
2. The pong-timeout child registers a sleeper with deadline 35 (sleepers: 1). The ping child bumps `pingCount` to 1 and returns `true` straight away (the stub doesn't hang).
3. The parent task has to be scheduled to take `group.next()`. Only then does the `defer { group.cancelAll() }` run `ManualClock`'s `onCancel`, which removes the deadline-35 sleeper. Then the loop registers the next interval sleeper with deadline 50.

Between steps 2 and 3, `pingCount == 1 && sleeperCount == 1` is already true, but the one sleeper is the pong timeout. The test's 5 ms poll can land in that window, and on a loaded VM the parent's hop can take that long. When it does, the second `advance(by: 25)` (now = 50) fires the deadline-35 pong sleeper and finds no interval sleeper yet. That result is discarded, because `group.next()` already returned `true` or is about to. The loop then registers its interval sleeper at 50 + 25 = 75, which the test never reaches. Result: `pingCount` stays 1 and `sleeperCount` is 1, which is exactly the logged failure. (A rarer variant: the pong sleeper's resume wins `group.next()`, the client reconnects, and `pingCount` is still 1. Same cause, same fix.)

**Production code is fine.** `withTaskGroup` waits for every child before it returns, so in the real client the pong-timeout sleep is always cancelled before the next interval sleep starts. Nothing in `Sources/` changes.

**Files**

- `Packages/PlayerKit/Tests/MusicAssistantKitTests/TestSupport.swift`: give `ManualClock` a read-only accessor for the pending deadlines, read under the lock and sorted. For example: `var sleeperDeadlines: [Duration] { state.withLock { $0.sleepers.values.map(\.deadline.offset).sorted() } }`. Keep `sleeperCount`, because the other 20 or so uses don't need to tell sleepers apart.
- `Packages/PlayerKit/Tests/MusicAssistantKitTests/ClientConnectionTests.swift`, `pingIsSentEveryIntervalWhileConnected`: wait on the deadline, not the count. A deadline only the interval sleeper can have proves the pong sleeper is gone and the loop is parked in its next interval sleep:
  - After connect: `waitFor { rig.clock.sleeperDeadlines == [.seconds(25)] }`
  - After the first advance: `waitFor { rig.transport.pingCount == 1 && rig.clock.sleeperDeadlines == [.seconds(50)] }`
  - After the second advance: `waitFor { rig.transport.pingCount == 2 && rig.clock.sleeperDeadlines == [.seconds(75)] }`
  - Keep the close/reconnect tail and the final `pingCount == 2` check as they are.
- Optional tightening, same file: in `aMissingPongReconnects` (line 108) the pong sleeper is the one that should be there, so `sleeperDeadlines == [.seconds(35)]` states the intent exactly. That test isn't racy today, because the hanging ping keeps the pong sleeper alive. Leave the other `sleeperCount == 1` waits alone: while the client isn't connected, the reconnect loop's sleeper is the only one.

**Verification (VM only; fast tier is enough, since no code a slow test guards is touched).**

1. `scripts/run-tests-vm.sh`: the fast tier must pass. Quote the `PASS`/`TIER` and PlayerKit summary lines.
2. Stress the one test. `--stress N` is currently hard-wired to `MixedFormatRealtimeTests/mixedFormatsAdvanceWithoutGapRealtime` with `AUDIOCORE_REALTIME=1` (`scripts/stress-realtime-gapless.sh`), so it can't target this test as it stands. Make a small, backward-compatible change:
   - `scripts/stress-realtime-gapless.sh`: take the filter from an optional third argument or a `STRESS_FILTER` variable, defaulting to the current one. Its "1 test passed" check already works for any single test.
   - `scripts/run-tests-vm.sh`: add `--stress-filter F` (needs `--stress`) and forward it.
   - `docs/testing-in-vm.md`: add a line about the new option.

   Then run `scripts/run-tests-vm.sh --stress 200 --stress-filter 'ClientConnectionTests/pingIsSentEveryIntervalWhileConnected'`; it should show `stress: 0/200 failed`. A `--load` run of the same is a good extra, because CPU pressure widens the old window.

   If the script change is judged out of scope, file it as its own issue. Then rely on reasoning about the deadline-based wait (it can't match the pong sleeper) plus three or more clean fast-tier runs, and say so in `## Verification`.

## Root cause

Test-only, as the plan says. `ManualClock.sleeperCount == 1` after the first advance could match the ping's pong-timeout sleeper (deadline 35 s) before the parent task cancelled it and registered the next interval sleeper. The second `advance(by: 25)` then fired the pong sleeper instead, the loop parked its interval sleep at 75 s, and the second ping never went out. Production code is correct (`withTaskGroup` awaits both children before the next sleep).

## Fix

- `ManualClock` gains `sleeperDeadlines: [Duration]` (absolute offsets, sorted, read under the lock) and `hasSleeper(dueIn:)`, built on it, which #0088 reuses. `sleeperCount` stays.
- `pingIsSentEveryIntervalWhileConnected` waits for `sleeperDeadlines == [25 s]`, then `pingCount == 1 && == [50 s]`, then `pingCount == 2 && == [75 s]`. The optional tightening in `aMissingPongReconnects` was taken (`== [35 s]`).
- `scripts/run-tests-vm.sh --stress N --stress-filter F` forwards F as the third argument of `scripts/stress-realtime-gapless.sh` (which also reads `STRESS_FILTER`). The default is still the gapless test, and `AUDIOCORE_REALTIME=1` is set only for it. Small additions beyond #0083's plan, taken from #0088's plan so #0088 needs no script changes: the pass check accepts any non-zero count (`Test run with [1-9][0-9]* tests?( in N suites?)? passed`, so 0 tests still fails), and the grep no longer matches the gapless-specific `✔ Test mixed` line. The stress script prints a `stress: filter …` line. Documented in `docs/testing-in-vm.md` and the usage comments.
