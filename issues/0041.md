# 0041 — Player state is stale while a track is still loading

## Description

Between `play(at:)` and the async track resolve finishing, `Player.state` is still `.stopped` (from cold) or the previous track's `.playing`, so a second Play press restarts the load. Found in the #0002 review.

## Steps to reproduce

1. With the player stopped, call `play(at:)` on a track whose resolve takes a moment.
2. Read `state`, or press Play again before the resolve finishes.

## Expected behavior

The player reports that it is loading the track, and a repeated Play during the load does not start it again.

## Actual behavior

`state` reports the old value, and a second Play restarts the load.

## Plan

Written while #0003 is landing in `Player.swift` (the per-player `generation` counter has moved into `GaplessScheduler`, bumped by `scheduler.invalidate()` / `discardSchedule()`), so this describes the state machine rather than line numbers. Builds on #0040's `startCurrentTrack(autoplay:)` and its `autoplayAfterLoad` flag; if #0040 has not landed first, add them here.

### State

Add `case loading` to `PlaybackState` (`Packages/PlayerKit/Sources/AudioCore/PlaybackState.swift`) rather than a separate `isLoading` flag: one value can't disagree with itself, and every `switch` (including the app's play indicator) is forced to handle it. `.loading` means "a track is selected and its resolve/open is in flight; nothing is scheduled; `currentTime` is 0". The pending intent (play or park paused) lives in `autoplayAfterLoad`.

Transitions:

| From | Event | To |
|---|---|---|
| any | `play(at:)`, `next()`, `previous()`, `removeTrack` of current (non-stopped), natural end → next track | `.loading` (synchronous) |
| `.loading` | resolve + open succeed, `begin(file)` | `.playing` if `autoplayAfterLoad`, else `.paused` at 0:00 |
| `.loading` | resolve/open throws | `.stopped` + `errorMessage` (existing `fail`) |
| `.loading` | `stop()` | `.stopped` (load task cancelled, schedule invalidated) |
| `.loading` | `play()` | `.loading`; `autoplayAfterLoad = true` (no new resolve) |
| `.loading` | `pause()` | `.loading`; `autoplayAfterLoad = false` |
| `.loading` | `togglePause()` | `.loading`; flips `autoplayAfterLoad` |
| `.loading` | `seek(to:)` | no-op (`file` is nil during a load) |
| `.loading` | a new selection | `.loading` again; the old load is superseded |

### Change (`Player.swift`)

1. `startCurrentTrack(autoplay:)` sets state synchronously: cancel `loadTask`, invalidate the schedule, stop the node, `file = nil`, `currentTime = 0`, `errorMessage = nil`, `autoplayAfterLoad = autoplay`, `state = .loading`, then launch the load task. Also cancel the time loop (it already exits when `state != .playing`).
2. Supersede by generation, not by track id. Capture `let gen = scheduler.generation` after the invalidate and, after the `await` resolve (and again after opening the file, which #0003 may move to a detached task), `guard !Task.isCancelled, scheduler.generation == gen else { return }`. The current `queue.current?.id == track.id` check misses "same track re-selected" (`previous()` restarting a track, or play(at:) on the current index); the generation covers that because every new selection invalidates. Keep the `Task.isCancelled` check too so a cancelled task never calls `begin`.
3. `play()` gains `case .loading: autoplayAfterLoad = true` (a no-op when already set — it must never call `startCurrentTrack`). `pause()`'s guard becomes a switch: `.playing` as today, `.loading` → `autoplayAfterLoad = false`, else return. `togglePause()`: `.loading` → flip the flag.
4. `begin(file)` consults `autoplayAfterLoad` (#0040) and is the only place that leaves `.loading` on success; `fail` leaves it on error via `stop()`.
5. `removeTrack(at:)` of the current track while `.loading` → `startCurrentTrack(autoplay: autoplayAfterLoad)` or `stop()` when the queue is empty.
6. `handleConfigurationChange()` returns early for `.loading` as it does for `.stopped` (nothing scheduled; the load will connect and start the engine when it finishes). `scheduleNextIfNeeded()` (#0003) must not pre-schedule while `.loading`: its `scheduler.items.count == 1` guard already covers it, but add `state == .playing || state == .paused` for clarity.
7. Swift 6 / `@Observable` notes: `state` and `autoplayAfterLoad` are plain stored properties — no `didSet` (the #0002 Gotchas recursion). The load task is an unstructured `Task {}` created inside a `@MainActor` method, so it inherits the main actor and may read `scheduler.generation` and mutate `state` after the `await` without a hop; the only non-isolated code remains the `.dataPlayedBack` closure, which captures only the `Sendable` token. Adding an enum case is a source-breaking change for exhaustive switches: update `togglePause()`, `pause()`, and `App/MainWindowView.swift`'s `playIndicator`.

### Tests (`Packages/PlayerKit/Tests/AudioCoreTests/`, headless — no engine)

Wrap the wait in `withTaskCancellationHandler` so a cancelled load resumes with `CancellationError` instead of leaking a continuation; have every test release whatever is still pending before it ends. Releasing with a URL to a nonexistent file makes `AVAudioFile(forReading:)` throw, which is the headless way to observe "this load was acted on" (`state == .stopped`, `errorMessage != nil`) versus ignored (state unchanged, `errorMessage == nil`). - `restartingSameTrackSupersedesLoad`: `play(at: 0)`, `previous()` (restarts track 0) → `calls == [t0, t0]`; release the first with a bad URL → still `.loading`.
- `stopDuringLoadCancels`: `play(at: 0)`, `stop()` → `.stopped`; release `t0` → settle → still `.stopped`, `errorMessage == nil`.
- `loadFailureStops`: release with `.failure(AudioCoreError.unresolvableSource(...))` → `.stopped`, `errorMessage != nil`.
- `removeCurrentWhileLoadingReloadsNext`: `play(at: 0)`, `removeTrack(at: 0)` → `.loading`, `current?.id == t1.id`, `calls == [t0, t1]`; with `pause()` first, `autoplayAfterLoad` stays `false` across the reload.
- `nextAtEndOfQueueDuringLoadStops`: single track, `play(at: 0)`, `next()` → `.stopped`, later release ignored.

> 🟢 Resolved 2026-10-12 — `Player` enters `PlaybackState.loading` synchronously on every new selection, a repeated Play during a load only sets the autoplay intent, Pause/toggle flip it, and stale loads are discarded by the scheduler generation (code commit e03d518).

Generation guard proven by mutation in a scratch copy of the package: with `!Task.isCancelled` removed from both load-task guards (generation check alone) `LoadingStateTests` still passes 14/14; with the guard replaced by the old `queue.current?.id == track.id` check and no cancel check, `restartingSameTrackSupersedesLoad`, `stopDuringLoadCancels` and `nextAtEndOfQueueDuringLoadStops` fail. So the `honorsCancellation: false` tests do discriminate, and the Gotcha saying the two checks overlap understates them.

Diff checked: every `scheduler.invalidate()` path reachable during a load either cancels the load task (`stop`, `startCurrentTrack`) or is gated off (`seek`/`reconcileSchedule` need `file`, which is now nil; `handleConfigurationChange` returns for `.loading`), so a live load cannot be stranded in `.loading`. All #0040 follow-ups are handled (`loadPending` gone, `file = nil`, `removeTrack` keeps `autoplayAfterLoad`, generation replaces the track-id check). Every `PlaybackState` consumer handles `.loading`: the play indicator, `PlayerModel.isLoading`, the `wasIdle` import check (`.stopped` only), Now Playing (rate 0 / paused at elapsed 0 is the right call: nothing is audible yet), remote commands (route through `play`/`pause`/`togglePause`/`seek`). The extra `paused -> loading -> paused` on removing the current track while paused is accurate (a load really happens) and #0040's tests are unchanged.

Minor, not blocking: a superseding selection during a load emits a second `stateChanged(.loading)` (the `didSet` emits on equal values); the Now Playing republish is idempotent.

## Root cause

`startCurrentTrack` left `state` at its old value (`.stopped`, or the previous track's `.playing`/`.paused`) until the async resolve finished and `begin` ran, so nothing could tell a load was in flight. A second Play saw `.stopped` and started the load again; #0040 papered over the parked case with a `loadPending` flag.

## Fix

Followed the plan (`Packages/PlayerKit/Sources/AudioCore/Player.swift`):

- New `PlaybackState.loading`, set synchronously by `startCurrentTrack`, together with `file = nil`, `currentTime = 0`, `errorMessage = nil` and `autoplayAfterLoad = autoplay`. `begin` leaves it for `.playing` (autoplay) or `.paused` (parked).
- `play()` in `.loading` sets `autoplayAfterLoad = true` and never starts a second load; `pause()` sets it to false; `togglePause()` flips it. This covers the #0040 follow-up about pausing a pending play.
- #0040 follow-ups: `file = nil` in `startCurrentTrack` (seek, reschedule and device change do nothing during a load); `removeTrack` passes `autoplayAfterLoad` when `.loading`; `loadPending` and its resets in `stop()`/`begin` and the `play()` branch are gone; the load task now checks `!Task.isCancelled && scheduler.generation == generation` (captured after `discardSchedule()`), in the catch path too, instead of the track-id early return.
- `handleConfigurationChange` returns early for `.loading`; `scheduleNextIfNeeded` requires `.playing`/`.paused`. `autoplayAfterLoad` is now `private(set)` so tests can read it.
- App: `MainWindowView.playIndicator` shows `MAIN_PLAYING_INDICATOR` for `.loading` (Winamp shows play while opening a file); `PlayerModel.isLoading` added for the marquee / #0013 / #0022 (the working indicator stays that follow-up).
- Now Playing: `.loading` publishes as `playbackState = .paused` with rate 0 and elapsed 0 (the bridge already mapped every non-`.playing` state that way, only a comment was added). Rate 1 would run the lock-screen clock ahead of audio that has not started. The track title now appears while loading, so `installedBridgePublishesAndClearsInfoCenter` was adjusted to expect rate 0 first and rate 1 once `.playing`.

Deviation: the plan's `GateResolver` gets an `honorsCancellation` flag (default true). The supersede tests use `false` so the stale resolve really arrives and the generation guard is what discards it.

## Gotchas

- Because `state` is no longer `.stopped` during a load, the Now Playing bridge publishes the track immediately (paused, rate 0) instead of after the load; any test waiting on the title as a proxy for "playing" must wait on `player.state`.
- Removing the current track while paused now goes `.paused` -> `.loading` -> `.paused` (observers see an extra `stateChanged(.loading)`); `#0040`'s tests still pass unchanged.
- With a cancellation-ignoring resolver the stale result arrives after `Task.isCancelled` is already true, so the cancel check and the generation check overlap; the generation check is the one that matters if a load task were ever not cancelled.

## Notes

Harmless with local files, which resolve almost instantly. It matters once Plex tracks are downloaded through `TrackCache` (#0013), which is where a "Buffering…" state belongs. See the `## Review notes` in [#0002](0002.md).
