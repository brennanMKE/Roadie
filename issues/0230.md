# 0230 — The playlist editor's skinned pop-up menus are invisible to VoiceOver

| | |
|---|---|
| **Status** | open |
| **Module** | App |
| **Platform** | macOS |
| **First seen** | 2026-10-27 |

## Description

The SORT LIST and MISC OPTIONS menus that the playlist editor's MISC button pops up (`PlaylistContextMenus.popUp`, `NSMenu.popUp(positioning:at:in: nil)`) don't appear in the accessibility tree: XCUITest finds their entries neither under the application nor under any window (runs 20261024-233202-39035 and 20261027-163806-30550, #0203's `testSortMenu` probe, which also tried #0208's window-level pop-up lookup). `testSortMenu` has to pick entries with the keyboard (Down arrows, Return) instead. VoiceOver users likely can't read or choose them either.

#0226's menu-bar Playlist menu gives VoiceOver another way to reach the sort commands, but the pop-ups themselves should be accessible.

## Expected

The pop-ups' entries are exposed as menu items (VoiceOver reads and chooses them; XCUITest finds them as `menuItems`), e.g. by popping up in the playlist window's view (`in: view`) rather than `nil`, or through `NSMenu.popUpContextMenu(_:with:for:)`. `testSortMenu` then clicks the entry instead of using the keyboard fallback.

## Plan

Starts after #0226 lands: by then SORT LIST and MISC OPTIONS are built by `PlaylistMenuBuilder` from `PlaylistMenu.sortEntries` / `miscOptionsEntries` (titles renamed to the menu bar's: "Sort by Title", …), and #0203's `PlaylistUITests` (with `testSortMenu` and its keyboard fallback) is on main. The fix lands where the built `NSMenu` is popped, `PlaylistContextMenus.popUp`, so SORT, MISC OPTIONS and LIST › Load's Library Playlist… / Playlist File… chooser (`PlayerModel.loadList()`) all get it.

### Why the menus are missing

Three native menus in the app, three results:
- The main window's options and visualizer menus: `menu.popUp(positioning: nil, at:, in: hosting)` (`SkinWindowController.popUp(_:atSkinPoint:)`). XCUITest finds them under the main window (#0208, `RoadieUIApp.Main.popUpMenu`; `SkinsUITests.openPopUpItem` clicks their items).
- The row menu: `NSMenu.popUpContextMenu(_:with:for: self)` (`PlaylistTrackListView.rightMouseDown`). Found as `app.menuItems["File Info…"]` (#0203's `testFileInfoPanel`).
- SORT / MISC OPTIONS: `menu.popUp(positioning: nil, at: NSEvent.mouseLocation, in: nil)`. With no view, AppKit opens the menu in a window of its own that isn't a child of any app window in the AX tree, so neither XCUITest nor VoiceOver reaches it.

So the difference is the `in:` view. Give it the playlist window's view, the same call the main window makes.

### Fix (approach A: `in:` the playlist window's hosting view)

- `SkinWindowController`: `func popUpAtPointer(_ menu: NSMenu)`. It converts `NSEvent.mouseLocation` into the hosting view: `hosting.convert(window.convertPoint(fromScreen:), from: nil)` (the hosting view is flipped, so use `convert`, not raw `y`). Then it calls `menu.popUp(positioning: nil, at: p, in: hosting)`. Same top-left-at-pointer placement as today, so nothing moves on screen.
- `PlaylistContextMenus` gets a host to pop in: `static weak var host: SkinWindowController?`. `AppDelegate`'s `playlist` controller sets it when it is built (only the `.playlist` kind). `popUp` (after the `popUpOverride` check and inside the existing `Task { @MainActor in … }`, which lets the skinned menu close first) resolves the host in order:
  1. the playlist controller if its window `isVisible`: `host.popUpAtPointer(menu)`;
  2. else `NSApp.keyWindow?.contentView`, at the converted pointer. This covers #0226's menu-bar Load Playlist… (⌥⌘L) with the editor closed and the chooser popping at the pointer;
  3. else `in: nil`, as today.
  Put the order in a small pure helper, `static func popUpView(playlist: NSView?, playlistVisible: Bool, key: NSView?) -> NSView?`, so a unit test pins it.
- Alternative: `PlaylistMenusView` could read `@Environment(\.skinWindow)` and pass it down. That doesn't reach `PlayerModel.loadList()`, so the static host is simpler. Either is fine if all three pop-ups are covered.
- Placement against Winamp: Winamp 2.x pops Sort List and Misc Options at the cursor, inside the editor, not anchored to the MISC button, and so does Webamp. Today's placement already matches that, and the fix doesn't change it. Don't anchor at the button (`popUp(_:atSkinPoint:)`).
- Update the doc comments: `PlaylistContextMenus` says the menus pop "at the pointer". Add that they pop in the playlist window's view so VoiceOver and XCUITest see them (#0230).

**Fallback (approach B), only if A's UI run still can't find the items:** synthesize a `.rightMouseDown` `NSEvent.mouseEvent(with:location:modifierFlags:timestamp:windowNumber:context:eventNumber:clickCount:pressure:)` at the pointer in the playlist window and call `NSMenu.popUpContextMenu(menu, with: event, for: hosting)`, the call the row menu makes (proven visible). Placement is the same. Record in `## Fix` which approach shipped.

**Spike:** none separate. The regression test's `--expect-fail` run proves today's code hides the items, and the first post-fix `--ui` run proves A. If that run fails only on the lookup, switch to B and run again. That counts as one of the three runs, so say so in `## Notes`.

## Tests

Fast, XCTest, hosted (`Tests/RoadieTests/PlaylistMenusTests.swift`):
- `testPopUpViewPrefersTheVisiblePlaylistWindow`: `popUpView(playlist:playlistVisible:key:)` returns the playlist view when it is visible, the key window's view when the playlist is hidden or nil, and nil when neither exists.
- `testPopUpPointIsThePointerInTheHostView`: put a flipped `NSView` in an offscreen `NSWindow` at a known frame. The screen→view conversion helper (factor it out of `popUpAtPointer` as `static func point(_ screen: NSPoint, in view: NSView) -> NSPoint`) maps a screen point to the expected flipped coordinates. That pins the menu to the pointer, not somewhere off by the window's height.
- `PlaylistMenusTests.testSortMenuIsDisabledOnRemote` and `testMiscOptionsHasGenerateHTML` (from #0211/#0226) stay green: `popUpOverride` still short-circuits before any host lookup.

Regression test: the UI test `PlaylistUITests.testSortMenu` (below), changed first. No unit test can see the AX tree, so the regression is proven in the UI tier: `scripts/verify.sh --ui --ui-filter PlaylistUITests --expect-fail testSortMenu` before the fix.

## By hand

1. Load base-2.91 and a queue of a few tracks. In the playlist editor, MISC › SORT LIST: the menu opens at the pointer, as before. Choose Reverse; the list reverses.
2. MISC › MISC OPTIONS › Generate HTML Playlist opens the HTML page in your browser.
3. Turn VoiceOver on (⌘F5). Open SORT LIST with the mouse. VoiceOver reads "menu" and the first item; VO-Down walks the items, and VO-Space chooses one.
4. With the Library having playlists (Music Assistant, local queue), LIST › Load: the Library Playlist… / Playlist File… chooser opens at the pointer and VoiceOver reads it. Close the editor and run Playlist › Load Playlist… (⌥⌘L, #0226) from the menu bar: the chooser still opens (at the pointer, in the front window).
5. Scale 2× (and a docked/moved playlist window): the menus still open right at the pointer, not offset.
