The `removedAnchor` deviation in ## Fix is right for the case it handles. The bug below is still there.

**Bug: removing the anchor row while shuffled skips one entry.** In `remove(at:)`, when the removed entry sits at `p == shufflePosition`, `shuffleOrder.remove(at: p)` slides the next entry (call it Z) into position `p`, and `shufflePosition` stays at `p`. The old code relied on that: the new current became `shuffleOrder[p]` = Z. But with the queue, `shufflePosition` means "the last pass entry played", and resuming uses `shufflePosition + 1`. That makes Z get skipped in two cases, neither tested (`removingTheCurrentEntryPlaysTheHeadOfUpNext` is unshuffled):

1. Shuffled, current X (the anchor) is playing, `upNext = [Q]`, and the user deletes X's row. This is common: delete the playing row. Q plays, and the next track end gives `shuffleOrder[p + 1]`, skipping Z. `previous()` from Q also returns Z, which hasn't played.
2. Shuffled, a queued entry Q is playing, and the user deletes the anchor row X (not the current entry). `wasCurrent` is false, so nothing adjusts. The next track end skips Z the same way.

The plan's step 3 ("leave `shufflePosition` as the existing code left it") is where the mistake comes from, so this is a plan error the implementer followed.

**Fix for the next pass:** in the shuffle bookkeeping of `remove(at:)`, treat `p == shufflePosition` like `p < shufflePosition`: decrement `shufflePosition`, so it again means "the last entry played before the slot". Then:
- upNext-head branch: keep `shufflePosition`. The queue now resumes at Z.
- `isPlayingFromUpNext && isShuffled` branch: always `shufflePosition + 1`, clamped to `0...count - 1`. The `removedAnchor` special case is no longer needed.
- Plain shuffled `wasCurrent` branch: `shufflePosition + 1` when the anchor was removed (always true there), clamped as above. This gives the same result as today, including the last-position clamp.
- Not current: the decrement is all that's needed.

`previousTarget` already guards `shufflePosition == -1`. Check that `-1` with a non-nil `currentIndex` only happens while `isPlayingFromUpNext`.

**Add tests** (and to the `--expect` list): `removingTheCurrentEntryWhileShuffledPlaysUpNextThenTheNextInPass` (case 1: after Q, the next entry is the peeked `next()` from before the removal) and `removingTheAnchorWhileAQueuedEntryPlaysDoesNotSkip` (case 2). Run the full tier again.

## Description

Phase B of M15, the model. Winamp's queue is separate from playlist order: an ordered list of entries to play next, which empties as it plays. When the current song ends, the queued entries play in order, and then normal playlist order resumes. `PlayQueue` has nothing like it: `next()`, `advanceAfterTrackEnd()` and `indexAfterCurrentEnds()` only follow list or shuffle order.

This issue adds an `upNext` list of entry ids to `PlayQueue`, and `Player` methods to change it that keep gapless prescheduling right. There's no UI here: #0179 adds `Q`, the markers and the menu; #0180 the Jump to File Queue button; #0181 Library Play Next. Saving the list comes in #0178.

Spec: [docs/music-selection-features.md](../docs/music-selection-features.md) §3 Phase B, "Model (local)". The names differ from the spec because `Player.enqueue(_ tracks:)` already exists (see "API" below).

**Rules used until #0174 confirms them** (rows 2, 5 and 6):

- After the queue empties:
  - Not shuffled: playback continues from the entry after the last queued track.
  - Shuffled: it continues from the shuffle position where the queue began.
- Playing a queued entry directly (`select`/`play(at:)`) takes it off the queue.
- The current entry may be queued, and then it plays again after itself.

## Root cause

`PlayQueue` had no play-next state. Its navigation (`next`, `advanceAfterTrackEnd`, `indexAfterCurrentEnds`) only followed list or shuffle order, so there was nothing a Winamp-style queue could build on.

## Fix

Followed the plan:
- `PlayQueue` gains `upNext: [Track.ID]` and the private `isPlayingFromUpNext` flag, plus the API from the plan.
- `upNextTarget()` comes before `nextTarget` in both `endTarget()` (except under repeat-one) and `next()`.
- `commit` pops the head without moving `shufflePosition`, so a shuffled pass resumes where the queue began.
- `previous()` ignores `upNext`; while shuffled it returns to the anchor.
- `remove`, `removeAll`, `select` and `setShuffle` keep `upNext` and the flag consistent.
- The `Player` methods go through one `changeUpNext` helper, which calls `reconcileSchedule()` only when `upNext` actually changed.

Two divergences from the plan:
- **Removed anchor:** when the removed current entry is itself the shuffle anchor (the current entry was queued), playback resumes at the anchor's old position instead of `+1`. The entry after the anchor has already slid into that position.
- **Test location:** the pure tests are in a new `UpNextTests.swift` suite instead of `PlayQueueTests.swift`. They're in the same target and use the same helpers.

## Plan

### 1. State (`Packages/PlayerKit/Sources/AudioCore/PlayQueue.swift`)

```swift
/// Winamp's play-next queue (#0177): entry ids (`Track.id`), played in order before list or shuffle order resumes.
/// Ids, not indices, so reorders keep it; removals drop their ids. Never holds an id that isn't in `tracks`.
public private(set) var upNext: [Track.ID] = []
/// The current entry was reached from `upNext`. While shuffled, `shufflePosition` then stays where the queue began
/// (so it no longer points at `currentIndex`), which is what lets the pass resume from there.
private var isPlayingFromUpNext = false
```

- `PlayQueue` is `Equatable`, and the new fields take part in it.
- Update `shufflePosition`'s doc comment: it's the position of `currentIndex` in `shuffleOrder`, except while `isPlayingFromUpNext`.

### 2. API (`PlayQueue`)

```swift
/// 1-based place of `id` in `upNext`, nil when not queued.
public func upNextPosition(of id: Track.ID) -> Int?
/// Appends the ids not already queued, in the given order (Q, the Queue button). Unknown ids are ignored.
public mutating func appendUpNext(_ ids: [Track.ID])
/// Puts `ids` at the front of `upNext`, in the given order, taking them out of where they were (Play Next, #0181).
public mutating func prependUpNext(_ ids: [Track.ID])
public mutating func removeFromUpNext(_ ids: [Track.ID])
/// When every id is queued, dequeues them all; otherwise appends the ones that aren't (#0174 row 3 default).
public mutating func toggleUpNext(_ ids: [Track.ID])
public mutating func clearUpNext()
```

- Look up ids through `Set(tracks.map(\.id))`, built once per call.
- `toggleUpNext([])` does nothing.

### 3. Removal and other mutations

- `remove(at index:)`:
  - Capture `let removedID = tracks[index].id` first, then `upNext.removeAll { $0 == removedID }`.
  - **Current removed while `upNext` is non-empty:** after the existing index and shuffle bookkeeping, the new current is the head of `upNext`. Pop it, set `isPlayingFromUpNext = true`, and leave `shufflePosition` as the existing code left it.
  - **Current removed while `isPlayingFromUpNext` and `upNext` is now empty:**
    - Not shuffled: the existing rule, `min(index, count - 1)`, is already "the entry after".
    - Shuffled: the existing rule would land on `shuffleOrder[shufflePosition]`, the track the queue began from, and replay it. Instead use position `min(shufflePosition + 1, shuffleOrder.count - 1)`: set `shufflePosition` to it and `currentIndex = shuffleOrder[shufflePosition]`.
    - Set `isPlayingFromUpNext = false` in both cases.
  - `remove(at: IndexSet)` and `crop(keeping:)` go through `remove(at:)`, so they follow automatically.
- `removeAll()`: `upNext = []`, `isPlayingFromUpNext = false`.
- `select(_:)`:
  - `isPlayingFromUpNext = false`, and `upNext.removeAll { $0 == tracks[index].id }`.
  - The existing shuffled branch already starts a new pass headed by the row, which re-anchors `shufflePosition`.
- `setShuffle(_:using:)`: `isPlayingFromUpNext = false` in both directions. Turning shuffle on re-anchors on the current entry; turning it off doesn't use `shufflePosition`.
- `append`, `apply` (move, reorder, sort, reverse, randomize): no change. They keep ids, and ids survive reorders.

### 4. Navigation

- Add `var fromUpNext = false` to the private `Target`.
- New helper:
  ```swift
  /// The head of `upNext`, keeping `shufflePosition` (it stays where the queue began).
  private func upNextTarget() -> Target? {
      guard let id = upNext.first, let index = tracks.firstIndex(where: { $0.id == id }) else { return nil }
      return Target(index: index, position: shufflePosition, fromUpNext: true)
  }
  ```
  `firstIndex` is O(n) per call, which is fine. `indexAfterCurrentEnds` runs on queue changes and track ends, not per frame.
- `endTarget()`: with `repeatMode == .one`, keep returning the current entry (track end repeats it). Otherwise `upNextTarget() ?? nextTarget(wrap: repeatMode == .all)`.
- `next()`: `upNextTarget() ?? nextTarget(wrap: repeatMode == .all)`. So under repeat-one, Next still honours `upNext`.
- `advanceAfterTrackEnd()` and `indexAfterCurrentEnds()` already use `endTarget()`, so the gapless scheduler preloads the queued file with no change in `Player`.
- `previousTarget(wrap:)` ignores `upNext`, with one rule: shuffled and `isPlayingFromUpNext` with `shufflePosition >= 0` gives `Target(index: shuffleOrder[shufflePosition], position: shufflePosition)`, the track the queue began from. Otherwise the existing code applies.
- `commit(_:)`:
  - If `target.fromUpNext`: `upNext.removeFirst()`, `isPlayingFromUpNext = true`, `currentIndex = target.index`. Don't touch `shufflePosition`, and ignore `rollover`, which is always false here.
  - Otherwise `isPlayingFromUpNext = false`, then the existing body.
- **Why the resume rule holds:**
  - Not shuffled: `nextTarget` uses `currentIndex + 1`, the entry after the last queued one.
  - Shuffled: `nextTarget` uses `shufflePosition + 1`, which didn't move while the queue played.
  - Neither `shuffleOrder` nor `nextPass` changes, so both stay permutations of `tracks.indices`.
  - A queued entry that played stays in the pass and may play again later in it (umbrella decision 5).

### 5. `Player` (`Packages/PlayerKit/Sources/AudioCore/Player.swift`, "Queue" section)

Add, each mutating `queue` and then calling `reconcileSchedule()`. That is the same path as `moveTracks`, so a prescheduled file that is now the wrong one gets replaced:

```swift
public func appendUpNext(_ ids: [Track.ID])
public func prependUpNext(_ ids: [Track.ID])
public func removeFromUpNext(_ ids: [Track.ID])
public func toggleUpNext(_ ids: [Track.ID])
public func clearUpNext()
```

- Skip `reconcileSchedule()` when `upNext` didn't change (compare before and after), so a no-op doesn't reschedule.
- `segmentFinished(.advanced(id))` already checks `queue.current?.id == id` after `advanceAfterTrackEnd()`, so a queued file the node has moved on to is followed. `trackFailed` uses `indexAfterCurrentEnds()` and `advanceAfterTrackEnd()` and needs no change.
