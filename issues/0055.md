## Description

`MixedFormatRealtimeTests.mixedFormatsAdvanceWithoutGapRealtime` failed once in a Tart VM run during #0011 (run `20261013-115928-87225`) and passed on the next run with no change. The recorder at the EQ output found 21 consecutive silent 128-frame blocks (about 2,700 frames, roughly 56 ms) between the first and last audible block, on both channels. That is either a real gap at a track boundary under load, which is exactly what #0003 and #0042 promise never happens, or an artifact of the test or the guest's virtual output device.

## Plan

### What the recorded failure already says

Read the attached excerpt against the test before changing anything. The run failed with exactly two issues, lines 265 and 266 (silent blocks inside the audible span on both channels). Line 267, `abs(audible - 2.0 * outputRate) <= 2048`, **passed**. Four 0.5 s files are 2.0 s of audio on the node timeline, so the span was within 2,048 frames of nominal even though it contained 21 × 128 = 2,688 frames of zeros. The silence therefore **replaced** audio; it was not **inserted**.

That distinction is the whole diagnosis, because the two failure modes leave different fingerprints:

| | Scheduling gap (what #0003/#0042 forbid) | Guest underrun (node or device) |
|---|---|---|
| Mechanism | `GaplessScheduler` / `Player.scheduleNextIfNeeded` queued the next file too late, or not at all, so the node ran dry at a boundary | `AVAudioPlayerNode`'s file-reading / rate-converting thread (not real-time priority) was starved on a loaded 6-vCPU guest and the node rendered zeros for the frames it could not deliver in time |
| Where the silence sits | Exactly at an item's `startFrame` (a multiple of 0.5 s into the span) | Anywhere, including mid-track |
| Audible span | Grows by the gap: `scheduleSegment(at: nil)` on a node that has run out starts the segment when it is scheduled, so every frame still plays, later | Unchanged: the timeline keeps going and the late frames are dropped |
| `Player` bookkeeping | Head completion comes back `.reachedEnd` (→ `trackEnded()` → `startCurrentTrack()` restart), or `.advanced` with a schedule lead ≤ 0 | Every completion before the last is `.advanced`, every pre-schedule happened well before its boundary |
| Test outcome today | Lines 265–267 all fail | Only 265–266 fail (what we saw) |

Working hypothesis: a guest underrun. Do not trust the inference; prove it with the instrumentation below, then make the test assert the actual gapless guarantees (which it only approximates today) and treat a span-preserving dropout as what it is. Nothing in this plan relaxes detection of a real gap: an inserted gap must still fail, and it will be caught three independent ways instead of one.

### Step 1 — Instrument `Player` (small, internal, test-only hook)

`Player` already exposes `hasPreScheduledNext` for tests; add the same kind of internal hook so the test can see the node timeline the way the scheduler does. In `Packages/PlayerKit/Sources/AudioCore/Player.swift`:

- `struct ScheduleDiagnostic: Sendable { let trackID: UUID; let startFrame: Int64; let nodeSampleTimeAtSchedule: Int64?; let wallClock: ContinuousClock.Instant }` and `enum CompletionDiagnostic: Sendable { case stale, advanced(UUID), reachedEnd }` (or reuse `GaplessScheduler.CompletionOutcome`, which is already `Sendable`).
- `@ObservationIgnored var recordsDiagnostics = false` (internal) plus `@ObservationIgnored private(set) var scheduleDiagnostics: [ScheduleDiagnostic] = []` and `completionDiagnostics: [...] = []`. Append in `schedule(_:trackID:from:)` and `segmentFinished(_:)` only when the flag is on, so the app pays nothing. Cap the arrays (keep the last 32) so a long test cannot grow them.
- `nodeSampleTimeAtSchedule` is the player's own timeline: `playerNode.lastRenderTime`, guarded with the same `isSampleTimeValid || isHostTimeValid` check `updateCurrentTime()` uses, mapped through `playerNode.playerTime(forNodeTime:)`, `.sampleTime`. `nil` before the first render. **Lead** for an item = `startFrame - nodeSampleTimeAtSchedule`, in node frames; divide by `graph.processingSampleRate` for seconds. The scheduler is blameless if every lead is positive and close to the previous file's length (~0.49 s here); it is guilty if a lead is ≤ 0 or a completion is `.reachedEnd` before the last track.

Keep `GaplessScheduler.swift` as it is; it is pure bookkeeping and already tested. Do not make the hook public.

### Step 2 — Make the test record what it saw and print it on failure

In `Packages/PlayerKit/Tests/AudioCoreTests/MixedFormatTests.swift`:

- Extend `PeakRecorder` to keep, per tap buffer, the `AVAudioTime` the tap block receives (`when.sampleTime`, `when.sampleRate`) and `frameLength`, alongside the per-128-frame peaks. Then a zero run can be reported as a sample range on the EQ node's render clock, and a hole in the tap stream (consecutive `when.sampleTime` not advancing by `frameLength`) is visible too. A dropped tap buffer shortens the recording rather than adding zeros, so if `when` ever jumps, say so in the output; it is a third, test-side artifact, distinct from both rows of the table.
- Compute the zero runs inside `[first...last]` (start block, length, start as seconds from `first`, nearest track boundary at `k * 0.5 s` and the distance to it, which track it falls in).
- On any failure, `print` a compact report: `outputRate`, the audible span in frames and its delta from `2.0 * outputRate`, the zero runs, the `scheduleDiagnostics` with their leads in ms, the `completionDiagnostics` in order, and any tap-time jumps. Cap it; never print the raw block arrays (the excerpt shows `#expect` already dumps 21 zeros, which is as far as that should go).
- Set `player.recordsDiagnostics = true` right after `let player = Player()`.

### Step 3 — Loop the test in one VM run to get a failure rate

One VM run is ~15 s boot plus cold SwiftPM builds; booting 30 clones to get a rate is not an option. Add a stress mode that reuses one guest and the already-built test binary:

- `scripts/run-tests-vm.sh`: new options `--stress N` (repeat the real-time gapless test N times in the guest, as an extra step after `playerkit-tests`) and `--load` (only with `--stress`: run four `yes > /dev/null` hogs in the guest during the loop; the golden has 6 vCPUs, leave two for the test and `tart exec`). Both default off; a plain run is unchanged. Parse them next to `--head`/`--launch`, document them in the header comment and in the Quick start of `docs/testing-in-vm.md`.
- `scripts/stress-realtime-gapless.sh` (new, runs **in the guest**, so it is plain zsh with no Tart in it): `N=$1`, `LOAD=$2`. Loop `AUDIOCORE_REALTIME=1 swift test --package-path Packages/PlayerKit --skip-build --filter 'MixedFormatRealtimeTests/mixedFormatsAdvanceWithoutGapRealtime'` N times (the preceding `playerkit-tests` step built the binary; `--skip-build` keeps each iteration to a few seconds), count failures, print one line `stress: <fails>/<N> failed` at the end, exit non-zero if any failed. With `LOAD`, start the hogs before the loop and `pkill -x yes` in an `EXIT` trap (#0044 found `jobs -p` unreliable for this; use `pkill`/`pgrep`). After the loop, capture `uptime` and `/usr/bin/log show --last 15m --predicate 'process == "coreaudiod" OR subsystem == "com.apple.coreaudio"'` into `~/results/guest-coreaudio.log` so a device-side overload or an `AVAudioPlayerNode` complaint from the guest is in `build/vm-tests/<run-id>/` next to the test log. The test's own `print` report lands in `playerkit-stress.log`.
- In `run-tests-vm.sh` the step is `run_step playerkit-stress "scripts/stress-realtime-gapless.sh $STRESS $LOAD"`, so it participates in the PASS/FAIL summary like every other step, and the existing `grep` for summary lines should also pick up the `stress:` line.
- Optional, only if the rate without `--load` is zero: add a `kAudioDeviceProcessorOverload` listener (`AudioObjectAddPropertyListenerBlock` on the default output device, global scope, main element) in the test for the duration of the run and print the count. It tells a HAL overload apart from a node underrun; it is not needed to tell either apart from a scheduling gap.

Run order in the guest is unchanged for a normal run; only `--stress` adds work. Expect ~5 s per iteration, so `--stress 30` adds a few minutes.

### Step 4 — Classify, then fix the right thing

Run `scripts/run-tests-vm.sh --stress 30` and `scripts/run-tests-vm.sh --stress 30 --load` **before** touching assertions and record both rates in `## Verification`. Read the printed reports and decide:

**A. Zero runs that preserve the span, every completion `.advanced` until the last, every lead > 0** → underrun, as hypothesised. Fix is in the test, and it must get stricter about gaps while recognising dropouts:

1. Assert the gapless mechanism directly (new, always enforced): `completionDiagnostics` before the final one are all `.advanced` and the final one is `.reachedEnd` (so `trackEnded()` / `startCurrentTrack()` never ran mid-queue); every pre-schedule lead is > 0 (one render quantum, 1,024 frames, is a reasonable floor; record the minimum lead in the report). These catch a late schedule even when it produces only a few frames of silence, which the block test could miss at a boundary.
2. Keep the span assertion exactly as it is. An inserted gap lengthens the span and fails here; that is the second net.
3. Keep the "no silent block inside the span" check as the third net for anything the first two miss, but classify before deciding the attempt failed: a zero run is a **dropout** only if the span is within tolerance **and** no completion was `.reachedEnd` **and** no lead was ≤ 0 **and** the tap stream had no time jumps. Any other silence is a gap and fails the test immediately, no retry.
4. For a classified dropout, retry the whole measurement with a fresh `Player` on the same files, at most 3 attempts; the test fails if every attempt had a dropout, and the report for each attempt is printed. Structure the body as a `run() async throws -> Attempt` returning the recorded data and classification, with the hard assertions inside it and the retry loop outside. Alternative if the retry reads as too much machinery: wrap only the dropout check in `withKnownIssue("guest underrun, #0055", isIntermittent: true) { ... }` — but prefer the retry, because it still requires a clean run and keeps the dropout visible in the log as a classified event rather than a known issue.
5. If a dropout and a boundary coincide (an underrun right where the node switches files and converters is plausible under load), the classification above still applies, because the span and lead/completion checks are what define a gap, not the position. Note that in the test's doc comment.

**B. Any lead ≤ 0, any `.reachedEnd` before the last track, or a span that grew** → a real scheduling gap. Then fix `Player`, and the test stays strict:

- The only path that can be late is the hop from the engine's completion queue to the main actor and the preload `Task` in `segmentFinished(.advanced)` → `scheduleNextIfNeeded()`: the item after the one that just started is queued only once the boundary has been crossed, so the lead is the new file's length minus main-actor latency. For a 0.5 s file on a stalled main actor that can run out. Mitigations in order of cost: (i) open the next `AVAudioFile` off the main actor (`AVAudioFile` is not `Sendable`; open it in a `Task.detached` and move it in with `nonisolated(unsafe)` or a `sending` result, keeping the generation/queue re-checks on the main actor as they are now); (ii) move the `scheduleSegment` call itself off the main actor is **not** safe, since the scheduler's bookkeeping must stay in step with the node — leave it; (iii) a look-ahead depth of 2 changes the `restartCurrent` reasoning in `GaplessScheduler` and is a separate issue, not this one. If the measured leads are large (hundreds of ms) and the failure still reproduces, the scheduler is not the cause and you are in case A.
- Lengthening the test files (e.g. 1.0 s each) to give the main actor more slack is acceptable as a test-side mitigation for case B, with the lead assertion keeping it honest; it is not a fix for case A.

**C. Tap time jumps** → the recorder fell behind and the test measured itself. Reduce the tap work (the `PeakRecorder` already does little; check nothing else runs on its queue) and rerun; the lead/completion assertions still apply.

Do not: raise `threshold`, widen the span tolerance, drop `.serialized`, or touch the `RealtimeAudio` gate. The test must stay silent: `player.volume = 0`, recorder on the EQ node, the guest muted by the script.

### Risks

- Retry can hide a real intermittent gap if the classification is wrong; that is why the lead and completion assertions are unconditional and run before any retry. Review should check that an inserted gap cannot be classified as a dropout.
- `--load` hogs can starve `tart exec`'s agent; four hogs on six vCPUs, killed by the trap, is the ceiling. If the guest becomes unreachable, drop to two.
- `swift test --skip-build --filter` must find the binary the previous step built with the same package path; if SwiftPM rebuilds anyway, accept the cost rather than fight it.
- Swift 6 strict concurrency: `AVAudioFile` across isolation (case B) needs an explicit `nonisolated(unsafe)` or `sending`; do not weaken the package's concurrency settings to get it through.
- `playerNode.lastRenderTime` can be invalid right after `play()` (the lead for the very first item is `nil`, which is fine; the assertions are about pre-scheduled items).
- Printing from a Swift Testing test interleaves with the harness output in the log; keep the report to a handful of lines so it stays readable in `playerkit-stress.log`.

## Root cause

A guest underrun, not a scheduling gap. In stress run `20261013-224147-20596` (`--stress 30 --load`) one iteration produced 82 silent 128-frame blocks at +0.507 s (6.7 ms past the first track boundary) while the audible span stayed within tolerance, every completion before the last was `.advanced`, and the pre-schedule leads were about 465 ms (the scheduler queued each next file ~0.46 s ahead). Silence replaced audio rather than being inserted, so the node's file-reading/rate-converting thread starved on the loaded guest. Without load, 30/30 iterations were clean. The old test could not tell this from a gap.

## Fix

- `Player` gets a test-only hook (`recordsDiagnostics`, capped `scheduleDiagnostics` with node-timeline lead, `completionDiagnostics`); free when off.
- `mixedFormatsAdvanceWithoutGapRealtime` now asserts the mechanism directly (completions `.advanced` x3 then `.reachedEnd`; 3 pre-schedules each with lead > 1024 frames), keeps the span check, and classifies leftover silence: a dropout (span, completions and leads intact) or a tap artifact (time jumps) is retried with a fresh `Player`, at most 3 attempts; any scheduler/span failure is a `gap` and fails at once. `PeakRecorder` now records tap render-clock times and jumps. A compact `[#0055]` report is printed per attempt.
- `scripts/run-tests-vm.sh --stress N [--load]` and `scripts/stress-realtime-gapless.sh` (guest side).
- Case A of the plan; `Player` scheduling itself is unchanged.
