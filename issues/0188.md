# 0188 — Library rows can't be dragged onto the skinned playlist editor

| | |
|---|---|
| **Status** | open |
| **Module** | App |
| **Platform** | macOS |
| **First seen** | 2026-10-24 |

## Description

The user can't drag anything from the Library (⌘L) to the skinned playlist editor. There are two parts:

1. **Most Library rows have nothing to drag.** Artist rows have no `.draggable`, and Artists is the section the Library opens on. Playlist rows have none either; #0189 covers those.
2. **Album and track rows are draggable, but the drop has never been seen to work.** Since #0136 they've been `.draggable(MediaIDTransfer(...))`, and #0184 made the editor's AppKit track-list view accept them. #0184 was resolved without the by-hand check its review called "first" (#0184 resolution notes, check 1), and the SwiftUI fallback its plan described was never built. If AppKit doesn't see SwiftUI's drag data, nothing happens: no notice, no log.

This issue makes artist rows draggable, hardens the AppKit drop target, adds the SwiftUI fallback for the rest of the window, and logs each step so a failed drag can be diagnosed from Console.

## Steps to reproduce

1. Open the Library (⌘L). It opens on Artists.
2. Drag an artist onto the skinned playlist editor. Nothing drags.
3. Open Albums and drag an album onto a row of the playlist editor. Per the user, nothing is added.

## Expected behavior

Artists, albums and tracks dragged from the Library onto the playlist editor go in at the drop row on This Mac's local queue (#0184), or are appended on a Music Assistant queue (#0173 decision 4).

## Actual behavior

Artists don't drag. Album and track drops do nothing.

## Root cause

**Confirmed: artist rows have no drag source.** `App/Browser/ArtistListView.swift:14–23` builds each row as a `FavoriteRow` with only a `.contextMenu { FavoriteMenuItem }`. There's no `.draggable`, and no Play / Play Next / Add to Queue either. Both backends can already play an artist id:

- `FolderBackend.play` expands `.artist` (`FolderBackendKit/FolderBackend.swift:370–372`).
- Music Assistant's `play_media` takes the artist URI (`MusicAssistantBackend.play`, `MusicAssistantBackend.swift:530–552`).

**Not confirmed: why album and track drops fail.** It can't be tested without a person dragging. These are the candidates, from reading `App/Playlist/PlaylistWindowOverlays.swift:180–220`:

1. **The operation.** `dragOperation` always returns `.copy`. A destination is meant to return an operation in `sender.draggingSourceOperationMask`, and SwiftUI's drag source sets that mask, not Roadie. If the mask has no `.copy`, the drop is refused and the drag image slides back.
2. **Only the first pasteboard item is read.** `draggingPasteboard.data(forType:)` reads the first item. A SwiftUI drag puts each `Transferable` on its own `NSPasteboardItem`, with data filled in lazily from an `NSItemProvider`. If the media-id data isn't on the first item, or the type is advertised but the provider hands back nil, the drop falls through to the file-URL branch and returns `false` silently.
3. **Nothing logs.** There's no way to tell "the drag never reached the view" apart from "the type was missing" or "the data was nil".

What isn't the cause:

- The type is exported. `co.sstools.roadie.media-id` conforms to `public.data` (`project.yml:99–101`, `App/Info.plist`).
- The overlay is the topmost view over the rows. `SkinWindowController.swift:136–143` adds the hosting view, then the overlays, then the title-bar drag view, which covers only the title bar.
- Its `hitTest` returns `self` unless a skinned menu is open.

## Plan

### 1. One drag helper for Library rows (`App/Browser/LibraryPlaybackActions.swift`)

Add a `View` extension so every source drags the same way, and put the logging there:

```swift
/// A Library row dragged onto a playlist (#0136) or the playlist editor (#0184, #0188).
func libraryDraggable(_ ids: [MediaID]) -> some View {
    draggable(MediaIDTransfer(ids))
}
```

Replace every `.draggable(MediaIDTransfer(...))` with `.libraryDraggable(...)`. They're in `TrackListView.swift:94`, `AlbumListView.swift:50`, `SearchResultsView.swift:51` and `:62`, and `PlaylistTracksView.swift:39`. The helper is a single seam to switch to `.onDrag { NSItemProvider }` later if the by-hand check shows SwiftUI's `.draggable` never puts the type on the pasteboard. Don't switch now.

### 2. Artist rows (`App/Browser/ArtistListView.swift`)

- Add `.libraryDraggable([artist.id])` to each row, where `artist` is `group.members[0]`, as the row already uses.
  - Dragging all of a group's members would queue the same songs once per provider.
  - Note in `## Fix` that a name grouped across providers drags its first member only.
- Generalise the album menu into a container menu, so artists use it here and playlists use it in #0189:
  - Rename `libraryAlbumMenu(_:favorite:model:)` to `libraryContainerMenu(_ id: MediaID, favorite: Bool?, model: PlayerModel, addsToPlaylists: Bool = true)`, and `libraryAlbumActions` to `libraryContainerActions` with the same new parameter.
  - The menu is Play (`PlayRequest(items: [id], mode: .replace())`), Play Next (`.next`), Add to Queue (`.append`).
  - Then, only when `addsToPlaylists`, `Divider()` and `AddToPlaylistMenu`.
  - Then `FavoriteMenuItem`.
  - `PlayRequest.play(album:)` etc. are fine for any container id. Add `PlayRequest.play(container:)`, `.append(container:)` and `.next(container:)` in `Packages/PlayerKit/Sources/MusicBackendKit/PlayRequest.swift`. Keep the `album:` ones as one-line wrappers, so callers and tests don't churn.
  - Update every caller of the old names: `AlbumListView`, `SearchResultsView`, and anything else `grep -rn "libraryAlbum" App` finds.
- On artist rows use `libraryContainerMenu(artist.id, favorite: artist.isFavorite, model: player, addsToPlaylists: false)`. Adding an artist to a playlist isn't supported: `addsDroppedItems` only takes tracks and albums. This replaces the row's current favourite-only `.contextMenu`.
- **No double-click on artists.** A single click opens the artist's albums, and an extra tap gesture is a candidate for blocking drags (see the by-hand decision tree).

### 3. Harden the AppKit drop target (`App/Playlist/PlaylistWindowOverlays.swift`)

- Add `private static let dropLog = Logger(subsystem: "co.sstools.roadie", category: "LibraryDrop")` (`import os`).
- **Operation:** replace the fixed `.copy` with a helper:

  ```swift
  /// The operation to offer: copy if the source allows it, else whatever it allows (a SwiftUI source sets the mask).
  private static func operation(for mask: NSDragOperation) -> NSDragOperation {
      for op in [NSDragOperation.copy, .generic, .move] where mask.contains(op) { return op }
      return []
  }
  ```

  Use it for the media-id case. Leave file URLs as they are (Finder offers `.copy`), but use the helper for them too if it's simpler.
- **Detection:** `hasMediaID(_ pasteboard:)` is true if `pasteboard.types` contains the type, or any `pasteboard.pasteboardItems` item's `types` does.
- **Reading:** `mediaIDs(from pasteboard:) -> [MediaID]?` walks `pasteboard.pasteboardItems ?? []`, calls `item.data(forType: mediaIDType)` on each, JSON-decodes `MediaIDTransfer`, and concatenates the ids in item order. If no item yields data, it falls back to `pasteboard.data(forType:)`. nil when nothing decodes.
- **Logging,** with no ids or names, only counts and type identifiers:
  - In `draggingEntered`: `"drag entered: types=\(pasteboard.types?.map(\.rawValue) ?? []) mask=\(mask.rawValue) items=\(pasteboard.pasteboardItems?.count ?? 0)"`, at `.debug`.
  - In `performDragOperation`: `"drop: \(ids.count) id(s) at row \(row)"` at `.info`, or `"drop: media-id type present but no data decoded"` at `.error`.
- `performDragOperation` uses `mediaIDs(from:)`. If `hasMediaID` is true but decoding fails, post a marquee notice ("Couldn't read the dragged items") via `model.post(StatusNotice(text:))` and return `false`, rather than silently trying file URLs.

### 4. SwiftUI fallback for the rest of the window (`App/Playlist/PlaylistWindowView.swift`)

The AppKit view covers only the track list. Drops on the title bar, the scroll bar or the bottom bar land on the hosting view, which accepts only URLs (`PlaylistView`'s `.dropDestination(for: URL.self)`, line 57).

- Add `.dropDestination(for: MediaIDTransfer.self) { transfers, _ in … }` to `PlaylistWindowView.normalBody`'s `ZStack` and to `PlaylistShadeView`'s body. Put it on the inner view, so it doesn't stack on the same view as the URL destination.
- It appends: `model.playFromLibrary(PlayRequest(items: transfers.flatMap(\.ids), mode: .insert(at: model.playlist.count)))`, returns `true` when there are ids, and logs at `.info` with the same `LibraryDrop` category. Use a small `PlayerModel` method if one is needed for the logger.
- This is also the second route the by-hand check compares against: if a drop on the bottom bar works and one on the rows doesn't, the AppKit pasteboard is the problem (step 3), not the source.

## By hand (the user, on their Mac)

Before starting, run `log stream --level debug --predicate 'subsystem == "co.sstools.roadie" AND category == "LibraryDrop"'` in Terminal.

1. **Folder library, This Mac:** drag an album from Albums onto row 3 of the playlist editor. Its tracks go in at row 3, in album order.
2. Drag a track from an album's track list onto row 1, and one from search results below the last row. The first goes in at row 1; the second is appended.
3. Drag an artist from Artists onto the editor. All of the artist's tracks go in at the drop row.
4. Drag an album onto the editor's bottom bar (the SwiftUI fallback). It's appended.
5. **Music Assistant, This Mac or a speaker:** drag an album onto the editor. It's appended to the Music Assistant queue and shows at the end after the refetch.
6. Right-click an artist: Play, Play Next and Add to Queue work. There's no Add to Playlist.
7. Dragging an album onto a playlist in the Library's Playlists list still adds it there (#0136).

**If a drop still fails, read the log:**

- **No "drag entered" line:** the drag never reached the view. If a drag image moved, the window isn't taking the drop; check that the overlay is registered and that `hitTest` returns it. If no drag image moved, the source never started. Compare albums (`simultaneousGesture(TapGesture(count: 2))`) with plain track rows. If tracks drag and albums don't, the gesture is blocking it: move album double-click to a List-level `contextMenu(forSelectionType:primaryAction:)`.
- **"drag entered" without `co.sstools.roadie.media-id` in `types`:** SwiftUI's `.draggable` didn't write the type. Switch `libraryDraggable` to `.onDrag { NSItemProvider }` that registers the JSON for the type identifier with `.ownProcess` visibility.
- **The type is present but "no data decoded":** the lazy provider returned nil. Use the same `.onDrag` switch.

Record which route received the data in `## Fix` (or in `## Notes` after the user's check).
