## Description

In #0212's run `20261029-191545-21712`, #0208's UI tests and #0211's unit tests left `SkinBrowserWindowView` at 96 %, `SkinCellView` at 97.4 %, `MuseumCellView` at 95.4 % and `SkinLibraryModel` at 82.2 % (185 of 225 lines). `testFolderSetAndClear` and `testApplyDefaultFolderKeepsASetFolder` (`Tests/RoadieTests/PlaylistMenusTests.swift:126-158`) already check `setFolder` and "No folder chosen", and #0209 (merged) added `applyDefaultFolderCreatesAndStoresTheDefault`. Four gaps remain:

- `SkinLibraryModel.countsText` with a folder but no index ("Not indexed yet") and after a scan (`N skins in M files`), and `statusText` after a scan, are never checked (#0211's follow-up).

## Plan

1. `Tests/RoadieTests/SkinLibraryModelTests.swift` (new, or added to the `SkinLibraryModelTests` class in `PlaylistMenusTests.swift`), on a temp folder seeded from `TestSkins/` (or the SkinKit fixture skins when the cache is absent): `countsText` is "Not indexed yet" with a folder set and no scan, then `N skins in M files` and `statusText` `N ok, P partial, F failed` (counts from the seeded folder) after `scan()`. 2. Next and previous wrap. Random never returns the current skin when there are two or more. These replace the `crashChecksOnly` rows in `PlayerModelDispatchTests`.
3. The status views' choice of content: move it into a small `static` function or enum next to each view (`SkinBrowserStatusView`'s phase → needs folder / failed with message / progress; `MuseumStatusView.content`'s loading / offline / failed / empty / results and when `folderPrompt` shows; the grid footers' error / loading / nothing) with no behaviour change, and test them with `SkinMuseumStub` and a `SkinBrowserModel` on a missing or unreadable index.

## Root cause

No real bug in this issue's files: the gaps were untested branches. The status views and grid footers chose their content inline in SwiftUI `body`s that the UI tests never drive into the no-folder, failed, offline, empty or load-more-error states, and no unit test had an indexed skins folder. Writing the navigation test found one real problem outside these files: Random Skin can pick the skin already showing (`SkinIndexStore.randomSkin` is a plain `ORDER BY random()`), filed as [#0256](0256.md).

## Fix

- `SkinBrowserStatusContent` (`SkinBrowserStatusView.swift`), `MuseumStatusContent` with `showsFolderPrompt(hasFolder:)` (`MuseumStatusView.swift`) and `GridFooterContent` (`SkinGridView.swift`, used by `MuseumGridView` too): the choice of content as small enums; the views switch on them, with the same text and identifiers.
- `Tests/RoadieTests/SkinWindowLogicTests.swift`: `SkinLibraryModelTests` gains the counts/status text, `addDownloaded` and main-menu navigation tests on a generated folder (three distinct skins, a byte-identical copy, a junk `.wsz`), so no test-skin cache is needed; `SkinWindowContentTests` covers the three enums plus a model with no folder and an index provider that throws.
- `PlayerModelDispatchTests`: the `crashChecksOnly` loop is gone; next, previous and random skin are checked by `testMainMenuNextPreviousRandomSkin`.
- Divergence: "random never returns the current skin" isn't asserted, since the code doesn't guarantee it; the test checks random picks a loadable skin and that next and previous wrap. #0256 adds an injectable random source and a strict test.
- Feature inventory (`docs/design/test-automation.md` §5.8) updated.
