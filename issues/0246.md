## Description

Found while planning and reviewing #0244. With Music Assistant as the source, the first server resolution (`old == nil`) still goes through `activeMusicAssistantServerChanged()` in `App/PlayerModel.swift` (around lines 714–727 and 781–797). That runs `Task { await ma.disconnect() }`, which can land after a connection is already up and drop it with nothing reconnecting. It also resets `outputSelection` and `selectedOutput` to This Mac, so a late first resolution can send a play or a drop meant for a speaker to the local queue instead.

No run has shown this failure yet. It would look like one `auth` in the scripted server's log, a "Not connected" notice, or a drop landing in the local queue.

## Resolution notes

> 🟢 Resolved 2026-10-29 — A first Music Assistant server resolution no longer disconnects the backend or resets the output to This Mac; a real change of server still does both.

Proven by `RoadieTests.PlayerModelOutputTests.testFirstServerResolutionKeepsTheConnectionAndTheSpeaker` (EXPECT-FAIL 20261029-064642-46321), guard `.testServerChangeDisconnectsAndSwitchesToThisMac` and `PlayerModelDropTests.testDropOnAMusicAssistantQueueAppends`; passing runs 20261029-070551-55323 (implementer) and 20261029-071747-61011 (review).

## Root cause

`musicAssistantServerChanged(from:to:)` called `activeMusicAssistantServerChanged()` for every non-nil winner, including the first one (`old == nil`). That path reset the output to This Mac (with "Output switched to This Mac") and ran `Task { await ma.disconnect() }`, which nothing orders against the connect that needed the resolution, so under main-actor load it could close a freshly opened socket.

## Fix

As planned: `activeMusicAssistantServerChanged(replacing: old)` resets the output and disconnects only when `old != nil`. `sources.reload` and `picker.refresh()` still run in both cases. The `new == nil` branch, the `fallback.retryNow()` branch and the notice order are unchanged.

Deviation in the tests only: on a real change, the "Music Assistant: <name>" notice is posted after "Output switched to This Mac" and replaces it, and the app truncates it to 31 UTF-16 units. So the guard test expects `"Music Assistant: " + PlayerModel.truncated(other.name, to: 31 - prefix.utf16.count)` instead of the switch notice the plan named.

## Gotchas

- On a real server change the visible notice is "Music Assistant: <name>", truncated to 31 UTF-16 units; "Output switched to This Mac" is replaced at once.
- Review: after a "none reachable" decision (A → none → B), the first winner is also `old == nil`, so a speaker picked on server A is no longer reset to This Mac when a *different* server B wins. The `new == nil` branch already disconnected, so no stale connection survives (and `connect()` replaces a connection whose identity differs), but the output can point at A's player until `refreshOutputs()` reconciles it (Library connect, Output menu). A → none → A now keeps the speaker, which is better. Candidate follow-up: reset the output when the new winner differs from the last resolved server, not only when `old != nil`.

## Expected behavior

The first resolution of the active server, when nothing was resolved before, neither disconnects the backend nor resets the chosen output. A real change from one server to another still does both. A regression test, proven to fail first, covers the first-resolution case.

## Plan

### What the code does

- `MusicAssistantSelectionController.apply` (`Packages/PlayerKit/Sources/MusicAssistantKit/MusicAssistantSelectionController.swift:197–218`) calls `onChange(old, new)` whenever the winner's identity changes, and `(nil, server)` counts as a change. So the first resolution of each launch (and the first winner after a "none reachable" decision) fires `onChange(nil, server)`.
- `PlayerModel.init` wires it to `musicAssistantServerChanged(from:to:)` (`App/PlayerModel.swift:589–592`). With Music Assistant as the selected source, that calls `activeMusicAssistantServerChanged()` (`:729–730`) whatever `old` is. Only the "Music Assistant: <name>" notice checks `old != nil` (`:734`).
- `activeMusicAssistantServerChanged()` (`:786–802`) does two things:
  1. **Synchronously:** if `outputSelection != .thisMac`, it sets `outputSelection = .thisMac` and `selectedOutput = thisMacID` and posts "Output switched to This Mac".
  2. **In an unstructured main-actor `Task`:** it runs `await ma.disconnect()`, then `sources.reload(ma.sourceID)` and `await picker.refresh()`.

  Both steps are right for a real change of server. Neither has anything to undo when nothing was resolved before.

### Is the hazard real?

**The disconnect: confirmed, but latent.** The `Task { await ma.disconnect() }` runs on every first resolution. That includes the launch resolution (`:596–602`), the one inside `connect()`'s `requireConfiguration()` → `selection.currentOrResolve()`, and the source probe's `resolveNow()`. Nothing orders it against the connect that needed the resolution:

- `onChange` fires inside `resolveNow()` before it returns. The connect that asked for the server then continues on the backend actor (`openConnection`, `MusicAssistantBackend.swift:199–252`) and needs no more main-actor time.
- The disconnect `Task` first has to be scheduled on the main actor, behind whatever main-actor work is already queued. Only then does it hop to the backend.
- When the main actor is idle, the disconnect reaches the backend during the handshake. `client` is still nil then, so it only broadcasts a spurious `.disconnected`, and the connection survives. That is why no run has shown the failure.
- When the main actor is busy for longer than the handshake (launch: windows, skin, visualizer; a loaded guest), the disconnect lands **after** `openConnection` installed the client. `disconnect()` (`MusicAssistantBackend.swift:263–281`) then clears `client` and closes the fresh socket.
- Nothing reconnects unless the Library window is open. The `sources.reload` that follows rebuilds the browser (`LibrarySourceController.swift:102–119`), and a visible Library connects again. That costs a second `auth` and a Library flash.

The holds from #0244 can't force this order. Holding `auth` only lengthens the handshake, so the disconnect lands earlier, which is harmless. The late case needs a main-actor backlog, and only load produces one.

**The output reset: refuted in practice, real by construction.** `selectedOutput` is not persisted. `restoreWindowState` restores no output, and the only other writers are `selectOutput`, `adopt` (`PlayerModel+Ownership.swift:57`) and `refreshOutputs`. Each of them needs a connection, and a connection needs a resolved server. The reset runs synchronously inside `onChange(nil, …)`, before any connect can get past `requireConfiguration()`. So on a first resolution `outputSelection` is always `.thisMac`, and the reset does nothing. **A restored selected speaker at launch is not the symptom:** there is no restored speaker. The reset is still wrong for `old == nil`, because there are no "old server's players" to clear. It would drop a speaker if the callback ever came after one was chosen, which is what the regression test sets up.

**The user-visible symptom** is the late disconnect at launch, with Music Assistant as the source and a verified server:

- Roadie connects, then drops the connection within a moment. If the activity snapshot came first, it may already have adopted the playing speaker ("Output: Kitchen", #0121).
- Without the Library window open, Roadie stops following Music Assistant. The Output menu shows the not-connected hint. A play, transport or drop on the adopted speaker fails with "Not connected", and nothing reconnects until the Library opens.
- With the Library open, the user sees an extra reconnect and the Library rebuilding.

It is timing-dependent and rare, which matches the absence of any recorded failure.

### Fix (`App/PlayerModel.swift` only)

1. Pass `old` through: `musicAssistantServerChanged` calls `activeMusicAssistantServerChanged(replacing: old)`.
2. In `activeMusicAssistantServerChanged(replacing old:)`:
   - Run the output reset to This Mac, with its notice, only when `old != nil`.
   - In the `Task`, call `await ma.disconnect()` only when `old != nil`.
   - Keep `sources.reload(ma.sourceID)` and `await picker.refresh()` in both cases. The reload is what lets a Library that failed with "No Music Assistant server reachable" (`MusicAssistantServerRanking.noneReachableText`) retry when a first winner appears later, after a "none" decision. Rebuilding never disconnects the backend.
   - Update the doc comment: "nothing was resolved before: nothing to drop, keep the connection and the output".
3. A real change of server (`old != nil`, a different identity) behaves exactly as now. So does `new == nil` (`:721–727`). Leave the `fallback.retryNow()` branch alone.
4. `CHANGELOG.md`: a Fixed line, for example "A Music Assistant connection made right at launch could drop again a moment later."

Not in scope: the spurious `.disconnected` broadcast from `disconnect()` with no client, the `new == nil` branch's own unordered disconnect, and `sendspinController.serverChanged()` on the first resolution (Sendspin's own logic decides there).

## Tests

Fast, XCTest, `Tests/RoadieTests/PlayerModelOutputTests.swift` (a `PlayerModelTestCase`). Use `makeModel(scenario: .libraryIdle)`, `connectedSpeaker(_:)` and `waitUntil`.

The callback is invoked directly so the run is deterministic. `model.musicAssistantSelection.onChange` is `public var`, and calling it with `(nil, server)` while connected and on a speaker is exactly the state a late first resolution leaves. No holds, sleeps or load are involved. Take the server configuration from `model.musicAssistantSelection.current?.server` after connecting (XCTUnwrap). Not `ScriptedMusicAssistant.verifiedServer()`: it makes a new random `id` on each call (`App/TestSupport/ScriptedMusicAssistant+Roadie.swift:21`), so it is a different identity.

- **`testFirstServerResolutionKeepsTheConnectionAndTheSpeaker`**: the **regression test**, which must fail on the current code.
  1. Make sure Music Assistant is the selected source (`model.sources.selectedID == model.musicAssistant.sourceID`; select it with `persist: false` if the fallback moved it).
  2. `let speaker = try await connectedSpeaker(model)`, then `model.selectOutput(speaker)` (idle speaker: a plain select). Record `server.transports.count`, the `auth` count in `commands(server)` and `model.sources.generation`. Call `model.clearNotice()`.
  3. `model.musicAssistantSelection.onChange?(nil, configuration)`.
  4. Check synchronously: `model.selectedOutput == speaker`, `model.outputSelection.leader == speaker` and `model.notice == nil`. On the current code these fail at once, because the selection is reset and "Output switched to This Mac" is posted.
  5. `try await waitUntil("the Library reload") { model.sources.generation > before }`. This is the barrier: the reload runs after the disconnect in the same `Task`, before and after the fix.
  6. Expect `await model.musicAssistant.isConnected` (current code: false), `server.transports.count` and the `auth` count unchanged, and `server.transports.last?.closeCodes.isEmpty == true` (current code: the socket was closed).
  7. User-visible check: `model.dropLibraryItems([MediaIDTransfer([MediaID(.album, "library://album/27")])], replacing: false)`, then wait for `player_queues/play_media` with `queue_id == ScriptedMusicAssistant.speakerID`. On the current code this goes to This Mac's local queue or fails "Not connected".
- **`testServerChangeDisconnectsAndSwitchesToThisMac`**: guards the real change, which must keep doing both. Same setup through step 2. Then call `onChange?(configuration, other)`, where `other` is `configuration` with a new `id` (so `sameIdentity` is false).
  - Expect `selectedOutput == OutputDevice.thisMacID`, `outputSelection == .thisMac` and the notice "Output switched to This Mac".
  - After the generation barrier, expect `server.transports.last?.closeCodes.isEmpty == false` (the old socket was closed). Don't assert on `isConnected` afterwards: the backend's provider still returns the scripted server, and a reconnect may follow.
  - This test passes before and after the fix. It goes in `--expect`, not `--expect-fail`.
- Unchanged, but in `--expect` to show the launch connect and drops are unaffected: `testDropOnAMusicAssistantQueueAppends` (`PlayerModelDropTests`).
