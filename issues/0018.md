## Description

Map Plex tracks to `Track` and support play (double-click) and Add to Playlist from the browser.

## Acceptance criteria

- Playing an album queues all of its tracks in order.
- The marquee shows "Buffering…" until TrackCache delivers the file; cached tracks start immediately.
- kbps, kHz and mono/stereo come from Plex media metadata.

## Plan

### Scope and decisions

This issue lands after #0062 (`MusicBackend`, `PlexBackend`, `LocalPlayerOutput`) and is written against that plan, not against PlexKit. #0062 already does most of what the description asks for: `PlexBackend.play(_:on:mode:)` expands an `.album` id into its tracks in order (`client.allItems { tracks(of:page:) }`), maps each `PlexTrack` with the existing `Track(plexTrack:machineIdentifier:)`, and hands the pairs to `LocalPlayerOutput`, whose `.replace` clears and starts the queue and whose `.append` adds behind what is playing. The `Player`'s `PlexTrackResolver` → `TrackCache` path is untouched, so a Plex track still resolves to a cached local file, and `Player.state` is `.loading` from the moment `play(at:)` runs until the file opens. What is left for this issue:

- **The browser's intent, as a pure value.** `PlayRequest` in `MusicBackendKit` turns "double-click on this row" and "Add to Playlist on these rows" into `([MediaID], PlayMode)`, so the rule is tested without a view and is the same for Plex, Music Assistant and the folder backend. Double-click on an album row plays the album (`[.album]`, `.replace()`); double-click on a track row inside an album plays the album from that row, sent as the explicit track ids in display order with `.replace(startIndex:)`, so what plays is what the user saw, not a second listing; a track row outside an album (search results) plays alone; several selected rows play in display order. Add to Playlist appends the same ids with `.append`. The queue is the playlist until M5.
- **Double-click and the context menu come from one modifier.** SwiftUI's `contextMenu(forSelectionType:menu:primaryAction:)` (macOS 13+) gives the double-click (`primaryAction`), the Return key and the right-click menu for a selectable `List`/`Table` in one call, and it hands over the selection, so multi-row Add to Playlist comes for free. #0016 is planned in parallel; the assumptions about its view are listed in section 5.
- **Buffering needs no new state.** `Player.state = .loading` is synchronous at `play(at:)`, the resolver awaits `TrackCache.file(forKey:)` (a hit returns at once, a miss waits for the download), then `AVAudioFile` opens and the state becomes `.playing`. #0021's `MarqueeText.display(queue:state:)` prints "Buffering…" for `.loading` on a `.plex` source, and #0062's `NowPlaying.State.loading` mirrors it on the stream. This issue proves the chain end to end with a silent `Player` over a real `TrackCache` (section 6) rather than adding a flag. A cached track passes through `.loading` for two actor hops; that is milliseconds, not a visible "Buffering…", and section 8 says what to do if it ever flickers.
- **kbps and channels are already Plex metadata; kHz is not in a listing.** `Track(plexTrack:)` maps `Media.bitrate` and `Media.audioChannels` today and `sampleRate` is nil because the recorded `/children` and `type=10` responses carry no sample rate (none of the fixtures has a `Stream` array; `scripts/record-plex-fixtures.sh` does not strip it). Plex sends the rate only in a `Part.Stream` entry (`streamType == 2`, `samplingRate`), which appears on single-item `/library/metadata/<id>` answers and on some servers' listings. This issue decodes `Stream` when present and maps it into `Track.sampleRate` and `LibraryTrack.sampleRate` (with `Stream.channels` as a fallback for `audioChannels`); when absent, #0022's `player.currentFormat` supplies kHz and channels from the opened file, which is when Winamp first shows them anyway. No per-track metadata request is added: it would cost one round trip per play and has no fixture.
- **Nothing here touches `Player`, `PlayQueue`, `TrackCache`, `LocalPlayerOutput` or the protocol.** The additions are one value type, one decoding extension, two mapping lines, one `PlayerModel` entry point and one view modifier.
- **Verification is `scripts/run-tests-vm.sh --launch` only.** Every new test answers from `StubURLProtocol` routes or the in-process `StubDownloader`; the one test that plays audio does so in manual rendering mode (`enableManualRenderingMode(.offline, …)`, the `renderSilently` pattern from `AudioCoreTests`) so no output device opens; nothing reaches joe; no token exists in the guest; no error, log line, URL or file may carry a test secret.

### 1. `MusicBackendKit`: `PlayRequest` (`Sources/MusicBackendKit/PlayRequest.swift`, new)

```swift
/// What the browser asks a backend to play: the result of a double-click, Play or Add to Playlist.
/// Pure, so the rules are tested without a view and are the same for every backend.
public struct PlayRequest: Hashable, Sendable {
    public var items: [MediaID]
    public var mode: PlayMode
    public init(items: [MediaID], mode: PlayMode)

    /// An album row: the album in order, replacing the queue. The backend expands the id.
    public static func play(album: MediaID) -> PlayRequest            // [album], .replace()
    public static func append(album: MediaID) -> PlayRequest          // [album], .append

    /// Track rows, `rows` in display order. One selected row inside `album` plays every row from
    /// that one (`.replace(startIndex:)`); several rows, or a row with no album (search), play just
    /// the selected rows in display order. nil when nothing selected is in `rows`.
    public static func play(_ selected: Set<MediaID>, in rows: [LibraryTrack], album: MediaID?) -> PlayRequest?
    /// The selected rows in display order, appended. nil when none is in `rows`.
    public static func append(_ selected: Set<MediaID>, in rows: [LibraryTrack]) -> PlayRequest?
}
```

`play(_:in:album:)`: `let picked = rows.filter { selected.contains($0.id) }`; empty → nil; `picked.count == 1 && album != nil` → `PlayRequest(items: rows.map(\.id), mode: .replace(startIndex: rows.firstIndex { $0.id == picked[0].id }!))`; otherwise `PlayRequest(items: picked.map(\.id), mode: .replace())`. The ids sent are `.track` ids the backend has listed (`PlexBackend.knownTracks` is filled by `tracks(of:)` and `search`), which is always the case for rows the browser is showing. For Music Assistant the same request maps to `play_media` with `start_item` (#0062 section 10).

### 2. `PlexKit`: the audio stream (`Sources/PlexKit/Models/PlexTrack.swift`)

```swift
/// One `Part.Stream` entry. Only the audio stream (`streamType == 2`) is used; video and lyric
/// streams decode too so a listing never fails on them.
public struct PlexStream: Codable, Hashable, Sendable, Identifiable {
    public var id: Int
    public var streamType: Int?
    public var codec: String?
    /// Hz, audio streams only.
    public var samplingRate: Int?
    public var channels: Int?
    /// kbps.
    public var bitrate: Int?
    public var isAudio: Bool { streamType == 2 }
}

// PlexPart
public var streams: [PlexStream]          // `Stream`, [] when absent
// PlexTrack
public var audioStream: PlexStream? { primaryPart?.streams.first(where: \.isAudio) }
```

`PlexPart` becomes a hand-written `init(from:)` like `PlexTrack`'s so `streams` reads `(try? c.decodeIfPresent([PlexStream].self, forKey: .streams)) ?? []`: a stream of an unexpected shape yields no streams, never a failed track. Keep `file` undecoded.

### 3. Mapping (`Sources/TrackCache/PlexTrackMapping.swift`; `Sources/PlexBackendKit/PlexMapping.swift` from #0062)

The doc comment drops "sampleRate nil (not in the listing JSON)" for "sampleRate from the audio stream when the server sends one".

### 4. App: `PlayerModel` (`App/PlayerModel.swift`)

```swift
/// The browser's entry point. nil (nothing selected) is a no-op. Errors such as `.notConnected`,
/// `.notFound` and "no file on the server" land in `errorMessage`, as transport errors do (#0062).
func playFromLibrary(_ request: PlayRequest?) {
    guard let request else { return }
    Task {
        do { try await backend.play(request.items, on: selectedOutput, mode: request.mode) }
        catch { errorMessage = error.localizedDescription }
    }
}
```

- **Buffering flicker on cached tracks.** `.loading` lasts the resolver's hop to the cache actor (`hit()` also rewrites `index.json` synchronously, on the actor) and the `AVAudioFile` open: a few milliseconds, below one frame. If it ever shows, the fix is a `Player`-level "resolving vs opening" distinction that `MarqueeText` can read, not a change here; note it in `## Gotchas` if observed.
- **`@testable import AudioCore` from `TrackCacheTests`** works under `swift test` (debug, testing enabled), which is how the VM runs the package; the app build compiles no tests. Keep `renderSilently` in the test file; AudioCore gains no public test hook.
- **Manual rendering must be enabled before the first `play`.** `Player.begin` calls `ensureGraph()` then `graph.start()`; with the engine already in offline manual rendering mode nothing opens an output device. Calling `renderSilently` after `play()` would open the guest's (muted, host-less) device: wrong, even though silent.
- **File naming in the buffering test.** `TrackCache.fileName` takes the extension from the part key, so the test's WAV body must come through a `.wav` part key; a `.m4a` name over WAV bytes may fail to open.
- **Explicit track ids need a prior listing.** `PlexBackend` only plays `.track` ids it has listed in this process (`knownTracks`); the browser always lists before it shows rows, so this holds. Restoring a saved queue across launches (M5) is a later concern and goes through `AudioCore.Track`, not `MediaID`.
- **`Stream` shapes.** Plex's `samplingRate`, `channels` and `bitrate` are integers in JSON; `streamType` 1 video, 2 audio, 3 subtitle, 4 lyrics. Decoding is lenient so an unexpected field never fails a listing. When joe's answers can be re-recorded, one more line in `scripts/record-plex-fixtures.sh` (`rec track-metadata "/library/metadata/$TRACK" 0 1`) would show whether a single-item answer carries `Stream` and give the mapping a real fixture; that is a host-side, token-bearing step for the user, not for this issue's implementer.
- **Overlapping double-clicks.** Two quick `.replace` requests run as two tasks against the backend actor; the second clears the first's queue, which is the intent. No debounce.

## Root cause

The library browser listed artists, albums and tracks but nothing in it could start playback or add to the queue, and the Plex mapping dropped the audio stream's sample rate (and had no fallback for channels and bitrate) because `PlexKit` did not decode `Part.Stream`.

## Fix

Followed the plan against the landed #0062/#0016/#0017 code. `MusicBackendKit.PlayRequest` turns browser intent into `([MediaID], PlayMode)`. `PlayerModel.playFromLibrary(_:)` sends it to `backend.play` on the selected output, logs the item count and mode case only, and reports errors through `errorMessage`. `PlexKit` gains `PlexStream` and `PlexPart.streams` (lenient decoding), `PlexTrack.audioStream`; `Track(plexTrack:)` and `LibraryTrack(plex:)` map `sampleRate`, with `channels`/`bitrate` falling back to the audio stream. `Player`, `PlayQueue`, `TrackCache`, `LocalPlayerOutput` and `PlexBackend` are untouched: `.loading` already covers "Buffering..." so no new state was added (the marquee, #0021, and kbps/kHz display, #0022, are not built here).

Adaptations to the landed code:
- #0016 attach points: `TrackListView` (selectable `List` with `Set<MediaID>`, `libraryTrackActions(rows:album:model:)`, album = `library.selectedAlbum?.id`), `SearchResultsView` (the list is now `List(selection:)`; track rows get the same modifier with `album: nil`; album buttons get a context menu) and `AlbumListView` (rows go through the generic single-selection `PagedListView`, so they use the per-cell fallback from the plan: context menu plus `onTapGesture(count: 2)`; single click still selects/opens the album). New `App/Browser/LibraryPlaybackActions.swift` holds `libraryTrackActions`, `libraryAlbumActions` and `libraryAlbumMenu`. `PagedListView` was not changed.
- Existing test file names differ from the plan: the backend playback tests went into the existing `Tests/PlexBackendKitTests/PlaybackTests.swift` (suite `PlexBackendPlaybackTests`), not a new `PlexBackendPlaybackTests.swift`.
- The buffering test file uses a private main-actor `pollMain` helper because `TrackCacheTests.waitFor` takes a nonisolated closure.
