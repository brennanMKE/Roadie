# 0221 — A playlist the user created in Music Assistant is listed under "Built-in" and can't be renamed or deleted

| | |
|---|---|
| **Status** | open |
| **Module** | PlayerKit / MusicAssistantKit / LibraryBrowser |
| **Platform** | macOS |
| **First seen** | 2026-10-27 |

## Description

On the user's server (read-only look, 2026-10-27) `music/playlists/library_items` returns 9 playlists, all with `provider: "library"`, one provider mapping `builtin`/`builtin`, and `owner: "Music Assistant"`. Eight are MA's generated playlists (`is_editable: false`: 500 Random tracks, All favorited tracks, Infinite Mix ×2, Random Album, Random Artist, Recently added, Recently played). The ninth, **Party** (item_id 9), is one the user made: `is_editable: true`.

`MAMapping.playlistSource` (`Packages/PlayerKit/Sources/MusicAssistantKit/MAMapping.swift:28`) returns `.builtIn` for the `builtin` domain when `owner == "Music Assistant" || isEditable != true`. MA sets that owner on user-created playlists too, so Party is classified `.builtIn`:

- the Library's Playlists list shows no "My Playlists" group; Party sits in "Built-in" among the generated ones;
- `LibraryPlaylist(ma:)` leaves `.rename` and `.delete` out of `editing` for `.builtIn`, so Party can't be renamed or deleted from Roadie.

The synthetic fixtures gave user playlists `owner: "user"` (`ScriptedMusicAssistant.swift:862`), so nothing caught it.

## Expected

An editable playlist on the `builtin` provider is the user's: grouped under "My Playlists", renamable and deletable (as the server allows). MA's generated playlists stay "Built-in".

## Plan

**Root cause, two layers.**

1. `MAMapping.playlistSource` (`Packages/PlayerKit/Sources/MusicAssistantKit/MAMapping.swift`) treats `owner == "Music Assistant"` as "generated by the server". On 2.10.6 the builtin provider stamps that owner on **every** playlist it holds, the user's own too (Party: `owner: "Music Assistant"`, `is_editable: true`). The owner can't tell them apart; `is_editable` and the provider mapping's `item_id` can.
2. Nothing caught it because the recorder rewrites every `owner` to `"user"` (`Targets.scrub` in `scripts/record-ma-fixtures.py`, `if k == "owner" ...: out[k] = "user"`). So `playlists-page.json` shows the generated playlists with `owner: "user"`, the mapping comment says "2.10.6 records them with `owner: "user"`", and `ScriptedMusicAssistant.createPlaylist` copied that shape. "Music Assistant" isn't personal data; the scrubber was hiding a real server value.

**The rule after the fix** (builtin domain only; `library`/nil and provider domains are unchanged):

- `.builtIn` when the first provider mapping's `item_id` is one of the builtin provider's generated ids (`providers/builtin/constants.py`, design `docs/design/playlists.md` §1.2): `all_favorite_tracks`, `random_artist`, `random_album`, `random_tracks`, `recently_played`, `recently_added_tracks`, `infinite_mix`, `infinite_mix_favorites`. Keep them in one `static let builtinPlaylistIDs: Set<String>` next to `playlistSource`.
- Otherwise `.builtIn` when `is_editable != true` (a read-only builtin playlist we don't know yet stays safe: no rename or delete).
- Otherwise `.user`. The owner isn't read.

Then `LibraryPlaylist(ma:)` gives Party `[.addRemove, .rename, .delete]` (plus `.reorder` with `canReorder`), `PlaylistGrouping` puts it under "My Playlists", and `PlaylistGrouping.detailLine` already hides an owner of "Music Assistant", so the header reads "Music Assistant" (not "Music Assistant · Music Assistant").

**Steps**

1. **Scripted server first** (so the regression tests below fail on the current mapping): in `ScriptedMusicAssistant.createPlaylist` set `"owner": "Music Assistant"` (was `"user"`), and fix the doc comment ("A user playlist on the builtin provider, shaped as the real server sends it: `owner: "Music Assistant"`, `is_editable: true`, a builtin mapping whose `item_id` is the playlist's own id"). Also `save_as_playlist` goes through `createPlaylist`, so it follows. Mark the owner as SYNTHETIC-from-live in the class's exceptions list ("user playlists' `owner` is the live server's value, 2026-10-27, #0221; the recorded `owner` is scrubbed").
2. **Regression tests** (see `## Tests`); run `--expect-fail` before step 3.
3. **Mapping fix** in `MAMapping.playlistSource` as above; rewrite its doc comment (drop the "2.10.6 records them with owner: user" sentence; say the recorder scrubbed owners before #0221 and the live server stamps "Music Assistant" on all builtin playlists).
4. **Recorder:** in `Targets.scrub`, keep `owner` verbatim when it is exactly `"Music Assistant"`; any other string still becomes `"user"`. Don't re-record in this issue (#0222 records genres in its own mode; the next default run picks the real owners up, and `playlistDecodesEditableOwnerAndSource`'s `owner == "user"` line will then need the recorded value: note that in the test as a comment).
5. **AXID for the group headers** (the UI test needs them): `AXID.Library.playlistGroup(_ kind: String)` → `library.playlists.group.<mine|builtIn|provider-name sanitised>`, on the header `HStack` in `PlaylistListView` (`App/Browser/ArtistListView.swift`). Add the id to `AXIDTests` if that test enumerates ids.
6. **Notes:** `docs/ma-protocol-notes.md` › Quirks: add **(d) Builtin playlists all have `owner: "Music Assistant"`**: the user's own included (seen live 2026-10-27, #0221); tell them apart by `is_editable` and the mapping's `item_id`. The recorded fixtures before #0221 have `owner: "user"` (scrubbed), so `recordedQuirksHold` skips (d) until a re-record carries the real owner: add the entry with that skip, the way (a) is pending.
