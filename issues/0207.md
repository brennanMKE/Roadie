## Description

The equalizer window's on/off, bands, preamp, level labels, presets menu, graph, shade mode and persistence are only covered by package tests of `EQState` and `EQLayout`. This issue adds `EqualizerUITests` over the folder library with the base skin. Rows: [docs/design/test-automation.md](../docs/design/test-automation.md) §5.4.

## Plan

Launch: folder library, `windows: [.main, .eq, .playlist]`, a track playing (`-RoadieOpenFiles`).

### `Tests/RoadieUITests/EqualizerUITests.swift`

- `bandsAndToggles`: `eq.on` toggles `.isSelected` and `probe.eq.isEnabled`; drag `eq.band.3` to the top → its value is `12.0`; `adjust` `eq.preamp` to 0.25 → `-6.0`; click `eq.level.minus` → every band `-12.0`; `eq.level.zero` → `0.0`; `eq.auto` is clickable and changes nothing (no-op by design).
- `presetsMenu`: click `eq.presets` → the menu lists the built-in presets (`EQPreset.builtIn` names: compare to the first three), From EQF…, Save…; choose "Rock" (or the first) → bands match the preset's values (`eq.graph` value equals the preset's ten numbers); From EQF… with `-RoadieOpenFiles <fixture.eqf>` (write a `.eqf` in the test with `EQFFile`'s format, or reuse `EQFFileTests`' bytes) → bands change; Save… with `-RoadieSaveTo` → the file exists and round-trips.
- `graphValue`: `eq.graph`'s value follows two band changes.
- `shadeAndClose`: `eq.title.shade` → `shade.eq.*` present (volume and balance in the shade: check `EQLayout.shade`); ⌃⌘E back; `eq.title.close` → the window is gone and `main.eq` is not selected; ⌘2 brings it back docked under main.
- `eqPersistsAcrossRelaunch`: set band 0 to 12, preamp to −6, on; relaunch keeping defaults → the same values (`equalizer` default).
- `eqIsDisabledOnASpeaker` (if `PlayerModel+Equalizer` refuses on a remote output; check): with scenario `queueLoaded` and the speaker selected, moving a band shows the refusal notice in the marquee. Skip if the EQ applies to This Mac regardless.

## Root cause

No UI test drove the equalizer window: only the package tests of `EQState` and `EQLayout` covered it. In UI-test mode, Presets › From EQF… and Save… were recorded in `panelRequests` and then dropped, so no test could load or save a preset file.

## Fix

- `Tests/RoadieUITests/EqualizerUITests.swift` adds `bandsAndToggles`, `presetsMenu`, `graphValue`, `shadeAndClose` and `eqPersistsAcrossRelaunch`. Bands and the preamp are moved by coordinate drags; values are read from the probe.
- The probe gains `eq` (`isEnabled`, `preamp`, `gains`, `windowOpen`, `shaded`), in UI-test mode only (`App/PlayerModel+Probe.swift`, `ProbeState.EQProbe`).
- **Beyond the plan:** Debug-only stand-ins for the EQF panels. `-RoadieLoadEQF` answers From EQF…, and Save… writes to `-RoadieSaveTo` (`App/TestSupport/PanelStandIns.swift`). To share the code, `PlayerModel+Equalizer` now does the file read and write in `applyEQF(at:)` and `writeEQF(_:to:)`, called by both the real panels and the stand-ins. The sandboxed runner can't write a `.eqf` file itself, so `presetsMenu` saves Rock with the app, zeroes the bands, then loads the same file back.
- **Dropped:** `eqIsDisabledOnASpeaker`. `PlayerModel+Equalizer` doesn't refuse on a remote output: the window still edits and saves `player.eq`, and nothing changes audibly until the output is This Mac again. There is no refusal to test.
- The §5.4 rows in `docs/design/test-automation.md` are updated, including a new UI row for persistence.

## Gotchas

- **The first press after the PRESETS menu closes may be swallowed, possibly a real app bug.** In run 20261029-203010-55326, `testPresetsMenu` chose Load › Rock, and the next preamp drag (press at window point (56, 144), drag to (56, 163.5)) changed nothing: the probe still showed `"preamp":0` with Rock's gains. Just before the press, XCUITest logged:

  ```
  Found 1 interrupting element:
  Window at {{0.0, 494.0}, {550.0, 406.0}} from Target Application 'co.sstools.roadie'
  … No monitors handled UI interruption … Did not handle the interruption, but will attempt to continue…
  ```

  That frame is the **playlist window**. In the `column` launch layout at 2x, the main window is 232 pt tall, the equalizer is at {{0, 262}, {550, 232}} (the drag's target), and the playlist is docked under it at y 262 + 232 = 494, 406 pt tall (116 + 3 × 29 skin px at 2x).

  The interruption line is **not** the cause. The same "Found 1 interrupting element" appears on every drag in this run, 10 times, including the drags in `testBandsAndToggles`, `testGraphValue` and `testEqPersistsAcrossRelaunch` that landed. So this is not plainly an XCUITest interruption-handler artefact. The press seems to be lost only after the SwiftUI `Menu` (`.borderlessButton`) closes, for example if the equalizer window isn't key again yet or the menu's tracking eats the next mouse-down.

  The test now clicks the equalizer's title strip after each PRESETS menu and retries the preamp drag once. That workaround could hide the bug. Filed as [#0250](0250.md) ("The first drag on the equalizer after its PRESETS menu closes may be lost").
