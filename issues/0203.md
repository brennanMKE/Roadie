## Description

The playlist editor is where 0.0.4's bugs showed. On the local queue nothing drives its rows, selection, double-click, menus, `[n]` markers, scrolling, resizing or shade mode. This issue adds `PlaylistUITests` over the folder library (the Music Assistant queue is #0206), covering the `PlaylistUITests` rows of [docs/design/test-automation.md](../docs/design/test-automation.md) §5.5, including the local half of the #0187 regression (double-click plays that row, not row 0).

## Plan

Launch: `app.launch(library: .folder, windows: [.main, .playlist], extra: ["-RoadieOpenFiles", musicFolder])` so the queue holds the fixture library's 9 tracks in Finder order (#0195's `ExpectedLibrary` gives the titles), stopped at row 0. The playlist is 3 steps tall (`-playlistWindowSize 0 3`): rows 0–11 visible, so 9 rows fit without scrolling; `scrollResizeShade` adds the folder twice.

## Root cause

No tests yet. Nothing covered the playlist editor's rows, selection, menus, markers, scrolling or shade mode on the local queue, which is where 0.0.4's bugs showed (#0187). Writing the tests found no app bug. Two of the plan's expectations were wrong (see Fix), and so is one accessibility assumption: the MISC › Sort pop-up isn't in the accessibility tree (#0230).

## Fix

- `Tests/RoadieUITests/PlaylistUITests.swift`: the 16 tests in the expect list. `RoadieUIApp` gains `dataDirectory(testName:paths:)` (relaunching keeps the data directory, because the app creates it and never wipes it, #0208); `Playlist.menu(_:_:)` opens a skinned pop-up menu and clicks an entry.
- `App/TestSupport/PanelStandIns.swift` (Debug, `-RoadieUITest 1` only): `-RoadieOpenFiles` (the queue at launch, loaded stopped, and File › Open), `-RoadieAddFiles` (File › Add to Playlist…, ADD › Add File), `-RoadieAddFolder` (ADD › Add Folder), `-RoadieLoadList` (LIST › Load) and `-RoadieSaveTo` (LIST › Save). Several paths separate with `|`. #0202's `-RoadieOpenFiles` wasn't on main, so it lives here. `savePlaylistFile`'s write moved into `writePlaylistFile(_:to:)` so the stand-in and the panel share it.

Deviations from the plan:

- **7 rows, not 9.** `LocalTrackLoader` opens the fixture folder as its 7 audio files (files before subfolders: Single, Tone A–C, Tone D–F; `Party.m3u` inside a folder isn't expanded). Titles are read from the probe, which uses the same `displayName` as the rows. `scrollResizeShade` adds the folder twice, 21 rows.
- **`addURL`:** on the folder library ADD › Add URL does nothing (it adds a radio station only with a radio-capable source, #0147); there is no URL sheet. The test asserts nothing is added and the menu closes.
- **`listMenuLocal`:** the local queue's save goes to a file (`QueueSaveTarget` `.file`), not refused; loading uses `-RoadieLoadList` rather than relaunching with `-RoadieOpenFiles`.
- **`selection`:** shift-click asserts a superset of the anchor–row range rather than an exact set.
- **`queueMarkers`** uses rows 2 and 3 (Tone B and C, 2.0–2.5 s): Tone D–F are under a second and auto-advance before the probe sees them current. A plain press on an already-selected row keeps the whole selection (for block drags), so the test clicks row 0 before row 2 to leave only row 2 selected for the dequeue. The play-next order is read stopped: each ⌃⌘B is followed at once by Stop (⌃⌘V) and the stopped current index is checked (row 3, then row 4: unshuffled, the list carries on after the queued row that played, as `UpNextTests.upNextPlaysBeforeListOrderAndEmpties` has it; the plan's "then row 1" was wrong), since the short tracks auto-advance past a playing check (run 20261024-235522-51106).
- **`rowsShowTheQueue`:** durations load asynchronously and display rounded down, so each row is polled for its own value: `0:02` for Tone A–C (and Single), `0:00` for Tone D–F (0.5–0.75 s); the running time is about 0:11, not 0:17.
- **`scrollResizeShade`:** the rows sit under `PlaylistListInputView` and have no hit point, so the wheel scrolls at a coordinate (and reverses if XCUITest's sign goes the other way).
- **`sortMenu`:** MISC › Sort pops its NSMenu with no view (`popUp(positioning:at:in: nil)`); it shows on screen but isn't in the accessibility tree (re-checked after #0208, see Notes), so the test picks entries with Down arrows and Return (it clicks the menu item instead when one is found).
- EQ sliders untouched (not in this plan).

## Notes

- **Sort menu accessibility gap (filed as #0230).** After merging main, `testSortMenu` looked for the MISC › Sort entries both at the app root (`app.menuItems`) and under every window, the way #0208's `main.popUpMenu` finds the options pop-up. Run 20261027-163806-30550 found neither: `PlaylistContextMenus.popUp` calls `popUp(positioning:at:in: nil)`, and the entries don't show up anywhere in the accessibility tree. The test uses the keyboard fallback (Down arrows, Return), and clicks the item instead if a lookup ever finds it.
- The merge with main dropped `launch(keepingData:)`. On main the app creates the data directory itself (the sandboxed runner can't write it, #0208) and never wipes it, so the directory already survives relaunches within a test.
