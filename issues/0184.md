Review (code commit b007cae): the drop route is the AppKit one only; the plan's SwiftUI `.dropDestination` fallback was not built. It should work. `MediaIDTransfer`'s only representation is `CodableRepresentation(contentType: .roadieMediaID)`, a plain data representation (no `ProxyRepresentation`, no file promise), whose default coder is JSON. `co.sstools.roadie.media-id` is exported in `project.yml` / `App/Info.plist` (conforms to `public.data`), so it isn't a `dyn.` type. A SwiftUI `.draggable` on macOS writes each data representation's type identifier to the drag pasteboard as a pasteboard item, providing the data lazily. In-process, `data(forType:)` on that identifier calls the provider and returns the bytes. This was not exercised in a test, so by-hand check 1 below is the gate. If it returns nil, the drop does nothing (no crash, `performDragOperation` falls through to file URLs and returns false), and the fallback from the plan is the next step.

The rest checks out. `LocalPlayerOutput`'s `.insert` clamps the row and goes through `Player.insert`, which is `PlayQueue.insert` (#0183; current index, `upNext` and the shuffle order stay right) plus `reconcileSchedule()`. An idle player has an empty queue, so it plays the first inserted track at row 0. A past-the-end row clamps to `tracks.count`, and `PlayQueue.insert` appends there. Music Assistant sends `play_media` `option: add`. Every `PlayMode` switch handles `.insert` (the package and app builds pass with exhaustive switches). `FolderBackend.play` passes the mode through after expanding albums. The drop row reuses #0183's `row(atY:)` / `skinPoint(windowPoint:)`, with `playlist.count` below the last row. `.copy` is offered for the media-id type before file URLs.

## Description

Phase C of M15. In Winamp 5 you dragged rows from the Media Library into the playlist editor, and they went in at the drop row. Roadie's Library rows are already `.draggable(MediaIDTransfer(...))` (#0136): albums in `AlbumListView` and `SearchResultsView`, tracks in `TrackListView`, `PlaylistTracksView` and `SearchResultsView`. But only the Library's own playlist sidebar accepts them (`AddToPlaylistMenu.swift`). The playlist editor takes only file URLs.

This issue makes the track-list drop target from #0183 accept `MediaIDTransfer` too. It plays the dropped items through the backend with a new `PlayMode.insert(at:)`:

- **Local (folder library on This Mac):** the backend expands albums and artists into tracks, and they go in before the drop row.
- **Music Assistant:** they're **appended** (`MAQueueOption.add`). Moving them to the drop row afterwards would need the new items' queue ids from the next refetch, and the moves can be refused when buffered. That's fragile, so it's left out (umbrella decision 4).

## Root cause

The playlist editor's AppKit drop target (`PlaylistListInputView`) registered only `.fileURL`, so the `MediaIDTransfer` a Library row drags was refused. There was also no `PlayMode` that puts library items at a given queue row.

## Fix

- `PlayMode.insert(at:)`. `LocalPlayerOutput` clamps the row, registers the items' MediaIDs, calls `Player.insert` (#0183), and starts playback only if the output was idle with nothing queued. `MusicAssistantBackend` sends `play_media` with `option: add`, so a drop on a speaker's queue appends (#0173 decision 4). `playFromLibrary` logs it as "insert".
- `PlaylistListInputView` registers `co.sstools.roadie.media-id`, accepts it in `draggingEntered`/`Updated`, and checks for it before file URLs in `performDragOperation`. It decodes the data as JSON `MediaIDTransfer` and calls `playFromLibrary(PlayRequest(items:, mode: .insert(at: row)))`, where `row` is the row under the pointer, or `playlist.count` below the last row. The backend gates (folder library on a speaker → notice) still apply.
- Changed from the plan: there is no drop-row indicator. #0183 didn't add one, so there was nothing to reuse.
- **Drop route: only the primary AppKit-pasteboard route is built; the SwiftUI `.dropDestination` fallback is not.** The fallback needs a hit-test change while a drag is in flight, so it isn't cheap. Whether `data(forType:)` receives the SwiftUI `.draggable` data has not been checked by hand yet (step 7 below). If it comes back nil, the drop does nothing and the fallback from the plan is needed.

### 2. Local (`Packages/PlayerKit/Sources/LocalPlayback/LocalPlayerOutput.swift`)

```swift
case .insert(let index):
    guard !items.isEmpty else { return }
    let at = min(max(index, 0), player.queue.tracks.count)
    register(items)
    player.insert(items.map(\.track), at: at)
    if wasIdle { player.play(at: at) }
```

`Player.insert(_:at:)` comes from #0183.

### 3. Drop target (`App/Playlist/PlaylistWindowOverlays.swift`, `PlaylistListInputView`)

- Register `NSPasteboard.PasteboardType(UTType.roadieMediaID.identifier)` as well as `.fileURL`. This needs `import MusicBackendKit` and `import UniformTypeIdentifiers`.
- `draggingEntered` / `draggingUpdated` also accept a pasteboard that has that type. Use the same drop-row indicator as #0183.
- In `performDragOperation`, check for a media-id drop **before** the file URLs:
  - `sender.draggingPasteboard.data(forType: mediaIDType)`, then `try? JSONDecoder().decode(MediaIDTransfer.self, from: data)`. `MediaIDTransfer` uses `CodableRepresentation`, whose default encoding is JSON.
  - Then `model.playFromLibrary(PlayRequest(items: transfer.ids, mode: .insert(at: row)))`, where `row` is computed as in #0183 and is `model.playlist.count` below the last row.
  - `playFromLibrary` routes to the selected output's backend and applies the existing gates. A folder library with a speaker selected is refused with a notice. It also switches the feed.
- **Verify early, by hand, that the AppKit side receives the data.** SwiftUI's `.draggable` writes through an `NSItemProvider`; in-process the pasteboard should serve `data(forType:)`.
  - If it comes back nil, fall back to a SwiftUI `.dropDestination(for: MediaIDTransfer.self) { transfers, location in … }` on `PlaylistTrackListView`. Map `location.y` to a row with `PlaylistLayout.rowHeight` and `playlist.visibleRange`; the location is in skin points, because the view is inside `scaleEffect`. Then make the overlay's `hitTest` return nil while a drag is in progress.
  - Record whichever route works in `## Fix`.
- **Remote queue showing:** pass `.insert(at: row)` all the same. The Music Assistant backend appends, so no special case is needed.
