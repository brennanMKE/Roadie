## Description

`seekInResampledFileKeepsFileTime`, a real-time test added in #0042, sleeps a fixed 200 ms of wall-clock time after seeking to 0.6 s and expects `currentTime` within a narrow window. When the engine is slow to start under parallel test load it reads outside the window (0.664 was seen during #0004), so `swift test` can fail even though playback is correct.

## Steps to reproduce

1. Run `swift test --package-path Packages/PlayerKit` repeatedly, especially alongside the offline render tests.

## Expected behavior

The test passes whenever playback is correct, regardless of machine load.

## Actual behavior

It occasionally fails on the time window. It passed 3 of 3 in the #0004 review and failed once during #0004's implementation.

## Plan

Both tests live in `Packages/PlayerKit/Tests/AudioCoreTests/MixedFormatTests.swift` in `@Suite(.serialized) struct MixedFormatRealtimeTests`. Keep the suite `.serialized`, keep `@Test(.enabled(if: RealtimeAudio.isAvailable))` on both, and keep `MixedFormatSupport.waitUntil`. Only the test file changes; no `AudioCore` source changes.

Why the window is wrong, not the player: `Player.currentTime` is refreshed by a 100 ms `Task` timer from `node.lastRenderTime` (`startTimeUpdates` / `updateCurrentTime`), so any reading is up to ~100 ms stale, and `seek(to:)` does `playerNode.stop()` → reschedule → `play()`, so the first rendered frame after a seek lands some tens of ms later (more under load). A fixed 200 ms sleep followed by `0.7...0.9` demands ≥100 ms of observed playback inside 200 ms of wall time, which load can break (0.664 seen). The wall-clock sleeps are the problem; everything measured in sample frames or node time is already load-safe.

### 1. `seekInResampledFileKeepsFileTime`

Replace the fixed sleep + fixed window with a deadline poll and an elapsed-time bound:

1. Add a small helper in `MixedFormatSupport` (next to `waitUntil`) that polls a condition every 10 ms until a `ContinuousClock` deadline and returns the elapsed `Duration` (or reuse `waitUntil` and measure with `ContinuousClock.now` around it).
2. After `player.seek(to: 0.6)` and the existing `#expect(player.currentTime == 0.6)`, record `let seekStart = ContinuousClock.now`, then poll (deadline 2 s) until `player.currentTime > 0.65`. `#expect` the poll succeeded — this is the real claim: playback resumed from the seek point in file seconds, not from 0 and not from node time. 0.65 is one half timer period past the seek, so it cannot be satisfied by the initial `currentTime = target` write alone.
3. While polling, also track the minimum `currentTime` seen and `#expect(minimum >= 0.6)` — the position never dipped below the seek target (a run that restarted from 0 would show values < 0.6 before climbing).
4. Upper bound relative to measured time: `let elapsed = seekStart.duration(to: .now)` in seconds; `#expect(player.currentTime <= 0.6 + elapsed + 0.05)`. Justification: `currentTime` can only lag real time (timer staleness, restart latency), never lead it, so the only positive slack needed covers `lastRenderTime` being read a few ms after the clock sample plus the clamped position math; 50 ms is generous for that and still catches a wrong-rate mapping (44.1 vs 48 kHz would be ~9 % off, >50 ms within ~0.6 s).
5. Also `#expect(player.currentTime < 1.0)` (still inside `a.wav`, 1.0 s) and `#expect(player.queue.currentIndex == 0)` at that point, so the seek-point assertion is not accidentally satisfied by a reading from the next track.
6. Keep the advance check but make its second assertion race-free: after `waitUntil(timeout: 300) { player.queue.currentIndex == 1 }`, assert `player.currentTime < 0.5` (b.wav is 0.5 s, so any value ≥ 0.5 means the time did not reset to b's file time; the current `< 0.3` can fail if the poll loop is descheduled for 200 ms). Keep `waitUntil(timeout: 300) { player.state == .stopped }` and `errorMessage == nil`; 3 s is already ample for ~0.9 s of remaining audio.

Net effect: no fixed sleep remains in the test; both bounds are derived from the measured elapsed wall time or from file durations.

### 2. `mixedFormatsAdvanceWithoutGapRealtime`

The assertions that matter (`indices == [0,1,2,3]`, `monotonic`, `audible` frame count within 2048 frames of `2.0 * outputRate`, no sub-threshold blocks inside the audible span) are all in sample frames or node time, so they are load-safe. `inRange` (`t > 0.55`) is also safe because `GaplessScheduler.position` clamps `played` to the item's `frameLength`. Two wall-clock pieces to harden:

1. The sampling loop `for _ in 0..<600 { ... sleep 10 ms }` is an iteration count, not a deadline; replace it with a `ContinuousClock` deadline (10 s; nominal playback is ~2 s plus engine start) that breaks on `player.state == .stopped`, and `#expect` that it exited on `.stopped` rather than on the deadline. Under load each 10 ms sleep stretches, which today only makes the loop longer, so this is a clarity/robustness change rather than a fix for a current failure.
2. The `Task.sleep(200 ms)` before `removeTap` exists because the tap lags the render thread (~100 ms, #0042 Gotchas). Replace it with a drain poll: sample `recorder.blocks.left.count` every 50 ms until it is unchanged across two consecutive samples (deadline 2 s), then remove the tap. This waits as long as the machine needs instead of a guess, so a late tap under load cannot truncate the audible span and fail the `audible` bound.

Leave `waitUntil(timeout: 500) { player.state == .playing }` (5 s) as is.

If a run still fails under load, note the measured `elapsed` and `currentTime` values from the failure message (use `#expect` with the values in the expression so swift-testing prints them) rather than widening tolerances blindly; a failure whose `currentTime` exceeds `0.6 + elapsed + 0.05` is a player bug, not load.

Review (Opus): the seek test still proves file time is kept — `currentTime` must climb past 0.65 from the 0.6 seek point without ever dipping below 0.6 (a restart from 0 or a node-time reading fails), stay on track 0 and under 1.0, and never lead wall time by more than 50 ms, which is sound because the 100 ms timer only lags. The mixed-format assertions (indices, monotonic, in-range, gap-free audible span in frames) are unchanged; the 10 s deadline is `#expect`ed to end on `.stopped`, so a hang still fails rather than being masked. `.serialized`, both `.enabled(if: RealtimeAudio.isAvailable)` gates, and `graph.installsAnalyzer = false` are intact. Caveat: because the poll exits soon after 0.65, elapsed is ~0.1 s, so the +50 ms upper bound would not catch a ~9 % rate-mapping error on its own (neither did the old 0.7...0.9 window); rate correctness rests on the frame-based assertions elsewhere. ## Root cause

The tests measured wall-clock time with fixed sleeps. `seekInResampledFileKeepsFileTime` slept 200 ms after the seek and required `currentTime` in 0.7...0.9, but `currentTime` is refreshed by a 100 ms timer and the engine restarts after a seek, so under load fewer than 100 ms of playback could be visible (0.664 seen). `mixedFormatsAdvanceWithoutGapRealtime` used an iteration-count loop and a guessed 200 ms tap-drain sleep. Playback itself was correct; no product bug.

## Fix

Test-only, in `MixedFormatTests.swift`. Seek test: after `seek(to: 0.6)`, poll (shared `waitUntil(timeoutMillis: 2000)` from `TestSupport.swift`) until `currentTime > 0.65`, tracking the minimum (`>= 0.6`); then assert `currentTime <= 0.6 + elapsed + 0.05`, `< 1.0`, and `currentIndex == 0`; the post-advance check is now `currentTime < 0.5`. Mixed-format test: sampling loop uses a 10 s `ContinuousClock` deadline and `#expect`s it ended on `.stopped`; the 200 ms tap sleep is replaced by polling `recorder.blocks.left.count` every 50 ms until unchanged across two samples (2 s deadline). Deviations from plan: `graph.installsAnalyzer = false` kept as required; used the existing `waitUntil(timeoutMillis:)` in `TestSupport.swift` for the seek poll (the `MixedFormatSupport.waitUntil` is iteration-based and kept for the rest); the minimum is tracked inside the poll closure rather than a separate helper.
