# 0072 — Docked windows are not raised together

| | |
|---|---|
| **Status** | open |
| **Module** | App |
| **Platform** | macOS |
| **First seen** | 2026-10-14 |

## Description

Clicking the main window brings only that window forward. The EQ and playlist windows stay behind whatever other app's window was over them, so a docked group ends up split across the stacking order. In Winamp the EQ and playlist are owned windows and come forward with the player. #0030 planned this (a `windowDidBecomeKey` on the skinned windows that orders the other visible skinned windows directly below the key one) and left it out by decision.

## Expected behavior

When any skinned window becomes key, the other visible skinned windows (not hidden, not miniaturized) are ordered directly beneath it, so the whole set comes forward. No permanent child windows (`addChildWindow` would make AppKit move the children with the parent, which fights `WindowDockingCoordinator`); `orderWindow(.below, relativeTo:)` is enough. The Library and Settings windows are not part of the set.

## Plan

### Scope and decisions

One ordering rule, applied from two triggers: when a skinned window becomes key, and when one is clicked. The rule itself (which window goes below which) is a pure function in the `WindowDocking` target with tests; the app side is one coordinator method plus two one-line forwards. Status stays `open`; this plan writes no code.

**Reference.** Webamp checkout in the session scratchpad (`…/scratchpad/webamp-src/webamp/packages/webamp/js`): `reducers/windows.ts` 109–119 (`SET_FOCUSED_WINDOW` moves the focused window to the end of `windowOrder`, i.e. on top, the others keep their order), `components/FocusTarget.tsx` 17–21, 70–75 (`onPointerDown` → `setFocusedWindow`: a click anywhere in a window focuses it, not only its title bar), `selectors.ts` 525–535 (`getNormalizedWindowOrder`), `components/WindowManager.tsx` 160–200 (windows rendered in that order).

- **Ordering only, never key.** The group is raised with `NSWindow.order(.below, relativeTo:)` chained from the key window: each other visible skinned window goes directly beneath the previous one, in the front-to-back order they already have. Nothing calls `makeKey…`/`orderFront` on the others, so the key window is whatever AppKit chose and the selected title-bar sprite (#0025) stays on one window. No `addChildWindow` (the issue's reason: AppKit would move children with the parent and fight the coordinator's per-window origins).
- **Winamp/Webamp divergence, deliberate.** Winamp's EQ and playlist are owned windows and stay above the main window even when main is clicked; Webamp mirrors that (`getNormalizedWindowOrder` always renders main first, so it is always at the bottom). The issue's expected behaviour puts the *key* window on top and the others beneath it in their old order, which is what this plan does: one window the user clicked is never hidden by a sibling. If owned-window behaviour is wanted later it is one branch in `WindowStacking.raise` (when the key is `.main`, place main `.below` the lowest other window instead); note it in `## Gotchas`, do not do it here.
- **Two triggers, one method.** (a) `NSWindowDelegate.windowDidBecomeKey` on `SkinWindowController` (the controller is already each window's delegate): covers a click on an inactive window, ⌘1/⌘2/⌘3 and `show()`, Dock reopen and Cmd-Tab back to the app. (b) A left mouse-down anywhere in a `SkinWindow` (Webamp's `FocusTarget`): covers a click on a window that is *already* key while another app's window has since been put over a sibling (e.g. a Finder window raised by Finder itself over the EQ). (b) is `SkinWindow.sendEvent` calling a closure after `super.sendEvent` for `.leftMouseDown`; it runs after AppKit's own key change for that click, so (a) and (b) may both fire for one click. The rule is idempotent (at most three `order` calls), so that is fine.
- **Mission Control, Spaces, Stage Manager untouched.** Only windows registered with the coordinator take part; `collectionBehavior` and levels are not changed; a skinned window that is not `isOnActiveSpace` (parked on another Space) is left out of the group, so clicking main on this Space never drags a sibling over from another. The Library and Settings windows are never ordered or keyed by this code; when the group is raised above them that is the point (they are "unaffected" in that they keep their own key/order behaviour).
- **Front-to-back order comes from `NSApp.orderedWindows`** (front to back, on-screen windows of this app). It cannot show other apps' windows interleaved with ours, so the rule always emits the full chain instead of trying to detect "already together"; three `order` calls per key change is nothing.
- **Scaled-down scope.** No persistence of z-order (Webamp persists `windowOrder` only in memory), no change to `applicationShouldHandleReopen` (its `show()` calls become key one after another and the rule runs on each, ending with Winamp's playlist / EQ / main stack from the top, which is what the delegate comment there already asks for), no change to the EQ/playlist open/close observers.

### 1. Engine: `Packages/SkinKit/Sources/WindowDocking/WindowStacking.swift` (new)

```swift
/// Which windows go beneath which when a skinned window comes to the front: Webamp's `windowOrder` after
/// `SET_FOCUSED_WINDOW` (reducers/windows.ts 109-119) expressed as AppKit `order(.below, relativeTo:)` steps.
public enum WindowStacking {
    public struct Placement<ID: Hashable>: Equatable { public let window: ID; public let below: ID }

    /// `frontToBack` is the app's on-screen windows, front first (`NSApp.orderedWindows` mapped to ids; windows that
    /// are not in `group` are passed through and ignored). Returns the steps that put every other member of `group`
    /// directly beneath `key`, keeping their relative order; apply them in order. Empty when `key` is not a member of
    /// `group` or is not on screen, or when no other member is on screen.
    public static func raise<ID: Hashable>(group: Set<ID>, key: ID, frontToBack: [ID]) -> [Placement<ID>]
}
```

Algorithm: `guard group.contains(key), frontToBack.contains(key)`; `others = frontToBack.filter { group.contains($0) && $0 != key }` with duplicates dropped (first occurrence wins); `anchor = key`; for each `window` in `others`: emit `Placement(window: window, below: anchor)`, `anchor = window`. Generic over the id so the tests can use strings that include non-group windows; the coordinator uses `WindowKind`.

### 2. App

`App/Window/WindowDockingCoordinator.swift`, new section `// MARK: Z-order`:

```swift
/// Brings the visible skinned windows forward together, directly beneath `controller`'s window and in their current
/// order (Winamp's owned windows; Webamp's `windowOrder`). Ordering only: nothing is made key, nothing outside the
/// group is touched, windows on other Spaces stay there.
func raiseGroup(around controller: SkinWindowController)
```

Body: `guard isVisible(controller) else { return }`; build `kinds: [NSWindow: WindowKind]` from `controllers` where `isVisible($0) && $0.window.isOnActiveSpace`; `frontToBack = NSApp.orderedWindows.compactMap { kinds[$0] }`; for each `Placement` from `WindowStacking.raise(group: Set(kinds.values), key: controller.kind.windowKind, frontToBack:)`: `controllers[p.window]?.window.order(.below, relativeTo: controllers[p.below]!.window.windowNumber)` (guard both exist). No flag against re-entrancy is needed: `order(_:relativeTo:)` posts no key/main notifications. Reuse the existing `isVisible(_:)` (visible and not miniaturized).

`App/Window/SkinWindowController.swift`: add `func windowDidBecomeKey(_ notification: Notification) { coordinator?.raiseGroup(around: self) }` next to the existing `windowDidResignKey`; in `init`, after `window.delegate = self`, set `window.onLeftMouseDown = { [weak self] in guard let self else { return }; coordinator?.raiseGroup(around: self) }`.

`App/Window/SkinWindow.swift`: add `var onLeftMouseDown: (() -> Void)?` and

```swift
/// A click anywhere in the window (Webamp's `FocusTarget`), after AppKit has handled it, so a window that is already
/// key can still pull its group forward.
override func sendEvent(_ event: NSEvent) {
    super.sendEvent(event)
    if event.type == .leftMouseDown { onLeftMouseDown?() }
}
```

Nothing else changes: `AppDelegate`, `PlayerModel`, the SwiftUI views, `TitleBarDragView` and the engine's drag/resize/persistence code are untouched.

### 6. Risks

- **`orderedWindows` timing.** A window ordered in during the same run-loop turn (`show()` from the open observers) may not be in `NSApp.orderedWindows` yet when the previous window's `windowDidBecomeKey` fires; it is simply not placed then, and its own `windowDidBecomeKey` places the rest beneath it. No retry loop.
- **Click-through on an inactive app.** `TitleBarDragView.acceptsFirstMouse` is true; clicking it activates the app and makes the window key (as today), so trigger (a) fires. If the SwiftUI buttons' first click ever stops making the window key, trigger (b) still raises the group on the mouse-down. Both are needed for the reasons in the decisions; do not drop one.
- **Flicker.** Three `order` calls may be composited separately; if a sibling visibly pops on the user's Mac, order the chain from the back (reverse the placements, `.below` relative to the same anchors) inside one `NSAnimationContext` grouping, and note it in `## Gotchas`. Not expected.
- **`NSOpenPanel`.** File › Open… makes a panel key; when it closes the skinned window becomes key again and the group is raised, which is harmless.
- **Stage Manager** groups the app's windows itself; the rule still only orders within our group. If Stage Manager fights it, leave it (the user's setting wins) and note it.
- **No owned-window semantics** (see decisions): a user who leaves the EQ over the main window and clicks main covers the EQ, unlike Winamp. Documented divergence, one branch to change.
