# 0101 — Titles and durations from a playlist file are dropped on import

## Description

`PlaylistFile.parse` reads `#EXTINF` and PLS `TitleN`/`LengthN` into `Entry.title` and `Entry.duration`, but `LocalTrackLoader.expandPlaylists` keeps only the resolved URL. A track with no embedded tags then shows its filename even when the playlist carries a proper "Artist - Title", which Winamp would display.

Expected:

- When a track loaded from a playlist has no title tag, the playlist's title is used (split into artist and title on the first " - ", as the writer `PlaylistFile.serialize` joins them); embedded tags still win.
- A playlist duration is used only while the file's own duration is unknown.
- Tests: tagged file plus playlist title (tags win), untagged file plus playlist title (playlist wins), no playlist title (filename as today).

## Resolution notes

> 🟢 Resolved 2026-10-19 — Tracks loaded from a playlist now take the entry's `#EXTINF`/PLS title (split into artist and title on the first " - ") and length when the file has no title tag or known duration; embedded tags still win.

## Root cause

`LocalTrackLoader.expandPlaylists` resolved each `PlaylistFile.Entry` to a URL and dropped the entry's `title` and `duration`, so `loadTrack` could only fall back to the filename.

## Fix

Followed the plan on #0100's recursive shape. Added public `LocalTrackLoader.PlaylistHint`; `expandPlaylists` returns `(url, hint)` items, the hint coming from the entry in the innermost playlist that lists the track (outer entries naming a nested playlist contribute nothing; direct URLs get none). `load` keeps hints aligned by index (folders get none) and passes them to `loadTrack(at:hint:)` (defaulted, so existing callers compile). New internal `applyingPlaylistHint` fills a missing title tag from the playlist title, split on the first `" - "` into artist/title (artist only if no artist tag), and an unknown duration from the playlist length; it runs before the bitrate fallback. No deviations.

## Plan

**Re-read first.** #0100 lands before this and rewrites the same code (`LocalTrackLoader.expandPlaylists`, `PlaylistFile.resolve`, likely making expansion recursive with a visited set and depth limit). Read `Packages/PlayerKit/Sources/AudioCore/LocalTrackLoader.swift` and `PlaylistFile.swift` as #0100 left them and fit the steps below onto that shape; don't undo its cycle/depth handling.

Files to change:

- `Packages/PlayerKit/Sources/AudioCore/LocalTrackLoader.swift`
- `Packages/PlayerKit/Tests/AudioCoreTests/LocalTrackLoaderTests.swift`

No App changes: `PlayerModel` only calls `LocalTrackLoader.load`. `PlaylistFile.parse`/`Entry` already carry `title` and `duration`; `PlaylistFile.swift` needs no change unless #0100 moved expansion into it (then carry the entry there the same way).

Approach:

1. **Hint type.** In `LocalTrackLoader`, add an internal `struct PlaylistHint: Equatable, Sendable { var title: String?; var duration: Int? }` (from `PlaylistFile.Entry.title` / `.duration`).
2. **Carry it through expansion.** Change `expandPlaylists` to return `(items: [(url: URL, hint: PlaylistHint?)], skipped: [SkippedFile])` instead of `urls: [URL]`. A URL passed in directly gets `hint: nil`; each `.file(url)` resolved from an entry gets `PlaylistHint(title: entry.title, duration: entry.duration)`. With #0100's recursion, a track inside a nested playlist takes the hint from the entry in the playlist that actually lists it (the innermost one); the outer entry that pointed at the nested playlist contributes nothing (its `#EXTINF` names the playlist, not a track). If #0100 used a recursive helper that appends into a `[URL]`, change that accumulator to the tuple array.
3. **Keep hints aligned in `load`.** Replace `let all = collectAudioURLs(from: expanded.urls)` with a loop that builds `all: [URL]` and `hints: [Int: PlaylistHint]`: for each item, if it has a hint and `!isDirectory(item.url)`, record `hints[all.count] = hint` then append the URL; otherwise `all += collectAudioURLs(from: [item.url])` (folders listed in a playlist get no hint). Pass `hints[index]` into the task: `loadTrack(at: url, hint: hint)` (capture the hint value before `group.addTask`, as `url` is).
4. **`loadTrack(at url: URL, hint: PlaylistHint? = nil)`.** Keep it public with the defaulted parameter so `FolderIndexer`'s `{ try await LocalTrackLoader.loadTrack(at: $0) }` and test call sites still compile; make `PlaylistHint` public too if the compiler requires it for the public signature (it will: make it `public` with a public memberwise `init(title:duration:)`). After the metadata/bitrate block and before building `Track`, call the pure merge below on `title`, `artist`, `duration`.
5. **Pure merge, unit-testable.** Add `static func applyingPlaylistHint(_ hint: PlaylistHint?, title: String?, artist: String?, duration: TimeInterval) -> (title: String?, artist: String?, duration: TimeInterval)` (internal, `@testable` reaches it):
   - If `title == nil` (no title tag) and `hint?.title` is non-empty: split on the **first** `" - "` (`range(of: " - ")`). With a separator: playlist artist = text before, title = text after (both trimmed); if either part is empty, use the whole string as title and no artist. Without a separator: title = whole string. Set `title` to that; set `artist` to the split artist only if `artist == nil` (an artist tag still wins).
   - If `title != nil` (tag present): leave title and artist untouched.
   - Duration: if `duration <= 0` (or not finite) and `hint?.duration` is `> 0`, use `TimeInterval(hint.duration)`; otherwise keep the file's.
   - The existing filename fallback (`title ?? url.deletingPathExtension().lastPathComponent`, `artist ?? ""`) stays after the merge.
   - Do the bitrate fallback with the final duration (move the merge above the `bitrate == nil` block) so a hint duration can still estimate bitrate.
6. Update the doc comment on `expandPlaylists` to say entries carry their playlist title/duration.
