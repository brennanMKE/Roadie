## Description

Phase B of M15. On a Music Assistant queue (a speaker, or This Mac fed by Music Assistant), the playlist editor's `Q`, the row menu's Queue (#0179) and Jump to File's Queue (#0180) do nothing. Music Assistant has no separate play-next list, so there are no `[n]` markers.

Instead, **Queue moves the selected rows to play right after the current item**, in the order chosen. It uses the existing remote reorder path: `QueueEdit.move`, which is `player_queues/move_item` with `pos_shift`.

- Successive Queue actions go after the rows queued before them. Roadie counts these locally, and the count resets when the current item changes.
- There's no Dequeue and no Clear Queue on a remote queue.

**Constraints from the code:**

- Music Assistant moves **one item per call** (#0145, `QueueEditPlan.Move.refusedMultiple`). So queueing several rows is a sequence of moves. `PlaylistModel.sendRemote` already chains edits in order, with an optimistic `QueueEditPlan.apply`.
- Music Assistant refuses a move at or before its buffered index (`QueueEditError.buffered`, "Track already buffered"). If the item right after the current one is already buffered (crossfade, flow mode), the move fails, and the existing notice shows that text. That's acceptable; note it in the docs.
- The snapshot is capped at 2,000 items, so only fetched rows can be queued.

## Resolution notes

> 🟢 Resolved 2026-10-24 — On a Music Assistant queue, Queue (Q, the row menu, Jump to File) moves the selected rows to play right after the current item and the rows queued before them, one `move_item` per row, and a refused move stops the batch and leaves the count alone.

Second review (Opus, medium) of c5c48cf plus 54ed1f1, after the bounce in 544ccb1. Every point in the review notes is addressed:

- `sendRemote(_ batch:)` runs the whole batch as one link in `remoteEditChain`. The first refusal returns from the loop, so nothing after it is sent, and the notice shows once.
- On a refusal it restores `batch.before[k]`, which is `working` captured before edit k is applied: the real state with no later optimistic moves in it. It restores only if `remote?.output` still matches the batch's start.
- `batch.counted[k]` is the number of rows counted from edit k's row to the end of the batch (`added - countedBefore`), so rows already in place before the refused one stay counted. `uncount` does nothing unless the anchor still matches `anchorItemID`, and clamps at 0.
- The drag path's `sendRemote(_ edit:)` is unchanged. `plan` is now `batch(...).edits` with the same algorithm, so the first review's "what's right" list (rows above and below the current, shift tracking, chosen order, current row skipped, in-place rows, reset on current-item and output change, menu, Jump to File, local path) still holds.
- The 4 new tests check `counted`, the `before`/`after` snapshots, an in-place row before the refusal, and a stale anchor. They can't build against c5c48cf, which has no `batch` or `uncount`.

Known limitation, not a blocker: suppose a second Q runs while the first batch is still in flight, and the first batch is then refused. The second batch was planned on the first batch's optimistic state, and it is still sent. If it is refused too, its restore can briefly show the first batch's moves until the next refetch. The drag path's chained `sendRemote` has the same behaviour already, and a one-LAN-round-trip window makes it rare. The count stays anchored and never goes negative.

## Plan

### 1. Plan type (`Packages/PlayerKit/Sources/LibraryBrowser/QueueRows.swift`, next to `QueueEditPlan`)

```swift
/// Queue (Q) on a remote queue (#0182): moves rows to play right after the current item, each after the ones queued
/// before it since the current item last changed. Music Assistant has no separate play-next list.
public struct RemoteUpNext: Hashable, Sendable {
    /// The current item's queue id when counting began.
    public private(set) var anchorItemID: String?
    /// How many rows were queued after the anchor.
    public private(set) var count = 0
    public init() {}
    /// Resets the count when the snapshot's current item is no longer the anchor.
    public mutating func sync(to snapshot: RemoteQueueSnapshot)
    /// The moves that put `rows` (snapshot indices, in the order chosen) after the current item and the rows
    /// queued before them. Skips the current row and rows that are already in place (they still count). Empty with
    /// no current item.
    public mutating func plan(queueing rows: [Int], in snapshot: RemoteQueueSnapshot) -> [QueueEdit]
}
```

`plan` algorithm:

1. Call `sync(to:)`.
2. `var working = snapshot`, `let currentID = working.items[currentIndex].id`.
3. For each row in order:
   - Find its item id in the *original* snapshot. Skip it if it's the current item.
   - Find `from` in `working`, and `c = working.currentIndex`.
   - The final index is `to = (from < c ? c : c + 1) + count`, clamped to `working.items.count - 1`. Removing a row above the current one shifts the current one up.
   - If `to != from`, append `.move(itemID:, shift: to - from)` and `working = QueueEditPlan.apply(that, to: working)`.
   - `count += 1`.
4. `apply` keeps `currentIndex` on the current item's id, so `c` stays right after each step.

### 2. Model (`App/Playlist/PlaylistModel.swift`)

- `@ObservationIgnored private var remoteUpNext = RemoteUpNext()`.
- In `remote`'s `didSet`:
  - If the output changed (`oldValue?.output != remote?.output`), reset it to `RemoteUpNext()`.
  - If there's a snapshot, call `remoteUpNext.sync(to:)`.
- `toggleQueue(_ indices:)`, the remote branch that #0179 left for #0182:
  ```swift
  if let remote {
      let edits = remoteUpNext.plan(queueing: indices, in: remote)
      if remote.currentIndex == nil { onRemoteNotice("Nothing is playing") }
      for edit in edits { sendRemote(edit) }
      return
  }
  ```
  `sendRemote` applies each edit at once and sends it after the previous one. A refusal puts the rows back and shows the notice (existing).
- `selectionIsQueued`: false on a remote queue, so the menu always says Queue.
- `hasUpNext`: stays false on a remote queue (no Clear Queue).

### 3. Menus and panel

- `PlaylistContextMenus.rowMenu`: show Queue on a remote queue too, titled "Queue", never "Dequeue".
- `PlaylistListInputView.keyDown`: `Q` already calls `toggleQueueForSelection()`, which now reaches the remote branch.
- `JumpToFilePanel`: enable Queue unless the source is `.none`. The button is always titled "Queue" on a remote queue. Remote results show no marker. After a remote Queue the rows move, so `results` (indices) go stale; the panel's `tracks` watcher rebuilds the index, and the selection is kept by `Track.id`.

The `RemoteUpNext` planning is correct: rows above and below the current item, the shift after each move, the chosen order, skipping the current row, rows already in place, and the reset when the current item or output changes. The menu, Jump to File and local paths are fine. What fails is the refusal path. Music Assistant refuses moves at or before its buffered index. That is the documented crossfade/flow case, and by-hand step 6 relies on it. A refusal currently leaves Roadie wrong in two ways:

1. **The count includes refused moves.** `plan` adds 1 to `count` for each row before anything is sent. When `sendRemote` gets a refusal, it snaps the rows back but never lowers the count. So after "Track already buffered", the next `Q` puts the row at current + 2 (or later), after a track nobody queued, instead of right after the current item. Every refusal widens the gap until the current item changes.
2. **A multi-row Queue snaps back to a wrong state.** Each `sendRemote` captures `before`, which is the optimistic state that already includes the moves earlier in the batch. Suppose move 1 is refused and then move 2 is refused too, which is likely, since both target the buffered slot. Move 1 restores `before1`, then move 2 restores `before2`, and `before2` still shows move 1 as done. The playlist then shows a move Music Assistant never made. Nothing refetches, because MA changed nothing. Later moves in the batch also keep being sent after a refusal, with shifts planned against a state that doesn't exist.

**The next pass must:**

- Send a Queue batch so that the first refusal stops it. Don't send the batch's remaining moves. Restore the snapshot from before the refused move, the real one with no later optimistic edits in it, only if the output is unchanged (as `sendRemote` does now). Show the notice once. One option is a batch variant of `sendRemote` that runs the edits as a single link in `remoteEditChain`. Leave the drag path's `sendRemote` alone unless the same fix falls out cleanly.
- Leave the refused row and every row after it in that batch out of `RemoteUpNext.count`, so the next Q targets the slot right after the last row that really moved. One way is a `mutating func uncount(_ n: Int, anchor: String?)` that lowers the count only when the anchor still matches, and never below 0. Rows earlier in the batch that were already in place still count.
- Add tests to `RemoteUpNextTests` for the pure part, for example `aRefusedMoveIsNotCounted`: plan `[7, 8]`, uncount from the first row, and the next plan of row 8 lands at current + 1. Add them to the expect list along with the existing eight.

Implementation runs at medium after this bounce (AGENTS.md).

## Root cause

#0179 and #0180 built Queue on AudioCore's play-next list only; `toggleQueue`, the row menu and Jump to File's `canQueue` returned early or hid Queue on a remote queue, and Music Assistant has no play-next list to add to.

## Fix

As planned. New `RemoteUpNext` in `QueueRows.swift` turns the chosen rows into one `.move(itemID:shift:)` per row (after the current item plus the count queued since the current item last changed), simulating each step with `QueueEditPlan.apply`. `PlaylistModel` keeps one, resets it when the output changes, syncs it in `remote`'s `didSet`, and the remote branch of `toggleQueue` sends the moves through the existing `sendRemote` chain (optimistic apply, snap back plus notice on refusal). "Nothing is playing" notice when there's no current item. The row menu always shows Queue (never Dequeue on remote, since `selectionIsQueued` is false there); Jump to File enables Queue unless the source is `.none` and keeps the title "Queue" on a remote queue. No deviations from the plan.

**After the review bounce (54ed1f1, Opus medium):** the refusal path is fixed. `RemoteUpNext.batch(queueing:in:)` returns a `Batch`: the edits, the snapshot just before each edit (no later optimistic edits in it), how many counted rows each edit and the rows after it account for, the final snapshot, and the anchor id. `plan` is now `batch(...).edits`. `uncount(_:anchor:)` lowers the count only while the anchor is still the current item, and never below 0. `toggleQueue`'s remote branch sends the batch through a new `sendRemote(_ batch:)`, which runs as one link in `remoteEditChain`. The first refusal stops the batch, so the remaining moves aren't sent. It then restores `before[k]` if the output is unchanged, uncounts the refused row and the ones after it, and shows the notice once. Rows earlier in the batch that were already in place still count. The drag path's `sendRemote(_ edit:)` is unchanged.
