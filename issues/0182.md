# 0182 — Queue does nothing on a Music Assistant queue

| | |
|---|---|
| **Status** | open |
| **Module** | App / LibraryBrowser |
| **Platform** | macOS |
| **First seen** | 2026-10-23 |

## Description

Phase B of M15. On a Music Assistant queue (a speaker, or This Mac fed by Music Assistant), the playlist editor's `Q`, the row menu's Queue (#0179) and Jump to File's Queue (#0180) do nothing. Music Assistant has no separate play-next list, so there are no `[n]` markers.

Instead, **Queue moves the selected rows to play right after the current item**, in the order chosen. It uses the existing remote reorder path: `QueueEdit.move`, which is `player_queues/move_item` with `pos_shift`.

- Successive Queue actions go after the rows queued before them. Roadie counts these locally, and the count resets when the current item changes.
- There's no Dequeue and no Clear Queue on a remote queue.

**Constraints from the code:**

- Music Assistant moves **one item per call** (#0145, `QueueEditPlan.Move.refusedMultiple`). So queueing several rows is a sequence of moves. `PlaylistModel.sendRemote` already chains edits in order, with an optimistic `QueueEditPlan.apply`.
- Music Assistant refuses a move at or before its buffered index (`QueueEditError.buffered`, "Track already buffered"). If the item right after the current one is already buffered (crossfade, flow mode), the move fails, and the existing notice shows that text. That's acceptable; note it in the docs.
- The snapshot is capped at 2,000 items, so only fetched rows can be queued.

## Plan

### 1. Plan type (`Packages/PlayerKit/Sources/LibraryBrowser/QueueRows.swift`, next to `QueueEditPlan`)

```swift
/// Queue (Q) on a remote queue (#0182): moves rows to play right after the current item, each after the ones queued
/// before it since the current item last changed. Music Assistant has no separate play-next list.
public struct RemoteUpNext: Hashable, Sendable {
    /// The current item's queue id when counting began.
    public private(set) var anchorItemID: String?
    /// How many rows were queued after the anchor.
    public private(set) var count = 0
    public init() {}
    /// Resets the count when the snapshot's current item is no longer the anchor.
    public mutating func sync(to snapshot: RemoteQueueSnapshot)
    /// The moves that put `rows` (snapshot indices, in the order chosen) after the current item and the rows
    /// queued before them. Skips the current row and rows that are already in place (they still count). Empty with
    /// no current item.
    public mutating func plan(queueing rows: [Int], in snapshot: RemoteQueueSnapshot) -> [QueueEdit]
}
```

`plan` algorithm:

1. Call `sync(to:)`.
2. `var working = snapshot`, `let currentID = working.items[currentIndex].id`.
3. For each row in order:
   - Find its item id in the *original* snapshot. Skip it if it's the current item.
   - Find `from` in `working`, and `c = working.currentIndex`.
   - The final index is `to = (from < c ? c : c + 1) + count`, clamped to `working.items.count - 1`. Removing a row above the current one shifts the current one up.
   - If `to != from`, append `.move(itemID:, shift: to - from)` and `working = QueueEditPlan.apply(that, to: working)`.
   - `count += 1`.
4. `apply` keeps `currentIndex` on the current item's id, so `c` stays right after each step.

### 2. Model (`App/Playlist/PlaylistModel.swift`)

- `@ObservationIgnored private var remoteUpNext = RemoteUpNext()`.
- In `remote`'s `didSet`:
  - If the output changed (`oldValue?.output != remote?.output`), reset it to `RemoteUpNext()`.
  - If there's a snapshot, call `remoteUpNext.sync(to:)`.
- `toggleQueue(_ indices:)`, the remote branch that #0179 left for #0182:
  ```swift
  if let remote {
      let edits = remoteUpNext.plan(queueing: indices, in: remote)
      if remote.currentIndex == nil { onRemoteNotice("Nothing is playing") }
      for edit in edits { sendRemote(edit) }
      return
  }
  ```
  `sendRemote` applies each edit at once and sends it after the previous one. A refusal puts the rows back and shows the notice (existing).
- `selectionIsQueued`: false on a remote queue, so the menu always says Queue.
- `hasUpNext`: stays false on a remote queue (no Clear Queue).

### 3. Menus and panel

- `PlaylistContextMenus.rowMenu`: show Queue on a remote queue too, titled "Queue", never "Dequeue".
- `PlaylistListInputView.keyDown`: `Q` already calls `toggleQueueForSelection()`, which now reaches the remote branch.
- `JumpToFilePanel`: enable Queue unless the source is `.none`. The button is always titled "Queue" on a remote queue. Remote results show no marker. After a remote Queue the rows move, so `results` (indices) go stale; the panel's `tracks` watcher rebuilds the index, and the selection is kept by `Track.id`.

### By hand (needs a Music Assistant server)

1. With a speaker playing a 20-track queue, select row 15 and press `Q`. It moves to right after the current row in Roadie, and in Music Assistant's own UI after the refetch.
2. Queue row 18, then row 2: they land second and third after the current row.
3. When the current track changes, the next `Q` goes right after the new current row.
4. Select three rows and press `Q`: three moves, in row order, with no "Drag one track at a time" notice.
5. Jump to File on the speaker: Queue moves the result, and the panel's list follows the new order.
6. With crossfade on (the next item buffered), Queue on a later row shows "Track already buffered", and the rows snap back.
