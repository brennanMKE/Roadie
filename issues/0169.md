# 0169 — First-launch experience: default skins folder, museum, music folder, optional Music Assistant

| | |
|---|---|
| **Status** | open |
| **Module** | App / SkinBrowser / LibraryBrowser / Tooling |
| **Platform** | macOS |
| **First seen** | 2026-10-23 |

## Description

A fresh install of Roadie 0.0.1 opens to a grey "No Skin Loaded" box and nothing else. There is no skins folder, so the Skins window says "Choose a folder of .wsz files in Settings › Skins", the Museum tab says "Choose a skins folder to download skins", and the Library window can't open anything until a music folder or a Music Assistant server is set up in Settings. Every first step is buried in Settings and nothing tells the new user the order.

The user asked for (2026-10-23):

- `~/Roadie/Skins` is the default skins folder: define it and create it when no skins folder is configured.
- When there are no skins, open the Skins window on the Winamp Skin Museum right away so skins can be downloaded.
- Offer choosing a folder of songs, and optionally connecting to Music Assistant, without going through Settings.
- Music Assistant stays optional: local folders alone are a complete experience.

Users who already ran 0.0.1 and have settings must not be nagged.

## Expected behavior

- **Default skins folder.** At every launch with no `skinsFolderPath` set, Roadie creates `~/Roadie/Skins` (intermediate `~/Roadie` included), stores it as the skins folder and starts the index. A folder the user chose is never replaced. If the folder can't be created, nothing is stored and the Welcome window offers Choose Folder….
- **Welcome window.** On a fresh install a non-modal "Welcome to Roadie" window opens with three rows: Skins, Music Folder, Music Assistant (optional). Each row shows live status and one or two buttons:
  - Skins: the folder path and the indexed count, with **Browse the Skin Museum…** (opens the Skins window on the Museum tab), **Choose Folder…** and **Open Skin…** (a `.wsz` file).
  - Music Folder: the path and index status, with **Choose Music Folder…** (the same picker as Settings › Library) and **Open Library** once a folder is chosen. Choosing a folder also makes the folder the Library source when no Music Assistant server is verified, so the Library browses it at once.
  - Music Assistant (optional): "Not set up" or the verified server's name, with **Set Up Music Assistant…**, which opens Settings on the Music Assistant tab (server list, network discovery, token, Test Connection all live there already). No discovery runs until the user asks for it, so no Local Network prompt at launch (docs/music-assistant-integration.md).
  - **Continue** (or the window's close button) dismisses it and marks first run done.
- **Museum at once.** When the skins folder has no `.wsz` files at first run, the Skins window opens on the Museum tab together with the Welcome window, with the Skins window in front. A download applies the skin, as today (#0126).
- **Upgrading from 0.0.1.** A user with any of a skins folder, a last skin, a music folder or a verified Music Assistant server never sees the Welcome window: first run is marked done silently. The default skins folder is still created for them when they have none.
- **Re-run.** Help › Welcome to Roadie… opens the window again at any time.
- **No skin, later.** On any launch where no skin is loaded, the main window's placeholder gets a **Browse the Skin Museum…** button next to Open Skin…, so the way to skins is one click from the first thing a user sees.
- **The VM smoke launch stays offline.** `scripts/run-tests-vm.sh --launch` passes `-firstRunVersion 1` so the guest never opens the Welcome window or asks the Museum for a page.

## Actual behavior

A fresh 0.0.1 shows an empty placeholder; the skins folder, the Museum, the music folder and Music Assistant are each a Settings trip away and nothing points at them.

## Plan

Roadie is unsandboxed (`ENABLE_APP_SANDBOX: NO` in project.yml; LibrarySettingsView's comment), so folders are plain paths in `UserDefaults`, no security-scoped bookmarks. The App target has no test target, so every decision lives in a package type with tests, and the app only wires it up. Fast tier: nothing under `SkinLibrary/` or `AudioCore/` changes (the new folder helper goes in `SkinBrowser`, which already depends on `SkinLibrary`, to stay off the full-tier list).

### 1. `FirstRunPolicy` (PlayerKit › LibraryBrowser) — the decision, pure

New file `Packages/PlayerKit/Sources/LibraryBrowser/FirstRunPolicy.swift`:

```swift
/// Whether to show the Welcome window at launch. Pure: the app reads the defaults and acts on the decision.
public struct FirstRunState: Hashable, Sendable {
    /// `FirstRunPolicy.defaultsKey`; 0 when never set.
    public var completedVersion: Int
    public var hasSkinsFolder: Bool   // skinsFolderPath set (read BEFORE the default folder is applied)
    public var hasLastSkin: Bool      // lastSkinPath set
    public var hasMusicFolder: Bool   // FolderBackend.storedFolder() != nil
    public var hasVerifiedServer: Bool // MusicAssistantServerStore.hasVerifiedServer
    public init(...)
}

public enum FirstRunDecision: Hashable, Sendable {
    /// Already done: nothing to do.
    case skip
    /// An existing user (settings from 0.0.1): record the version, show nothing.
    case markCompleted
    /// A fresh install: show the Welcome window.
    case welcome
}

public enum FirstRunPolicy {
    public static let defaultsKey = "firstRunVersion"
    public static let currentVersion = 1
    public static func decide(_ state: FirstRunState) -> FirstRunDecision
}
```

Rules: `completedVersion >= currentVersion` → `.skip`; else any of the four `has…` true → `.markCompleted`; else `.welcome`. "Configured" means the key is present, not that the path is reachable: an upgrader whose drive is unplugged still isn't shown the Welcome.

Tests: `Packages/PlayerKit/Tests/LibraryBrowserTests/FirstRunPolicyTests.swift` (Swift Testing, like the suites there):
- `freshInstallShowsWelcome` (all false, version 0 → `.welcome`)
- `existingSettingsMarkCompletedWithoutWelcome` (one case per flag: skins folder, last skin, music folder, verified server → `.markCompleted`)
- `completedVersionSkips` (version 1 with all false → `.skip`; version 1 with flags → `.skip`)

### 2. `DefaultSkinsFolder` (SkinKit › SkinBrowser) — the folder, with I/O behind parameters

New file `Packages/SkinKit/Sources/SkinBrowser/DefaultSkinsFolder.swift`:

```swift
/// `~/Roadie/Skins`: the skins folder Roadie creates when none is configured (#0169).
public enum DefaultSkinsFolder {
    public static let relativePath = "Roadie/Skins"
    public static func url(home: URL = FileManager.default.homeDirectoryForCurrentUser) -> URL
    /// Creates the folder (intermediates included) if missing; returns it. A file in the way or a failure throws.
    @discardableResult
    public static func ensure(at url: URL, fileManager: FileManager = .default) throws -> URL
    /// True when the folder holds no `.wsz` at any depth (FolderScanner.list), or can't be read.
    public static func hasNoSkins(_ url: URL) -> Bool
}
```

`ensure` uses `createDirectory(at:withIntermediateDirectories: true)`; if a non-directory exists at the path it throws (`CocoaError(.fileWriteFileExists)`). `hasNoSkins` wraps `FolderScanner.list(folder:)` (`SkinLibrary`), returning true on throw.

Tests: `Packages/SkinKit/Tests/SkinBrowserTests/DefaultSkinsFolderTests.swift`, using a temporary directory made in the test (SkinBrowserTests has no `TempDir`; make one with `FileManager.default.temporaryDirectory.appending(path: UUID().uuidString)` and remove it in `defer`):
- `urlIsRoadieSkinsUnderHome`
- `ensureCreatesTheFolderAndIntermediates` (home/Roadie doesn't exist → both created, directory)
- `ensureKeepsAnExistingFolder` (pre-existing folder with a file: untouched)
- `ensureThrowsWhenAFileIsInTheWay`
- `hasNoSkinsIsTrueForEmptyAndFalseWithAWsz` (empty → true; `sub/a.wsz` → false; missing folder → true)

### 5. The Welcome window (App › Welcome/)

New `App/Welcome/WelcomeWindowController.swift`, modelled on `FileInfoPanel`:

/// "Welcome to Roadie" (#0169): one NSWindow (titled, closable, not resizable, `isReleasedWhenClosed = false`),

### Manual check (user's Mac, after review)

1. `defaults delete co.sstools.roadie` (or a fresh user) → launch: `~/Roadie/Skins` exists, the Welcome window and the Skins window on Museum open, a download applies a skin, Choose Music Folder… fills the Library, Continue closes; relaunch shows no Welcome.
2. With 0.0.1 settings present (a skins folder or server): launch shows no Welcome; Help › Welcome to Roadie… opens it.
3. Museum unreachable (Wi-Fi off): the Museum tab shows its offline state with Retry; Open Skin… still loads a local `.wsz`.

### Edge cases covered

- `~/Roadie/Skins` can't be created (a file named `Roadie` in the home folder, read-only home): logged, no folder stored, the Welcome shows "No folder chosen" with Choose Folder….
- Skins folder deleted later: `SkinLibraryModel` reports the scan error as today; the policy never re-shows the Welcome because the key is still present.
- Music folder unplugged: `FolderSettingsModel` keeps the path (its comment); the Welcome shows the failed status like Settings does.
- Museum offline at first run: the Museum tab's existing offline state; nothing in the Welcome blocks on the network.
- Two quick launches / Help menu while already open: `show` reuses the one window (`makeKeyAndOrderFront`).
