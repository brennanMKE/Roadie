# 0056 — Track downloads fail until relaunch if the cache folder is deleted while the app runs

| | |

## Description

`TrackCache` creates `~/Library/Caches/<bundle id>/Tracks/` and its `tmp/` folder only on first use. If macOS purges the Caches folder, or the user deletes `Tracks/`, while SkinAmp is running, every later download fails because the temp file can't be created. It recovers only after a relaunch. Found in the #0013 review.

## Steps to reproduce

1. Play or prefetch a Plex track so the cache folders exist.
2. Delete `~/Library/Caches/<bundle id>/Tracks/` while SkinAmp keeps running.
3. Play another Plex track that isn't cached.

## Expected behavior

The cache recreates its folders and the download succeeds.

## Actual behavior

The download fails until SkinAmp is relaunched.

## Notes

Fix: when creating the temp file fails because a folder is missing, recreate `Tracks/` and `tmp/` and retry once. Add a test that deletes the cache directory between two downloads.

Two smaller follow-ups from the same review belong with this fix:

- `cancelledEarly` in `Packages/PlayerKit/Sources/TrackCache/TrackCache.swift` can't be reached by a real early cancel, since the waiter is registered before its cancellation handler can run. It only collects ids from cancels that arrive after a waiter was already answered, so it grows without bound. Remove it, and correct the Gotchas line in #0013 that describes it.
- Missing tests: unpinning a download that has no waiters cancels it; Clear Cache while a download is in flight leaves the download and `tmp/` alone and the finished file is indexed.

## Plan

### Scope and decisions

Three small changes, all in `Packages/PlayerKit/Sources/TrackCache/TrackCache.swift` and `Packages/PlayerKit/Tests/TrackCacheTests/TrackCacheTests.swift`, plus one corrected line in `issues/0013.md`. Nothing in `PlexPartDownloader`, the resolver, the pinner, the settings model or the app changes; `PlayerModel` keeps calling `prepare()` once at launch.

- **Recreate the folders lazily, at the one place that needs them.** `startDownload` is the only method that needs `tmp/` to exist: `FileManager.createFile` there returns `false` when it is gone, which is the failure in the description. When that create fails *and* `tmp/` is missing, recreate `Tracks/` and `tmp/` with `createDirectory(withIntermediateDirectories: true)` (idempotent, a no-op for whatever still exists) and try the create once more. `prepare()` keeps its once-per-launch role; the mid-run recreate must **not** wipe `tmp/` (other downloads may be writing there) and must not reload the index. The guard on `tmp/` being missing keeps every other `createFile` failure (disk full, permissions) on its current path.
- **Drop the entries whose files went with the folder.** When `Tracks/` itself was deleted, every indexed file is gone but `entriesByKey` still lists them, so `stats()` reports phantom bytes and the Cache tab shows them until each key is requested (`hit()` drops them one at a time). In the recreate path, keep only the entries whose file still exists (one `fileExists` per entry, on this rare path only). When only `tmp/` was deleted this is a no-op.
- **Index writes need no retry.** `writeIndex()` always writes the whole index, so the first write after the folders are back (the insert that completes the retried download) makes `index.json` current. A write that fails in between is logged, as today, and loses only touches of entries whose files were deleted with the folder. On a relaunch with no index and no files, `prepare()` starts empty, which is the right answer. Leave it.
- **Remove `cancelledEarly`.** `leave` is reached only through `Task { await self.leave(…) }` from the cancellation handler, and that task needs the actor. The continuation is stored in the same actor turn that starts or joins the download (`file(forKey:)` has no `await` between reading `inflight[key]` and `download.waiters[waiterID] = continuation`), so by the time `leave` runs the waiter is registered. A `leave` that finds no waiter is a cancel that arrived *after* the waiter was already answered (the download finished, failed, or was abandoned by `setPinned` or another `leave`); the right response is to ignore it. The set only ever grew. `StubDownloader.cancelledEarly` in `TestSupport.swift` and `GateResolver` in `AudioCoreTests` are a different case (their `onCancel` runs synchronously on the cancelling thread, not through an actor, so it really can run before registration) and stay as they are.
- **Tests use the harness as it is**: `Harness`, `StubDownloader` gates, `waitFor`, `filesOnDisk`, `tempContents`. No new helpers. `h.dir` *is* the `Tracks/` directory, so "delete the cache folder" is `removeItem(at: h.dir)`.

### 1. `TrackCache.swift`

Extract the directory creation from `prepare()`:

```swift
/// Creates `Tracks/` and `tmp/` if they are missing. Safe to call while downloads are in flight.
private func createDirectories() throws {
    let fm = FileManager.default
    try fm.createDirectory(at: directory, withIntermediateDirectories: true)
    try fm.createDirectory(at: tempDirectory, withIntermediateDirectories: true)
}
```

`prepare()`: create `directory`, remove `tmp/` if present, then `try createDirectories()`, all inside the existing `do/catch` that maps to `.io`.

`startDownload`, replacing the `guard FileManager.default.createFile(…)`:

```swift
let fm = FileManager.default
var created = fm.createFile(atPath: tempURL.path, contents: nil)
if !created && !fm.fileExists(atPath: tempDirectory.path) {
    // Caches was purged, or Tracks/ deleted, while the app runs: put the folders back and retry once.
    do { try createDirectories() } catch { throw TrackCacheError.io(error.localizedDescription) }
    let before = entriesByKey.count
    entriesByKey = entriesByKey.filter { fm.fileExists(atPath: directory.appendingPathComponent($0.value.fileName).path) }
    log.info("cache folders were missing; recreated them and dropped \(before - self.entriesByKey.count) entries")
    created = fm.createFile(atPath: tempURL.path, contents: nil)
}
guard created else { throw TrackCacheError.io("could not create a temporary file") }
```

No `writeIndex()` after the filter: the insert that follows writes it, and if the download fails there is no index on disk to be wrong (it went with the folder).

`cancelledEarly`: delete the property and its doc comment, delete the `if cancelledEarly.remove(waiterID) != nil { … }` block at the top of the continuation body in `file(forKey:)`, and change `leave`'s `guard … else` to a plain `return` with a comment:

```swift
// An unknown waiter was already answered: the download finished, failed, or was abandoned
// before this cancel reached the actor. Nothing to do.
guard let download = inflight[key], let continuation = download.waiters.removeValue(forKey: waiter) else { return }
```

After the edit, `grep -n cancelledEarly Packages/PlayerKit/Sources/TrackCache` prints nothing.

### 6. Risks

- **A download in flight when `Tracks/` is deleted.** Its temp file is unlinked underneath the downloader's `FileHandle`, which keeps writing to the dead inode; `insert` then stats a missing file, gets 0, and fails with `.sizeMismatch` ("The download was incomplete."). The next request recreates the folders and succeeds. One error for that track is acceptable and is not covered by this fix or its tests (the stub writes with `Data.write(to:)`, which would fail with `.io` instead).
- **If the ordering argument for `cancelledEarly` is wrong,** a cancelled waiter would hang instead of being resumed. The symptom is a timeout in one of the existing cancel tests listed under Verification, which run in the same VM pass; none of them has ever needed the early path, which is the evidence the reviewer gave.
- **Phantom entries before the first download.** Between the purge and the next miss, `stats()` and the Cache tab still count the deleted files, and `hit()` drops them one at a time. Only a download triggers the bulk drop. Acceptable; the alternative (a stat of every entry on every `stats()` call) is the 2 s Cache tab refresh stat-ing hundreds of files.
- **`writeIndex()` logs an error per touch** while the folder is missing and no download has run. That is today's behaviour; it stops at the first retried download.
- **Test 4 pins down behaviour, not a change.** `clear()` already leaves `inflight` and `tmp/` alone; the test exists so a later edit to `clear()` (for example, cancelling downloads on Clear Cache) is a deliberate change with a failing test, not an accident.

## Resolution notes

> 🟢 Resolved 2026-10-13 — TrackCache now recreates `Tracks/` and `tmp/` and retries the temp-file create once when the folders vanish mid-run, dropping index entries whose files went with them; the unreachable `cancelledEarly` set is gone.

- Reviewed 4322e95 against the plan. The retry runs only when `createFile` fails *and* `tmp/` is missing, and happens once, so there is no loop; other create failures keep the old `.io` path. The entry filter runs only on that path, and the next `insert` rewrites `index.json` (test 1 checks this through `reopen()`).
- `cancelledEarly` removal is sound: `withTaskCancellationHandler` and `withCheckedThrowingContinuation` inherit the actor's isolation (the body reads `inflight` synchronously), so there is no suspension between an `onCancel` firing (even for an already-cancelled task) and `download.waiters[waiterID] = continuation`. `leave` runs in a separate `Task` that needs the actor, so it always finds the waiter registered or already answered. A body that throws resumes the continuation itself, so an unknown-waiter `leave` has nothing to resume and no continuation leaks.
- Using `FileManager.default` directly instead of a local `fm` (to avoid the Swift 6 region-isolation error) changes nothing.
- The four new tests exercise what they say: the whole `Tracks/` folder deleted (phantom entry A dropped, index rewritten, A downloaded again), only `tmp/` deleted (A still a hit), unpin of a waiterless pinned download (cancel, temp removed, next request starts fresh), and Clear Cache during a download (temp and in-flight untouched, finished file indexed). All use `makeTempDir()` and the stub; none touches the real Caches folder.

## Root cause

`TrackCache.prepare()` creates `Tracks/` and `tmp/` once per launch. `startDownload` then called `createFile` in `tmp/` with no recovery, so once the folders were purged while the app ran, every download threw `.io` until relaunch. Separately, `cancelledEarly` could never catch a real early cancel (the waiter is registered in the same actor turn that starts or joins the download), so it only collected ids from late cancels and grew without bound.

## Fix

Followed the plan. `createDirectories()` is extracted from `prepare()`. In `startDownload`, when `createFile` fails and `tmp/` is missing, it recreates `Tracks/` and `tmp/`, drops index entries whose files no longer exist, and retries once. `cancelledEarly` is removed and `leave` ignores unknown waiters. The #0013 Gotchas line is corrected. Deviation: the retry path calls `FileManager.default` directly instead of a local `fm`, because the local tripped a Swift 6 region-isolation error ("sending 'fm' risks causing data races") in the actor.
