## Description

Dragging from the Library (⌘L) to the skinned playlist editor never worked for the user (#0188), and #0184/#0188 were resolved without anyone seeing a drop land. This issue adds `LibraryUITests` over the folder library: opening on the search field, browsing, search, double-click to play, context menus, and the drags from album, track and artist rows onto a playlist row and onto the bottom bar. It is also the answer to #0188's open question (does the AppKit target see the SwiftUI pasteboard?). The Music Assistant-only parts (playlists, favorites, discover, radio, output picker) are #0206. Rows: [docs/design/test-automation.md](../docs/design/test-automation.md) §5.7.

## Plan

Launch: folder library, main and playlist windows open, queue holding the first album's 3 tracks (`-RoadieOpenFiles <album folder>`). The Library opens at 960×600 centred; the skinned column is at the top-left, so they don't overlap at 2560×1300.

### `Tests/RoadieUITests/LibraryUITests.swift`

- `commandLOpensTheLibraryWithSearchFocused`: ⌘L → `app.windows["Library"]` exists, the search field has focus (`library.search` or `app.searchFields.firstMatch.hasFocus`), the sidebar shows Artists, Albums, Favorites (no Playlists, no Discover, no Radio for the folder library: check `LibrarySection` availability per backend), Artists selected.
- `browseArtistAlbumTracks`: click `library.row.artist.<Tone Artist>` → its two albums; click the two-disc album → tracks in disc order (6 rows); the album art view exists; `Other Artist` → the single.
- `search`: type `tone c` in the search field → Tracks section has one row, Albums has the album; clear → back to the section.
- `doubleClickAlbumPlays`: double-click an album row → `probe.state == playing`, the playlist editor shows the album's tracks (`pl.row.N` labels), `pl.row.0` current. Double-click a track row in the track list → it plays within its album (the queue is the album, current is that row: check `PlayRequest.play(ids, in: rows, album:)`).
- `contextMenus`: right-click a track → Play, Play Next, Add to Queue (no Add to Playlist for the folder library: `AddToPlaylistMenu` is empty without `.playlistEditing`; assert absent or disabled per the actual code); Play Next → the track appears right after the current row (`pl.row.<current+1>`); Add to Queue → appended. Right-click an album → the container menu (Play / Play Next / Add to Queue / Favorite). Right-click an artist → the same without Add to Playlist (#0188).
- `dragAlbumOntoPlaylistRow` (**#0188**): with the queue at 3 rows, press `library.row.album.<Two Discs>` for 0.3 s and drag to `pl.row.1` → the queue is 9 rows and rows 1–6 are the album's tracks in order (inserted at the drop row, #0183/#0184); `probe.maRequests` is empty (local). Attach a screenshot always for this test (it's the evidence #0188 lacked).
- `dragTrackOntoBottomBar`: drag a track row to `pl.runningTime` (the bottom bar, SwiftUI fallback) → appended as the last row.
- `dragArtistOntoPlaylist`: drag `library.row.artist.<Other Artist>` to `pl.row.0` → the single is inserted at row 0.
- `dragWithoutDropLeavesTheQueue`: drag a track to the main window (not a drop target) → the queue is unchanged and the drag image returns (just assert the queue).
- `unreachableSourceShowsRetry`: launch with `-LibraryFolderPath /nonexistent` → the status view shows "Can't open the library" with Retry and Open Settings…; Open Settings… opens Settings on the Library tab.
- `fallbackToFolderNotice`: launch with `library: .musicAssistant`, `scenario: .unreachable` and a valid folder → the Library falls back to the folder source and `main.marquee` shows the fallback notice (`LibraryFallbackPolicy` text), Settings › Library shows the reason (`library.maReason`).
- `addRadioURL`: only with Music Assistant (radios need the backend); move to #0206 if the folder library has no Radio section. Check `LibraryWindowView`'s toolbar conditions.

### If the drag doesn't land

`dragAlbumOntoPlaylistRow` is the first time the Library → editor drop is observed. If it fails: read `LibraryDrop` log lines from the guest (`log show --predicate 'subsystem == "co.sstools.roadie" AND category == "LibraryDrop"' --last 10m` after the run, add it to `run-tests-vm.sh`'s results when `--ui`) and follow #0188's decision tree. If the SwiftUI `.draggable` never writes the type, switch `libraryDraggable` to `.onDrag { NSItemProvider }` as #0188 planned, in this issue, with the test as the proof; note it in `## Fix`. If XCUITest itself can't produce the drag (the drag image never appears), fall back to a `RoadieTests` unit test that performs the drop with a constructed `NSDraggingInfo` through `LibraryDropDecoder` (#0210) and mark the drag rows in design §5 *by hand*; say so in `## Notes`.
