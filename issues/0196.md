## Description

#0187 happened because `player-queue-items.json` was recorded against an empty queue, so `BackendQueueTests.itemJSON` invented rows with `"index": n`, and the real server's `"index": 0` on every row was never seen by a test. Two things are missing: a recording of a loaded queue, and a rule (with a test) that recorded quirks are kept and noticed when they change. This issue extends the read-only recorder with `--record-queue`, adds the quirk registry and its test, and replaces the synthetic rows in `BackendQueueTests` with the recording once it exists. Design: [docs/design/test-automation.md](../docs/design/test-automation.md) §2.3.

The recording step needs the user: `scripts/record-ma-fixtures.py --record-queue` runs on the host against their server with a queue loaded and playing. The code below doesn't block on it; `MAFixture.isRecorded` stays false for the new names until then and the tests skip or use the synthetic fallback.

## Resolution notes

> 🟢 Resolved 2026-10-24 — `--record-queue` records a loaded queue read-only, a quirk registry with `recordedQuirksHold` pins the server's `"index": 0`, and the recorded pages answer any `limit` up to 50 so the recorded-queue test runs once the user records (b50f2af); the live recording is still to do.

## Root cause

The only queue-items fixture was recorded against an empty queue, so the tests built queue rows by hand with `"index": n`. The real server sends `"index": 0` on every row, and no test ever saw that. There was also no rule, and no test, that kept recorded server quirks written down and flagged a change in them.

## Fix

- `scripts/record-ma-fixtures.py --record-queue [--queue-id ID] [--events-seconds N]`: sends only reads from `ALLOWED` and picks the playing queue, or the one named. It stops with "load and play a queue first" when no queue has items. It writes `players-all-playing`, `player-queue-get-loaded`, `player-queue-items-loaded` and `player-queue-items-page2` (up to 50 rows each) and `events-queue` through the existing scrub and secret gate, and `--check` checks their shape. Beyond the plan, a later default run keeps these five files and doesn't overwrite a recorded `player-queue-items-loaded`.
- A `## Quirks` section in `docs/ma-protocol-notes.md` with entries (a) to (c), checked by `MAFixtureTests.recordedQuirksHold`. `fixturesAreVerbatimRecordings` checks that each call fixture has `command`, `args` and `frames`, that no fixture carries a `synthetic` key, and that the fixtures folder matches `MAFixture.recorded`. `commands-names.json` (derived from `commands.json`, not a recording) and the per-row `recommendations-items-*` files are allowed.
- `FixtureScript.recorded` routes `player_queues/items` through `FixtureScript.loadedQueueRoutes`: an exact route for the baseline `player-queue-items` args comes first, then each recorded page answers any request at its `queue_id` and `offset` whose `limit` is at most 50, with that many rows (`MAQueueWatch` asks for `min(pageSize, wanted - items.count)`). `loadedQueueRoutesSliceToTheAskedLimitAndSpareTheBaseline` checks this over a synthetic page. The plan said to route by offset only.
- `BackendQueueTests`: the synthetic rows now default to `serverIndex: 0`. The new `queueRowsFromTheRecordedLoadedQueueAreNumberedByPosition` is turned off with `.enabled(if:)` until the recording exists. Queue rows have no `isCurrent`, so the test checks `currentIndex` against `current_index` instead.
- **The live `--record-queue` recording has not been done yet.** The orchestrator will run it read-only after merge. Until then, quirk (a) and the recorded-queue test are skipped.

## Review notes

Bounced 2026-10-24 (review of a271dbd). The read-only recorder, the token handling, the "load and play a queue first" refusal, the quirk entries (b) and (c), the `serverIndex: 0` default and the `recorder-tests` step are fine. One defect blocks approval, because it fails the fast tier as soon as the recording lands:

1. **The recorded-queue route only answers a request whose `limit` is exactly 50, but `MAQueueWatch` asks for less.** `MAQueueWatch.refetch` sends `limit = min(policy.pageSize, wanted - items.count)`. `queueRowsFromTheRecordedLoadedQueueAreNumberedByPosition` sets `items` to the number of recorded rows. With fewer than 50 rows, the first request is `limit: <count>`. With 51 to 99 rows, the second request is `limit: <count - 50>`. Neither matches the route's `$0["limit"] == limit` (50), so the request falls through to `any(.playerQueueItems)`, gets `[]`, and `waitFor` times out. The test passes only when the recorded queue has exactly 50 rows or at least 100. Most playlists don't, and the orchestrator records right after merge. Fix: let the route answer any request at the recorded `queue_id` and `offset` whose `limit` is at or below the recorded one, and return only the first `limit` rows. Keep the baseline `player-queue-items` request (its own `queue_id`, `limit: 3`, `offset: 0`) from being hijacked when the recorded queue has the same id (the baseline id is a real player id, so it can): add an exact route for the baseline's recorded args ahead of the new routes, or match on something the baseline request doesn't share. Then add a test that needs no recording: a synthetic page put into the same route shape, asked for with a limit below the recorded one, gets a sliced answer, and the baseline args still get `[]`.

Smaller, fix in the same pass:

2. `fixturesAreVerbatimRecordings` looks for a `synthetic` key only in `frames()`. Fixtures without `frames` (`events`, `events-playlists`, `events-queue`, `server-info`, ...) and top-level keys are never checked, though `## Fix` says no fixture carries one. Walk `fixture.json` instead.
3. `--queue-id` as the last argument raises `IndexError` in `main`. `die` with a usage message instead.

Re-verify on the fast tier with the same `--expect` list, and add the new routing test to it.

Approved 2026-10-24 (second review, b50f2af, merged with main in f4de7ed). All three findings are fixed: the recorded pages answer every request `MAQueueWatch.refetch` sends for a recording of 1–49, 50, 51–99 or 100 rows, the baseline args are answered first by their own route, and the new test covers a short limit, the recorded limit, a limit over it, another offset and the baseline guard. `fixturesAreVerbatimRecordings` walks each whole fixture, and a missing flag value stops with usage. The merge kept #0198's `release-tools` line and this issue's `recorder-tests` step side by side. One accepted edge: a recorded queue on the baseline's player with exactly 3 rows would get the baseline's `[]` for its `limit: 3, offset: 0` request.

Follow-up 2026-10-24 (after the a47dbe5 recording): `queueRowsFromTheRecordedLoadedQueueAreNumberedByPosition` emitted nothing because the recorded queue is on a sync group (`syncgroup_…`) that the baseline `players-all` doesn't list, and `players/get` answers only the baseline player, so `requireOutput` threw `unknownOutput` and the watcher's refetch swallowed it. Not an app bug: the app lists outputs (`players/all`) before a queue is shown, and the group is in the same run's `players-all-playing` as an enabled, visible group. The test now answers `players/all` with `players-all-playing`, calls `outputs()` first (and checks the group is listed), then watches the group's queue. Fixtures unchanged.

## Plan

### 1. `--record-queue` (`scripts/record-ma-fixtures.py`)

- New entry point `record_queue(args)` next to `record()`. Read-only: it uses `Session(... allowed=ALLOWED)` and sends `players/all`, `player_queues/all`, `player_queues/get_active_queue`, `player_queues/get` and `player_queues/items` (offset 0 and one more page at `limit` 50) for the queue that has `state == "playing"` or, with `--queue-id`, the named one. It refuses to run (`die`) if no queue has items, saying "load and play a queue first".
- Writes, through `write_fixtures` (scrub, truncate per `TRUNCATE`, gate): `players-all-playing`, `player-queue-get-loaded`, `player-queue-items-loaded` (keep **all** rows up to 50, not the 5 of `TRUNCATE`: set `TRUNCATE["player-queue-items-loaded"] = 50` and record the real count in `original_item_counts`), `player-queue-items-page2` (the second page), and `events-queue` (`--events-seconds`, default 30, while the queue plays: `queue_updated`, `queue_items_updated`, `player_updated` frames).
- `--check` gains the new names in `shape_problems`. `scripts/tests/test_record_writes_cleanup.py`-style test `scripts/tests/test_record_queue.py`: with a `FakeSession`, `record_queue` sends only allow-listed commands, picks the playing queue, writes the expected fixture names, and dies when every queue is empty.

### 2. Quirk registry and test

- `docs/ma-protocol-notes.md`: a `## Quirks` section. First entries: (a) `player_queues/items` rows carry `"index": 0` whatever their position (MA 2.10.6, seen 2026-10-24, #0187); position is the paging offset plus the place in the page; (b) `playlist_tracks` streams chunk frames then an empty `partial: false` (from #0060's notes); (c) `players/get` of an unknown id is `result: null`. Each entry names the fixture that shows it.
- `Packages/PlayerKit/Tests/MusicAssistantKitTests/MAFixtureTests.swift`: `recordedQuirksHold`: for each quirk, assert it against its fixture (skip, with `XCTSkip`/`#expect` guard, the ones whose fixture `isRecorded == false`). For (a): every item in `player-queue-items-loaded` has `index == 0` while `current_index` in `player-queue-get-loaded` is > 0 (or the test states the recorded value). The doc comment says what to do when it fails: a re-record changed the server's behaviour; update the quirk entry and reconsider `MAQueueWatch.item(_:position:)`, don't edit the fixture.
- Add `fixturesAreVerbatimRecordings`: every call fixture has `command`, `args`, `frames`, and no frame carries a key named `synthetic`; and the file list equals `MAFixture.recorded` (no stray files, nothing missing).

### 3. Use the recording (`BackendQueueTests`, `FixtureScript`)

- `MAFixture`: add `playersAllPlaying`, `playerQueueGetLoaded`, `playerQueueItemsPage2`, `eventsQueue`. `playerQueueItemsLoaded` exists.
- `FixtureScript.recorded(token:)`: route `player_queues/items` by `offset` to `player-queue-items-loaded` / `-page2` when recorded, else to the existing empty fixture.
- `BackendQueueTests`: a new `queueRowsFromTheRecordedLoadedQueueAreNumberedByPosition` that runs the rig over the recorded fixture and asserts `items.map(\.index) == Array(0..<count)`, `items[current].isCurrent`, and that titles match the fixture's `media_item.name`s. Skipped while unrecorded. Keep `queueRowsUsePositionWhenTheServerSendsIndexZero` (synthetic, explicit) as the always-on guard; rename `itemJSON`'s default to `serverIndex: 0` so the synthetic rig matches the real server by default.

### 4. Docs

`docs/ma-protocol-notes.md`: the `--record-queue` recipe under the existing recording section; the Quirks section. `scripts/record-ma-fixtures.py` header: the new line.
