## Description

`MusicAssistantKitStub` replays recorded frames per command (`FixtureScript`), which is right for a unit test of one call. A UI test drives the whole app: it plays an album, expects the queue to show up in the playlist editor, double-clicks row 3, and expects the server to have received `play_index 3` and the row to become current. That needs a stub with state: queues that change when commands arrive, and pushed events that tell the client. This issue adds `ScriptedMusicAssistant`, a small in-memory server built on the recorded fixtures, with named scenarios, used by `RoadieConfiguration.musicAssistant = .scripted(...)` (#0194). Design: [docs/design/test-automation.md](../docs/design/test-automation.md) §2.2.

## Review notes

Bounced 2026-10-24 (review of d03a250, merged with main 015794f cleanly, no conflicts). Most of it is right: state is under one `OSAllocatedUnfairLock` with no lock inversion against `StubWebSocketTransport` (the server never holds its lock while taking a transport's, the handler captures the server weakly, and `MusicAssistantClient` is an actor, so one client's sends are serialized); `FixtureScript.handler` defaults to nil, so `FixtureScript.recorded` users are unchanged; rows keep `index: 0`; `queueLoaded` moving the 14 recorded rows from `syncgroup_uckfpbw8` (not in `players-all`) onto `ap223aed81fe30` is a fair stand-in; the tests go through `MusicAssistantBackend`. Three things need fixing before it can be the server the UI tests trust:

1. **The out-of-range error misleads the app.** `play_index` and `delete_item` out of range answer `error_code 999` with details `"IndexError: list index out of range"`. `MusicAssistantBackend.edit` maps any server error whose details contain `indexerror` to `QueueEditError.buffered` ("Track already buffered", `isBufferedRefusal`), so against the stub an out-of-range index shows the buffered-refusal notice, which is the real server's answer to a *different* case (a move or delete at or before the buffered index). Neither site is marked synthetic in the code. Fix: mark both `// SYNTHETIC` (and say so in the type's doc comment), and use details that don't match `isBufferedRefusal` (no `IndexError`, no `buffer`), for example `"SYNTHETIC: no queue item at index 7"`; keep 999 but call it assumed (MA's code for an unhandled exception). Add a test through `backend.edit(.play(index: 99))` that it throws a `MusicAssistantError.server`, not `QueueEditError.buffered`.
2. **Event order is fixed at reply-then-events, which the real server is not known to do.** `events-queue.json` captured no events, so the order is unrecorded; MA's handlers signal events while the command runs, so events usually go out *before* the result. Always sending the reply first can hide app bugs that only show when the event wins (a refetch racing the reply, an optimistic update overwritten). Fix: add an event-order setting on the server (`.afterReply`, `.beforeReply`; keep the current one as the default if you like), mark the order SYNTHETIC/unverified in the doc comment, and run `playIndexMovesTheCurrentRowAndPushesAnEvent` (or a new test) under both orders.
3. **The play-index test doesn't prove the client gets the command's event.** Its last part pushes a hand-built `queue_updated` with `data: ["current_index": 3]` (not a recorded shape) and checks the client saw *that*. Subscribe to `client.events()` before `edit(.play(index: 3))` and assert the client receives the server's own `queue_updated` with `current_index == 3`.

Also, in the same pass:

- `docs/ma-protocol-notes.md` "Scripted server" says "its replies are recorded shapes with state applied, never new shapes"; list the exceptions there: event payloads (`data` = whole object) are unrecorded, `current_media` while playing is synthetic, the speaker is marked available in `queueLoaded`/`playingOnSpeaker`, the out-of-range error is assumed, and the event order is a setting.
- Optional: every queue keeps `player-queue-get.json`'s `display_name`; `player-queue-get-loaded.json` or the player's name would be closer.

For #0194 when it merges (write this in #0194's `## Notes` as part of this pass): delete its placeholder `ScriptedMusicAssistant` and factory (same names, so leaving them is a redeclaration error); `MusicAssistantMode.scripted(scenario: String)` must map through `ScriptedMusicAssistant.Scenario(rawValue:)` (or take the enum, as design §2.2 has it) and handle `transportFactory(scenario:)` throwing; pass `factory.http` as the HTTP transport; keep `factory.server` as `PlayerModel.scriptedMusicAssistant` and add `-RoadieMAScenario` (plan step 2 here). The probe (#0199) must report `recentCommandSummaries()` / `receivedCommands` only, never `server.transports[].sent` or `sentRequests`, which keep the auth token unredacted.

Verification for the next pass: the same fast tier and `--expect` list, plus the new test names.

## Root cause

`MusicAssistantKitStub` only replayed recorded frames per command (`FixtureScript`); it had no state, so a whole-app test could not see a queue change after a command or receive the events that follow.

## Fix

Added `ScriptedMusicAssistant` (`MusicAssistantKitStub`): an `OSAllocatedUnfairLock`-guarded in-memory server. Library answers come from the recorded fixtures (`FixtureScript.recorded` is the base, consulted after the server's own handler via a new `FixtureScript.handler` hook). Players (from `players-all` / `players-all-sendspin`), one queue per player, favorites and an in-memory copy of the playlists change as the plan's commands arrive (plus `player_queues/next|previous|transfer|save_as_playlist` and `music/playlists/get|playlist_tracks|library_items|count`, favorite listings and counts). Each change emits `player_updated`, `queue_updated`, `queue_items_updated` (`object_id` = id, `data` = whole object). Elapsed time follows an injected clock. Scenarios: `libraryIdle`, `queueLoaded`, `playingOnSpeaker`, `thisMacIsASendspinPlayer`, `unreachable`, `badToken`. Introspection: `receivedCommands` (auth token redacted), `pushedEvents`, `queue(for:)`, `player(_:)`, `reset(to:)`, `recentCommandSummaries()` (`play_index index=3`). `transportFactory(scenario:)` returns a `ScriptedTransportFactory` (concrete, so callers reach `server` and `http`) whose transports all share one server.

Deviations:
- **Plan step 2 (app wiring: `-RoadieMAScenario`, `PlayerModel.scriptedMusicAssistant` for the probe) is deferred to #0194**, which already has a placeholder `ScriptedMusicAssistant` that will be replaced by this one. `recentCommandSummaries()` is ready for #0199's `maRequests`.
- Events caused by a command are appended after its reply on the sending transport (keeps reply-then-event order) rather than sent through `StubWebSocketTransport.push`; the public `push(_:)` does use `push` on the newest transport.
- `queueLoaded` puts the recorded 14 rows on `ap223aed81fe30` (rows' `queue_id` rewritten, `index` kept 0, speaker marked available); the recording itself is on `syncgroup_uckfpbw8`, which is not in `players-all`.
- `current_media` while playing is SYNTHETIC (as `SyntheticPlayback`); out-of-range `play_index`/`delete_item` answers an assumed code 999 "IndexError".

## Plan

### 1. `ScriptedMusicAssistant` (`Packages/PlayerKit/Sources/MusicAssistantKitStub/ScriptedMusicAssistant.swift`, new)

An `actor`-free, `OSAllocatedUnfairLock`-guarded class (like `StubWebSocketTransport`) that owns:

- **Library** from the recorded fixtures: artists, albums, tracks, playlists, radios, recommendations (`*-page`, `*-count`, `artist-albums`, `album-tracks`, `playlist-tracks`, `search`, `item-by-uri`), answered as `FixtureScript.recorded(token:)` does today. Reuse `recorded(token:)` as the base script and add routes in front.
- **Players** from `players-all` (or `players-all-sendspin` when the scenario says This Mac is a Sendspin player) with mutable `playback_state`, `volume_level`, `current_media`.
- **Queues**: one per player, `items: [QueueItem]` (each the recorded `media_item` shape; `index` **always 0** in what is sent, matching the quirk), `current_index`, `state`, `elapsed_time`, `repeat_mode`, `shuffle_enabled`.
- **Commands it applies** (everything the app sends; grep `client.call(` in `MusicAssistantBackend*.swift` for the list): `player_queues/items` (paged by `offset`/`limit`), `player_queues/get`, `player_queues/all`, `player_queues/get_active_queue`, `player_queues/play_index` (int or `queue_item_id` string), `player_queues/play_media` (`replace`/`next`/`add`/`replace_next`; expands an album/playlist/artist URI to its recorded tracks), `player_queues/move_item`, `player_queues/delete_item`, `player_queues/clear`, `player_queues/shuffle`, `player_queues/repeat`, `players/cmd/play|pause|play_pause|stop|next|previous|seek|volume_set|volume_mute`, `players/cmd/set_members`, `music/favorites/add_item|remove_item`, `music/playlists/create_playlist|add_playlist_tracks|remove_playlist_tracks|update` (on an in-memory copy), `music/library/remove_item`. Unknown commands fall through to the recorded unknown-command error.
- **Events**: after each state change it pushes `player_updated`, `queue_updated` and `queue_items_updated` frames with the envelope from `docs/ma-protocol-notes.md` (and `events-queue.json` when #0196 has recorded it) through `StubWebSocketTransport.push`. Elapsed time advances with an injected clock (`ContinuousClock` in the app, a manual clock in tests).
- **Scenarios** (`enum Scenario: String`): `libraryIdle` (recorded, nothing playing), `queueLoaded` (the recorded loaded queue when `MAFixture.playerQueueItemsLoaded.isRecorded`, else 12 synthetic rows built from `tracks-page.json` with `index: 0`, current index 2, playing on `ap223aed81fe30`), `playingOnSpeaker` (`SyntheticPlayback`), `thisMacIsASendspinPlayer` (`players-all-sendspin`), `unreachable` (`connectError`), `badToken`.
- **Introspection** for tests and the probe: `receivedCommands: [SentRequest]`, `queue(for:)`, `reset(to:)`.
- `static func transportFactory(scenario:) -> any MAWebSocketTransportFactory` returning a factory whose every transport talks to the one shared server instance (reconnects keep state), plus the matching `MAHTTPTransport` stub for `/info` and artwork (`StubHTTPTransport` exists).

### 2. Wire it (`App/RoadieConfiguration.swift`, #0194's `.scripted(scenario:)`)

`PlayerModel` keeps a reference to the server (`scriptedMusicAssistant`) so `testProbe()` (#0199) can report `maRequests` (the last 20 commands with their key arguments: `play_index index=3`).

### 3. Docs

`docs/ma-protocol-notes.md`: a short "Scripted server" paragraph naming the scenarios and the rule that its replies are recorded shapes with state applied, never new shapes.

## Tests

`Packages/PlayerKit/Tests/MusicAssistantKitTests/ScriptedMusicAssistantTests.swift`, through `MusicAssistantBackend` as the app uses it (`connectedBackend(script:)` helper, adapted to the factory):

- `queueLoadedRowsHaveIndexZeroAndPositionsFromPaging`: `MAQueueWatch` over the scripted queue gives positions `0..<n` and `isCurrent` at the scenario's current index.
- `playIndexMovesTheCurrentRowAndPushesAnEvent`: `backend.edit(.play(index: 3), on: speaker)`; the next `queue_updated` event has `current_index == 3`; `receivedCommands.last?.command == "player_queues/play_index"` with `index == 3`.
- `playMediaReplaceExpandsAnAlbum`: `play([album], mode: .replace())` → the queue holds the album's recorded tracks, current 0, state playing; `.next` inserts after current; `.append` appends.
- `deleteAndMoveUpdateTheQueue`: delete item 1, move item 3 to 1; rows and a `queue_items_updated` push follow.
- `transportCommandsChangeThePlayerState`: pause → `playback_state == "paused"` in the next `player_updated`; `volume_set 40`.
- `favoritesAndPlaylistsAreApplied`: add a favorite, create a playlist and add tracks; the library answers show them.
- `unreachableScenarioFailsToConnect`, `badTokenScenarioReturnsTheRecordedAuthError`.
- `repliesKeepRecordedShapes`: every reply the server builds decodes with the same `MA*` models the real fixtures do (`MAQueueItem`, `MAPlayer`, `MAPlayerQueue`), no `try?`.
