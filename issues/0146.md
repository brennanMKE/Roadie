## Root cause

The playlist editor's LIST › Save and Load always ran the local file panels (`savePlaylistFile()` / `loadPlaylistFile()`), whatever queue the window showed, so on a speaker or on This Mac with the Music Assistant feed they couldn't touch Music Assistant playlists.

## Fix

LIST › Save now calls #0140's `saveQueue()` (file panel for the local queue; name prompt + `player_queues/save_as_playlist` for a Music Assistant queue). LIST › Load calls the new `loadList()`, routed by `QueueSaveTarget.load` (the same choice as Save, following `QueueRowsSelection`): file panel for the local queue, a refusal notice for a backend without playlists, else the new `PlaylistPickerSheet` — the Library's playlists grouped by `PlaylistGrouping`, filtered by a name search; Load or a double click plays the playlist with replace.

Review: Save still asks for the name with #0140's `SaveQueueSheet` (an NSAlert sheet on the key window) rather than `PlaylistNameSheet`. Accepted: Save Queue runs from the Playback menu and the PL window while the Library window may be closed, and `PlaylistNameSheet` is wired to `PlaylistsModel.nameSheet` inside the Library window; the alert gives the same name-then-save flow. Unifying the two prompts is cosmetic and not needed for this issue. Known edge: the picker lists the current Library source's playlists, so with the folder source selected and a speaker shown it shows "No playlists" (and play refuses with the usual notice).
